# アナリティクスエンジニアリングにおけるデータモデリングの考え方

dbtモデリング、model grain（モデルの粒度）、テスト、ドキュメンテーション、BI / semantic layer での利用、ステークホルダーとの認識合わせ、意思決定支援のための出力を、ポートフォリオをもとに整理した概要資料です。

> English version: [`00_analytics_engineering_modeling_index.md`](00_analytics_engineering_modeling_index.md)

## 目的

この資料群は、アナリティクスエンジニアリングにおいて重要だと考えている dbtモデリングの観点を整理するものです。

内容は、ポートフォリオ実装での経験と公開情報に基づいています。特定企業の内部データ、本番システム、既存の dbt project へアクセスしていることを前提にはしていません。

目的は、事業上の問いを、ソースデータ、業務プロセス、model grain（モデルの粒度）、ファクト、ディメンション、中間ロジック、テスト、ドキュメンテーション、BI / semantic layer での利用、レポーティングマート、意思決定支援のための出力へ、どのように接続できるかを示すことです。

## この資料群で扱うモデリング原則

この資料群では、ポートフォリオで実践してきた内容をもとに、アナリティクスエンジニアリングの業務に取り組む際に重視したいモデリングの観点を整理しています。

- テーブル名からではなく、事業上の問いから考え始めること
- ファクトとディメンションを設計する前に、対象となる業務プロセスを特定すること
- model grain（1行が何を表すか）を明示すること
- ソースデータの整形と、業務上の意味づけを分離すること
- 明確な価値がある場合に、再利用可能なファクト、ディメンション、中間モデル、レポーティングマートを使い分けること
- 変換処理の失敗と、業務レビューシグナルを区別すること
- アナリティクスエンジニアリングの責任範囲と、事業判断の最終責任を区別すること
- 指標定義、レビューシグナル、モデル上の前提を、ステークホルダーや関連部署とすり合わせること
- dbtモデルを BI / semantic layer での利用へ接続すること
- スコープを絞ったポートフォリオ実装を、実際の事業文脈におけるアナリティクスエンジニアリングの実務的な観点へ接続すること

## ポートフォリオで示していること

この資料群の主な根拠となるポートフォリオは次のプロジェクトです。

- `access-governance-warehouse`  
  企業内AIツールのアクセスガバナンスを題材にした、dbt + DuckDB + BigQuery によるアナリティクスエンジニアリングのポートフォリオプロジェクトです。

このプロジェクトでは、以下を示しています。

- 決定論的に生成される合成 raw data
- dbt source contracts and tests
- 明示的な model grain
- staging、core、intermediate、marts のレイヤー構成
- 再利用可能なファクトとディメンション
- 中間モデルによる re-graining と stock logic の分離
- レポーティング用途のマート
- 変換処理の失敗と業務レビューシグナルの分離
- dbtのドキュメンテーションと lineage
- Looker Studio のダッシュボード成果物
- 静的レポート出力
- 再現可能なローカル実行経路
- BigQuery を用いた任意のクラウド実行経路

このポートフォリオプロジェクトは、意図的にスコープを絞っています。完全な本番アーキテクチャではありません。  
一方で、source contracts、明示的な grain、テストされた前提、ドキュメント化された制約、lineage、再現可能な実行、事業側が利用できる分析出力など、アナリティクスエンジニアリングにおいて応用可能な実践を示すものです。

## 入社90日間の立ち上がり・貢献方針

最初の30日間では、既存の業務プロセス、ソースシステム、dbt project の構成、model grain、指標定義、BIの利用状況、チーム固有のツールやワークフロー、現在の課題を理解することに重点を置きます。

60日目頃までには、ドキュメント更新、dbtテストの追加、モデルレビュー、lineage の確認、既存のレポーティングマートやダッシュボードの支援など、小さく範囲を絞った改善を通じて貢献機会を探します。

90日目頃までには、ポートフォリオで実践してきた原則を活かし、再利用可能で、意思決定に使いやすい分析モデルを支援できる状態を目指します。具体的には、明示的な grain、source contracts、テストされた前提、ドキュメント化された制約、変換処理の失敗と業務レビューシグナルの明確な分離を重視します。

目的は、既存のデータ基盤をすぐに再設計することではありません。  
まずはチームのアナリティクスエンジニアリング業務に慣れ、現在の環境を理解し、適切な問いを立て、既存のワークフローに安全に貢献しながら、より信頼でき再利用可能なアナリティクスエンジニアリングの実践を段階的に支援することです。

## 補足

この資料群は、ポートフォリオ実装での経験と公開情報に基づいています。

特定企業の内部データモデル、ソースシステム、本番アーキテクチャ、既存の dbt project について主張するものではありません。

目的は、構造化されたアナリティクスエンジニアリングの考え方を示すことです。つまり、事業上の問いを、ソースデータの確認、model grain、再利用可能なモデル、テスト、ドキュメント化された前提、BI または意思決定支援のための出力へどのように変換できるかを整理することです。
