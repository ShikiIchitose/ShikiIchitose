# dbtモデリングと分析用データ設計の共通原則

> English version: [`01_common_dbt_modeling_principles.md`](01_common_dbt_modeling_principles.md)

## 1. 目的と位置づけ

この資料では、業務システム由来の raw data を、テストされ、ドキュメント化され、再利用可能な分析用データ資産へ変換するための dbtモデリングの考え方を説明します。

内容は、ポートフォリオ実装での経験と公開情報に基づいています。特定企業の内部データ、本番システム、既存の dbt project へアクセスしていることを前提にはしていません。目的は、アナリティクスエンジニアリングの文脈で、事業上の問いを、ソースデータ、model grain（モデルの粒度）、ファクト、ディメンション、marts、テスト、ドキュメンテーション、BIでの利用へどのように接続できるかを示すことです。

ポートフォリオプロジェクトは、スコープを絞った実装であり、完全な本番アーキテクチャではありません。ただし、明示的な model grain、dbtテスト、ドキュメンテーション、lineage、再現性、事業側が利用できる分析出力など、本番運用を意識したデータエンジニアリングの実践を前提に構築しています。

以下の例には、実装済みポートフォリオのパターンと、本番運用を意識した例示的なパターンの両方が含まれます。区別が重要な箇所では、実装済みポートフォリオの内容と、本番運用を意識した例を分けて説明します。

## 2. dbtモデリングがもたらすもの

dbtモデリングは、業務システム由来の raw data を、意思決定に使いやすい分析モデルへ変換するための実践だと捉えています。

多くの組織では、重要な事業データが、アプリケーションデータベース、スプレッドシート、イベントログ、請求システム、CRMツール、広告プラットフォーム、その他の業務システムに分散しています。モデリング層がない場合、アナリストや事業側のステークホルダーが、同じ指標を何度も定義し直したり、変換ロジックを重複して実装したり、前提を追跡しにくいダッシュボードを作ってしまう可能性があります。

dbtモデリングは、事業データをより一貫性があり、再利用可能で、テスト可能で、理解しやすいものにするための、管理された変換層を作ることで貢献できます。

主な貢献領域は次の通りです。

| 領域 | 貢献 |
|---|---|
| 指標の一貫性 | 重要な定義を集約し、チームごとに同じ KPI（key performance indicator: 重要業績評価指標）を異なる方法で計算しないようにする |
| 再利用可能な変換 | 繰り返し使われる整形処理や業務ロジックを、ad hoc SQL や BIツール内の個別実装から切り出す |
| データ品質 | dbtテストを通じて、構造上・意味上の前提を検証する |
| lineage | 上流と下流の依存関係を見えるようにする |
| ドキュメンテーション | 下流の利用者が、model grain、カラム、前提、想定用途を理解できるようにする |
| BIの信頼性 | ダッシュボード、セルフサービスBI、レポーティングのために安定したモデルを提供する |
| 意思決定支援 | 業務上・経営上の判断を支える分析出力を公開する |

目的は、単にテーブルを作ることではありません。データを信頼しやすく、説明しやすく、再利用しやすく、行動につなげやすい形に整えることです。

## 3. モデリング原則

dbtモデリングでは、次の原則を重視します。

### 3.1 事業上の問いから始める

テーブル名だけから考え始めるのではなく、まず、そのデータモデルが支えるべき事業上の問いを理解します。

領域を問わず、例えば次のような問いが考えられます。

- どの商品、顧客、チーム、ツール、チャネルが成果を生み出しているのか
- どの業務状態に追加確認や対応が必要なのか
- どの指標を複数チームで信頼できる定義にする必要があるのか
- どのダッシュボード上の判断が、このモデルに依存しているのか

良い dbtモデルは、単に上流ソーステーブルの形を写すものではありません。業務プロセスを分析しやすくするものであるべきです。

### 3.2 業務プロセスを特定する

ファクトとディメンションを設計する前に、モデル化する業務プロセスを特定します。

本番運用を意識したモデリング検討では、例えば次のような業務プロセスを確認します。

- 注文プロセス
- 在庫スナップショットプロセス
- 価格設定プロセス
- サブスクリプションライフサイクル
- 承認ワークフロー
- プロダクト利用プロセス
- 倉庫移動プロセス

この手順が重要なのは、ファクトテーブルは、単に raw sources を都合よく結合したものではなく、業務プロセスや測定可能なイベントを表すべきだからです。

### 3.3 model grainを明示する

すべてのモデルには、明確な grain が必要です。

grain は、1行が何を表すかを定義します。明示的な grain がないと、指標の解釈を誤ったり、二重計上したりする可能性があります。

代表的な grain の例は次の通りです。

| モデル種別 | grain の例 |
|---|---|
| 注文ファクト | 注文明細ごとに1行 |
| 利用ファクト | ユーザー、プロダクト、日付ごとに1行 |
| 在庫スナップショット | 日付、倉庫、プロダクト、状態ごとに1行 |
| 月次レポーティングマート | レポート月、チーム、プロダクトごとに1行 |

指標は、そのモデルが公開している grain においてのみ解釈するべきです。事業上の問いが別の grain を必要とする場合、BI層やレポート層に存在しない詳細を推測させるのではなく、データウェアハウス側でその grain の別モデルを公開する方が望ましいです。

### 3.4 ソースデータの整形と業務上の意味づけを分離する

低レベルなソースデータの整形と、業務上の意味づけは分離します。

本番運用を意識した典型的な分離は次のようになります。

```text
sources
  -> staging
  -> intermediate
  -> marts / dimensional models
  -> BI or semantic layer
```

staging models は、raw grain を保ちながら、名前、型、タイムスタンプ処理、軽量なソースレベルの整形を標準化します。

業務ルール、結合、re-graining、指標ロジックは、意図をドキュメント化・テストしやすい後段のレイヤーで導入します。

正確なレイヤー名はプロジェクトによって異なります。私のポートフォリオでは、再利用可能なファクトとディメンションのために独立した `core` レイヤーを使いました。一方、本番運用を意識した構成では、それらのモデルが `marts` 配下の dimensional models として直接配置される場合もあります。

### 3.5 再利用可能なファクトとディメンションをモデル化する

本番運用を意識したモデリングでは、一般に次のような再利用可能な dimensional models を公開します。

```text
dim_*
fct_*
```

これらのモデルは、安定した業務エンティティや業務プロセスを表すべきです。

領域に応じて、例えば次のような再利用可能な dimensional models を検討します。

```text
dim_customer
dim_product
dim_device_model
dim_sales_channel
fct_order
fct_inventory_snapshot_daily
fct_usage_daily
fct_price_change
```

これらのファクトとディメンションは、BIツール、semantic layer、下流の marts、notebook、ad hoc SQL分析などから利用できます。

### 3.6 stock metrics と flow metrics を区別する

stock metrics と flow metrics は、安易に混在させるべきではありません。

flow metrics は、ある期間中の活動量を表します。

代表的な flow metric の例は次の通りです。

```text
orders_total
sales_amount
sessions_total
units_sold
monthly_spend
```

stock metrics は、ある時点の状態を表します。

代表的な stock metric の例は次の通りです。

```text
inventory_on_hand
open_requests
approved_users_at_month_end
active_subscriptions_at_month_end
```

stock metrics と flow metrics を組み合わせる場合は、レポート上の grain と時間の意味を明示する必要があります。そうしないと、見た目には妥当に見えても、誤った数値をダッシュボードが表示してしまう可能性があります。

### 3.7 変換処理の失敗と業務レビューシグナルを分離する

望ましくない業務状態がすべて pipeline を失敗させるべきとは限りません。

> Business exceptions are outputs. Transformation inconsistencies are failures.

つまり、業務上の例外は出力であり、変換処理の不整合は失敗です。

ここでは、次の2つを区別します。

| 種別 | 意味 | 扱い |
|---|---|---|
| 変換処理の失敗 | データモデルが構造的に壊れている、または必須の契約に違反している | dbtテストを失敗させる |
| 業務レビューシグナル | データとしては妥当だが、レビューすべき状態を示している | marts やダッシュボードに表示する |

領域を問わない業務レビューシグナルの例には、次のようなものがあります。

- 利用率が低い
- 在庫が滞留している
- 承認なしの利用がある
- 利用なしの支出がある
- 在庫の経過日数が長い
- 利益率がしきい値を下回っている
- 追加確認が必要な妥当な業務状態がある

例えば、必須キーが欠損している場合は、テストを失敗させるべきです。一方、利用率が低い、在庫が滞留している、承認なしの利用がある、利用なしの支出がある、といった妥当な行は、変換エラーではなく業務レビューシグナルとして扱う方が適切です。

### 3.8 テストで前提を検証する

dbtテストは、下流の利用者が依存している前提を検証するために使います。

代表的なテストの例は次の通りです。

- 主キーの一意性
- 必須フィールドの非NULL
- 許可値
- リレーションシップチェック
- 日付範囲の前提
- 指標の一貫性チェック
- ソースと変換後の合計値の照合

テストは単なる品質ゲートではありません。そのモデルが真であると仮定している内容を実行可能な形で表したドキュメンテーションでもあります。

### 3.9 前提、lineage、下流での利用方法をドキュメント化する

モデルのドキュメンテーションでは、次の内容を説明するべきです。

- そのモデルが何を表しているか
- grain
- 重要なカラム
- 業務上の前提
- 既知の制約
- 下流の利用者
- 解釈上の注意

良いドキュメンテーションは、下流の利用者が curated dataset を見つけ、理解することを助けます。dbt では、プロジェクトのドキュメントを生成し、Webサイトとして表示することもできます。

### 3.10 ツールと目的に応じてBIへの公開パターンを選ぶ

最終的な公開パターンは、利用可能な BI や semantic layer の機能に応じて決めるべきです。

Looker や Tableau のような十分な機能を持つ BI / semantic layer がある場合、テスト済みのファクトとディメンションをその層に公開し、管理された探索やダッシュボード作成に利用できます。

一方で、BI層が軽量である場合や、重い繰り返し集計、ダッシュボード性能、急ぎのレポーティング、業務レビューリストが必要な場合には、dbtレポーティングマートが安定したダッシュボード向け出力を提供できます。

## 4. 本番運用を意識したモデル構造

本番運用を意識した環境では、一般に Looker、Tableau、dbt Semantic Layer、または同等の BI / semantic layer を、再利用可能な dimensional models の主な利用層として扱います。

典型的な本番運用を意識した構造は次のようになります。

```text
sources
  ↓
staging
  ↓
intermediate
  ↓
marts / dimensional models
  - dim_*
  - fct_*
  ↓
BI / semantic layer
  - LookML Explores
  - Tableau relationships / data model
  - governed measures
  - semantic metrics
  ↓
dashboards / self-service BI / stakeholder reporting
```

この構造では、dbt がテストされ、ドキュメント化されたファクトとディメンションを提供します。その上で、BI / semantic layer が、利用者向けのリレーションシップ、measure、explore、ダッシュボード、セルフサービス分析体験を定義します。

このパターンにより、ダッシュボード固有の結合や計算をすべて ad hoc SQL に押し込むことを避けられます。同時に、BI層は事業ユーザーに柔軟な探索機能を提供できます。

ここでいう `marts / dimensional models` は、再利用可能で事業側に公開する `dim_*` と `fct_*` モデルを配置するレイヤーを指します。materialized aggregation や業務レビュー用ロジックに明確な価値がある場合は、レポーティング用途の marts を別途追加できます。

## 5. dbtレポーティングマートの役割

十分な機能を持つ BI / semantic layer がある場合でも、dbtレポーティングマートが有用な場面はあります。

例えば、次のように明確な価値がある場合には、dbtレポーティングマートを使います。

- 重い、または繰り返し実行される集計
- 複雑な stock-and-flow metrics
- ダッシュボード性能の最適化
- ダッシュボード向けに整えた抽出データ
- 業務レビュー候補テーブル
- 急ぎの軽量レポーティング
- BI、SQL、notebook、script をまたいだ再利用
- 単一のBIツールの外側で管理すべき重要な業務ロジック

本番運用を意識した例としては、次のようなモデルが考えられます。

- `inventory_health_daily`
- `sales_velocity_monthly`
- `pricing_performance_daily`
- `margin_by_model_grade_channel`
- `operations_review_candidates`

例えば、`fct_sales_order` と `dim_product` を使った利用者向けの探索を定義するには、BIツールが適している場合があります。一方で、`inventory_health_daily`、`sales_velocity_monthly`、`operations_review_candidates` のような継続的な業務向け出力は、複雑なロジック、安定した grain、繰り返し利用、明確なテストカバレッジが必要であれば、dbt側で直接モデル化する方が適している場合があります。

この意味で、dbtレポーティングマートは、軽量BIツールのための単なる代替手段ではありません。ロジックを再利用可能、テスト可能、高性能、レビュー可能、追跡可能にし、複数の下流利用者で共有する必要がある場合に、業務ロジックを制御された形で materialize する方法です。

## 6. ポートフォリオとの接続

私のポートフォリオプロジェクトは、スコープを絞った実装ですが、応用可能なアナリティクスエンジニアリングの実践を示すことを目的に設計しています。

`access-governance-warehouse` では、決定論的に生成される合成 raw data を使って、レイヤー化された dbt warehouse を実装しました。このプロジェクトでは、ソースデータの整形、再利用可能な warehouse semantics、中間的な re-graining ロジック、事業側に向けた分析出力を分離しています。

実装済みポートフォリオの構造は次の通りです。

```text
raw sources
  ↓
staging
  ↓
core
  ↓
intermediate
  ↓
marts
  ↓
Looker Studio / static report artifacts
```

実装上の責任分担は次の通りです。

| レイヤー | 役割 |
|---|---|
| Sources | raw input contracts を定義する |
| Staging | raw grain を保ちながら raw fields を標準化する |
| Core | 再利用可能なディメンションとファクトを定義する |
| Intermediate | re-graining、stock logic、再利用可能な mart support logic を分離する |
| Marts | 事業側に向けた分析出力を提供する |

これは、`dim_*` や `fct_*` モデルを `marts` 配下に直接配置し、Looker、Tableau、または semantic layer から利用するような、本番運用を意識した構造とは少し異なります。

私のポートフォリオでは、再利用可能なファクトとディメンションのために意図的に `core` を使い、`marts` はレポーティング用途で、ステークホルダー向けの出力に限定しました。この構成は、Looker Studio を軽量な可視化レイヤーとして使い、再利用可能な業務ロジックを BI層のカスタムロジックではなく dbt側に置くというポートフォリオのスコープに合っていました。

実装済みポートフォリオの例には、次のようなモデルがあります。

```text
dim_tool
dim_user
fct_access_request
fct_tool_usage_daily
fct_tool_spend_monthly
access_requests_monthly
tool_adoption_monthly
governance_exceptions_current
adoption_review_candidates_monthly
```

応用可能な点は、正確なフォルダ構造ではありません。応用可能なのは、次のようなモデリング規律です。

- 明示的な grain を定義すること
- source contracts（ソース契約）を保つこと
- ソースデータの整形と業務ロジックを分離すること
- 再利用可能なファクトとディメンションを作ること
- re-graining ロジックを分離すること
- 事業側に向けた分析出力を公開すること
- 構造上の前提をテストすること
- 制約と解釈ルールをドキュメント化すること

## 7. まとめ

dbtモデリングは、単にテーブルを変換する作業ではなく、事業データを信頼でき、再利用可能で、ドキュメント化され、意思決定に使いやすい形にするための実践だと考えています。

中心となる流れは次の通りです。

```text
事業上の問い
  → 業務プロセス
  → model grain
  → ファクトとディメンション
  → テストとドキュメンテーション
  → BI / semantic layer またはレポーティングマート
  → 事業上の意思決定支援
```

ポートフォリオは、意図的にスコープを絞った環境で、基礎となるモデリング原則を示すものです。次のケーススタディでは、その構造をそのまま移植するのではなく、ポートフォリオで示したモデリング規律を出発点として、再利用可能な業務領域における本番運用を意識したモデリング仮説へ展開します。
