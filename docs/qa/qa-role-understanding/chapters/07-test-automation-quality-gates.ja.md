6章では、テスト設計の基本を整理した。具体的には、要求、受け入れ条件、具体例、業務ルール、状態遷移、権限、データ整合性などをもとに、どの観点で確認するか、どの条件を代表として選ぶか、どこを重点的に確認するかを扱った。

この章では、その次の段階として、6章で整理したテスト観点やテスト条件を、どのテストレベルに割り当て、どこまで自動化し、どのように継続的に実行するかを扱う。

ここで重要なのは、テスト設計技法、テストレベル、自動化、品質ゲートを混同しないことである。

Equivalence Partitioning(同値分割)、Boundary Value Analysis(境界値分析)、Decision Table Testing(デシジョンテーブルテスト)、State Transition Testing(状態遷移テスト)などは、主に「どの条件を確認するか」を考えるための技法である。

一方、Unit Test(単体テスト)、API Test、Integration Test(結合テスト)、E2E(End-to-End:エンドツーエンド) Testなどは、主に「どの範囲で確認するか」を表す確認単位である。

さらに、自動化は、それらの確認を人間が手で毎回行うのではなく、コード、ツール、CI/CD(Continuous Integration / Continuous Delivery:継続的インテグレーション / 継続的デリバリー)などを通じて、繰り返し実行できる状態にすることである。

たとえば、「50,000円以上の申請には追加承認が必要である」という業務ルールを考える。

6章の観点では、このルールに対して、49,999円、50,000円、50,001円のような境界値を確認する必要がある。また、複数明細の合計、申請後の金額変更、承認済み申請の変更可否、追加承認者が存在しない場合、権限のないユーザーによる承認なども確認候補になる。

7章では、それらの確認条件を、どの確認単位に割り当てるかを考える。

たとえば、金額が50,000円以上かどうかを判定する小さなロジックは、Unit Testで高速に確認しやすい。APIに申請作成リクエストを送ったとき、追加承認フローが作成されるか、権限のないユーザーが操作できないかは、API Testで確認しやすい。申請データがDB(Database:データベース)に保存され、承認フローや通知キューと連携するかは、Integration Testで確認しやすい。申請者が申請を作成し、承認者が承認し、履歴が残る一連の主要業務フローは、E2E TestやManual Test(手動テスト)で代表的に確認しやすい。

このように、同じ業務ルールから生まれた確認条件でも、すべてを同じテストレベルで確認する必要はない。

むしろ、すべてをE2E Testで確認しようとすると、テストの実行時間、環境依存、データ準備、画面変更への追従、flaky test(不安定なテスト)の問題が大きくなりやすい。一方で、すべてをUnit Testだけで確認しようとすると、API、DB、画面、外部連携、ユーザー操作を含む実際の業務フローを確認できない。

したがって、7章の中心は、テスト種別の名前を覚えることではない。重要なのは、確認したい品質リスクに対して、どのテストレベルで確認するのが適切か、どの確認を自動化すべきか、どの確認を人間が探索的に見るべきかを判断することである。

この章では、次の流れで整理する。

- テスト技法とテストレベルの関係

- テスト自動化の目的

- 自動化されたUnit Test、API Test、Integration Test、E2E Test

- CI/CD上の品質ゲート
- flaky testとの向き合い方
- 自動化と保守性
- 自動化すべき確認と、人間が探索すべき確認

7章を通じて、自動化は「手動作業を減らすための手段」だけではなく、「変更時に期待状態を継続的に確認し、チームが安心して変更できる状態を作るための仕組み」であることを整理する。

なお、生成AI(Generative AI:生成AI)やAI-assisted testing(AI支援テスト)の登場により、テスト設計、テストケース生成、自動テストの保守、E2E Testの実行・解析などのあり方は変化しつつある。

たとえば、自然言語からテストケースや自動テストコードを生成すること、画面変更に追従するself-healing test(自己修復型テスト)を利用すること、テスト失敗の原因分析をAIに支援させることなどは、今後のQA(Quality Assurance:品質保証)やQuality Engineering(品質エンジニアリング)に影響を与える可能性がある。

ただし、本章ではまず、AI時代以前から重要であり続けている基本的な考え方を扱う。具体的には、テスト設計技法とテストレベルの関係、テスト自動化の目的、Test Pyramid(テストピラミッド)、CI/CD(Continuous Integration / Continuous Delivery:継続的インテグレーション / 継続的デリバリー)上の品質ゲート、自動化と手動確認の分担を整理する。

AIによってQAやテスト自動化がどのように変化するかについては、11章で改めて扱う。

### 7.1 テスト技法とテストレベルの関係

テスト技法とテストレベルは、同じものではない。

テスト技法は、主に「どの条件を確認するか」を考えるための方法である。6章で扱ったEquivalence Partitioning(同値分割)、Boundary Value Analysis(境界値分析)、Decision Table Testing(デシジョンテーブルテスト)、State Transition Testing(状態遷移テスト)、Use Case Testing / Scenario Testing(ユースケーステスト / シナリオテスト)、Exploratory Testing(探索的テスト)は、いずれも確認観点や確認条件を整理するために使う。

一方、テストレベルや確認単位は、主に「どの範囲で確認するか」を表す。

たとえば、Unit Testでは、関数、メソッド、クラス、小さなロジックなど、比較的狭い範囲を確認する。API Testでは、APIの入力、出力、ステータスコード、認可、エラー応答などを確認する。Integration Testでは、複数コンポーネント、DB、外部サービス、バッチ、通知などの連携を確認する。E2E Testでは、ユーザー操作に近い形で、システム全体に近い流れを確認する。

この関係は、1対1ではない。

たとえば、Boundary Value Analysis(境界値分析)によって作った確認条件は、Unit TestでもAPI Testでも使える。

「50,000円以上なら追加承認が必要である」というルールであれば、49,999円、50,000円、50,001円という境界値を、追加承認判定ロジックのUnit Testとして確認することもできる。また、申請作成APIにそれぞれの金額を送信し、追加承認フローが作成されるかをAPI Testとして確認することもできる。

同じように、Decision Table Testing(デシジョンテーブルテスト)で整理した条件の組み合わせも、複数のテストレベルに割り当てられる。

たとえば、「ユーザー種別」「申請状態」「金額」「承認者の有無」によって操作可否が変わる場合、条件の組み合わせそのものはデシジョンテーブルで整理できる。そのうえで、単純な判定ロジックはUnit Testで確認し、API経由の認可やエラー応答はAPI Testで確認し、申請から承認までの代表的な業務フローはE2E TestやManual Testで確認する、という分担が考えられる。

State Transition Testing(状態遷移テスト)も同様である。

下書き、申請中、承認済み、却下、取消済みといった状態を持つ申請フローでは、状態とイベントの組み合わせを整理する必要がある。その確認の一部は、状態遷移ロジックのUnit Testとして確認できる。一方で、実際にAPIを呼び出して状態が更新されるか、許可されない遷移がエラーになるかはAPI Testで確認しやすい。さらに、ユーザーが画面上で申請、承認、却下、再申請を行う代表的な流れは、E2E TestやManual Testの対象になりやすい。

つまり、テスト技法は、確認条件を作るためのレンズである。テストレベルは、その確認条件をどの範囲で実行するかを決める配置先である。

この関係を整理すると、次のようになる。

| テスト技法 | 主に作るもの | 割り当て先になり得る確認単位 |
|---|---|---|
| Equivalence Partitioning(同値分割) | 有効値・無効値・代表値 | Unit Test / API Test / Manual Testによる代表確認 |
| Boundary Value Analysis(境界値分析) | 境界値とその前後 | Unit Test / API Test |
| Decision Table Testing(デシジョンテーブルテスト) | 条件の組み合わせと期待結果 | Unit Test / API Test / Integration Test / Manual Test |
| State Transition Testing(状態遷移テスト) | 状態、イベント、遷移可否 | Unit Test / API Test / Integration Test / E2E Test |
| Use Case Testing / Scenario Testing(ユースケーステスト / シナリオテスト) | ユーザーや業務の一連の流れ | E2E Test / Manual Test |
| Exploratory Testing(探索的テスト) | 未知リスク、違和感、仕様抜けの発見 | Manual Test / セッションベースの確認 |

この表からわかるように、あるテスト技法が、特定のテストレベルだけに対応するわけではない。

重要なのは、「境界値分析だからUnit Testで確認する」「状態遷移テストだからE2E Testで確認する」と機械的に決めることではない。確認したいリスクに対して、どのテストレベルで確認するのが、速く、安定し、原因を特定しやすく、保守しやすいかを考えることである。

### 7.2 テスト条件をどのレベルに割り当てるか

テスト条件をどのテストレベルに割り当てるかは、テスト自動化を考える前に整理しておくべき重要な判断である。

なぜなら、同じ確認内容でも、どのレベルで確認するかによって、実行速度、安定性、原因調査のしやすさ、保守負荷、ユーザー行動への近さが変わるからである。

一般に、粒度の細かいテストは速く、失敗原因を特定しやすい。たとえばUnit Testは、特定の関数やロジックだけを確認するため、実行が速く、失敗したときに原因を追いやすい。一方で、Unit Testだけでは、API、DB、画面、外部連携、ユーザー操作を含む一連の流れは確認できない。

反対に、E2E Testは、ユーザーに近い流れを確認しやすい。申請者が申請を作成し、承認者が承認し、通知が送られ、履歴が残るといった主要フローを確認するには有効である。しかし、E2E Testは実行時間が長くなりやすく、画面変更やテストデータの状態に影響されやすく、失敗したときに原因の切り分けが難しい場合がある。

そのため、テスト条件を割り当てるときには、次のような問いを持つとよい。

- この確認は、小さなロジックとして確認できるか
- API単位で確認した方が、UI(User Interface:ユーザーインターフェース)に依存せず安定するか
- DB保存、トランザクション、外部連携、通知などの連携まで確認する必要があるか
- ユーザーの一連の業務フローとして確認する必要があるか
- 毎回同じ期待値を確認するものか
- 失敗したときに、どこが壊れたのかを切り分けやすいか
- その確認をE2Eで行う価値は、実行時間や保守負荷に見合うか
- 人間が画面を見て判断すべき違和感や業務上の不自然さを含むか

たとえば、次のように割り当てることができる。

| 確認したいリスク | 向きやすい確認単位 | 理由 |
|---|---|---|
| 金額が閾値以上かどうかの判定 | Unit Test | 小さなロジックとして高速に確認しやすい |
| 入力値に対するAPIのバリデーション | API Test | UIに依存せず、入力・出力・エラー応答を確認しやすい |
| 権限のないユーザーによる操作拒否 | API Test | 画面上のボタン非表示だけでなく、サーバー側の認可を確認できる |
| 申請データの保存と承認フロー作成 | Integration Test | API、DB、ドメインロジックの連携を確認できる |
| 外部通知サービスとの連携 | Integration Test | 外部依存との接続や契約を確認する必要がある |
| 申請作成から承認完了までの主要フロー | E2E Test / Manual Test | ユーザーの業務フローとして確認しやすい |
| 画面上の分かりにくさや業務上の違和感 | Manual Test / Exploratory Testing | 人間の判断や文脈理解が必要になる |

ここで注意すべきなのは、上位のテストレベルが下位のテストレベルより優れているわけではないという点である。

E2E Testは、ユーザーに近い確認ができるため重要である。しかし、すべての境界値、すべての入力パターン、すべての条件分岐をE2E Testに寄せると、自動テスト全体が遅く、不安定で、保守しにくくなる可能性がある。

一方で、Unit TestやAPI Testは速く安定しやすいが、それだけではユーザーが実際に目的を達成できるかまでは確認できない。画面遷移、複数機能の連携、ユーザーが迷わず操作できるか、業務として自然か、といった観点は、E2E Test、Manual Test、Exploratory Testingによる確認も必要になる。

したがって、テスト条件の割り当てでは、次のような分担を意識するとよい。

- 細かいロジック、分岐、境界値はUnit Testに寄せる
- APIの入力、出力、認可、異常系はAPI Testに寄せる
- DB、外部サービス、バッチ、通知などの連携はIntegration Testに寄せる
- 主要な業務フローはE2E Testで代表的に確認する
- UX上の違和感、仕様の妥当性、未知リスクはManual TestやExploratory Testingで確認する

この分担は、絶対的なルールではない。プロダクトの構造、技術スタック、リリース頻度、チームのスキル、ドメインリスクによって、適切な配分は変わる。

しかし、共通して重要なのは、確認条件をただ増やすことではない。どのリスクを、どのレベルで、どの程度の深さで確認するかを意識的に決めることである。

この整理ができて初めて、次に「どの確認を自動化するか」を考えられる。

すべての確認を手動で行うことは現実的ではない。特に、変更のたびに同じ期待値を確認する回帰的な確認は、人間が毎回手で行うと時間がかかり、確認漏れも起きやすい。

そのため、次節では、テスト自動化の目的を整理する。

### 7.3 テスト自動化の目的

テスト自動化の目的は、単に手動作業を減らすことだけではない。

もちろん、人間が毎回同じ手順を繰り返す確認を自動化できれば、作業時間を減らせる。リリース前に毎回同じ画面を操作し、同じ入力値を入れ、同じ期待結果を確認する作業は、時間もかかり、確認漏れも起きやすい。そのような反復的な確認を自動化することには大きな価値がある。

しかし、テスト自動化の、より重要な目的は、変更時に期待される状態を継続的に確認できるようにすることである。

ソフトウェアは一度作って終わりではない。機能追加、仕様変更、リファクタリング、依存ライブラリの更新、DB(Database:データベース)スキーマの変更、UI(User Interface:ユーザーインターフェース)変更、外部API(Application Programming Interface:アプリケーションプログラミングインターフェース)連携の変更などが継続的に発生する。

そのたびに、既存機能が意図せず壊れていないかを確認する必要がある。その確認をすべて手動で行おうとすると、変更が増えるほど確認コストが増え、リリース速度や開発者の変更しやすさを妨げる。

自動テストは、この問題を軽減するための仕組みである。

たとえば、Pull Request(PR:プルリクエスト)が作成されたときに、Unit Test(単体テスト)、API Test、Integration Test(結合テスト)、lint、type check、build checkなどが自動実行されれば、変更によって既存の期待状態が壊れていないかを早い段階で確認できる。

これにより、開発者は変更の影響を早く知ることができる。QA(Quality Assurance:品質保証)は、毎回同じ確認を手動で繰り返すだけでなく、よりリスクの高い領域、仕様の妥当性、UX上の違和感、探索的な確認に時間を使いやすくなる。チーム全体としても、品質確認を個人の注意力だけに依存させにくくなる。

テスト自動化には、主に次のような目的がある。

| 目的 | 内容 |
|---|---|
| 変更時の早いフィードバック | コード変更や仕様変更によって、既存の期待状態が壊れていないかを早く知る |
| Regression(回帰)の検知 | 以前は動いていた機能が、別の変更によって壊れていないかを確認する |
| 確認作業の再現性向上 | 同じ条件、同じ手順、同じ期待結果で繰り返し確認できるようにする |
| 品質確認の属人化防止 | 特定の人が覚えている確認手順だけに依存しないようにする |
| 変更しやすさの向上 | 自動テストがあることで、開発者が安心してリファクタリングや改善を行いやすくする |
| CI/CD上の品質ゲート化 | Pull Request、マージ、リリース前などに自動実行し、一定の品質条件を満たしているか確認する |

ここで注意すべきなのは、自動テストがあること自体が品質を保証するわけではないという点である。

自動テストは、あらかじめ定義された条件と期待結果を繰り返し確認する仕組みである。そのため、テスト設計が不十分であれば、重要なリスクを確認できないまま「自動テストは通っている」という状態になることがある。

たとえば、正常系のAPI Testだけが自動化されていても、権限違反、境界値、無効な状態遷移、外部連携失敗、二重送信、監査ログの不足などが確認されていなければ、重要な品質リスクは残る。

また、自動テストが壊れやすかったり、実行が遅すぎたり、失敗しても原因がわかりにくかったりすると、チームはそのテスト結果を信用しなくなる。自動テストは、作ることだけでなく、継続的に信頼できる状態で運用することが重要である。

したがって、テスト自動化は、単なる省力化ではなく、品質確認を開発フローに組み込み、変更に対する継続的なフィードバックを得るための仕組みとして理解する必要がある。

### 7.4 自動化に向く確認

すべての確認が自動化に向くわけではない。

自動化に向くのは、期待結果が明確で、同じ条件で繰り返し確認でき、変更のたびに壊れていないかを確認したいものが中心である。

たとえば、次のような確認は自動化に向きやすい。

- 入力値に対して、期待される出力が決まっている
- 境界値や条件分岐の期待結果が明確である
- APIのステータスコード、レスポンス、エラー形式が定義されている
- 権限のあるユーザーと権限のないユーザーの挙動が明確である
- 状態遷移の許可・不許可が定義されている
- DBに保存される値や更新される状態が確認できる
- 過去に不具合が出た箇所で、再発を防ぎたい
- Pull Requestやリリース前に毎回確認したい
- 人間が手で確認すると時間がかかるが、期待結果は明確である

たとえば、「50,000円以上の申請には追加承認が必要である」というルールでは、49,999円、50,000円、50,001円の期待結果は明確である。このような境界値の確認は、Unit TestやAPI Testとして自動化しやすい。

また、「一般ユーザーは他人の申請を承認できない」という権限ルールも、自動化に向きやすい。画面上でボタンが見えないことだけでなく、APIを直接呼び出した場合に403 Forbiddenなどの適切なエラーになることを確認できるためである。

状態遷移も、自動化候補になりやすい。たとえば、下書きから申請中へ進める、申請中から承認済みに進める、承認済みから下書きには戻せない、といったルールが明確であれば、API TestやIntegration Testとして確認しやすい。

一方で、自動化しにくい、または自動化だけでは不十分な確認もある。

たとえば、画面上の説明文がユーザーにとって自然か、エラーメッセージが次の行動につながるか、業務フローとして違和感がないか、ユーザーが迷わず目的を達成できるか、といった確認には人間の判断が必要になりやすい。

また、仕様そのものの妥当性も、自動テストだけでは判断できない。自動テストは、定義された期待結果に対して実際の挙動を比較することはできる。しかし、その期待結果自体が業務上正しいか、ユーザー価値に合っているか、プロダクトの文脈に照らして妥当かは、PM(Product Manager:プロダクトマネージャー)、開発者、QA、業務担当者、CS(Customer Success:カスタマーサクセス)、Support(サポート)などの議論が必要になる。

自動化に向く確認を整理すると、次のようになる。

| 自動化に向く条件 | 説明 |
|---|---|
| 期待結果が明確である | 入力、操作、状態に対する期待結果を機械的に判定できる |
| 繰り返し実行する価値がある | Pull Request、マージ、リリース前などで何度も確認したい |
| 手動確認の負荷が高い | 人間が毎回行うと時間がかかり、確認漏れが起きやすい |
| 失敗時に調査しやすい | テスト失敗から、どの機能や条件が壊れたかを追いやすい |
| 実行条件を安定させられる | テストデータ、環境、外部依存を制御しやすい |
| 仕様変更時に更新可能である | テストが読みやすく、期待値の変更に追従しやすい |

逆に、次のような確認は、自動化だけに頼るべきではない。

| 自動化だけでは不十分な確認 | 理由 |
|---|---|
| UX上の違和感 | ユーザーが迷うか、不安を感じるかは人間の判断が必要になりやすい |
| 仕様の妥当性 | 期待結果そのものが正しいかは、関係者間の合意が必要である |
| 業務上の自然さ | 実際の業務フローに合っているかは、ドメイン文脈を踏まえる必要がある |
| 未知リスクの探索 | 事前に期待結果を定義していない問題は、探索的テストで見つかることがある |
| 視覚的・文脈的な違和感 | レイアウト、文言、情報量、操作順序などは機械的判定だけでは難しい場合がある |

ここで重要なのは、自動化と手動確認を対立させないことである。

自動化は、毎回同じ期待結果を確認する作業を安定して繰り返すために有効である。一方で、Manual Test(手動テスト)やExploratory Testing(探索的テスト)は、仕様の抜け、UX上の違和感、未知のリスク、業務上の不自然さを見つけるために重要である。

むしろ、両者は補完関係にある。

探索的テストで見つかった重要な不具合は、再発防止のために自動テストへ追加されることがある。逆に、自動テストが通っていても、ユーザー視点や業務視点で違和感があれば、人間による確認や仕様見直しが必要になる。

したがって、自動化に向く確認を見極めることは、単に「何を自動化するか」を決めることではない。どの確認を機械に任せ、どの確認を人間が判断し、どの結果をチームの品質判断に使うかを設計することである。

次節では、自動化されたUnit Test、API Test、Integration Test、E2E Testが、それぞれどのようなリスクを確認しやすいのかを整理する。

### 7.5 自動化されたUnit Test / API Test / Integration Test / E2E Test

7.4では、自動化に向く確認として、期待結果が明確で、同じ条件で繰り返し確認でき、変更のたびに壊れていないかを確認したいものを整理した。

この節では、そのような確認が、Unit Test(単体テスト)、API Test、Integration Test(結合テスト)、E2E(End-to-End:エンドツーエンド) Testではどのように現れるのかを整理する。

ここで重要なのは、これらのテストレベルが、単純な優劣関係ではないという点である。Unit TestはE2E Testより下位だから価値が低い、ということではない。また、E2E Testはユーザーに近いから常に最も重要、ということでもない。

それぞれのテストレベルには、確認しやすいリスクと確認しにくいリスクがある。

#### Unit Test(単体テスト)

Unit Test(単体テスト)は、関数、メソッド、クラス、小さなロジックなど、比較的狭い範囲を確認するテストである。

自動化されたUnit Testは、実行が速く、失敗したときに原因を特定しやすい。そのため、入力値に対する計算結果、条件分岐、境界値、バリデーション、状態判定などを確認するのに向いている。

たとえば、「50,000円以上の申請には追加承認が必要である」というルールでは、追加承認が必要かどうかを判定するロジックをUnit Testとして確認できる。

```text
amount = 49,999 -> additional approval is not required
amount = 50,000 -> additional approval is required
amount = 50,001 -> additional approval is required
```

このような確認は、Boundary Value Analysis(境界値分析)で作った条件を、Unit Testに割り当てた例である。

Unit Testに向きやすい確認には、次のようなものがある。

- 金額、日付、件数、文字数などの境界値判定
- 入力値の有効・無効判定
- ステータスやフラグに応じた分岐
- 権限判定ロジックの一部
- 計算式や集計ロジックの一部
- エラー条件の判定
- データ変換やフォーマット処理

Unit Testの価値は、早く、安定して、狭い範囲の期待結果を確認できる点にある。

一方で、Unit Testだけでは、API、DB(Database:データベース)、画面、外部サービス、通知、ユーザー操作を含む一連の流れは確認できない。また、モックを多用しすぎると、実際のコンポーネント間の接続が壊れていてもテストが通ることがある。

したがって、Unit Testは重要だが、それだけで品質を判断することはできない。

#### API Test

API Testは、APIの入力、出力、ステータスコード、レスポンス形式、認可、エラー処理などを確認するテストである。

API Testは、UI(User Interface:ユーザーインターフェース)に依存せずに、バックエンドの振る舞いを確認しやすい。画面変更の影響を受けにくく、E2E Testよりも実行が速く安定しやすい場合が多い。

たとえば、申請作成APIに対して、次のような確認ができる。

- 正しい入力なら申請を作成できる
- 必須項目が不足している場合はエラーになる
- 50,000円以上なら追加承認フローが作成される
- 権限のないユーザーは申請を作成できない
- 他人の申請IDを指定して更新しようとすると拒否される
- 不正なステータス遷移はエラーになる
- エラー時に適切なステータスコードとエラーメッセージが返る

API Testは、特に権限品質と相性がよい。

画面上でボタンが非表示になっていても、APIを直接呼び出したときに操作できてしまえば、セキュリティ・権限品質として問題がある。そのため、重要な操作については、UI上の表示だけでなく、サーバー側で認可が正しく行われているかをAPI Testで確認する価値がある。

また、API Testは、Equivalence Partitioning(同値分割)、Boundary Value Analysis(境界値分析)、Decision Table Testing(デシジョンテーブルテスト)、State Transition Testing(状態遷移テスト)で整理した条件を割り当てやすい。

一方で、API Testだけでは、ユーザーが画面上で迷わず操作できるか、画面遷移が自然か、複数機能をまたいだ実際の業務フローが成立するかまでは確認しにくい。そのため、API Testは重要な自動化対象であるが、E2E TestやManual Test(手動テスト)を完全に置き換えるものではない。

#### Integration Test(結合テスト)

Integration Test(結合テスト)は、複数のコンポーネントが連携したときに期待どおりに動くかを確認するテストである。

Unit Testでは個別のロジックが正しく、API TestではAPIの入出力が正しく見えていても、実際にはDB保存、トランザクション、外部サービス連携、通知、バッチ処理、非同期処理などの接続部分で問題が起きることがある。

Integration Testでは、たとえば次のような確認を行う。

- APIから受け取った申請データがDBに正しく保存される
- 申請作成時に承認フローが作成される
- 承認時にステータス、履歴、更新時刻が正しく更新される
- 通知キューやメール送信処理に必要なデータが作られる
- バッチ処理が対象データを正しく抽出・更新する
- 外部サービスの失敗時に、処理が安全な状態で終了する
- トランザクション失敗時に中途半端なデータが残らない

Integration Testは、コンポーネント間の接続リスクを確認するために重要である。

特に、DB、外部サービス、メッセージキュー、ファイル入出力、バッチ、通知などが関わる場合、Unit Testだけでは確認できないリスクがある。実務では、外部サービスを本物に近い形で使う場合もあれば、テスト用の代替サービス、モック、スタブ、コンテナ化されたテスト用環境などを使う場合もある。

Integration Testは、Unit Testより実行が重くなりやすい。一方で、E2E Testよりは範囲を限定できるため、接続部分のリスクを比較的狙って確認しやすい。

ただし、Integration Testを増やす場合は、テストデータ、環境、外部依存、実行順序、後片付けを管理する必要がある。これらが不安定だと、テスト結果が信頼しにくくなり、flaky test(不安定なテスト)の原因になる。

なお、外部APIやマイクロサービス間の連携では、Contract Test(契約テスト)が使われることもある。Contract Testは、APIのconsumer(利用側)とprovider(提供側)の間で期待されるリクエスト、レスポンス、ステータスコード、スキーマ、必須項目などの取り決めが破られていないかを確認するテストである。

内部ロジックが正しくても、接続先APIのレスポンス形式や必須項目が変われば、連携部分で不具合が起きることがある。Contract Testは、このようなサービス間の「約束」を比較的早く確認するために使われる。

ただし、Contract Testはシステム全体の副作用や業務フロー全体を確認するものではない。DBへの保存、通知、トランザクション、複数コンポーネントをまたぐ実際の処理結果は、Integration TestやE2E Testで確認する必要がある。本章では詳細には踏み込まず、複数サービスや外部API連携のリスクを扱うテストの一例として理解しておく。

#### E2E(End-to-End:エンドツーエンド) Test

E2E(End-to-End:エンドツーエンド) Testは、ユーザー操作に近い形で、システム全体に近い流れを確認するテストである。

たとえば、申請機能であれば、次のような流れを確認する。

```text
申請者が申請を作成する
-> 承認者が申請を確認する
-> 承認者が承認する
-> 申請ステータスが承認済みになる
-> 履歴が残る
-> 必要な通知が行われる
```

E2E Testは、主要な業務フローが壊れていないことを確認するうえで有効である。複数機能、画面遷移、認証、権限、API、DB、通知などを含む流れを、ユーザーに近い形で確認できるためである。

一方で、E2E Testは重くなりやすい。

画面変更、テストデータの状態、実行環境、ネットワーク、非同期処理、外部サービス、待機処理などの影響を受けやすく、失敗したときに原因の切り分けが難しい場合がある。また、すべての境界値、すべての入力パターン、すべての権限、すべての状態遷移をE2E Testで確認しようとすると、実行時間と保守負荷が大きくなる。

そのため、E2E Testは、主要な業務フローやユーザー価値に直結する代表シナリオに絞る方が扱いやすい。

たとえば、次のような確認はE2E Testに向きやすい。

- ログインから主要機能の完了までの正常系フロー
- 申請作成から承認完了までの代表的な業務フロー
- 購入、予約、申請、承認、登録など、ユーザー価値に直結するフロー
- リリース前に必ず壊れていないことを確認したい最重要フロー

一方で、細かい境界値、条件分岐、異常系の網羅、権限の組み合わせは、Unit Test、API Test、Integration Testに寄せた方が速く安定しやすいことが多い。

#### 各テストレベルの使い分け

ここまでを整理すると、次のようになる。

| テストレベル           | 確認しやすいリスク                            | 注意点                           |
| ---------------- | ------------------------------------ | ----------------------------- |
| Unit Test        | 小さなロジック、境界値、分岐、計算、バリデーション            | コンポーネント間連携やユーザー操作は確認しにくい      |
| API Test         | 入力、出力、認可、エラー応答、状態遷移、サーバー側の振る舞い       | UI上の使いやすさや画面遷移は確認しにくい         |
| Integration Test | DB、外部サービス、通知、バッチ、トランザクション、コンポーネント間連携 | 環境やデータ管理が不安定だとflakyになりやすい     |
| E2E Test         | 主要業務フロー、画面遷移、ユーザーに近い操作、複数機能の連携       | 実行が重く、保守負荷が高く、原因切り分けが難しい場合がある |

このように、テストレベルはそれぞれ異なるリスクを扱う。

重要なのは、すべてを1つのテストレベルで確認しようとしないことである。細かいロジックはUnit Test、APIの振る舞いはAPI Test、接続部分はIntegration Test、主要業務フローはE2E Testというように、確認したいリスクに応じて適切な確認単位を選ぶ必要がある。

この考え方は、次に扱うRegression Test(回帰テスト)にも関係する。

Regression Testは、Unit Test、API Test、Integration Test、E2E Testと同じ分類軸の言葉ではない。Regression Testは、確認範囲ではなく、既存機能が壊れていないことを確認する目的を表す。

### 7.6 Regression Test(回帰テスト)と自動化

Regression Test(回帰テスト)は、変更によって既存機能が意図せず壊れていないことを確認するためのテストである。

ここで重要なのは、Regression Testは、Unit Test、API Test、Integration Test、E2E Testと同じ分類軸ではないという点である。

Unit Test、API Test、Integration Test、E2E Testは、主に「どの範囲で確認するか」を表す。一方、Regression Testは、「何のために確認するか」を表す。

つまり、Regression Testは、Unit Test、API Test、Integration Test、E2E Testのような複数の確認単位で成立する。また、自動化されていないManual Testとして行われることもある。

たとえば、次のようなものはすべてRegression Testになり得る。

| 確認単位 | 回帰確認としての例 |
|---|---|
| Unit Test | 過去に金額境界の不具合が出たため、49,999円、50,000円、50,001円の判定を継続確認する |
| API Test | 以前、権限のないユーザーが他人の申請を更新できたため、API経由で403エラーになることを継続確認する |
| Integration Test | 過去に通知キューへの登録漏れがあったため、申請作成時に通知データが作られることを継続確認する |
| E2E Test | 以前、申請から承認完了までの主要フローが壊れたため、代表シナリオを継続確認する |
| Manual Test | 自動化されていない重要画面について、リリース前に既存機能の代表操作を確認する |

このように、Regression Testは、特定のテストレベルを意味するものではない。

Regression Testの目的は、変更によって既存の期待状態が壊れていないかを確認することである。そのため、繰り返し実行する価値が高く、自動化と相性がよい。

特に、次のような確認はRegression Testとして自動化する価値が高い。

- 過去に不具合が出た箇所
- リリース前に毎回確認している重要フロー
- 変更頻度が高く、壊れやすい領域
- 金銭、権限、承認、通知、外部連携など影響が大きい領域
- 手動確認に時間がかかるが、期待結果が明確な確認
- 開発者が変更時に早くフィードバックを得たい確認

たとえば、過去に「50,000円ちょうどの申請で追加承認が作成されない」という不具合があった場合、その修正後に50,000円ちょうどの確認を自動テストとして追加することが考えられる。これにより、同じ不具合が将来の変更で再発した場合、早い段階で検知できる。

また、過去に「画面上では承認ボタンが非表示だが、APIを直接呼ぶと承認できてしまう」という不具合があった場合、API Testとして権限違反のRegression Testを追加する価値が高い。このような確認は、手動で毎回行うよりも、自動化して継続実行した方が再発防止につながりやすい。

ただし、Regression Testを増やすときにも注意が必要である。

不具合が見つかるたびに、すべてをE2E Testとして追加すると、自動テスト全体が遅く、壊れやすく、保守しにくくなる可能性がある。重要なのは、不具合の原因やリスクに応じて、どのレベルのRegression Testとして追加するかを考えることである。

たとえば、境界値判定の不具合であればUnit TestやAPI Testに追加する方がよい場合が多い。権限チェックの抜けであればAPI Testが向いている。DB保存や通知連携の漏れであればIntegration Testが向いている。ユーザーの主要フロー全体が壊れていた場合は、E2E Testとして代表シナリオを追加する価値がある。

Regression Testの追加判断では、次のような問いが有効である。

- この不具合は、どのレベルで最も早く検知できるか
- 同じ不具合を再発させないために、どの条件を固定すべきか
- Unit TestやAPI Testで十分に確認できるか
- E2E Testで確認する必要があるほど、ユーザーの主要フローに関わるか
- テストを追加した場合、実行時間や保守負荷は妥当か
- そのテストは、失敗したときに原因を特定しやすいか

Regression Testは、品質活動を過去の不具合から学習する仕組みに変える。

ここで、本資料の前半で整理したQA(Quality Assurance:品質保証)の重要な役割を思い出すとよい。QAは、不具合を見つけて終わる活動ではない。不具合、問い合わせ、インシデント、探索的テストで得られた気づきを、その場限りで消費せず、次の要求整理、テスト設計、自動化、品質ゲート、運用改善へ還元することも重要な役割である。

不具合が見つかったとき、それを一度修正して終わりにするのではなく、「なぜ見逃したのか」「どのテストレベルで検知できたのか」「同じ種類の不具合を今後どう防ぐか」を考えることで、テスト設計と自動化を改善できる。

この意味で、Regression Testは、単なる再確認ではない。過去に得られた品質情報を、継続的な確認の仕組みへ変換する活動でもある。

次節では、自動テストをどのようなバランスで持つべきかを考えるためのモデルとして、Test Pyramid(テストピラミッド)を扱う。

---

### 7.7 Test Pyramidとテスト配分の考え方

Test Pyramid(テストピラミッド)は、自動テストをどのような粒度で持つべきかを考えるための代表的なモデルである。

基本的な考え方は、粒度が細かく、実行が速く、失敗原因を特定しやすいテストを多く持ち、粒度が粗く、実行が重く、保守負荷が高くなりやすいテストは重要なものに絞る、というものである。

典型的には、Unit Test(単体テスト)を土台として厚く持ち、その上にAPI TestやIntegration Test(結合テスト)を置き、E2E(End-to-End:エンドツーエンド) Testは主要な業務フローに絞る、という形で説明されることが多い。

この考え方は、7.5で整理した各テストレベルの特徴と対応している。

Unit Testは、実行が速く、失敗したときに原因を特定しやすい。そのため、金額、日付、文字数、状態判定、バリデーション、分岐、計算など、小さなロジックを継続的に確認するのに向いている。

API TestやIntegration Testは、Unit Testだけでは確認できないサーバー側の振る舞い、認可、DB(Database:データベース)保存、外部サービス連携、通知、バッチ処理などを確認するのに向いている。

E2E Testは、ユーザーに近い形で主要業務フローを確認できる。一方で、画面変更、テストデータ、待機処理、外部サービス、実行環境の影響を受けやすく、実行時間や保守負荷が大きくなりやすい。

したがって、すべての確認をE2E Testに寄せるのではなく、細かい境界値や条件分岐はUnit TestやAPI Testに寄せ、コンポーネント間の接続はIntegration Testで確認し、E2E Testはユーザー価値に直結する代表的な流れに絞る、という配分が基本になる。

ただし、Test Pyramidは、すべてのプロダクトにそのまま当てはめるべき固定比率ではない。

実務では、プロダクトの構造、技術スタック、ドメインリスク、チームのスキル、変更頻度、リリース頻度、外部依存の多さによって、適切なテスト配分は変わる。

たとえば、ドメインロジックが厚いアプリケーションでは、Unit Testによる細かいロジック確認の価値が高くなりやすい。一方で、複数サービスの連携や外部API(Application Programming Interface:アプリケーションプログラミングインターフェース)との接続が品質リスクの中心である場合は、Integration TestやContract Test(契約テスト)の重要度が高くなることがある。

また、フロントエンド中心のプロダクトでは、コンポーネント間の連携やユーザー操作に近い確認が重要になる場合がある。このような背景から、Testing Trophy(テスティングトロフィー)、Testing Diamond(テスティングダイヤモンド)、Testing Honeycomb(テスティングハニカム)のように、Test Pyramidとは異なる形でテスト配分を説明する議論もある。

ここで重要なのは、形そのものにこだわりすぎないことである。

「Unit Testを何割、Integration Testを何割、E2E Testを何割にするべきか」という固定比率だけを議論しても、プロダクトの品質リスクに合っていなければ意味がない。また、Unit TestやIntegration Testという言葉自体も、組織や技術スタックによって指す範囲が異なることがある。

そのため、Test Pyramidは、絶対的なルールではなく、次のような問いを考えるためのモデルとして扱う方がよい。

- この確認は、どのレベルで最も速く、安定して実行できるか
- 失敗したときに、原因を特定しやすいか
- その確認をE2E Testで行う必要があるか
- Unit TestやAPI Testで十分に確認できる条件を、E2E Testで重複確認していないか
- 逆に、Unit Testだけでは確認できない接続リスクや業務フローを見落としていないか
- テスト全体が遅すぎて、開発者が頻繁に実行しなくなっていないか
- テストが不安定すぎて、失敗しても無視される状態になっていないか
- テストの保守負荷が、得られる品質情報に見合っているか

Test Pyramidの本質は、単に「Unit Testを多く、E2E Testを少なく」と覚えることではない。

重要なのは、速く、信頼でき、失敗したときに意味があり、保守可能なテスト群を作ることである。プロダクトの品質リスクに応じて、Unit Test、API Test、Integration Test、E2E Test、Manual Test(手動テスト)、Exploratory Testing(探索的テスト)を組み合わせることが必要になる。

この意味で、Test Pyramidは、7章で扱っているテスト自動化の全体設計を考えるための出発点である。

次節では、このように設計された自動テストや静的チェックを、CI/CD上でどのように品質ゲートとして扱うかを整理する。

---

### 7.8 CI/CD上の品質ゲート

CI/CD(Continuous Integration / Continuous Delivery:継続的インテグレーション / 継続的デリバリー)上の品質ゲートとは、コード変更、マージ、リリースなどの節目で、自動テストや各種チェックを実行し、一定の品質条件を満たしているかを確認する仕組みである。

品質ゲートの目的は、人間が毎回思い出して確認する状態を減らし、開発フローの中で継続的に品質情報を得られるようにすることである。

たとえば、Pull Request(PR:プルリクエスト)が作成されたときに、lint、type check、Unit Test、API Test、build checkなどが自動実行されれば、変更が既存の期待状態を壊していないかを早い段階で確認できる。

また、main branchへのmerge前、release candidate作成時、本番に近い検証環境への反映後、リリース前などに、Integration Test、E2E Test、security scan、外部連携確認などを実行すれば、より広い範囲の品質リスクを段階的に確認できる。

品質ゲートには、さまざまなチェックが含まれる。

| チェック | 主な目的 |
|---|---|
| lint | コードスタイル、構文上の問題、単純なミスを検出する |
| type check | 型の不整合や誤った使い方を検出する |
| Unit Test | 小さなロジック、境界値、分岐、バリデーションを確認する |
| API Test | APIの入力、出力、認可、エラー応答を確認する |
| Integration Test | DB、外部サービス、バッチ、通知などの連携を確認する |
| E2E Test | 主要な業務フローが壊れていないかを確認する |
| build check | アプリケーションや成果物が正しくビルドできるかを確認する |
| security scan | 依存関係、既知脆弱性、設定ミスなどを検出する |
| 静的解析 / コード品質・カバレッジチェック | バグにつながり得るコード、保守性を下げるコード、重複、脆弱性、テストカバレッジなどを確認する |

また、品質ゲートには、アプリケーションを実行して期待結果を確認するテストだけでなく、静的解析やコード品質チェックも含まれる。

たとえば、SonarQubeのようなツールは、ソースコードの静的解析結果やテストカバレッジの情報をもとに、バグにつながり得るコード、脆弱性、保守性を下げるコード、重複、カバレッジ不足などを確認するために使われる。このようなツールでは、新しく追加・変更されたコードに対して、重大な問題がないか、重複が一定以下か、カバレッジが一定以上か、といった条件をQuality Gate(品質ゲート)として設定できる。

ここでいうテストカバレッジは、主にコードカバレッジを指す。つまり、自動テストを実行したときに、新しく追加・変更されたコードのどの程度が実行されたかを表す指標である。

ただし、コードカバレッジが高いことは、重要な仕様、業務ルール、境界条件、権限、状態遷移を十分に確認できていることを意味しない。静的解析やコードカバレッジは、テスト設計やレビューを置き換えるものではなく、機械的に確認しやすい品質リスクを継続的に検出するための補助的な品質ゲートとして扱う必要がある。

どのチェックを品質ゲートに含めるかは、プロダクトの性質やチームの責任範囲によって変わる。

ここで重要なのは、すべてのチェックを同じタイミングで実行する必要はないという点である。

なお、実行時間の目安はプロダクトやCI/CD環境によって変わる。DORAのTest Automationでは、自動テストはローカル環境とCI上の両方で10分未満にフィードバックを返せることが望ましいとされている。また、DORAのContinuous Integrationでも、commitごとの自動テストは数分でフィードバックを返すべきだと説明されている。

したがって、次の表は標準規格ではなく、初学者が実務上の感覚を掴むための参考値として扱う。

| 実行タイミング | 実行時間の目安 | 例 |
|---|---:|---|
| 開発者のローカル環境 | 数秒〜1分程度 | lint、Unit Test |
| Pull Request作成時 | 数分〜10分程度 | lint、type check、Unit Test、軽量なAPI Test |
| マージ前 | 10分前後〜20分程度。長い場合は分離や並列化を検討する | API Test、Integration Test、重要なE2E Test |
| 本番に近い検証環境への反映後 | 数十分程度になることもある | E2E Test、security scan、外部連携確認 |
| 定期実行 | 30分〜数時間もあり得る | 重いE2E Test、大きな回帰確認、外部連携確認 |

この表は、実行時間の感覚を掴むための補助である。次の表では、その時間感覚を踏まえて、品質ゲートをどのタイミングに配置するかを整理する。短いフィードバックが必要な確認はPR時までに置き、重い確認は定期実行や本番に近い検証環境への反映後に分けると、開発フローを止めにくくなる。

実行が速く、失敗原因を特定しやすいチェックは、Pull Requestごとに実行しやすい。たとえば、lint、type check、Unit Test、軽量なAPI Testは、開発者に早いフィードバックを返すためにPR時に実行する価値が高い。

一方で、実行時間が長いE2E Testや、外部依存を含む重いIntegration Testは、すべての変更ごとに実行すると開発フローを遅くする場合がある。その場合、重要なE2E TestだけをPull Request時に実行し、実行時間の長いテストは、夜間や定期バッチとしてまとめて実行する、本番に近い検証環境へ反映した後に実行する、リリース前に実行する、といった分け方が考えられる。

品質ゲートの実行タイミングは、たとえば次のように分けられる。

| タイミング | 実行しやすいチェックの例 | 目的 |
|---|---|---|
| 開発者のローカル環境 | lint、type check、Unit Test | コミット前に早く問題を見つける |
| Pull Request作成時 | lint、type check、Unit Test、軽量なAPI Test、build check | レビュー前に基本的な不具合を検出する |
| マージ前 | API Test、Integration Test、重要なE2E Test | main branchに壊れた変更を入れにくくする |
| 本番に近い検証環境への反映後 | Integration Test、E2E Test、security scan、外部連携確認 | 本番環境に出す前に、環境差分や連携を含めて確認する |
| リリース前 | 重要なE2E Test、回帰確認、残リスク確認 | リリース判断に必要な品質情報を集める |
| 定期実行 | 重いE2E Test、外部連携確認、依存関係スキャン | PRごとに実行しにくい確認を継続的に行う |

品質ゲートでは、失敗したときにどう扱うかも重要である。

たとえば、Unit Testやtype checkが失敗した場合は、mergeを止めるべきことが多い。なぜなら、コードの基本的な期待状態が壊れている可能性が高いからである。

一方で、一部のsecurity scanや外部依存チェックでは、警告として扱い、重要度に応じて対応期限を決める場合もある。すべての警告で即座にmergeを止めると、開発フローが過度に止まる可能性があるためである。

つまり、品質ゲートには、failとして止める条件と、warningとして可視化する条件がある。

| 扱い | 例 | 考え方 |
|---|---|---|
| failとして止める | build失敗、Unit Test失敗、type check失敗、重要API Test失敗、重大な品質ゲート違反 | 変更を進める前に修正すべき問題として扱う |
| warningとして可視化する | 軽微なlint警告、低重要度の脆弱性、非重要なテストの一時的失敗、軽微なコード品質指摘 | 可視化し、優先度や期限を決めて対応する |
| manual reviewに回す | 残リスク、既知不具合、UX上の判断、仕様判断 | 自動判定だけではなく人間の判断を入れる |

ただし、品質ゲートを増やせば増やすほど品質が高くなるわけではない。

品質ゲートが多すぎたり、実行が遅すぎたり、flaky test(不安定なテスト)が多かったりすると、開発者はテスト結果を信用しなくなる。チェックが頻繁に失敗するが、実際には問題がない状態が続くと、品質ゲートは安全装置ではなく、単なる障害物として扱われるようになる。

したがって、品質ゲートは、速さ、信頼性、重要度、保守性のバランスを考えて設計する必要がある。

良い品質ゲートは、次のような特徴を持つ。

- 重要な問題を早く検出できる
- 失敗したときに原因を特定しやすい
- 開発フローを過度に遅くしない
- flaky testが少なく、結果を信頼できる
- failとwarningの基準が明確である
- 誰が対応するか、いつ対応するかが決まっている
- 品質情報がチームの判断に使われている

CI/CD上の品質ゲートは、QA(Quality Assurance:品質保証)だけが使うものではない。開発者、QA、SRE(Site Reliability Engineering:サイト信頼性エンジニアリング)、Data / Analytics(データ / 分析)、Security(セキュリティ)などが、それぞれの品質観点を開発フローに組み込むための仕組みである。

なお、QAがCI/CDパイプラインそのものを常に実装するわけではない。CI/CDの構築や保守は、開発者、SET(Software Engineer in Test:テスト専門のソフトウェアエンジニア)、SDET(Software Development Engineer in Test:テスト開発エンジニア)、Platform Engineer、SREなどが担うことも多い。

QAの重要な関与は、CI/CD上でどの品質リスクを自動確認すべきか、どのチェックをfailとして扱い、どのチェックをwarningとして扱うか、テスト結果をどのようにリリース判断へ接続するかを整理することである。

つまり、CI/CD上の品質ゲートは、QAが一人で実装・運用するものではなく、開発者や関連職種と連携しながら、品質確認を開発フローへ組み込むための仕組みである。

QAの観点では、品質ゲートは、品質確認を個人の注意力やリリース直前の手作業だけに依存させないための重要な仕組みである。

一方で、品質ゲートは、すべての品質判断を自動化するものではない。仕様の妥当性、UX上の違和感、業務上の自然さ、未知リスク、残リスクの受容判断は、人間の判断を必要とする。

したがって、CI/CD上の品質ゲートは、自動化できる確認を開発フローに組み込むための仕組みであり、人間の判断を不要にするものではない。

次節では、この品質ゲートの信頼性を大きく損なう要因であるflaky testとの向き合い方を扱う。

---

### 7.9 flaky testとの向き合い方

flaky test(不安定なテスト)とは、コードや仕様に明確な変更がないにもかかわらず、実行するたびに成功したり失敗したりするテストである。

たとえば、同じPull Request(PR:プルリクエスト)に対して、1回目はE2E(End-to-End:エンドツーエンド) Testが失敗し、再実行すると成功するような場合がある。あるいは、開発者のローカル環境では通るが、CI/CD(Continuous Integration / Continuous Delivery:継続的インテグレーション / 継続的デリバリー)上では時々失敗する、という場合もある。

flaky testは、自動テストや品質ゲートの信頼性を大きく損なう。

自動テストの価値は、失敗したときに「何か確認すべき問題がある」とチームが判断できることにある。しかし、flaky testが増えると、テストが失敗しても「またいつもの不安定な失敗だろう」と見なされやすくなる。結果として、本当に重要な不具合が混ざっていても見逃される可能性がある。

これは、品質ゲートにとって特に危険である。

品質ゲートは、コード変更、マージ、リリースなどの節目で、一定の品質条件を満たしているかを確認する仕組みである。しかし、そのゲートに含まれるテストが頻繁に不安定な失敗を起こすと、開発者はゲートを安全装置ではなく障害物として感じるようになる。失敗したテストを調査せずに再実行する、失敗を無視する、一時的に無効化する、といった運用が常態化すると、品質ゲートの意味は弱くなる。

flaky testの原因には、次のようなものがある。

| 原因 | 例 |
|---|---|
| 待機処理の不備 | 画面描画、非同期処理、ジョブ完了を待たずに検証している |
| 時刻依存 | 現在時刻、タイムゾーン、日付境界に依存している |
| テストデータ依存 | 既存データの状態や実行順序に依存している |
| 実行順序依存 | あるテストの後に実行した場合だけ成功・失敗する |
| 外部サービス依存 | 外部API、メール、通知、決済、ストレージなどの状態に左右される |
| 環境差分 | ローカル、CI、本番に近い検証環境で設定や性能が異なる |
| 並行実行の影響 | 複数テストが同じuserや申請データを共有し、一方のテストが変更した状態によって、別のテストの期待結果が変わってしまう |
| UIの不安定な指定 | 画面要素のセレクタが壊れやすい、表示タイミングに依存している |
| ランダム性 | 乱数や生成データが固定されておらず、条件が毎回変わる |

flaky testに対して重要なのは、「再実行すれば通るから問題ない」と扱わないことである。

もちろん、実務では一時的な再実行が必要になることはある。たとえば、外部サービスの一時的な応答遅延やCI環境の一時的な問題により、テストが失敗する場合もある。その場合、再実行によって一時的にリリース判断を進めることはあり得る。

しかし、再実行は根本対策ではない。

同じテストが繰り返し不安定になるなら、そのテストは品質情報として信頼しにくい。放置すれば、チームはテスト失敗を無視するようになり、品質ゲート全体への信頼が下がる。

flaky testに対しては、次のような対応が考えられる。

| 対応 | 内容 |
|---|---|
| 原因を分類する | 待機処理、データ依存、外部依存、環境差分、並行実行など、何が原因かを切り分ける |
| 再現条件を記録する | どの環境、どのタイミング、どのデータ、どの順序で失敗したかを残す |
| 一時的に隔離する | 品質ゲート全体を壊す場合は、対象テストを一時的に隔離し、修正対象として管理する |
| 待機条件を明確にする | 固定sleepに頼らず、画面状態、API応答、ジョブ完了などの明確な条件を待つ |
| テストデータを制御する | テストごとに専用のuserや申請データを作成し、実行順序や他テストの変更に依存しないようにする |
| 外部依存を制御する | モック、スタブ、テスト用サービス、Contract Test(契約テスト)などで外部影響を減らす |
| 並行実行を前提に設計する | 共有リソース、固定ID、同じファイル、同じキューを不用意に使わない |
| テストを削除・再設計する | 価値が低く、保守負荷だけが高いテストは、削除や別レベルへの移動も検討する |

ここで注意すべきなのは、flaky testを隔離することと、放置することは違うという点である。

隔離は、品質ゲート全体の信頼性を守るための一時的な対応である。隔離したテストは、原因調査、修正、再設計、削除のいずれかを判断する必要がある。単に「時々失敗するから見ないことにする」という扱いにすると、自動テストの価値は下がっていく。

QA(Quality Assurance:品質保証)の観点では、flaky testは単なるテストコードの問題ではない。品質情報の信頼性の問題である。

QAがCI/CDやテストコードを直接実装しない場合でも、flaky testがリリース判断やチームの品質判断に与える影響を整理することは重要である。どのテストが不安定なのか、どの失敗はマージを止めるべきなのか、どの失敗はwarningとして扱うべきなのか、どのテストは修正・隔離・削除すべきなのかを、開発者やSET(Software Engineer in Test:テスト専門のソフトウェアエンジニア)、SDET(Software Development Engineer in Test:テスト開発エンジニア)、SRE(Site Reliability Engineering:サイト信頼性エンジニアリング)と連携して整理する必要がある。

flaky testへの対応は、自動化の信頼性を保つための継続的な活動である。

次節では、自動化を長く運用するうえで重要になる、保守性の観点を整理する。

### 7.10 自動化と保守性

自動テストは、作って終わりではない。

プロダクトの仕様、画面、API、DB(Database:データベース)スキーマ、外部サービス、データモデル、業務ルールが変われば、自動テストも更新が必要になる。自動テストが古い仕様を前提にしたまま残っていると、テストは品質確認の手段ではなく、変更を妨げる負債になることがある。

自動化の価値は、テストが継続的に信頼できる状態で運用されて初めて発揮される。

たとえば、次のような自動テストは、長期的には負債になりやすい。

- 何を確認しているのか読み取りにくい
- テスト名と期待結果が対応していない
- 失敗したときに原因がわかりにくい
- 仕様変更のたびに大量のテストが壊れる
- テストデータの前提が暗黙になっている
- 実行順序や外部環境に依存している
- 画面の細かい構造変更だけで頻繁に壊れる
- 重複が多すぎて、変更時に多数の期待値を手で直す必要がある
- 抽象化しすぎて、テスト本文から意図が読めない

自動テストの保守性を考えるときには、次の観点が重要になる。

| 観点 | 確認すること |
|---|---|
| 読みやすさ | テスト名、入力、操作、期待結果から、何を確認しているかがわかるか |
| 失敗時の調査しやすさ | 失敗メッセージ、ログ、スクリーンショット、差分から原因を追いやすいか |
| テストデータ管理 | テストごとに必要なデータが明確で、他のテストに依存していないか |
| 環境依存の少なさ | ローカル、CI、本番に近い検証環境で同じように動くか |
| 変更への追従性 | 仕様変更時に、どのテストを更新すべきかを判断しやすいか |
| 実行速度 | 開発フローを過度に遅くしていないか |
| 安定性 | flaky testになりにくいか |
| 所有者の明確さ | 壊れたときに誰が調査・修正するかが明確か |

特に重要なのは、テストの読みやすさである。

プロダクションコードでは、重複を避けるためにDRY(Don't Repeat Yourself:繰り返しを避ける原則)が重視されることが多い。一方で、テストコードでは、過度に共通化しすぎると、テスト本文を読んだだけでは何を確認しているのかわかりにくくなることがある。

そのため、テストコードではDAMP(Descriptive And Meaningful Phrases:記述的で意味のある語句)という考え方が参考になることがある。これは、多少の重複を許容してでも、テストが何を確認しているのかを読みやすくする考え方である。

たとえば、入力値、操作、期待結果がテスト本文に明確に見えていれば、失敗したときに原因を追いやすい。逆に、共通関数やヘルパーに期待値が隠れすぎていると、テストが失敗したときに、どの条件で何を期待していたのかを読み解くのに時間がかかる。

もちろん、テストコードで共通化をしてはならないわけではない。

テストデータ作成、認証処理、APIクライアント、画面操作の補助など、共通化した方が読みやすくなる部分もある。重要なのは、共通化によってテストの意図が隠れていないかを確認することである。

また、E2E Testでは、画面構造への依存を減らすことも重要になる。

たとえば、画面上の見た目やDOM(Document Object Model:文書オブジェクトモデル)構造に強く依存したテストは、UI(User Interface:ユーザーインターフェース)の軽微な変更で壊れやすい。ユーザーが操作する意味に近いセレクタや、安定したテスト用属性を使うことで、保守しやすくなる場合がある。

ただし、E2E Testを壊れにくくするために、ユーザーが実際には行わない不自然な操作で確認してしまうと、テストの価値が下がる。E2E Testでは、保守性とユーザー行動への近さのバランスが必要である。

自動テストの保守性を高めるには、次のような工夫が有効である。

| 工夫 | 内容 |
|---|---|
| テスト名を具体的にする | どの条件で、何を期待しているかがわかる名前にする |
| 入力・操作・期待結果を明示する | テスト本文から確認意図を読み取れるようにする |
| テストデータを独立させる | 他のテストや既存データに依存しないようにする |
| 失敗時の情報を残す | ログ、差分、レスポンス、スクリーンショットなどを確認できるようにする |
| 外部依存を制御する | モック、スタブ、テスト用環境を使い、外部要因による不安定さを減らす |
| 重いテストを分離する | Pull Request時、マージ前、定期実行など、実行タイミングを分ける |
| 壊れたテストの扱いを決める | 修正、隔離、削除、再設計の判断基準を持つ |
| テストレビューを行う | 自動テストもプロダクションコードと同じくレビュー対象にする |

ここで重要なのは、自動テストにもライフサイクルがあるという点である。

最初に作ったテストが、いつまでも同じ価値を持つとは限らない。仕様変更により不要になったテストもあれば、過去の不具合を踏まえて追加すべきテストもある。重複しているテスト、ほとんど失敗しないが保守負荷が高いテスト、失敗しても誰も見ないテストは、見直しの対象になる。

QAの観点では、自動テストの保守性は、開発者やSET / SDETだけの問題ではない。

QAが直接テストコードを実装しない場合でも、どの確認が重要な品質情報を提供しているか、どのテストがリリース判断に使われているか、どのテストが不安定で信頼されていないかを把握することには価値がある。必要に応じて、テスト観点の見直し、自動化候補の整理、不要な確認の削減、探索的テストから自動テストへの還元などを、開発者と一緒に行うことができる。

自動化は、テストを増やすことそのものが目的ではない。

重要なのは、プロダクトの品質リスクに対して、必要な確認を、適切なレベルで、継続的に信頼できる形で実行できる状態を作ることである。

次節では、この考え方を踏まえて、自動化すべき確認と、人間が探索すべき確認の分担を整理する。

### 7.11 自動化すべき確認と、人間が探索・判断すべき確認

ここまで、テスト設計技法とテストレベルの関係、自動化に向く確認、Regression Test(回帰テスト)、Test Pyramid(テストピラミッド)、CI/CD(Continuous Integration / Continuous Delivery:継続的インテグレーション / 継続的デリバリー)上の品質ゲート、flaky test(不安定なテスト)、自動テストの保守性を整理してきた。

この節では、7章のまとめとして、自動化すべき確認と、人間が探索すべき確認の分担を整理する。

まず重要なのは、自動化と手動確認を対立関係として捉えないことである。

自動テストは、期待結果が明確で、繰り返し確認する価値があり、変更時に早くフィードバックを得たい確認に向いている。一方で、人間による確認は、仕様の妥当性、UX(User Experience:ユーザー体験)上の違和感、業務上の自然さ、未知のリスク、残リスクの受容判断などに向いている。

つまり、自動化と人間の確認は、役割が違う。

自動化は、すでに定義された期待状態を、安定して、繰り返し、素早く確認するための仕組みである。人間による探索や判断は、期待状態そのものが妥当か、仕様に抜けがないか、ユーザーや業務の文脈に照らして自然か、未知の問題が隠れていないかを考えるための活動である。

たとえば、「50,000円以上の申請には追加承認が必要である」というルールであれば、49,999円、50,000円、50,001円の境界値確認は、自動化に向きやすい。期待結果が明確であり、変更のたびに壊れていないかを確認したいからである。

一方で、「この追加承認フローは、実際の業務として自然か」「ユーザーはなぜ追加承認が必要なのかを理解できるか」「承認者が不在の場合に、業務が止まりすぎないか」といった確認は、自動テストだけでは判断しにくい。これらは、PM(Product Manager:プロダクトマネージャー)、開発者、QA(Quality Assurance:品質保証)、業務担当者、CS(Customer Success:カスタマーサクセス)、Support(サポート)などが文脈を踏まえて判断する必要がある。

自動化に向きやすい確認には、次のような特徴がある。

| 自動化に向きやすい確認 | 理由 |
|---|---|
| 境界値や条件分岐の確認 | 入力と期待結果が明確で、繰り返し確認しやすい |
| APIの入力・出力・エラー応答 | UI(User Interface:ユーザーインターフェース)に依存せず、機械的に判定しやすい |
| 権限違反の確認 | 画面表示だけでなく、サーバー側の認可を継続確認できる |
| 状態遷移の許可・不許可 | 状態とイベントの組み合わせを固定しやすい |
| 過去に不具合が出た箇所 | Regression Testとして再発防止に使いやすい |
| 主要な業務フローの代表シナリオ | E2E(End-to-End:エンドツーエンド) Testとして、重要フローが壊れていないことを確認できる |
| lint、type check、build check | 開発フロー内で自動実行しやすく、早いフィードバックを得やすい |
| dbt testなどのデータ品質確認 | データモデルの一意性、非NULL、参照整合性、業務ルールを継続確認しやすい |

一方で、人間が確認すべき領域には、次のようなものがある。

| 人間の判断が必要になりやすい確認 | 理由 |
|---|---|
| 仕様の妥当性 | 期待結果そのものが業務上・ユーザー価値上正しいかは自動判定しにくい |
| UX上の違和感 | ユーザーが迷う、不安に感じる、誤操作しやすいといった感覚は人間の判断が必要になりやすい |
| 業務上の自然さ | 実際の業務フローや例外運用に合っているかは、ドメイン文脈を踏まえる必要がある |
| 未知リスクの探索 | 事前に期待結果を定義していない問題は、Exploratory Testing(探索的テスト)で見つかることがある |
| エラーメッセージの分かりやすさ | ユーザーが次に何をすべきか理解できるかは、文脈を踏まえた確認が必要である |
| 残リスクの受容判断 | 既知不具合や制約を受け入れてリリースするかは、関係者の判断が必要である |
| 仕様変更時の影響整理 | どの受け入れ条件、テスト、データ、運用に影響するかは、人間が整理する必要がある |

この分担を考えるときには、次の問いが役に立つ。

- この確認は、期待結果を明確に書けるか
- 同じ条件で繰り返し確認する価値があるか
- 変更のたびに壊れていないかを確認したいか
- 失敗したときに、原因を特定しやすいか
- 自動化することで、手動確認の負荷や確認漏れを減らせるか
- 逆に、人間が見なければ気づきにくい違和感や業務上の不自然さを含むか
- その確認は、リリース判断や残リスク判断にどう使われるか

ここで重要なのは、人間が行った確認を、その場限りで終わらせないことである。

探索的テストで見つかった不具合、リリース後の問い合わせ、インシデント、手動確認で見つかった仕様の抜けは、次のテスト設計や自動化に還元できる場合がある。たとえば、探索的テストで見つかった境界値の不具合は、Unit TestやAPI Testとして追加できる。権限漏れが見つかった場合は、API TestとしてRegression Testを追加できる。主要業務フローの破壊が見つかった場合は、E2E Testの代表シナリオとして追加できる。

逆に、自動テストの結果も、人間の判断を支える材料になる。

自動テストが失敗した場合、それが仕様変更による期待値の更新なのか、本当に不具合なのか、テストデータや環境の問題なのか、flaky testなのかを人間が判断する必要がある。品質ゲートがwarningを出した場合、それをリリース前に解消すべきか、期限を決めて後続対応にするか、残リスクとして関係者に共有するかを判断する必要がある。

このように、自動化と人間の判断は循環する。

```text
人間がリスクを発見する
-> 繰り返し確認すべきものを自動化する
-> 自動テストや品質ゲートで継続確認する
-> 失敗や警告を人間が解釈する
-> 新しいリスクや改善点をテスト設計へ戻す
```

この循環を作ることが、Quality Engineering(品質エンジニアリング)や現代的QAにおいて重要である。

自動化は、QAを不要にするものではない。また、手動確認は、自動化できなかったものの残り物ではない。

自動化は、繰り返し確認すべき期待状態を安定して確認するための仕組みである。手動確認や探索的テストは、仕様、ユーザー、業務、未知リスクに対して、人間の判断を使うための活動である。

QAの役割は、その両方を理解し、どの品質リスクを自動化された確認に任せ、どの品質リスクを人間が探索し、どの情報をリリース判断や改善活動に使うかを整理することである。

したがって、7章で扱ったテスト自動化の本質は、「人間の確認をなくすこと」ではない。

重要なのは、品質確認を個人の注意力だけに依存させず、繰り返し確認すべきものは仕組みに組み込み、人間はより文脈理解、リスク判断、探索、改善に集中できる状態を作ることである。

### 7.12 Key Takeaways

7章では、6章で整理したテスト観点やテスト条件を、どの確認単位に割り当て、どこまで自動化し、どのように継続的に運用するかを整理した。

テスト自動化は、単に手動作業を減らすためのものではない。変更時に既存の期待状態が壊れていないかを早く確認し、Regression Test(回帰テスト)を通じて過去の不具合から学び、CI/CD(Continuous Integration / Continuous Delivery:継続的インテグレーション / 継続的デリバリー)上の品質ゲートとして開発フローに品質確認を組み込むための仕組みである。

一方で、自動化は万能ではない。自動テストは、あらかじめ定義された期待結果を繰り返し確認することには向いているが、仕様の妥当性、UX(User Experience:ユーザー体験)上の違和感、業務上の自然さ、未知リスク、残リスクの受容判断までは自動的に判断できない。

そのため、QA(Quality Assurance:品質保証)にとって重要なのは、自動化と手動確認を対立させることではなく、それぞれの役割を理解し、どの品質リスクを仕組みに任せ、どの品質リスクを人間が探索・判断すべきかを整理することである。

- テスト設計技法とテストレベルは同じものではない。  
  Equivalence Partitioning(同値分割)、Boundary Value Analysis(境界値分析)、Decision Table Testing(デシジョンテーブルテスト)、State Transition Testing(状態遷移テスト)などは、確認条件を作るための技法である。一方、Unit Test(単体テスト)、API Test、Integration Test(結合テスト)、E2E(End-to-End:エンドツーエンド) Testは、その確認をどの範囲で実行するかを表す確認単位である。

- テスト条件は、品質リスクに応じて適切な確認単位へ割り当てる必要がある。  
  細かいロジックや境界値はUnit Test、APIの入力・出力・認可・異常系はAPI Test、DB(Database:データベース)や外部サービスとの連携はIntegration Test、主要な業務フローはE2E TestやManual Test(手動テスト)で確認する、というように分担を考える。

- テスト自動化の目的は、手動作業の削減だけではない。  
  変更時の早いフィードバック、Regression(回帰)の検知、確認作業の再現性向上、品質確認の属人化防止、CI/CD上の品質ゲート化が重要な目的である。

- 自動化に向く確認は、期待結果が明確で、繰り返し実行する価値がある確認である。  
  境界値、条件分岐、APIのエラー応答、権限違反、状態遷移、過去に不具合が出た箇所、主要業務フローの代表シナリオなどは、自動化候補になりやすい。

- Regression Testは、Unit TestやE2E Testと同じ分類軸ではない。  
  Regression Testは「既存機能が変更によって壊れていないことを確認する目的」を表す。Unit TestとしてのRegression Test、API TestとしてのRegression Test、Integration TestとしてのRegression Test、E2E TestとしてのRegression Test、Manual TestとしてのRegression Testはいずれもあり得る。

- Regression Testは、過去の不具合から学ぶ仕組みである。  
  不具合を修正して終わりにするのではなく、なぜ見逃したのか、どのテストレベルで検知できたのか、同じ種類の不具合を今後どう防ぐかを考えることで、テスト設計と自動化を改善できる。

- Test Pyramid(テストピラミッド)は、固定比率ではなく、テスト配分を考えるためのモデルである。  
  Unit Testを厚くし、E2E Testを少なくするという単純な暗記ではなく、速く、信頼でき、失敗したときに意味があり、保守可能なテスト群を作ることが重要である。

- CI/CD上の品質ゲートは、自動化された確認を開発フローに組み込む仕組みである。  
  lint、type check、Unit Test、API Test、Integration Test、E2E Test、build check、security scan、dbt testなどを、Pull Request作成時、マージ前、本番に近い検証環境への反映後、リリース前、定期実行などに分けて実行する。

- QAがCI/CDパイプラインそのものを常に実装するわけではない。  
  CI/CDの構築や保守は、開発者、SET(Software Engineer in Test:テスト専門のソフトウェアエンジニア)、SDET(Software Development Engineer in Test:テスト開発エンジニア)、Platform Engineer、SRE(Site Reliability Engineering:サイト信頼性エンジニアリング)などが担うことも多い。QAの重要な関与は、どの品質リスクを品質ゲートに乗せるか、結果をどう解釈し、リリース判断へどう接続するかを整理することである。

- flaky test(不安定なテスト)は、自動テストや品質ゲートの信頼性を損なう。  
  再実行すれば通るから問題ないと扱うのではなく、原因を分類し、待機条件、テストデータ、外部依存、環境差分、並行実行の影響などを調査し、修正、隔離、削除、再設計を判断する必要がある。

- 自動テストは、作って終わりではない。  
  仕様変更、画面変更、API変更、DBスキーマ変更、外部サービス変更に合わせて保守する必要がある。読みやすさ、失敗時の調査しやすさ、テストデータ管理、実行速度、安定性、所有者の明確さが重要になる。

- 自動化と手動確認は対立しない。  
  自動化は、繰り返し確認すべき期待状態を安定して確認するための仕組みである。Manual TestやExploratory Testing(探索的テスト)は、仕様の妥当性、UX上の違和感、業務上の自然さ、未知リスクを見つけるために重要である。

- 7章の中心は、テストを増やすことではなく、品質リスクに応じて確認を設計・配置・運用することである。  
  重要なのは、品質確認を個人の注意力だけに依存させず、繰り返し確認すべきものは仕組みに組み込み、人間は文脈理解、リスク判断、探索、改善に集中できる状態を作ることである。その先に、変更を続けながらも、ユーザーや顧客にとってより良いプロダクトと安定したサービスを維持する、というQAの目的がある。
