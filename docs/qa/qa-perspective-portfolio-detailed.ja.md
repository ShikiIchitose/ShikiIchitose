## 概要

この資料は、AE(Analytics Engineering:分析エンジニアリング) / DE(Data Engineering:データエンジニアリング)を主軸として作成したポートフォリオ群を、QA(Quality Assurance:品質保証)、DQA(Data Quality Assurance:データ品質保証。ここでは必要に応じてData Quality Assessment:データ品質評価の観点も含める)、QE(Quality Engineering:品質エンジニアリング)の観点から再解釈するための補助資料である。

中心となるポートフォリオ群は、AIツール利用ガバナンスを題材に、業務アプリケーション、イベント取り込み境界、rawデータ、dbtによるwarehouse(分析基盤)モデリング、業務向けmart、BI(Business Intelligence:ビジネスインテリジェンス)出力、分析APIまでの流れを小さく表現したものである。これらはもともとQA職向けに設計したものではなく、AE / DE領域での実装力、データモデリング、再現性、検証可能性、ドキュメント化を示すために作成した。

一方で、QA職能を学ぶ中で、これらの実装判断には、品質・検証・データ品質・テスト容易性・運用品質と接続する要素が含まれていることが見えてきた。たとえば、業務フローや権限の保護、入力契約の明確化、厳格な入力検証、source contracts(入力データの前提契約)、model grain(モデルの粒度)、dbt data tests(dbtによるデータ品質テスト)、期待出力、外部依存を避けたCI上の確認、BI出力による関係者への共有などは、QA / DQA / QEの観点からも説明できる。

この資料の目的は、QA専任実務経験を主張することではない。また、各ポートフォリオがISO/IEC 25010やISO/IEC 25012などの品質モデルに準拠して設計されたと主張するものでもない。あくまで、AE / DEポートフォリオとして実装してきた内容を、後からソフトウェア品質、データ品質、QA職能の観点で整理し直し、実装時に重視してきた判断や、今後実務の中で深めたい品質観点をより体系的に説明するための資料である。

特に重視するのは、「データを扱い、意味のある情報として関係者に共有すること」と、「品質を扱い、期待状態・確認条件・リスク・判断材料をチームで共有できる状態を作ること」の接続である。AE / DEとQA / DQA / QEは異なる職能であるが、どちらも見えにくい前提を明確にし、関係者が同じ情報をもとに判断できる状態を作る点で接続している。

本資料では、各ポートフォリオを単なる技術スタックの一覧としてではなく、品質観点から見た設計判断の集合として整理する。そのうえで、現時点で説明できること、言いすぎるべきではないこと、今後QA / Quality Engineering領域で経験したいことを明確にする。

## 1. この資料の位置づけ

### 1.1 AE / DEポートフォリオとしての出発点

本資料で扱うポートフォリオ群は、もともとQA職向けに設計したものではない。出発点にあったのは、AE(Analytics Engineering:分析エンジニアリング) / DE(Data Engineering:データエンジニアリング)領域において、データの発生源、入力境界、rawデータ、warehouse(分析基盤)モデリング、mart層、BI出力、分析APIまでの流れを、小さくても一貫した形で表現することであった。

中心となる題材は、企業内でのAIツール利用ガバナンスである。AIツールの利用申請・承認、利用イベント、利用実績、費用、承認状態、利用状況に基づくレビュー対象を、業務アプリケーションと分析基盤の両側から扱えるようにした。これは、実際の本番システムを構築したものではなく、ポートフォリオとしてレビュー可能な範囲に絞った小規模な実装である。

その中で重視したのは、単に技術スタックを並べることではない。データがどこで発生し、どのような契約で受け取られ、どの粒度で保存・変換され、どのような指標やレビュー対象として関係者に共有されるのかを、実装とドキュメントの両方で説明できる状態にすることだった。

### 1.2 QA / DQA / QE観点で再解釈する理由

当初は、これらのポートフォリオをQA(Quality Assurance:品質保証)の文脈で作成していたわけではない。しかし、QA職能を学ぶ中で、実装時に重視していた再現性、検証可能性、入力契約、データ品質、テスト容易性、CI(Continuous Integration:継続的インテグレーション)、ドキュメント化は、QA / DQA / QEの観点からも説明できることが見えてきた。

たとえば、Djangoによる業務アプリケーションでは、申請者、承認者、管理者の責務分離、自己承認の禁止、承認済みデータの再レビュー防止、非アクティブなツールへの申請防止といった業務ルールを扱っている。これは、機能が動くかどうかだけでなく、権限、状態遷移、業務上許される操作を保護する品質観点として見ることができる。

Goによるイベント取り込み境界では、HTTPリクエスト、Content-Type、JSON項目、必須項目、参照データとの照合、追記専用のrawデータ保存を明示的に扱っている。これは、下流のwarehouse(分析基盤)に渡す前に、入力契約を明確にし、不正な構造のデータや想定外のスキーマずれを早期に見える化する取り組みとして再解釈できる。

dbtによるwarehouseプロジェクトでは、source contracts、model grain、dbt data tests、lineage、業務向けmart、BI出力を扱っている。これは、DQAの観点から、データが意図された用途に対して信頼できる状態かを確認し、関係者が同じ前提で判断できるようにする取り組みとして見ることができる。

このように、本資料では、各ポートフォリオを「QAのために作ったもの」としてではなく、「AE / DEポートフォリオとして作成したものを、後から品質・検証・データ品質・運用品質の観点で読み直すもの」として扱う。

### 1.3 この資料で扱う対象

本資料で中心的に扱うのは、以下のポートフォリオである。

- `ai-tool-access-requests`
  - Django + PostgreSQLによるAIツール利用申請・承認ワークフロー
  - 業務フロー、権限、状態遷移、重要な業務ルールの保護を扱う

- `go-ingestion-api`
  - GoによるAIツール利用イベントの取り込み境界
  - 厳格な入力検証、未知のJSON項目の拒否、参照データとの照合、追記専用JSONL形式のrawデータ保存を扱う

- `access-governance-warehouse`
  - DuckDB / BigQuery / dbt / Looker Studioによる分析エンジニアリングプロジェクト
  - source contracts、model grain、dbt data tests、mart層、BI出力、governance reportを扱う

- `analytics-metrics-api`
  - FastAPI + DuckDB + Parquetによる読み取り専用の分析API
  - 指標定義、期待出力、外部依存を避けたテスト、SQLからAPI出力までの追跡可能性を扱う

- `url-monitor`
  - Python CLIによる小規模なURL監視補助ツール
  - レイテンシ、エラー、p95、Markdown / JSON成果物を通じて、外部から見えるサービス品質を確認・記録する入口として扱う

このうち、中心となるのはAIツール利用ガバナンスを題材にしたAE / DEポートフォリオ群である。`url-monitor` は中心ポートフォリオではないが、QA / QE観点では、ブラックボックス監視や合成監視 / 外形監視(synthetic monitoring)に近い基礎的な運用品質の補助線として扱う。

なお、URL-MonitorのテストではHTTP通信をmockし、ネットワーク非依存でロジックを検証している。これは合成監視 / 外形監視そのものではなく、合成監視 / 外形監視に近いCLIツールを再現可能にテストするための設計である。

### 1.4 この資料で扱わないこと

本資料は、QA専任実務経験を示す資料ではない。また、各ポートフォリオがISO/IEC 25010やISO/IEC 25012などの品質モデルに準拠して設計されたと主張するものでもない。

そのため、本資料では以下の内容を扱わない。

- QA専任者としての実務実績の主張
- 本番運用中の大規模プロダクトに対するQA経験の主張
- ISO/IEC 25010 / ISO/IEC 25012への準拠の主張
- 本格的なSRE(Site Reliability Engineering:サイト信頼性エンジニアリング)監視基盤や可観測性基盤を構築したという主張
- 実務の欠陥管理、探索的テスト、テスト計画、リリース判定、横断的な品質改善を経験済みであるという主張

本資料の目的は、言い換えれば、経験を大きく見せることではなく、すでに作成したポートフォリオの中に含まれる品質観点を正確に整理することである。

そのため、本資料では「何を作ったか」だけでなく、「どのような品質観点と接続して説明できるか」「どこまでは現時点で説明できるか」「どこから先は今後実務の中で経験し、深めていきたい領域か」を明確にする。

### 1.5 本資料の読み方

本資料は、各リポジトリのREADMEを置き換えるものではない。個別の技術詳細、実行手順、テスト内容、ディレクトリ構成は、それぞれのREADMEや関連ドキュメントに委ねる。

ここでは、ポートフォリオ群を横断して、次の観点から整理する。

- 業務フロー、権限、状態遷移をどのように扱っているか
- 入力契約やイベント検証をどのように扱っているか
- データの粒度、source contracts、dbt data testsをどのように扱っているか
- 指標定義、期待出力、回帰確認をどのように扱っているか
- BI出力やレポートを通じて、関係者が同じ情報を見られる状態をどう作っているか
- 運用品質や外部から見える品質への関心がどこに現れているか

以降では、まずQA / DQA / QEの観点からポートフォリオ群を読み替えるための軸を整理し、そのうえで各ポートフォリオを品質観点から見直す。

## 2. 品質観点から読み替えるための軸

### 2.1 なぜ読み替え軸が必要なのか

本資料では、AE / DEポートフォリオ群をQA / DQA / QEの観点から再解釈する。ただし、ここで注意すべきなのは、各ポートフォリオを無理にQA活動へ分類することではない。

たとえば、Djangoによる業務アプリケーションは、主にはバックエンドアプリケーションとして作成したものである。Goによる取り込みAPIは、主にはイベント取り込み境界として作成したものである。dbtによるwarehouse(分析基盤)プロジェクトは、主には分析エンジニアリングプロジェクトとして作成したものである。FastAPIによる分析APIは、主には読み取り専用の分析サービスとして作成したものである。

しかし、それぞれの実装には、品質観点から説明できる判断が含まれている。

- 業務ルールをどこで保護するか
- 入力をどの段階で拒否するか
- データの粒度をどのように明示するか
- どの不整合をテストで検出するか
- どの状態をエラーではなく業務上のレビュー対象として扱うか
- 変更後も同じ出力が保たれていることをどう確認するか
- 関係者が同じ情報を見て判断できる状態をどう作るか
- 外部から見えるサービス品質をどう確認・記録するか

これらは、単に「テストを書いているかどうか」だけでは説明しにくい。QA(Quality Assurance:品質保証)、DQA(Data Quality Assurance / Data Quality Assessment:データ品質保証 / データ品質評価)、QE(Quality Engineering:品質エンジニアリング)の観点を使うことで、各実装判断をより体系的に整理できる。

本章では、後続章で各ポートフォリオを見直すための読み替え軸を整理する。

### 2.2 QA軸: 期待される挙動・業務ルール・確認条件を明確にする

QA(Quality Assurance:品質保証)の観点では、プロダクトや機能が期待される品質を満たしていると判断できる状態を作ることが重要になる。

本資料では、QA軸を次のように扱う。

> 期待される挙動、業務ルール、権限、状態遷移、確認条件を明確にし、プロダクトが意図したふるまいをしているか判断できる状態を作る観点。

この軸で見ると、特に `ai-tool-access-requests` が重要になる。

AIツール利用申請・承認ワークフローでは、単に「申請できる」「承認できる」という機能だけでは不十分である。誰が申請できるのか、誰がレビューできるのか、自分の申請を自分で承認できてよいのか、すでに承認・却下された申請を再レビューできてよいのか、非アクティブなツールに申請できてよいのか、といった業務上の条件が品質を左右する。

このような条件は、機能品質だけでなく、ドメイン品質、権限品質、状態遷移の品質にも関係する。

QA軸では、次のような問いを立てる。

- 期待される業務フローは明確か
- 正常系だけでなく、異常系や禁止すべき操作は定義されているか
- ユーザー種別ごとの権限は明確か
- 状態遷移として許される操作と許されない操作は明確か
- 業務ルールは画面上の導線だけでなく、サーバー側でも保護されているか
- 変更時に、重要な業務ルールが壊れていないことを確認できるか

この軸は、QAを「リリース前に画面を確認すること」に限定しない。むしろ、期待状態や確認条件を明確にし、実装・テスト・レビュー・ドキュメントを通じて、品質判断を可能にする観点として扱う。

### 2.3 DQA軸: データが意図された用途に対して信頼できるかを確認する

DQA(Data Quality Assurance / Data Quality Assessment:データ品質保証 / データ品質評価)の観点では、データそのものが品質対象になる。

本資料では、DQA軸を次のように扱う。

> データの意味、粒度、完全性、一貫性、参照関係、指標定義を明確にし、データが意図された用途に対して信頼できる状態かを確認する観点。

この軸で最も中心になるのは、`access-governance-warehouse` である。

dbtによるwarehouseプロジェクトでは、rawデータ入力、staging、core、intermediate、mart層という流れを通じて、データを分析可能な形に整える。その過程では、単にSQLを実行して表を作るだけではなく、次のような前提を明確にする必要がある。

- rawデータ入力がどのような列と型を持つか
- 各モデルの1行が何を表すか
- 主キーに相当する組み合わせは何か
- nullであってよい値と、nullであってはいけない値は何か
- 参照関係が壊れていないか
- ステータスや分類値が許可された値に収まっているか
- 集計前後で件数や金額に不整合がないか
- 指標がどの粒度で解釈されるべきか

特に重要なのが、model grain(モデルの粒度)である。model grainは、あるテーブルやモデルの1行が何を表しているかを示す。粒度が曖昧なまま指標を作ると、ユーザー数、申請数、利用回数、月次集計、チーム別集計などが混ざり、ダッシュボードやレポートの数値が誤って解釈される可能性がある。

また、DQA軸では、すべての異常を同じように扱わないことも重要である。

たとえば、重複してはいけない主キーの重複、参照関係の破損、許可されていないステータス値、マイナスになってはいけない件数や金額のようなものは、データ変換上の不整合として検出対象にするのが自然である。

一方で、承認済みだが最近利用されていない、利用実績があるが承認状態と整合していない、費用に対して利用が少ない、といった状態は、必ずしもパイプラインを停止すべきエラーではない。これらは、業務上の確認や判断が必要なレビュー対象として、mart層やBI出力に反映する方が自然である。

DQA軸では、次のような問いを立てる。

- このデータは何を表しているか
- 1行の粒度は明確か
- source contract(入力データの前提契約)は明確か
- 必須値、参照関係、一意性、許容値はテストされているか
- 指標定義は関係者間で揃っているか
- データ変換の失敗と、業務上のレビュー対象を分けて扱えているか
- BI出力やレポートで、関係者が同じ前提を見られる状態になっているか

この軸は、AE / DEポートフォリオ群とQA職能を接続するうえで、最も重要な軸である。

### 2.4 QE軸: 品質確認を仕組みに組み込む

QE(Quality Engineering:品質エンジニアリング)の観点では、品質を人間の注意力やリリース前の一回限りの確認だけに依存させず、設計、自動化、CI、テスト容易性、ドキュメント、改善に戻しやすい記録の中に組み込むことが重要になる。

本資料では、QE軸を次のように扱う。

> 期待状態や品質確認を、テスト、自動化、CI、検証処理、期待出力、ドキュメント、成果物として継続的に確認しやすい形に組み込む観点。

この軸では、複数のポートフォリオが関係する。

`go-ingestion-api` では、HTTP method、Content-Type、リクエスト本文サイズ、JSON項目の集合、必須項目、timestamp形式、参照データを明示的に検証している。これは、入力境界に品質確認を組み込む例である。

`analytics-metrics-api` では、決定的に再生成できるサンプルデータ、安定した指標定義、期待出力、外部依存を避けたテストを使って、APIの重要な出力が変更後も保たれているかを確認している。これは、分析APIにおける回帰確認を仕組みにした例である。

`access-governance-warehouse` では、dbt data tests、lineage、documentation、BigQuery実行証跡、生成されたレポート、BI出力を通じて、データ変換と分析出力の品質を継続的に確認しやすくしている。

QE軸では、次のような問いを立てる。

- 品質確認が個人の記憶や手作業に閉じていないか
- 変更時に壊れてはいけない期待状態を自動で確認できるか
- 入力境界で不正なデータを早く拒否できるか
- 重要な出力を期待出力やスナップショット的な形で確認できるか
- CI上でlint、test、type check、dbt testなどが実行されるか
- テスト結果や成果物が、レビュー可能な形で残るか
- 後から他者が実装判断を追跡できるドキュメントがあるか

QE軸で重要なのは、「自動化しているから品質が高い」と単純に言わないことである。自動化は、繰り返し確認すべき期待状態を安定して確認するための手段である。何を自動化するか、どの期待状態を守るか、どの結果を人間が判断すべきかを整理してこそ、Quality Engineeringとして意味を持つ。

### 2.5 運用品質軸: 外部から見える品質を確認・記録する

運用品質の観点では、リリース後や外部環境において、サービスが利用可能か、遅延していないか、失敗していないか、問題発生時に確認できる情報があるかが重要になる。

本資料では、運用品質軸を次のように扱う。

> 外部から見える可用性、レイテンシ、エラー、応答状態を確認・記録し、運用品質への関心を示す補助的な観点。

この軸では、`url-monitor` を補助的に扱う。

`url-monitor` は、URLにHTTP GETを行い、HTTPステータス、レイテンシ、エラー、p95、遅いURLの一覧をMarkdownレポートやJSON成果物として出力するPython CLIである。本格的なSRE(Site Reliability Engineering:サイト信頼性エンジニアリング)監視基盤ではなく、継続監視や負荷試験を目的にしたものでもない。

しかし、外部からURLを確認し、応答状態、失敗、遅延、p95によるテール側の遅延を記録する点では、ブラックボックス監視や合成監視 / 外形監視(synthetic monitoring)に近い基礎的な観点と一部重なる。

ここでいう合成監視 / 外形監視とは、実ユーザーを待つのではなく、外部から人工的にリクエストやユーザー操作を実行し、サービスが利用可能か、遅くないか、期待された応答を返しているかを確認する監視である。

一方で、`url-monitor` のテストでHTTP通信をmockし、ネットワーク非依存でロジックを検証していることは、合成監視 / 外形監視そのものではない。これは、合成監視 / 外形監視に近いCLIツールを、再現可能にテストするための外部依存を避けたテスト設計である。

運用品質軸では、次のような問いを立てる。

- 外部から見てサービスが利用可能か
- HTTPステータスやリクエスト失敗を確認できるか
- レイテンシやp95のようなテール側の遅延を記録できるか
- 成功応答と失敗応答を分けて見られるか
- レポートやJSON成果物として後から確認できるか
- 監視ツール自体のロジックを、mockによってネットワーク非依存でテストできているか
- 本格的な監視基盤ではない範囲を明示できているか

この軸は、本資料の主軸ではない。中心となるのはAE / DEポートフォリオ群におけるデータ品質、入力契約、指標定義、BI共有である。運用品質軸は、品質をリリース前の確認だけに閉じず、外部から見えるサービス状態にも関心を持っていることを示す補助線として扱う。

### 2.6 4つの読み替え軸の対応関係

ここまでの整理をまとめると、本資料では次の4つの軸でポートフォリオ群を読み替える。

| 読み替え軸 | 主に見るもの | 関係するポートフォリオ | 代表的な品質観点 |
|---|---|---|---|
| QA軸 | 期待挙動、業務ルール、権限、状態遷移、確認条件 | `ai-tool-access-requests` | 機能品質、ドメイン品質、権限品質 |
| DQA軸 | データの意味、粒度、source contracts、data tests、指標定義 | `access-governance-warehouse`, `analytics-metrics-api` | データ品質、指標定義、意思決定支援 |
| QE軸 | 検証処理、自動テスト、CI、期待出力、ドキュメント、成果物 | `go-ingestion-api`, `analytics-metrics-api`, `access-governance-warehouse` | テスト容易性、回帰防止、再現性 |
| 運用品質軸 | HTTPステータス、レイテンシ、エラー、p95、外部可視な応答状態 | `url-monitor` | 運用品質、ブラックボックス監視の入口 |

これらの軸は、厳密に分離された分類ではない。実際には重なり合う。

たとえば、`go-ingestion-api` の厳格な検証処理は、入力契約を守るというQE軸の取り組みであると同時に、下流のデータ品質を守るDQA軸にも接続する。`analytics-metrics-api` の期待出力は、回帰確認というQE軸の取り組みであると同時に、指標定義を安定させるDQA軸にも接続する。`access-governance-warehouse` のBI出力は、DQA軸の出力であると同時に、関係者が同じ前提を見て判断するためのQuality Assistance / Quality Enablementにも接続する。

したがって、本資料では、各ポートフォリオを一つの分類に固定するのではなく、複数の品質観点がどのように現れているかを整理する。

### 2.7 本資料での読み替え方

以降の章では、各ポートフォリオを次の順序で見直す。

第一に、そのポートフォリオがAE / DEまたはバックエンドプロジェクトとして何を示しているかを確認する。

第二に、その中に含まれる品質観点を、QA / DQA / QE / 運用品質の軸に沿って整理する。

第三に、現時点で示せることと言いすぎるべきではないことを分ける。

この順序を取る理由は、ポートフォリオをQA職向けに後付けで大きく見せるためではない。もともとAE / DEの実装として作ったものを、品質観点から正確に読み直すためである。

本資料で最も重視するのは、以下の点である。

- 期待状態を明確にすること
- データの意味と粒度を明確にすること
- 入力契約と検証条件を明確にすること
- 変更後も同じ期待状態を確認できるようにすること
- エラーとして止めるべき不整合と、業務上確認すべきレビュー対象を分けること
- 関係者が同じ情報を見て判断できる状態を作ること

これらは、AE / DEとQA / DQA / QEを無理に同一視するためのものではない。両者は異なる職能である。しかし、見えにくい前提を明確にし、再現可能な形で確認し、関係者が判断できる状態を作るという点では、強く接続している。

## 3. ポートフォリオ全体を品質観点で見る

2章では、AE / DEポートフォリオ群を読み替えるための軸として、QA軸、DQA軸、QE軸、運用品質軸を整理した。

本章では、その軸に沿って、各ポートフォリオを品質観点から見直す。

ここで重要なのは、各ポートフォリオをQA実務経験として言い換えることではない。まず、そのポートフォリオが本来どのようなAE / DEまたはバックエンドプロジェクトとして作られているのかを確認する。そのうえで、実装判断の中に含まれる品質観点を整理し、最後に、現時点で示せることと言いすぎるべきではないことを分ける。

この順序を取ることで、後付けで経験を大きく見せるのではなく、既に作成したポートフォリオを品質・検証・データ品質・運用品質の観点から正確に読み直すことを目的とする。

### 3.1 業務フロー・権限・状態遷移: `ai-tool-access-requests`

`ai-tool-access-requests` は、Django + PostgreSQLで実装した、企業内AIツール利用申請・承認フローのポートフォリオである。

AE / DEポートフォリオ群の中では、このプロジェクトは、AIツール利用ガバナンスに関する業務データの発生源を表現する位置づけを持つ。AIツールの利用申請、申請者、承認者、申請状態、対象ツールといった情報は、後続のwarehouse(分析基盤)モデリングやgovernance reportで扱うデータの業務的な前提になる。

一方で、QA / QEの観点から見ると、このプロジェクトは、業務フロー、権限、状態遷移、禁止操作をどのように明確化し、保護するかを示す題材になる。

この申請・承認フローでは、単に「申請できる」「承認できる」という機能だけでは不十分である。誰が申請できるのか、誰が確認・承認判断を行えるのか、自分の申請を自分で承認できてよいのか、すでに承認・却下された申請を再度レビューできてよいのか、非アクティブなツールに申請できてよいのか、といった業務上の条件が品質を左右する。

そのため、このプロジェクトでは、次のような条件を重要な品質観点として扱っている。

- 申請者・承認者・管理者の責務分離
- 申請者向けの経路と承認者向けの経路の分離
- 申請者は自分の申請のみ確認できること
- 承認者は承認待ち申請のみレビューできること
- 承認者が自分自身の申請をレビューできないこと
- 同じユーザーが同じツールに対して複数の承認待ち申請を持てないこと
- 非アクティブなAIツールに申請できないこと
- Django adminを業務フローの実行経路ではなく、安全な参照・確認用途に寄せること

これらは、機能品質だけではなく、ドメイン品質、権限品質、状態遷移の品質に関係する。特に、承認者という業務上の役割と、Django admin権限を同一視しないことは重要である。`is_staff=True` はDjango adminへアクセスするためのシステム側の権限であり、業務上の承認者ロールとは別に扱う必要がある。

また、このプロジェクトでは、業務ルールを一つの層だけで守るのではなく、フォーム層、ビュー層、モデル / データベース層、管理画面層に責務を分けて扱っている。たとえば、重複した承認待ち申請はフォーム層でユーザーに分かりやすく検出しつつ、データベース層でも保護する価値がある。自己承認の禁止やオブジェクト単位のアクセス制御はビュー層で重要になり、管理画面層では業務フローの迂回を避ける設計が重要になる。

QA / QE観点で示せるのは、小規模な業務フローを単なるCRUD(Create, Read, Update, Delete:作成・参照・更新・削除)として扱わず、役割、権限、状態、禁止操作を含む申請・承認フローとして整理していることである。また、重要な業務ルールをテストで保護し、通常のリファクタリングや運用変更によって業務フローの安全性が壊れるリスクを下げようとしている点も示せる。

ただし、これはQA専任実務経験を示すものではない。また、本番運用中の大規模な承認基盤、複数段階承認、専用の監査ログテーブル、通知、複雑な組織階層、監査証跡、本番水準の運用設計を実装したものでもない。

このプロジェクトで示せるのは、あくまで、小規模なバックエンドポートフォリオの中で、業務フロー、権限、状態遷移、業務ルール保護を意識して設計・実装したこと、そしてそれをQA / QE観点から説明できることである。

### 3.2 入力契約・イベント検証・rawデータ保存: `go-ingestion-api`

`go-ingestion-api` は、AIツール利用イベントを受け取る、Goによる小さなHTTP取り込みAPIである。

AE / DEポートフォリオ群の中では、このプロジェクトは、イベント発生元とwarehouseの間に置かれる取り込み境界(ingestion boundary)を表現している。つまり、業務アプリケーションや利用イベント発生元から送られてくるデータを、下流のrawデータ入力やdbtモデルへ渡す前の入口として扱っている。

このプロジェクトは、データ変換やBIを担当するものではない。役割は、HTTPリクエストとして送られてくる1件のイベントを受け取り、その構造と参照関係を検証し、受理したイベントを追記専用のJSONL形式のrawデータとして保存することである。

QA / QE / DQAの観点では、このプロジェクトは、入力契約をどこで明確にし、どの段階で不正なデータを拒否するかを示す題材になる。

具体的には、次のような検証を扱っている。

- HTTP methodの制限
- Content-Typeの確認
- リクエスト本文サイズの制限
- JSON objectとしての構造確認
- 未知のJSON項目の拒否
- 必須項目の確認
- 数値項目が明示的に存在することの確認
- RFC 3339形式のtimestamp確認
- 許可されたイベント種別の確認
- user_id / tool_codeの参照データとの照合
- 追記専用のJSONL出力

ここで重要なのは、入力データを「とりあえず受け取って後で直す」のではなく、取り込み境界で構造的に受け取れるものと受け取れないものを分けている点である。

たとえば、未知の項目を拒否することは、送信側のスキーマずれを早期に見える化する意味を持つ。必須の数値項目を省略不可にすることは、欠損値と明示的なゼロを区別する意味を持つ。user_idやtool_codeの参照データとの照合は、受け取ったイベントが最低限の参照データと整合しているかを確認する意味を持つ。

DQA観点では、これは下流のwarehouseに渡る前に、rawデータとして受け入れるための最低限の構造的品質を確認する取り組みとして読める。QE観点では、入力境界に検証処理を組み込み、テスト可能な小さなサービス境界として設計している取り組みとして読める。

一方で、このプロジェクトで言いすぎるべきではないこともある。

これは本番用の取り込み基盤ではない。一括取り込み、認証・認可、冪等性、重複イベント検出、Pub/Sub、Kafka、Cloud Run、Kubernetes、Terraform、BigQueryへの直接書き込み、スキーマ管理基盤、dead-letter queueなどは対象外である。

また、重複イベント検出、イベント順序、セッションライフサイクルの整合性、承認状態と利用イベントの整合性、月次利用実績の整合性、費用照合なども、この取り込みAPIでは扱っていない。それらは、下流のwarehouseや分析モデリング層で扱うべき条件として切り分けている。

したがって、`go-ingestion-api` で示せるのは、本番水準のデータ基盤を構築したことではない。示せるのは、小さな取り込み境界において、HTTPリクエストの契約、厳格なJSON解釈、参照データとの照合、追記専用のrawデータ保存を明確にし、下流のデータ品質に影響する入口を意識して設計したことである。

### 3.3 データ品質・model grain・BI出力: `access-governance-warehouse`

`access-governance-warehouse` は、AE / DEポートフォリオ群の中心に位置するdbt warehouse projectである。

このプロジェクトでは、AIツール利用ガバナンスを題材に、決定的に再生成できる合成rawデータを入力として用意し、それをstaging、core、intermediate、martsへと変換する。さらに、static governance reportやLooker Studio dashboard artifactsを通じて、mart層の出力を関係者向けに提示する。

AE観点では、このプロジェクトは、source contracts(入力データの前提契約)、layered dbt modeling(層構造を持つdbtモデリング)、再利用可能なdimension / fact、model grain(モデルの粒度)、業務向けmart、dbt documentation、lineage、BigQuery実行経路、BI出力を示す中心的な成果物である。

DQA観点では、このプロジェクトは、データが意図された用途に対して信頼できる状態かを確認する取り組みとして読める。

ここで重要になるのは、単にSQLでテーブルを作ることではない。各モデルの1行が何を表しているか、どの列が必須か、どの値が許容されるか、どの参照関係が成立しているか、どの集計値がどの粒度で解釈されるべきかを明確にすることである。

特に、model grainはこのプロジェクトの重要な品質観点である。たとえば、1行が「1 user」を表しているのか、「1 access request」を表しているのか、「1 user × 1 tool × 1 day」を表しているのか、「1 reporting month × 1 team × 1 tool」を表しているのかによって、集計の意味は大きく変わる。粒度が曖昧なままdashboardやreportを作ると、ユーザー数、申請数、利用回数、費用、承認率などが誤って解釈される可能性がある。

このプロジェクトでは、dbt data tests(dbtによるデータ品質テスト)を通じて、次のような構造的な不整合を検出する。

- not nullであるべき値の欠損
- uniqueであるべきkeyの重複
- relationshipsの破損
- accepted valuesに含まれない分類値
- negativeになってはいけない件数や金額
- 集計前後の照合不一致
- martの粒度に対する重複

これらは、データ変換上の不整合として検出対象にするのが自然である。

一方で、すべての気になる状態をエラーとして扱うわけではない。たとえば、承認済みだが最近利用されていない、利用実績があるが承認状態と整合していない、費用に対して利用が少ない、といった状態は、必ずしもdbt testで失敗させるべきではない。これらは、業務上の確認や判断が必要なレビュー対象として、martやBI出力に反映する方が自然である。

この分離は、DQA観点で非常に重要である。

- 構造的に壊れているデータはtestで検出する
- 業務上判断が必要な状態はレビュー対象として可視化する
- 判断に必要な情報はmartやBI出力に反映する
- 関係者が同じ前提を見て議論できる状態を作る

このプロジェクトでは、static governance reportやLooker Studio dashboard artifactsも重要である。これらは単なる見た目の成果物ではなく、dbt martsで定義された粒度や業務ロジックをもとに、経営層、業務担当者、非エンジニアを含む関係者が同じ情報を見られる状態を作るための出力である。

QE観点では、dbt build、dbt tests、documentation、lineage、BigQuery実行証跡、生成されたreport、BI出力が、品質確認を一回限りの手作業ではなく、再実行可能でレビュー可能な形にしている点も重要である。

ただし、このプロジェクトについても、言いすぎは避ける必要がある。

これは本番のenterprise data warehouseを構築したものではない。実データを扱っているわけでもなく、実運用中の権限管理、データアクセス制御、監査、データカタログ運用、SLA(Service Level Agreement:サービス水準合意)、SLO(Service Level Objective:サービスレベル目標)、本番データの可観測性を実装したものでもない。また、ISO/IEC 25012に準拠して設計したと主張するものでもない。

このプロジェクトで示せるのは、AE / DEポートフォリオとして、source contracts、model grain、dbt data tests、mart層、BI出力を通じて、データ品質と意思決定支援を意識したwarehouseモデリングを行ったことである。そして、それをDQA / QE観点から体系的に説明できることである。

### 3.4 指標定義・回帰確認・SQLからAPI出力までの追跡可能性: `analytics-metrics-api`

`analytics-metrics-api` は、FastAPI + DuckDB + Parquetで実装した、読み取り専用の分析APIである。

このプロジェクトは、決定的に再生成できる合成SaaSデータセットを対象に、事前定義した分析指標をHTTP APIとして提供する。`GET /metrics/{name}` による指標取得、`GET /users/{user_id}` によるユーザー情報の取得、軽量なジョブ実行履歴の参照などを扱っている。

AE / DE観点では、このプロジェクトは、分析用データをAPIとして提供する小さな読み取り層を表現している。warehouseやParquet形式のローカルデータに対して、DuckDBでクエリを実行し、FastAPIを通じて安定したレスポンス構造で返す構成である。

DQA観点では、指標定義を安定させることが重要になる。

たとえば、`dau`、`new_users`、`conversion_rate` のような指標は、一見すると分かりやすい。しかし、どのイベントを対象にするのか、どの期間で集計するのか、どの集計軸を許可するのか、どの列を必須項目とするのかが曖昧であれば、APIが返す数値の意味も曖昧になる。

このプロジェクトでは、指標カタログや事前定義した指標定義を通じて、利用できる指標とその条件を明示する。これは、API契約であると同時に、指標定義を安定させるためのDQA上の取り組みとしても読める。

QE観点では、期待出力(golden output)と外部依存を避けたテストが重要である。

決定的に再生成できるサンプルデータを固定し、期待される指標出力やユーザー情報出力を期待出力として持つことで、変更後も重要な出力が壊れていないかを確認できる。これは、分析APIにおける回帰確認の小さな例である。

また、外部依存を避けたテストにより、外部サービスやクラウド環境に依存せず、ローカルとCIで再現可能にテストできる。これは、ポートフォリオとしてのレビュー容易性だけでなく、品質確認の再現性という意味でも重要である。

SQLからAPI出力までの追跡可能性も、このプロジェクトの品質観点である。

ここでいうSQLからAPI出力までの追跡可能性とは、APIが返す指標値について、入力データ、指標定義、SQL集計ロジック、JSONレスポンス、期待出力の対応関係を追跡できる状態を指す。`analytics-metrics-api` では、DuckDBのクエリ層、指標カタログ、確認用SQL、期待出力テストにより、APIレスポンスがどの集計ロジックに基づいているかを確認しやすくしている。

APIが返す数値がどのSQLロジックに基づくのか、確認用SQLやクエリ層を通じて追跡できることは、指標の正しさを説明するうえで意味を持つ。指標APIでは、APIが正常に応答することだけでなく、その数値がどのロジックに基づいているかを説明できることが重要になる。

このプロジェクトで示せるのは、読み取り専用の分析APIにおいて、指標定義、レスポンス契約、期待出力、外部依存を避けたテスト、SQLからAPI出力までの追跡可能性を意識して設計したことである。

一方で、これは本番用の指標提供基盤ではない。認証・認可、キャッシュ、マルチテナント設計、大規模クエリ最適化、semantic layer integration、リアルタイム指標配信、本番監視などは対象外である。また、事業上の正式なKPI governanceを運用したものでもない。

したがって、このプロジェクトは、指標定義と回帰確認を備えた小さな分析APIとして、QA / DQA / QE観点から再解釈できるポートフォリオとして扱うのが適切である。

### 3.5 運用品質への入口: `url-monitor`

`url-monitor` は、Python CLIとして作成した初期ポートフォリオである。

このツールは、入力ファイルに列挙されたURLにHTTP GETを行い、HTTPステータス、レイテンシ、エラーを記録し、MarkdownレポートやJSON形式の成果物として出力する。集計結果として、成功・失敗件数、エラー率、ステータス分類、レイテンシ統計、p95、遅いURLの一覧などを扱う。

AE / DEポートフォリオ群の中心にあるプロジェクトではないが、QA / QE観点では、外部から見えるサービス品質を確認・記録する入口として補助的に扱える。

ここで重要なのは、`url-monitor` を本格的なSRE監視基盤として扱わないことである。このツールは継続監視、アラート通知、インシデント対応、SLO運用、分散トレーシング、white-box metrics、on-call運用を扱っていない。また、負荷試験や性能試験を目的としたものでもない。

一方で、外部からURLを叩き、応答状態、失敗、レイテンシ、p95によるテール側の遅延を記録する点では、ブラックボックス監視や合成監視 / 外形監視(synthetic monitoring)に近い基礎的な観点と一部重なる。

合成監視 / 外形監視とは、実ユーザーを待つのではなく、外部から人工的にリクエストやユーザー操作を実行し、サービスが利用可能か、遅くないか、期待された応答を返しているかを確認する監視である。この意味で、`url-monitor` は小規模ながら、外部から見える品質を見る入口として説明できる。

また、`url-monitor` のテストでは、HTTP通信をmockし、ネットワーク非依存の状態でロジックを検証している。これは合成監視 / 外形監視そのものではない。合成監視 / 外形監視に近いCLIツールを、再現可能にテストするための外部依存を避けたテスト設計である。

この区別は重要である。

- CLIとして実URLを叩く側面は、ブラックボックス監視 / 外形監視に近い
- テストでHTTPをmockする側面は、ツール自体のロジックを再現可能に検証する外部依存を避けたテストである

このプロジェクトで示せるのは、外部から見えるサービス品質、レイテンシ、エラー、p95、レポート成果物への関心である。また、ネットワーク非依存のテストによって、ツール自体をCIで検証しやすくしている点も示せる。

一方で、本番水準の可観測性、SRE運用、継続監視、アラート通知、インシデント管理を経験したと主張するべきではない。

したがって、`url-monitor` は本資料の主役ではなく、運用品質への関心を示す補助線として扱うのが適切である。

### 3.6 3章のまとめ

本章では、5つのポートフォリオを、品質観点から横断的に見直した。

`ai-tool-access-requests` は、業務フロー、権限、状態遷移、禁止操作、業務ルールの回帰防止を扱う題材である。QA軸で見ると、期待される業務挙動と確認条件を明確にする取り組みとして説明できる。

`go-ingestion-api` は、取り込み境界における入力契約と検証を扱う題材である。QE軸では、入力境界に品質確認を組み込む取り組みとして説明でき、DQA軸では、下流のデータ品質に影響する入口として説明できる。

`access-governance-warehouse` は、DQA軸の中心となる題材である。source contracts、model grain、dbt data tests、mart層、BI出力を通じて、データの意味、構造的品質、業務上のレビュー対象、関係者への共有を扱っている。

`analytics-metrics-api` は、指標定義、期待出力、外部依存を避けたテスト、SQLからAPI出力までの追跡可能性を扱う題材である。DQA軸では指標定義の安定性、QE軸では分析APIの回帰確認として説明できる。

`url-monitor` は、運用品質への補助線である。外部から見えるHTTPステータス、レイテンシ、エラー、p95を確認・記録する点で、ブラックボックス監視 / 外形監視に近い基礎的な観点と一部重なる。ただし、本格的なSRE監視基盤や本番水準の可観測性としては扱わない。

これらのポートフォリオに共通しているのは、品質を単なる最終確認としてではなく、期待状態、入力契約、データの意味、指標定義、回帰確認、共有可能な成果物として扱おうとしている点である。

このことは、QA実務経験の主張ではない。しかし、AE / DEポートフォリオとして実装してきた内容を、QA / DQA / QEの観点から体系的に説明するための補助材料になる。

次章では、この整理をポートフォリオ別の対応表としてまとめ、読み手が短時間で全体像を把握できる形に圧縮する。

## 5. このポートフォリオ群から示せること

3章では各ポートフォリオを品質観点から詳しく見直し、4章ではその対応関係を一覧表として整理した。本章では、それらを踏まえて、ポートフォリオ群全体から説明できることをまとめる。

ここで示したいのは、特定の技術スタックを使った経験の一覧ではない。また、QA専任実務経験を主張することでもない。むしろ、AE / DEポートフォリオとして作成してきた内容の中に、品質・検証・データ品質・運用品質と接続する設計判断が含まれていることを整理する。

### 5.1 個別ツールではなく、品質を扱う姿勢

このポートフォリオ群で一貫して重視しているのは、「作ったものが動くこと」だけではない。

むしろ、次のような観点を重視している。

- 期待される入力・出力・状態を明確にすること
- 業務ルールをコードとテストで保護すること
- 入力契約を曖昧にしないこと
- データの意味と粒度を明確にすること
- 構造的な不整合と、業務上確認すべきレビュー対象を分けて扱うこと
- 指標定義を安定させること
- 変更後も重要な出力が壊れていないことを確認できるようにすること
- 関係者が同じ情報を見て判断できる出力を用意すること
- 外部から見えるサービス状態にも関心を持つこと

これらは、単独ではそれぞれ小さな設計判断である。しかし、ポートフォリオ群全体として見ると、「品質を最後の確認作業に閉じず、実装、テスト、データ、ドキュメント、成果物の中に組み込もうとしている」という共通した姿勢として説明できる。

たとえば、`ai-tool-access-requests` では、業務フロー、権限、状態遷移を明確にし、重要な業務ルールをテストで保護している。`go-ingestion-api` では、入力契約と取り込み境界を明確にし、受け取れるデータと拒否すべきデータを分けている。`access-governance-warehouse` では、データの粒度、入力データの前提契約、dbtによるデータ品質テスト、業務向けmart、BI出力を通じて、データの意味と信頼性を扱っている。`analytics-metrics-api` では、指標定義、期待出力、SQLからAPI出力までの追跡可能性を扱っている。`url-monitor` では、外部から見えるHTTPステータス、レイテンシ、エラー、p95を確認・記録する入口を扱っている。

このように見ると、各リポジトリは別々の技術を使った独立プロジェクトでありながら、品質観点ではつながっている。

### 5.2 AE / DEとQA / DQA / QEの接続点

AE / DEとQA / DQA / QEは、同じ職能ではない。

AE / DEでは、データの発生源、取り込み、変換、モデリング、指標定義、BI出力、分析APIなどを扱う。一方で、QA / DQA / QEでは、期待状態、確認条件、品質リスク、データ品質、テスト容易性、回帰確認、品質活動の仕組み化などを扱う。

しかし、両者には接続点がある。

第一に、どちらも「前提を明確にする」ことが重要になる。

AE / DEでは、データの粒度、入力データの前提、指標定義、集計条件を曖昧にしないことが重要である。QA / DQA / QEでは、期待される挙動、受け入れ条件、禁止操作、確認観点を曖昧にしないことが重要になる。

第二に、どちらも「再現可能に確認できる状態」を重視する。

AE / DEでは、同じ入力から同じ変換結果や同じ指標を再現できることが重要になる。QA / QEでは、変更後も期待される挙動や重要な出力が保たれていることを確認できる必要がある。この資料で扱ったポートフォリオ群では、deterministicな合成データ、dbt data tests、期待出力、ネットワーク非依存のテスト、CIでの確認などが、この観点に接続している。

第三に、どちらも「関係者が同じ情報を見て判断できる状態」を重視する。

AE / DEでは、mart、レポート、BI出力、分析APIを通じて、関係者がデータを見て判断できる状態を作る。QA / DQA / QEでは、テスト結果、品質メトリクス、レビュー対象、ログ、レポートなどを通じて、品質リスクや判断材料を関係者間で共有する。この意味で、データを扱うことと品質を扱うことは、どちらも「判断可能な状態を作る」活動として接続している。

### 5.3 データ品質を中心にした接続

このポートフォリオ群の中で、特に中心に置きやすいのはDQAの観点である。

`access-governance-warehouse` では、source contracts、model grain、dbt data tests、mart層、BI出力を通じて、データがどのような意味を持ち、どの粒度で解釈され、どの用途に使えるのかを明確にしようとしている。

ここで重要なのは、データ品質を単に「エラーがないこと」として扱っていない点である。

構造的に壊れているデータは、dbt testで検出する対象になる。たとえば、欠損してはいけない値の欠損、一意であるべきkeyの重複、参照関係の破損、許容されない分類値、負になってはいけない件数や金額、集計前後の照合不一致などである。

一方で、業務上気になる状態をすべてエラーとして扱うわけではない。承認済みだが最近利用されていない、利用実績があるが承認状態と整合していない、費用に対して利用が少ない、といった状態は、業務上の確認や判断が必要なレビュー対象として扱う方が自然である。

この分離は、データ品質を扱ううえで重要である。

- 壊れているデータは検出する
- 判断が必要な状態は可視化する
- 判断に必要な情報はmartやBI出力に反映する
- 関係者が同じ前提を見て議論できる状態を作る

この観点は、品質を単なる検出作業ではなく、関係者が同じ情報をもとに判断できる状態を作る活動として捉える考え方と接続する。

### 5.4 品質確認を仕組みに組み込む姿勢

このポートフォリオ群では、品質確認を人間の一回限りの確認だけに依存させないことも重視している。

`ai-tool-access-requests` では、業務ルールや権限境界をテストで保護している。`go-ingestion-api` では、HTTPリクエストの契約、JSON構造、必須項目、参照データとの照合を取り込み境界で検証している。`access-governance-warehouse` では、dbt build、dbt data tests、ドキュメント、lineage、BigQuery実行証跡、レポート、BI出力を用意している。

また、外部ネットワークや外部サービスの状態に依存するテストは、実装ロジックとは無関係な要因で失敗する可能性がある。そのため、`analytics-metrics-api` ではFastAPIのTestClientを用いて、実サーバーや外部ネットワークに依存せずにAPIのリクエスト・レスポンス契約を検証している。`url-monitor` ではHTTP通信をmockし、固定された応答を使ってロジックを確認することで、ネットワーク遅延や外部サイトの一時的な失敗に左右されないテストにしている。

これは、非決定的なテスト(non-deterministic test)や不安定なテスト(flaky test)を避けるために、外部依存を制御し、再現可能なテスト条件を作る取り組みとして説明できる。特にHTTP通信をmockする設計は、外部サービスをテストダブル(test double)で置き換える手法の一部として見ることができる。

これらは、すべて本番水準の品質基盤を意味するものではない。しかし、品質確認を「手元で一度確認したから終わり」にせず、再実行可能なテスト、検証条件、ドキュメント、成果物として残そうとしている点に意味がある。

この姿勢は、QEの観点から説明できる。

QEでは、品質を人間の注意力だけに依存させるのではなく、テスト、自動化、CI、入力検証、ドキュメント、成果物の中に組み込むことが重要になる。このポートフォリオ群は、その考え方を実務経験としてではなく、ポートフォリオ上の設計判断として示している。

### 5.5 この資料で説明できること

ここまでの整理から、このポートフォリオ群について説明できることは、次のようにまとめられる。

第一に、AE / DEを主軸としながらも、品質・検証・データ品質への関心が実装判断の中に現れていることである。

第二に、データの発生源、取り込み境界、rawデータ、warehouseモデリング、mart層、BI出力、分析APIまでを、小さくても一貫した流れとして扱おうとしていることである。

第三に、業務ルール、入力契約、データの粒度、指標定義、期待出力、外部から見えるサービス状態を、確認可能な形にしようとしていることである。

第四に、構造的な不整合と業務上のレビュー対象を分け、止めるべきものと可視化すべきものを区別していることである。

第五に、テスト、CI、dbt data tests、期待出力、ネットワーク非依存のテスト、ドキュメント、レポート、BI出力を通じて、再現性とレビュー可能性を重視していることである。

これらは、QA実務経験そのものではない。しかし、QA / DQA / QEを学んだ現在の視点から見ると、AE / DEポートフォリオとして実装してきた内容を、品質・検証・データ品質・運用品質の観点から説明するための補助材料になる。

## 6. 限界と今後経験したい領域

5章では、このポートフォリオ群から説明できることを整理した。

本章では、この資料で言えること、言いすぎるべきではないこと、このポートフォリオ群だけでは示せないことを分けたうえで、今後QA / DQA / QEに関わる実務の中で深めたい領域を整理する。

### 6.1 この資料で言えること

この資料で言えるのは、AE / DEポートフォリオとして実装してきた内容の中に、品質・検証・データ品質・運用品質と接続する設計判断が含まれている、ということである。

具体的には、次のような観点で説明できる。

- 業務フロー、権限、状態遷移を明確にしようとしていること
- 入力契約を定義し、不正な入力を早い段階で拒否しようとしていること
- データの意味、粒度、参照関係、指標定義を明確にしようとしていること
- 構造的な不整合と、業務上のレビュー対象を分けて扱おうとしていること
- 重要な出力を、テストや期待出力によって回帰確認できるようにしていること
- レポートやBI出力を通じて、関係者が同じ情報を見て判断できる状態を作ろうとしていること

これらは、QA / DQA / QEを学んだ現在の視点から見ると、AE / DEポートフォリオを品質観点で説明するための補助材料になる。

### 6.2 この資料で言いすぎないこと

一方で、本資料で言いすぎるべきではないことも明確である。

本資料は、QA専任実務経験を示すものではない。また、実際の本番プロダクトに対して、QA計画、テスト設計、探索的テスト、欠陥管理、リリース判定、横断的な品質改善を担当した経験を主張するものでもない。

また、各ポートフォリオは、ISO/IEC 25010やISO/IEC 25012に準拠して設計したものではない。品質モデルやDQAの観点は、あくまで後から実装内容を整理するための参照軸として扱う。

さらに、これらは本番運用中の大規模な業務システム、データ基盤、監視基盤を構築したものではない。本番水準の可観測性、SRE運用、継続監視、アラート通知、インシデント管理、正式なKPIガバナンスを経験したと主張するものでもない。

したがって、本資料では、各ポートフォリオを「QA経験」そのものとしてではなく、「QA / DQA / QEの観点から再解釈できるAE / DEポートフォリオ」として扱う。

### 6.3 このポートフォリオ群では示せないこと

また、個人ポートフォリオという性質上、このポートフォリオ群だけでは、実際のプロダクト運用から得られる品質課題までは十分に示せない。

たとえば、リリース後の実ユーザーの利用状況、問い合わせ、不具合、障害、ログ、監視データをもとに品質課題を見つけ、改善サイクルへ戻すShift Right(リリース後や運用中の観測・学習を品質改善へ戻す考え方)の活動は、個人ポートフォリオだけでは再現しにくい。`url-monitor` では外部から見えるHTTPステータス、レイテンシ、エラー、p95を扱っているが、これは運用品質への補助線であり、本番プロダクトにおける監視、アラート、インシデント対応、ユーザー影響分析、再発防止までを経験したことを示すものではない。

また、実務上のQA活動には、PM、開発者、デザイナー、CS、サポートなどと品質リスクを共有し、要求や仕様、受け入れ条件、テスト観点、リリース判断を調整していく活動が含まれる。この資料で扱うポートフォリオでは、期待状態、入力契約、データ品質、テスト自動化、再現性を個人実装として示している一方で、チームの中で品質活動を設計し、失敗や問い合わせから改善を回す経験までは示せない。

したがって、本資料で説明できるのは、品質を意識した設計判断や、QA / DQA / QEと接続する考え方である。実際のプロダクト、ユーザー影響、チーム制約の中で品質をどう扱うかは、次節の今後経験したい領域として整理する。

### 6.4 今後経験したい領域

今後は、ここまで整理した関心を、QA / DQA / QEに関わる実務の中でさらに深めたい。

これまでのポートフォリオでは、再現性、検証可能性、入力契約、データ品質、テスト、CI、ドキュメント化を意識してきた。一方で、それらは個人ポートフォリオ上での実装判断であり、実際のプロダクト開発におけるQA活動そのものではない。

今後は、実際のプロダクト、実際のユーザー影響、実際の開発チームの制約を踏まえながら、要求や仕様の整理、品質リスクの共有、テスト観点の設計、不具合や問い合わせからの改善、他職種との連携などを経験したい。

特に、AE / DEポートフォリオで扱ってきたデータ品質、入力契約、指標定義、CI、テスト自動化、再現性といった関心を土台にしながら、QA関連職能の実務を通じて、品質をどのように定義し、確認し、改善し、チームの活動に組み込んでいくのかを実務の中で学びたい。
