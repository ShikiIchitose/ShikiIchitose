この章では、その次の段階として、テスト、レビュー、リリース、運用、問い合わせ、インシデントなどから得られる結果を、どのように次の品質改善へ還元するかを扱う。

QA(Quality Assurance:品質保証)において重要なのは、不具合を見つけることだけではない。見つかった不具合、テストで失敗した箇所、リリース後に発生した問題、問い合わせとして表面化したつまずき、レビューで繰り返し指摘される傾向、品質ゲートで止まりやすいチェックなどを、次のテスト設計、仕様確認、自動化、開発プロセス改善、リリース判断に戻していくことが重要である。

つまり、品質活動の結果を、その場限りの記録として終わらせないということである。

本章で扱う「データ」は、プロダクト利用分析や事業分析のためのデータではない。ここで対象にするのは、QA活動、開発活動、リリース、運用、問い合わせ、インシデントから得られる品質活動データである。

一方、プロダクト、業務、分析、意思決定に使われるデータそのものの品質は、9章のDQA(Data Quality Assurance / Data Quality Assessment:データ品質保証 / データ品質評価)で扱う。8章と9章は関連するが、対象は異なる。

### 8.1 品質メトリクスの目的と対象範囲

品質メトリクスとは、品質活動、開発活動、リリース、運用、問い合わせ、インシデントなどの状態を観測するための指標である。

ここで重要なのは、品質メトリクスを「品質を数字だけで評価するもの」として扱わないことである。品質は、単一の数字だけでは判断できない。品質には、機能品質、ドメイン品質、データ品質、セキュリティ・権限品質、UX品質、運用品質、開発プロセス品質など、複数の観点がある。したがって、品質メトリクスも、これらの品質観点を理解するための補助情報として扱う必要がある。

品質メトリクスの目的は、主に次の四つである。

第一に、QA活動や開発活動の状態を観測することである。

たとえば、どの機能領域で欠陥が多いのか、どの工程で欠陥が見つかっているのか、どの種類のテストで失敗が多いのか、どの品質ゲートで止まりやすいのか、レビューにどの程度時間がかかっているのか、リリース後にどのような問い合わせやインシデントが発生しているのかを確認する。

これにより、品質活動を感覚だけで捉えるのではなく、実際に起きている事象をもとに観測できるようになる。

第二に、品質課題を改善へつなげることである。

欠陥が多い領域が分かれば、次のテスト設計でその領域を厚く確認できる。リリース後流出欠陥の傾向が分かれば、どの観点がリリース前に不足していたのかを考えられる。問い合わせが特定の操作に集中していれば、画面説明、エラーメッセージ、ヘルプ、業務フローの見直しにつなげられる。インシデントの復旧に時間がかかっていれば、監視、ログ、アラート、手順書、オンコール体制の改善を検討できる。

このように、メトリクスは単に現状を眺めるためではなく、次の改善対象を見つけるために使う。

第三に、リリース判断や優先順位付けの材料にすることである。

リリース前に未解決の重大欠陥が残っているか、品質ゲートでどのような失敗が起きているか、前回リリース後にどの程度の流出欠陥や問い合わせが発生したか、修正リードタイムが長期化していないか、といった情報は、リリース可否や対応優先度を判断する材料になる。

ただし、メトリクスがリリース判断を自動的に決めるわけではない。メトリクスは判断材料であり、最終的な判断には、影響範囲、ユーザー影響、回避策、既知の制約、ビジネス上の必要性、運用体制なども含めて考える必要がある。

第四に、品質活動の学習効果を高めることである。

不具合、問い合わせ、インシデント、レビュー指摘、テスト失敗は、単なる失敗ではない。それらは、プロダクトや開発プロセスがどこで品質リスクを生みやすいかを示す情報でもある。重要なのは、その情報を次の要求確認、テスト設計、自動化、レビュー観点、品質ゲート、運用設計に戻すことである。

品質メトリクスは、この学習を個人の記憶や経験だけに依存させないための手段になる。

たとえば、過去に権限漏れによる流出欠陥が発生していたのであれば、次の類似機能では権限テストを厚くする必要がある。外部連携失敗によるインシデントが繰り返されているのであれば、外部サービス障害時の挙動、リトライ、監視、アラート、復旧手順を見直す必要がある。問い合わせが特定の用語や画面操作に集中しているのであれば、UXやドキュメントを改善する余地がある。

このように、品質メトリクスは、QA活動の結果を次の品質活動へ還元するための仕組みである。

一方で、品質メトリクスには限界もある。

数字で見えるものだけを重視すると、数字に表れにくい品質を見落とす可能性がある。たとえば、仕様の妥当性、ユーザーの不安、業務上の違和感、将来の保守性、チーム内の認識違いなどは、単純な件数では捉えにくい。

また、メトリクスは人の行動を変える。欠陥数だけを強く評価すれば、欠陥として登録すべきものを登録しなくなるかもしれない。テストケース数だけを評価すれば、重要性の低いテストケースが増えるかもしれない。リードタイムだけを評価すれば、難しい問題を避ける行動につながるかもしれない。

したがって、品質メトリクスは、チームや個人を単純に管理・評価するための成績表としてではなく、品質状態を観測し、対話し、改善するための材料として扱う必要がある。

本章で扱うメトリクスは、主にQA活動・開発活動・運用活動から得られる品質活動データである。プロダクト利用分析や事業分析のためのデータではなく、またDQAで扱うデータそのものの品質とも区別する。

この対象範囲を明確にしたうえで、次節では、品質活動の結果をどのようなデータとして扱えるのかを整理する。

### 8.2 品質活動の結果をデータとして扱う

品質活動の結果は、さまざまな場所に記録される。

たとえば、欠陥票はIssue Tracker、テスト実行結果はTest Management Tool、自動テストや品質ゲートの結果はCI/CD、リリース後のエラーはError Monitoring、インシデントはIncident Management Tool、問い合わせはSupport Toolに残ることが多い。

これらは、それぞれの業務を進めるための記録であると同時に、品質改善のためのデータでもある。

たとえば、欠陥票は、単に「修正すべき不具合の一覧」ではない。どの機能領域で欠陥が多いのか、どの工程で見つかったのか、どの重要度の欠陥が多いのか、修正にどれくらい時間がかかったのかを振り返る材料になる。

テスト実行結果も、品質改善の材料になる。どのテストが繰り返し失敗しているのか、どの機能領域で失敗が多いのか、flaky test(不安定なテスト)によるノイズが多くないかを確認することで、テスト自動化や品質ゲートの改善につなげられる。

品質ゲート結果も重要である。Pull Request(PR:プルリクエスト)ごとに、lint、type check、Unit Test、API Test、Integration Test、build check、security scan、静的解析などが実行されている場合、どのチェックで止まりやすいのか、どのチェックがwarningとして残り続けているのか、どのチェックが開発フローのボトルネックになっているのかを観測できる。

問い合わせやサポートデータも、品質活動データとして扱える。ユーザーが同じ箇所で迷っている場合、それは問い合わせ対応だけの問題ではなく、UX(User Experience:ユーザー体験)品質、ドキュメント品質、仕様の分かりやすさ、エラーメッセージ、業務フロー設計の問題として捉え直せる可能性がある。

インシデントデータも同様である。インシデント発生件数、検知経路、影響範囲、復旧時間、再発防止策などは、運用品質や開発プロセス品質を改善するための重要な情報になる。

PR・レビュー・リリースデータも、開発プロセス品質を観測する材料になる。PRサイズが大きすぎればレビュー漏れやテスト漏れが起きやすくなる可能性がある。レビュー時間が長期化していれば、変更単位、レビュー体制、仕様の明確さ、テスト容易性に課題があるかもしれない。リリース後に修正が多い場合は、リリース前の確認、品質ゲート、リスク判断、運用準備を見直す必要がある。

このように、品質活動データは一箇所にまとまっているとは限らない。

実務では、次のようなツールや仕組みに分散して蓄積されることが多い。

| データの種類 | 蓄積されやすい場所 | 例 |
|---|---|---|
| 欠陥・作業アイテム | Issue Tracker | Jira、GitHub Issues、GitLab Issues |
| テストケース・テスト実行結果 | Test Management Tool | TestRailなど |
| 自動テスト・品質ゲート結果 | CI/CD | GitHub Actions、GitLab CI、Jenkinsなど |
| 静的解析・コード品質 | Code Quality Tool | SonarQubeなど |
| 本番エラー・性能問題 | Error Monitoring / Observability Tool | Sentryなど |
| インシデント | Incident Management Tool | PagerDutyなど |
| 問い合わせ | Support Tool | Zendeskなど |

ただし、重要なのはツール名そのものではない。

重要なのは、品質活動の結果を、次の改善に使える形で記録し、分類し、解釈できるようにすることである。

たとえば、欠陥票があっても、重要度、発見工程、原因領域、影響範囲、修正完了日が記録されていなければ、後から傾向を分析しにくい。テスト結果が残っていても、どのバージョン、どの環境、どの変更に対する結果なのかが分からなければ、品質改善には使いにくい。問い合わせが蓄積されていても、どの機能、どの操作、どのユーザー層で発生しているのかが分からなければ、UX改善やドキュメント改善につなげにくい。

品質活動データを活用するには、単に記録を残すだけでは不十分である。

次のような観点で、後から読める状態にしておく必要がある。

- いつ発生したのか
- どの機能・画面・API・業務フローに関係するのか
- どの工程で見つかったのか
- どの程度の重要度・影響度なのか
- どのリリースや変更に関係するのか
- 原因は仕様、実装、テスト設計、環境、運用、ドキュメントのどこに近いのか
- 再発防止や追加確認にどうつなげるのか

このように記録された品質活動データは、次の品質活動に還元できる。

たとえば、過去に権限漏れの欠陥が多かったのであれば、次の類似機能では権限観点を厚くする。特定のE2E Testが頻繁に失敗しているのであれば、テストデータ、待機処理、外部依存、テスト設計を見直す。問い合わせが特定の操作に集中しているのであれば、画面説明、エラーメッセージ、ヘルプ、業務フローを改善する。

つまり、品質活動データは、過去の記録ではなく、次の品質改善の材料である。

ただし、品質活動データは、集めれば自動的に価値が出るものではない。データの定義、記録の粒度、分類方法、対象期間、対象範囲が曖昧であれば、数字は見えても判断には使いにくい。

そのため、品質メトリクスを扱うときには、後の8.9で扱うように、指標の定義、単位、前提をそろえる必要がある。

### 8.3 テスト実行結果と品質ゲート結果

7章では、テスト自動化とCI/CD上の品質ゲートについて整理した。

8章では、その品質ゲートから得られる結果を、品質活動データとしてどのように読むかを考える。

テスト実行結果や品質ゲート結果は、変更時に得られる重要なフィードバックである。Unit Test、API Test、Integration Test、E2E Test、lint、type check、build check、security scan、静的解析などの結果は、コード変更が既存の期待状態や品質基準を満たしているかを確認する材料になる。

たとえば、Pull Requestごとに自動テストが実行されている場合、単に「通った」「落ちた」を見るだけでなく、次のような情報を観測できる。

- どのテストが失敗したのか
- どの機能領域で失敗が多いのか
- どのチェックで止まりやすいのか
- 失敗は本当の不具合なのか、テストの不安定さによるものなのか
- 修正までにどれくらい時間がかかったのか
- 同じ種類の失敗が繰り返されていないか
- 特定のリポジトリ、チーム、機能領域に失敗が偏っていないか

このような情報は、テスト自動化や品質ゲートを改善するための材料になる。

たとえば、Unit Testの失敗が多い場合は、ロジック変更の影響範囲、テスト設計、テストデータ、仕様変更時のテスト更新が適切かを確認する必要がある。API Testの失敗が多い場合は、入力検証、認可、エラー応答、API仕様変更の影響を見直す必要がある。E2E Testの失敗が多い場合は、主要業務フローが壊れている可能性もあるが、同時にテストデータ、待機処理、外部依存、画面変更への追従が不安定になっている可能性もある。

特にflaky test(不安定なテスト)は注意が必要である。

flaky testが多いと、品質ゲートの信頼性が下がる。テストが失敗しても「また不安定なだけだろう」と見なされるようになると、本当に重要な問題が検出されても見落とされやすくなる。そのため、どのテストが、どの頻度で、どの条件で不安定になっているのかを観測し、修正、隔離、削除、再設計を判断する必要がある。

品質ゲート結果では、fail、warning、manual review(手動レビュー)の扱いも重要である。

すべての失敗を同じ重さで扱うと、開発フローが過度に止まる。一方で、本来止めるべき重大な問題をwarningとして扱い続けると、品質ゲートの意味が薄れる。

たとえば、build失敗、type check失敗、重要なUnit TestやAPI Testの失敗は、mergeを止める条件になりやすい。一方で、低重要度のsecurity scan結果、軽微なlint警告、非重要領域の一時的な失敗は、warningとして可視化し、対応期限や優先度を決めて扱う場合がある。UX上の判断、既知不具合の受容、残リスクの判断は、自動判定ではなくmanual reviewに回す必要がある。

このように、品質ゲート結果は、単なる合否ではなく、開発フロー上の意思決定情報として扱う必要がある。

また、品質ゲート結果は、実行時間の観点からも読む必要がある。

自動テストや品質ゲートが遅すぎると、開発者は頻繁に実行しなくなる。Pull Requestのたびに長時間待たされる状態が続くと、フィードバックが遅れ、開発フローが重くなる。一方で、速さだけを重視して重要な確認を外しすぎると、リリース前やリリース後に問題が見つかりやすくなる。

したがって、テスト実行時間、再実行回数、待ち時間、失敗原因の特定しやすさも、品質ゲートの改善材料になる。

たとえば、次のような観点を継続的に見るとよい。

| 観点 | 読み取れること |
|---|---|
| テスト成功率 / 失敗率 | 変更時にどの程度チェックが安定して通っているか |
| テスト実行時間 | フィードバックが遅すぎないか |
| 再実行回数 | flaky testや環境依存が多くないか |
| 失敗テストの偏り | 特定の機能領域やテストレベルに問題が集中していないか |
| 品質ゲートfail率 | PRやリリース前にどの程度止まっているか |
| warningの滞留 | 対応すべき警告が放置されていないか |
| manual review(手動レビュー)件数 | 自動判定だけでは扱えない判断が増えていないか |

ここで注意すべきなのは、品質ゲート結果を、単純にチームや個人の成績表として扱わないことである。

たとえば、あるチームの品質ゲートfail率が高い場合、それは単に「そのチームの品質が低い」という意味ではないかもしれない。新しい機能開発が多い、複雑な領域を担当している、既存の技術的負債が大きい、テスト環境が不安定である、品質ゲートの条件が厳しすぎる、という可能性もある。

メトリクスは、なぜその結果になっているのかを考えるための入口である。

テスト実行結果と品質ゲート結果は、開発フローの中で継続的に得られる品質情報である。これらを適切に読むことで、自動テストの保守、品質ゲート条件の見直し、flaky testの削減、レビュー前チェックの改善、リリース判断の精度向上につなげられる。

次節では、欠陥の発生状況や修正状況を把握するための欠陥メトリクスを扱う。

### 8.4 欠陥メトリクス

欠陥メトリクスは、欠陥や不具合の発生状況、発見状況、修正状況を把握するための指標である。

ここでいう欠陥とは、ソフトウェアが期待された振る舞いを満たさない原因となる問題を指す。実務では、bug(バグ)、defect(欠陥)、issue(課題)、不具合など、組織やツールによって異なる言葉が使われることがある。本章では、主に「プロダクトや開発成果物に対して、修正や判断が必要になる品質上の問題」という意味で扱う。

欠陥メトリクスでよく見られるものには、次のようなものがある。

| 指標 | 見ること |
|---|---|
| 欠陥数 | 一定期間やリリース単位で、どれだけ欠陥が見つかったか |
| 欠陥密度 | 機能規模、コード量、画面数、ストーリー数などに対して、どの程度欠陥が見つかったか |
| 重要度別欠陥数 | 重大、中程度、軽微など、影響度ごとにどの程度欠陥があるか |
| 発見工程別欠陥数 | 要求、設計、実装中、テスト、リリース後など、どの段階で欠陥が見つかったか |
| 修正リードタイム | 欠陥が報告されてから修正・確認が完了するまでにどれくらい時間がかかったか |
| 再発欠陥数 | 過去に修正したはずの問題や、同種の問題が繰り返し発生していないか |

欠陥数は、最も分かりやすい指標である。しかし、欠陥数だけで品質を判断するのは危険である。

たとえば、欠陥数が少ない場合でも、その意味は一つではない。

- 本当に品質が安定している
- テストが不足していて、欠陥を見つけられていない
- 欠陥として登録すべき問題が、口頭やチャットだけで処理されている
- 軽微な問題が記録されていない
- リリース後に問い合わせやインシデントとして表面化するまで見えていない

逆に、欠陥数が多い場合でも、必ずしも品質が悪いとは限らない。

たとえば、新しい機能領域を重点的に探索した結果、多くの欠陥が見つかっている場合もある。探索的テストやレビューが機能し、これまで見えていなかった問題が早い段階で見えるようになった可能性もある。

したがって、欠陥数を見るときには、数そのものだけでなく、どの工程で、どの種類の欠陥が、どの重要度で、どの機能領域に集中しているかを見る必要がある。

たとえば、テスト工程で軽微なUI(User Interface:ユーザーインターフェース)崩れが多く見つかっている場合と、リリース後に権限漏れやデータ不整合が見つかっている場合では、品質リスクの意味が大きく異なる。

前者は、画面確認やデザイン実装、レビュー観点の改善につなげられるかもしれない。後者は、要求・仕様段階での権限整理、テスト設計、API Test、Integration Test、品質ゲート、監査ログの設計まで見直す必要があるかもしれない。

欠陥密度も、注意して扱う必要がある。

欠陥密度は、一定の規模に対してどれだけ欠陥が見つかったかを見る指標である。たとえば、コード行数、機能数、ユーザーストーリー数、画面数などを分母にして、欠陥数を割る形で表現されることがある。

ただし、欠陥密度は、分母の取り方によって意味が変わる。コード行数を分母にする場合と、ユーザーストーリー数を分母にする場合では、比較している対象が異なる。また、単純なCRUD(Create, Read, Update, Delete:作成・参照・更新・削除)画面と、権限、承認、外部連携、監査証跡を含む複雑な業務フローでは、同じ規模でも品質リスクは異なる。

そのため、欠陥密度は、異なるチームや異なるプロダクトを単純に比較するための指標として使うよりも、同じプロダクト内での傾向や、特定領域のリスクを把握する補助指標として使う方が安全である。

重要度別欠陥数も重要である。

すべての欠陥を同じ「1件」として扱うと、品質リスクを誤って読む可能性がある。軽微な文言ミスが10件ある場合と、個人情報が見えてしまう重大な権限不具合が1件ある場合では、単純な件数だけでは比較できない。

欠陥メトリクスでは、件数だけでなく、影響度、緊急度、発生条件、影響範囲、回避策の有無も合わせて読む必要がある。

発見工程別欠陥数は、どの段階で欠陥が見つかっているかを見るために使える。

要求や仕様の段階で欠陥や曖昧さが見つかっているのであれば、Shift Left Testing(シフトレフトテスト)が機能している可能性がある。一方で、リリース直前やリリース後に重大な欠陥が多く見つかっている場合は、要求確認、仕様レビュー、テスト設計、自動化、品質ゲート、リリース判断のどこかに改善余地があるかもしれない。

修正リードタイムも、欠陥メトリクスとして有用である。

欠陥が見つかってから修正完了までに時間がかかっている場合、原因は単に開発者の対応が遅いことだけではない。再現手順が不十分である、期待結果が曖昧である、影響範囲が広い、仕様判断が必要である、テスト環境が不安定である、レビューや確認フローが詰まっている、という可能性がある。

つまり、修正リードタイムは、開発スピードだけでなく、欠陥報告の質、仕様の明確さ、調査しやすさ、レビュー体制、テスト環境、リリース判断の状態を映す指標でもある。

欠陥メトリクスを使う目的は、欠陥数を減らすこと自体ではない。

重要なのは、欠陥がどこで生まれ、どこで見つかり、どのように修正され、次に同じ問題を起こさないために何を改善できるかを考えることである。

たとえば、同じ種類の権限不具合が繰り返し発生しているなら、権限チェックリスト、API Test、レビュー観点、受け入れ条件の書き方を見直す必要がある。外部連携失敗時の欠陥が多いなら、異常系テスト、Integration Test、監視、リトライ設計、運用手順を見直す必要がある。

欠陥メトリクスは、品質を断定するための数字ではなく、品質リスクの傾向を見つけ、次の品質活動を改善するための材料として扱う必要がある。

### 8.5 リリース後流出欠陥

リリース後流出欠陥とは、リリース前の確認では検出できず、リリース後にユーザー、運用、監視、問い合わせ、インシデントなどを通じて表面化した欠陥である。

英語では、escaped defects(流出欠陥)やproduction defects(本番環境で見つかった欠陥)と呼ばれることがある。ここで重要なのは、リリース後に見つかった欠陥を単に「見逃し」として責めることではない。重要なのは、なぜリリース前に検出できなかったのか、どの品質活動に改善余地があるのかを学習することである。

リリース後流出欠陥は、品質活動にとって重要なフィードバックである。

なぜなら、リリース前のテスト、レビュー、品質ゲート、受け入れ確認では見えていなかった品質リスクが、実利用や運用環境の中で表面化したものだからである。

たとえば、次のような欠陥は、リリース後に表面化することがある。

- 特定の権限ロールだけで発生する不具合
- 一部のブラウザや端末だけで起きる表示崩れ
- 本番データの分布で初めて発生する性能問題
- 外部サービスの遅延や失敗時に起きる不整合
- 実際の業務フローでのみ発生する状態遷移の抜け
- ユーザーが想定外の順序で操作したときに起きる問題
- 監査ログや通知の不足により、後から問題に気づくケース

これらは、単純な正常系テストだけでは見つけにくいことがある。そのため、リリース後流出欠陥は、次のテスト設計や品質ゲートの改善材料として扱う必要がある。

リリース後流出欠陥を見るときには、件数だけでなく、次のような観点を確認する。

| 観点 | 確認すること |
|---|---|
| 影響度 | ユーザー、業務、セキュリティ、データ、運用にどの程度影響したか |
| 検出経路 | 問い合わせ、監視、ログ、サポート、社内利用、インシデントなど、どこで見つかったか |
| 発生条件 | どの権限、状態、データ、環境、操作順序で発生したか |
| 見逃した工程 | 要求、仕様、設計、実装、レビュー、テスト、品質ゲートのどこで検出できた可能性があったか |
| 再発防止 | テストケース追加、自動化、監視追加、ドキュメント更新、仕様明確化など、次に何を変えるか |

たとえば、リリース後に「一般ユーザーが他部署の申請データを閲覧できる」という欠陥が見つかったとする。

この場合、単に画面の表示条件を修正するだけでは不十分である。要求や受け入れ条件で権限範囲が明確だったか、API(Application Programming Interface:アプリケーションプログラミングインターフェース)側の認可テストがあったか、E2E(End-to-End:エンドツーエンド) Testではどの権限パターンを確認していたか、レビューで権限観点が見られていたか、監査ログで不正閲覧の影響範囲を追跡できるかを確認する必要がある。

このように、リリース後流出欠陥は、単に「どの不具合を修正するか」だけでなく、「次に同じ種類の問題をどう防ぐか」を考えるための材料になる。

ただし、リリース後流出欠陥をゼロにすることだけを目標にするのは現実的ではない。

ソフトウェアは、ユーザー、データ、外部サービス、環境、業務ルール、リリース頻度、組織体制の影響を受ける。すべての条件をリリース前に完全に再現し、すべてのリスクを検出することは難しい。

したがって、重要なのは、流出欠陥を単に責任追及の材料にすることではなく、品質活動の改善に使うことである。

リリース後流出欠陥が発生した場合、次のような問いを持つとよい。

- その欠陥は、どの品質観点に関わるものだったか
- リリース前に検出できる種類の欠陥だったか
- 検出できなかった理由は、テスト設計、環境、データ、仕様、レビュー、品質ゲートのどこにあったか
- 今後、どのテスト観点や自動テストに追加すべきか
- 監視やログで早期に検知できるようにすべきか
- リリース判断時に残リスクとして明示すべきだったか
- ドキュメントやユーザー向け案内で補足すべきだったか

このような振り返りを通じて、リリース後流出欠陥は、次の要求整理、テスト設計、自動化、品質ゲート、監視、運用改善へ還元される。

リリース後流出欠陥は、品質活動の失敗を示すだけの指標ではない。リリース前の想定と実利用・運用環境との差分を学ぶための重要な品質情報である。

### 8.6 インシデントデータ

インシデントデータは、リリース後に発生した障害、サービス影響、運用上の問題、緊急対応に関する記録である。

インシデントは、単なる不具合とは限らない。システム障害、性能劣化、外部サービス障害、設定ミス、運用手順の不備、監視漏れ、データ不整合、セキュリティ上の問題など、ユーザーや業務に影響を与えるさまざまな事象が含まれる。

インシデントデータでよく見られるものには、次のようなものがある。

| 指標・情報 | 見ること |
|---|---|
| インシデント発生件数 | 一定期間にどれだけインシデントが発生したか |
| 影響範囲 | どのユーザー、機能、業務、データ、外部連携に影響したか |
| 検知経路 | 監視、アラート、問い合わせ、社内利用、ログ確認など、どの経路で気づいたか |
| 検知までの時間 | 問題が発生してから、チームが認識するまでにどれくらいかかったか |
| 対応・復旧時間 | チームが問題を認識してから、ユーザー影響を解消するまでにどれくらいかかったか |
| 再発防止策 | 監視、テスト、自動化、設計、運用手順など、何を改善するか |

インシデントデータを見る目的は、単に障害件数を数えることではない。

重要なのは、リリース後にどのような品質リスクが現実化したのか、検知や復旧がどの程度機能したのか、再発を防ぐためにどこを改善すべきかを学ぶことである。

たとえば、インシデントの検知がユーザー問い合わせに依存している場合、監視やアラートが不足している可能性がある。復旧に時間がかかっている場合、ログ、メトリクス、トレース、手順書、ロールバック方法、オンコール体制に課題があるかもしれない。同じ種類のインシデントが繰り返されている場合、根本原因の修正ではなく、一時対応だけで終わっている可能性がある。

インシデントデータは、4章で扱ったShift Right Testing(シフトライトテスト)や運用後のQA関与とも強く関係する。

リリース後の実利用、問い合わせ、ログ、監視、インシデントから得られる情報は、次の要求、仕様、テスト、自動化、監視、運用設計へ活かす必要がある。インシデントは、運用品質だけでなく、機能品質、ドメイン品質、データ品質、セキュリティ・権限品質、開発プロセス品質の問題として読み直せる場合がある。

たとえば、外部サービス障害によって申請処理が途中で止まり、中途半端な状態のデータが残ったとする。

この場合、インシデント対応としては復旧作業が必要になる。しかし、QAの観点では、それだけでは不十分である。外部連携失敗時の仕様は明確だったか、Integration Testで異常系を確認していたか、リトライや補償処理は設計されていたか、状態遷移として存在してはいけない状態が残らないか、ログやアラートで早期に検知できたかを確認する必要がある。

このように、インシデントデータは、単なる運用記録ではなく、品質活動に還元すべき情報である。

インシデント後には、ポストモーテム(postmortem:事後分析)や振り返りを行うことがある。

ポストモーテムでは、何が起きたか、なぜ起きたか、どのように検知したか、どのように対応したか、何を改善するかを整理する。ここで重要なのは、個人を責めることではなく、システム、プロセス、設計、監視、テスト、運用手順の改善につなげることである。

インシデントデータから品質改善へつなげるには、次のような問いが有効である。

- インシデントはどの品質観点に関係していたか
- どの時点で検知できたか
- もっと早く検知するために、どの監視やアラートが必要か
- リリース前に再現・検出できる種類の問題だったか
- テスト設計や品質ゲートに追加すべき確認はあるか
- ロールバックや復旧手順は機能したか
- 影響範囲を調査できるログやデータは残っていたか
- 同じ種類のインシデントを減らすために、設計や運用をどう変えるか

インシデントデータは、リリース後の品質を観測するための重要な情報である。

インシデントを単なる障害対応として終わらせず、テスト設計、自動化、品質ゲート、監視、ログ、運用手順、リリース判断へ戻すことで、プロダクトと開発プロセスの両方を改善できる。

次節では、問い合わせやサポートデータを、品質改善の入力情報としてどのように扱うかを整理する。

### 8.7 問い合わせ・サポートデータ

問い合わせ・サポートデータは、ユーザーが実際にどこでつまずき、何を理解しにくく感じ、どのような問題に直面しているかを知るための重要な品質活動データである。

問い合わせは、単なるサポート対応の記録ではない。ユーザーが迷った箇所、仕様を誤解した箇所、期待と実際の挙動がずれた箇所、ドキュメントや画面説明が不足している箇所、エラーメッセージが行動につながっていない箇所を示す情報でもある。

たとえば、同じ機能について問い合わせが繰り返し発生している場合、次のような可能性がある。

- 仕様がユーザーに伝わっていない
- 画面上の説明が不足している
- 操作手順が直感的ではない
- エラーメッセージが分かりにくい
- ヘルプやドキュメントが不足している
- 業務上の例外パターンをプロダクトが十分に扱えていない
- 実際には不具合や権限設定の問題が発生している

このように、問い合わせは、UX(User Experience:ユーザー体験)品質、ドキュメント品質、ドメイン品質、機能品質、セキュリティ・権限品質と関係することがある。

問い合わせ・サポートデータでよく見る観点には、次のようなものがある。

| 観点 | 読み取れること |
|---|---|
| 問い合わせ件数 | どの機能や時期に問い合わせが集中しているか |
| 問い合わせカテゴリ | 不具合、仕様確認、操作方法、権限、請求、性能、連携など、どの種類の問題が多いか |
| 対象機能・画面 | どの機能、画面、API、業務フローでつまずきが多いか |
| 解決時間 | 問題の理解や解決にどれくらい時間がかかっているか |
| 再問い合わせ・再オープン | 一度の回答や修正で解決しているか |
| エスカレーション(引き継ぎ) | サポートだけで解決できず、開発、QA、SRE、Product側の判断が必要になっていないか |
| リリース後の問い合わせ増加 | 変更後にユーザーの混乱や不具合が増えていないか |

問い合わせ件数が多いことは、必ずしもプロダクト品質が低いことを意味しない。

たとえば、新機能のリリース直後には、利用者が増えたことで問い合わせが増えることがある。ユーザー数が増えれば、問い合わせ数そのものも増えやすい。サポート導線が改善され、これまで表面化していなかった困りごとが見えるようになった可能性もある。

一方で、同じ問い合わせが繰り返されている場合は、改善余地がある。

たとえば、「承認済みの申請を編集できない」という問い合わせが多い場合、それは単なる操作方法の問題ではないかもしれない。仕様として編集できない設計なのか、編集できない理由が画面上で説明されているのか、ユーザーが次に取るべき操作を理解できるのか、ヘルプやFAQ(Frequently Asked Questions:よくある質問)に十分な説明があるのかを確認する必要がある。

また、「権限がないため操作できない」という問い合わせが多い場合も、単に権限設定の問い合わせとして処理するだけでは不十分である。権限ルールが業務に合っているか、画面上で操作不可の理由が分かるか、申請や承認の導線が用意されているか、権限変更後の反映タイミングが明確かを確認する必要がある。

問い合わせ・サポートデータは、次のような改善につなげられる。

- 受け入れ条件や仕様説明の見直し
- 画面文言やエラーメッセージの改善
- ヘルプ、FAQ、ドキュメントの更新
- テスト観点への追加
- 探索的テストのチャーター作成
- リリースノートやユーザー向け案内の改善
- 権限、状態遷移、業務フローの再確認
- 監視やログだけでは見えないユーザー影響の把握

問い合わせ・サポートデータを見るときに重要なのは、件数だけで判断しないことである。

たとえば、問い合わせ件数が少ない場合でも、ユーザーが困っていないとは限らない。問い合わせる前に諦めている、社内の別担当者に聞いている、問題を回避して運用している、問い合わせ導線が分かりにくい、といった可能性がある。

逆に、問い合わせ件数が多い場合でも、すべてが不具合とは限らない。仕様確認、使い方の質問、権限申請、業務フロー上の相談、導入直後の学習コストなども含まれる。

したがって、問い合わせ・サポートデータは、件数、カテゴリ、対象機能、ユーザー影響、発生時期、リリースとの関係、解決までの流れを合わせて読む必要がある。

QAの観点では、問い合わせは「リリース後に得られる品質フィードバック」である。

問い合わせをサポート部門だけの情報として閉じるのではなく、QA、プロダクトマネージャー(PM: Product Manager)、開発者、デザイナー、カスタマーサクセス(CS: Customer Success) / サポートで共有することで、次の要求整理、テスト設計、UX改善、ドキュメント改善、リリース判断に還元できる。

### 8.8 PR・レビュー・リリースデータ

PR(Pull Request:プルリクエスト)・レビュー・リリースデータは、開発プロセス品質を観測するための重要なデータである。

ここで扱うのは、プロダクトの利用状況や事業成果のデータではなく、開発活動そのものから得られるデータである。たとえば、PRサイズ、レビュー時間、差し戻し傾向、リリース頻度、変更失敗率、リリース後の修正などが含まれる。

これらのデータは、開発プロセスのどこで手戻りが起きやすいか、どの変更がレビューしにくいか、どのタイミングで品質リスクが表面化しやすいかを考える材料になる。

PR・レビュー・リリースデータでよく見る観点には、次のようなものがある。

| 観点 | 読み取れること |
|---|---|
| PRサイズ | 変更がレビュー可能な大きさになっているか |
| レビュー時間 | レビューが滞留していないか |
| レビュー指摘数・差し戻し傾向 | 仕様理解、実装方針、テスト不足、設計上の論点がどこに多いか |
| マージまでの時間 | 変更が開発フロー上でどこに滞留しているか |
| リリース頻度 | 変更をどの程度の頻度でユーザーに届けているか |
| 変更失敗率 | リリースやデプロイ後に、障害、ロールバック、緊急修正がどの程度発生しているか |
| リリース後の修正 | リリース前確認やリスク判断で見落としがなかったか |

PRサイズは、品質リスクと関係する。

変更が大きすぎると、レビュー対象が増え、影響範囲を把握しにくくなる。仕様変更、DB(Database:データベース)変更、API(Application Programming Interface:アプリケーションプログラミングインターフェース)変更、画面変更、テスト変更が一つのPRに混ざると、レビュー観点が分散し、確認漏れが起きやすくなる。

もちろん、小さいPRであれば常に良いというわけではない。意味のある変更単位を過度に分割しすぎると、全体の流れが追いにくくなることもある。重要なのは、レビューしやすく、テストしやすく、影響範囲を説明しやすい単位で変更されているかである。

レビュー時間も、開発プロセス品質を見る材料になる。

レビューに時間がかかっている場合、単にレビュアーが忙しいだけではないかもしれない。仕様が曖昧で判断しにくい、変更が大きすぎる、テスト観点が不足している、影響範囲の説明が足りない、設計方針の合意ができていない、といった可能性がある。

レビュー指摘や差し戻し傾向も、重要な品質情報である。

たとえば、レビューで同じような指摘が繰り返されている場合、それは個別PRの問題だけではなく、チームの設計指針、コーディング規約、テスト方針、仕様確認、ドキュメント、レビュー観点の共有方法に改善余地があることを示しているかもしれない。

レビュー指摘は、欠陥として登録されないことも多い。しかし、リリース前に品質リスクを見つけ、修正できているという意味では、重要なShift Left Testing(シフトレフトテスト)の情報である。

リリースデータも、品質メトリクスとして扱える。

たとえば、リリース頻度、変更失敗率、ロールバック、緊急修正、リリース後問い合わせ、リリース後流出欠陥、インシデント発生状況などは、リリースプロセスの安定性を考える材料になる。

DORA(DevOps Research and Assessment)では、Deployment Frequency(デプロイ頻度)、Lead Time for Changes(変更のリードタイム)、Change Failure Rate(変更失敗率)、Failed Deployment Recovery Time(失敗したデプロイからの復旧時間)のような指標が、ソフトウェアデリバリーパフォーマンスを見る代表的なメトリクスとして扱われることがある。

ここで重要なのは、リリース頻度やリードタイムを単独で見るのではなく、品質への影響と合わせて読むことである。

たとえば、リリース頻度が高いこと自体は、必ずしも品質が高いことを意味しない。頻繁にリリースしていても、変更失敗率が高く、リリース後の緊急修正や問い合わせが多ければ、リリースプロセスに品質リスクがある可能性がある。

一方で、リリース頻度が低いことも、必ずしも安定していることを意味しない。変更を長期間ため込むことで、1回のリリースに含まれる差分が大きくなり、影響範囲の把握や問題発生時の切り戻しが難しくなる場合もある。

したがって、PR・レビュー・リリースデータは、速度だけを見るためのものではない。

重要なのは、変更がレビュー可能な単位になっているか、テストしやすい形で実装されているか、品質ゲートで適切に確認されているか、リリース後にどのような問題が発生しているかを合わせて読むことである。

PR・レビュー・リリースデータは、次のような改善につなげられる。

- PRテンプレートやレビュー観点の改善
- 変更単位の見直し
- テスト観点や自動テストの追加
- リリース前チェックリストの改善
- 品質ゲート条件の見直し
- レビュー体制や担当分担の改善
- リリース後の監視・問い合わせ確認の強化
- 開発プロセス上のボトルネックの可視化

ただし、これらのデータも、チームや個人を単純に評価するための成績表として扱うべきではない。

たとえば、あるチームのPRレビュー時間が長い場合、それは単に効率が悪いという意味ではないかもしれない。複雑なドメイン、慎重なレビューが必要な権限・セキュリティ領域、影響範囲の大きい変更、組織横断の調整が多い領域を担当している可能性もある。

また、変更失敗率が高い場合でも、挑戦的な変更や基盤刷新を多く扱っている時期かもしれない。逆に、変更失敗率が低くても、変更量自体が少ない、リリースを避けている、問題が記録されていない、という可能性もある。

メトリクスは、問いを立てるための入口である。

PR・レビュー・リリースデータは、開発プロセスを責めるための数字ではなく、どこで品質リスクが生まれやすいか、どこで手戻りが起きているか、どこを改善すれば安全に変更しやすくなるかを考えるための材料として扱う必要がある。

次節では、こうした品質メトリクスを誤読しないために、指標の定義、単位、前提をそろえる重要性を整理する。

---

### 8.9 指標の定義・単位・前提をそろえる

品質メトリクスを扱うときに重要なのは、指標名だけで判断しないことである。

同じ「欠陥数」「問い合わせ数」「インシデント数」「テスト失敗数」という言葉を使っていても、何を1件として数えているのか、どの期間を対象にしているのか、どの機能やチームを対象にしているのか、どの重要度まで含めているのかによって、意味は大きく変わる。

たとえば、「今月の欠陥数は30件」と言われても、それだけでは品質状態を判断できない。

その30件は、開発中に見つかった欠陥なのか、リリース後に見つかった流出欠陥なのか。軽微なUI(User Interface:ユーザーインターフェース)崩れも、重大な権限不具合も同じ1件として数えているのか。仕様確認の指摘や改善要望も含まれているのか。1つの根本原因から複数のチケットが作られているのか。逆に、複数の不具合が1つのチケットにまとめられているのか。

これらが分からなければ、欠陥数の増減を見ても、品質が良くなったのか、悪くなったのか、単に記録方法が変わったのかを判断しにくい。

問い合わせ数も同じである。

問い合わせ数が増えた場合、それはプロダクトに問題が増えたことを意味する場合もある。しかし、新機能の利用者が増えた、問い合わせ導線が改善された、これまで見えていなかった困りごとが表面化した、導入直後の学習コストが一時的に増えた、という可能性もある。

逆に、問い合わせ数が減った場合でも、ユーザーが困っていないとは限らない。問い合わせを諦めている、社内の別担当者に聞いている、問題を回避して運用している、サポート導線が分かりにくい、といった可能性もある。

したがって、品質メトリクスを見るときには、指標の定義、単位、前提を明確にする必要がある。

ここでいう「単位」とは、何を1件、1回、1対象として数えているのかということである。

たとえば、次のように、品質活動データにはさまざまな単位がある。

| 単位 | 例 | 注意点 |
|---|---|---|
| 欠陥単位 | 欠陥1件、不具合1件 | 1つの原因から複数欠陥が出る場合や、複数問題が1チケットにまとめられる場合がある |
| チケット単位 | Issue 1件、問い合わせ1件 | チケットの作り方によって件数が変わる |
| テスト実行単位 | テストケース1回、テストスイート1回、CI実行1回 | 再実行やflaky test(不安定なテスト)をどう扱うかで結果が変わる |
| リリース単位 | リリース1回、デプロイ1回 | 1回のリリースに含まれる変更量が大きく異なる場合がある |
| PR単位 | PR(Pull Request:プルリクエスト)1件 | PRサイズや変更内容が大きく異なる場合がある |
| サービス単位 | サービス1つ、システム1つ、プロダクト1つ | 対象範囲の大きさや複雑さが異なる場合がある |
| 期間単位 | 1日、1週間、1か月、1リリース期間 | リリース直後、繁忙期、導入直後などの時期要因を受ける |

これらの単位を混同すると、メトリクスを誤って読む可能性がある。

たとえば、テスト失敗数を見る場合、1つの失敗したテストケースを1件と数えるのか、1回のCI/CD(Continuous Integration / Continuous Delivery:継続的インテグレーション / 継続的デリバリー)実行失敗を1件と数えるのか、失敗したテストスイートを1件と数えるのかで意味が変わる。

flaky testが原因で同じテストを5回再実行した場合、それを失敗5件と見るのか、1つの不安定なテストとして扱うのかによって、品質ゲートの見え方も変わる。

また、リリース後流出欠陥を見る場合も、単純に件数だけを比較すると誤解が生まれやすい。

1回のリリースに含まれる変更が小さい場合と、大きな機能追加を含む場合では、同じ1件の流出欠陥でも意味が異なる。ユーザー影響が限定的な表示崩れと、権限漏れやデータ不整合のような重大な問題も、同じ1件として扱うだけでは品質リスクを正しく捉えられない。

そのため、品質メトリクスでは、件数だけでなく、対象範囲、影響度、重要度、期間、発生条件を合わせて読む必要がある。

指標の対象期間も重要である。

たとえば、月単位で問い合わせ件数を見る場合、リリース直後の月、年度末の繁忙期、導入直後の顧客が多い時期、サポート体制が変わった時期では、問い合わせ件数の意味が変わる。

同じように、インシデント件数も、単純な月次比較だけでは不十分なことがある。新しい監視が導入されたことで、これまで見えていなかった問題が検知されるようになった場合、インシデント件数は一時的に増えるかもしれない。しかし、それは品質が悪化したというより、観測能力が上がった結果である可能性もある。

対象チームや対象機能も明確にする必要がある。

たとえば、あるチームの欠陥数が多い場合、そのチームの品質が低いとは限らない。複雑なドメインを担当している、既存の技術的負債が大きい領域を扱っている、変更量が多い、外部連携や権限管理のようなリスクの高い機能を担当している、という可能性がある。

同じメトリクスでも、背景となるプロダクト特性やチームの責任範囲が異なれば、単純比較はできない。

したがって、品質メトリクスを扱うときには、少なくとも次のような前提を明示する必要がある。

- 指標名
- 何を1件、1回、1対象として数えているか
- 対象期間
- 対象チーム
- 対象機能・サービス
- 対象リリース
- 重要度や影響度の分類
- 含めるものと除外するもの
- データの取得元
- 記録方法や運用ルール
- 既知の制約や注意点

たとえば、「リリース後流出欠陥数」を扱う場合は、次のような観点を定義しておくと、後から解釈しやすい。

| 項目 | 定義例 |
|---|---|
| 指標名 | リリース後流出欠陥数 |
| 目的 | リリース前の確認で検出できなかった欠陥の傾向を把握し、テスト設計・品質ゲート・リリース判断を改善する |
| 単位 | 欠陥チケット1件 |
| 対象 | 本番リリース後に、ユーザー問い合わせ、監視、運用確認で発見された欠陥 |
| 除外 | リリース前に既知だった制約、仕様変更要望、軽微な文言修正 |
| 期間 | リリース日から14日以内 |
| 分類 | 重要度、影響範囲、発見経路、対象機能 |
| データ取得元 | Issue Tracker、Support Tool、Monitoring Tool、Incident Management Tool |
| 注意点 | チケット分割ルールや問い合わせ導線の変更により件数が変わる可能性がある |

このように定義しておけば、「リリース後流出欠陥が増えた」という事実を見たときに、何が増えたのか、どの範囲の欠陥を見ているのか、過去と比較できるのかを考えやすくなる。

問い合わせ件数やPRレビュー時間も同じである。

問い合わせ件数を見るなら、対象チャネル、問い合わせカテゴリ、botや自動応答を含むかどうか、再問い合わせをどう数えるかを決める必要がある。PRレビュー時間を見るなら、PR作成から最初のレビューまでなのか、PR作成からmergeまでなのか、休日や待機時間を含むのか、draft PRを含めるのかを明確にする必要がある。

定義が曖昧なままダッシュボードを作ると、見た目は整っていても、解釈が揃わない。

ある人は「問い合わせ数」を不具合問い合わせだけだと思って読み、別の人は使い方の質問も含むものとして読むかもしれない。ある人は「修正リードタイム」を修正着手から完了までと読み、別の人は欠陥報告から確認完了までと読むかもしれない。

このような状態では、数字を見ても議論がかみ合いにくい。

品質メトリクスは、数字そのものではなく、定義、単位、前提、文脈とセットで読む必要がある。

これは、メトリクスを厳密な分析資料にしなければならないという意味ではない。最初から複雑なデータ基盤や詳細な集計ルールを作る必要はない。

重要なのは、チームが同じ意味で数字を読めるようにすることである。

小規模であれば、スプレッドシートやIssue Trackerのラベル運用から始めてもよい。重要度、対象機能、発見工程、リリース、原因分類などを最低限そろえるだけでも、品質活動の振り返りはしやすくなる。

一方で、複数のチーム、複数のリポジトリ、複数のプロダクトにまたがって品質メトリクスを扱う場合は、定義や単位のずれが大きな問題になりやすい。この場合は、指標の定義書、分類ルール、ダッシュボードの注釈、集計条件の明示が重要になる。

品質メトリクスは、チームが品質について対話するための共通言語である。

その共通言語が曖昧であれば、同じ数字を見ていても、異なる意味で解釈してしまう。したがって、指標の定義・単位・前提をそろえることは、品質メトリクスを実務で使うための土台である。

次節では、このように定義した品質メトリクスを、チームで共有し、傾向を把握するためのダッシュボードによる可視化を扱う。

---

### 8.10 ダッシュボードによる可視化

品質メトリクスは、個別のチケットやテスト結果として残っているだけでは、チーム全体で傾向を把握しにくい。

そのため、欠陥、テスト実行結果、品質ゲート結果、問い合わせ、インシデント、PR(Pull Request:プルリクエスト)・レビュー・リリースデータなどを、必要に応じてダッシュボードで可視化することがある。

ここでいうダッシュボードは、品質状態を一目で断定するためのものではない。品質活動や開発活動の状態をチームで共有し、傾向を把握し、次にどこを確認・改善すべきかを考えるための補助である。

たとえば、次のような情報は、ダッシュボードで共有しやすい。

| 可視化する情報 | 読み取れること |
|---|---|
| 欠陥数の推移 | 欠陥が増えている領域や時期がないか |
| 重要度別欠陥数 | 重大な品質リスクが残っていないか |
| リリース後流出欠陥 | リリース前確認で見逃したリスクがないか |
| テスト成功率 / 失敗率 | 自動テストや品質ゲートが安定しているか |
| flaky test(不安定なテスト)の傾向 | 品質ゲートの信頼性を下げる要因がないか |
| インシデント件数・対応時間 | リリース後の運用品質や復旧力に課題がないか |
| 問い合わせ件数・カテゴリ | ユーザーがどこで迷っているか |
| PRサイズ・レビュー時間 | 変更がレビューしやすい単位になっているか |
| リリース頻度・変更失敗率 | 変更を安全に届けられているか |

ダッシュボードの価値は、数字を一覧表示することそのものではない。

重要なのは、チームが同じ情報を見ながら、品質状態について対話できるようにすることである。

たとえば、リリース後の問い合わせが増えている場合、単に件数を見て終わるのではなく、どの機能に集中しているのか、どのリリース後に増えたのか、問い合わせカテゴリは仕様確認なのか、不具合なのか、操作方法なのかを確認する必要がある。

同じように、品質ゲートのfail率が上がっている場合も、単に「失敗が多い」と見るだけでは不十分である。重要な不具合を早期検出できているのか、flaky testが増えているのか、品質ゲート条件が厳しすぎるのか、テスト環境が不安定なのかを分けて考える必要がある。

ダッシュボードでは、個別の数字よりも傾向を見ることが重要である。

一時的な増減だけで判断すると、誤解が生まれやすい。新機能リリース直後、ユーザー数の増加、サポート導線の変更、監視強化、テスト追加、チケット登録ルールの変更などによって、数字は変化する。

したがって、ダッシュボードでは、次のような見方が重要になる。

- 単月の数字だけでなく、継続的な推移を見る
- 件数だけでなく、重要度や影響度を見る
- 発生件数だけでなく、解決までの時間を見る
- 全体平均だけでなく、対象機能やリリース単位で見る
- 数字の増減だけでなく、記録方法や運用変更の影響も見る
- 異常値や急な変化があった場合は、背景を確認する

また、ダッシュボードでは、見せる相手によって、どの情報をどの詳しさで示すべきかが変わる。

開発チーム内では、失敗したテスト、flaky test、PRレビュー時間、未解決欠陥、品質ゲートのwarningなど、日々の改善に直結する情報が重要になる。

一方で、Product Managerや事業側と共有する場合は、リリース後流出欠陥、重大インシデント、問い合わせ傾向、リリース判断に影響する残リスクなど、意思決定に関係する情報を中心にした方がよい。

SRE(Site Reliability Engineering:サイト信頼性エンジニアリング)や運用担当者と共有する場合は、インシデント、検知経路、復旧時間、アラート、ログ、監視の不足などが重要になる。

つまり、すべての情報を一つのダッシュボードに詰め込めばよいわけではない。誰が、何を判断するために見るのかを考えて、表示する指標を選ぶ必要がある。

ダッシュボードを作るときには、次のような点に注意する。

- 指標の定義が明確である
- 対象期間や対象範囲が分かる
- 件数だけでなく、重要度や影響度も見られる
- 異常値や急な変化に気づける
- 詳細なチケットやログに辿れる
- 更新頻度が目的に合っている
- 古い指標や使われていない指標を放置しない
- ダッシュボードを見る場や使い方が決まっている

特に重要なのは、ダッシュボードを「作って終わり」にしないことである。

ダッシュボードは、チームの会話や意思決定に使われて初めて意味を持つ。たとえば、リリース後の振り返り、品質定例、インシデントレビュー、テスト改善会、スプリントレトロスペクティブなどで、ダッシュボードを見ながら次の改善を考えることが重要である。

ダッシュボードは、品質に関する答えを自動的に出すものではない。

品質メトリクスを見える化し、チームが同じ情報をもとに議論できるようにするための道具である。したがって、ダッシュボードは意思決定の補助であり、結論そのものではない。

### 8.11 指標を使うときの注意

品質メトリクスは、品質活動を改善するための強力な材料になる。

しかし、指標は扱い方を誤ると、かえって品質活動を歪めることがある。

最も注意すべきなのは、数字が目的化することである。

たとえば、「欠陥数を減らすこと」だけが強調されると、欠陥として記録すべき問題が記録されなくなるかもしれない。「テストケース数を増やすこと」だけが目標になると、重要性の低いテストケースが増え、本当に確認すべきリスクが見えにくくなるかもしれない。「リードタイムを短くすること」だけが重視されると、複雑な問題や根本原因の調査が後回しにされるかもしれない。

指標は、人の行動を変える。

そのため、指標を設計するときには、どのような行動を促すのか、どのような副作用が起こり得るのかを考える必要がある。

品質メトリクスを使うときに避けたいのは、次のような使い方である。

- 欠陥数だけで品質を判断する
- テストケース数だけでテストの十分性を判断する
- カバレッジだけで重要なリスクを確認できていると判断する
- 問い合わせ件数だけでユーザー満足度を判断する
- インシデント件数だけで運用品質を判断する
- PRレビュー時間だけでチームの効率を判断する
- チーム間で文脈の異なる数字を単純比較する
- 指標を個人評価や責任追及の材料として使う

たとえば、AチームとBチームの欠陥数を単純に比較して、Aチームの方が品質が低いと判断するのは危険である。Aチームが複雑な権限管理や外部連携を担当している一方で、Bチームが比較的安定した画面改修を担当しているなら、欠陥数の意味は異なる。

同じように、問い合わせ件数が多いチームを単純に問題視するのも危険である。そのチームがユーザー数の多い機能を担当している、導入直後の機能を担当している、サポート導線が整っていて困りごとが表面化しやすい、といった可能性がある。

品質メトリクスは、文脈なしに比較できない。

比較する場合は、少なくとも、対象機能、対象期間、変更量、リリース回数、ユーザー数、重要度、記録方法、チームの責任範囲を確認する必要がある。

また、測りやすいものだけを重視すると、重要だが測りにくい品質を見落とす可能性がある。

たとえば、欠陥数、テスト成功率、レビュー時間、問い合わせ件数は比較的数えやすい。一方で、仕様の分かりやすさ、ユーザーの不安、業務上の自然さ、保守性、チーム内の認識ずれ、将来の変更しやすさは、単純な数値にしにくい。

しかし、数値にしにくいからといって、品質上重要でないわけではない。

特に、QA(Quality Assurance:品質保証)では、数値化された情報と、人間の観察、探索的テスト、レビュー、問い合わせ内容、インシデントの振り返りを組み合わせて判断する必要がある。

指標は、品質を判断するための入口であり、結論ではない。

たとえば、問い合わせ件数が増えていることは、調査すべきサインである。しかし、その原因が不具合なのか、仕様の分かりにくさなのか、利用者増加なのか、導入直後の学習コストなのかは、件数だけでは分からない。

品質ゲートのfail率が上がっていることも、調査すべきサインである。しかし、それが重要な問題を早く検出できている状態なのか、flaky testが増えている状態なのか、品質ゲート条件が実態に合っていない状態なのかは、追加の確認が必要である。

したがって、品質メトリクスを見るときには、次の問いを持つとよい。

- この指標は、何を観測するためのものか
- この数字は、どのように記録・集計されたものか
- 増減の背景に、記録方法や対象範囲の変更はないか
- この数字だけで判断してよいか
- 他に合わせて見るべき指標や情報はないか
- この指標を目標にすると、どのような行動が促されるか
- 指標の改善が、実際のユーザー価値や品質改善につながっているか

品質メトリクスは、チームを責めるためのものではない。

重要なのは、メトリクスを使って、品質に関する会話を始めることである。

なぜこの欠陥が流出したのか。なぜこの問い合わせが繰り返されているのか。なぜこのテストは不安定なのか。なぜレビューに時間がかかっているのか。なぜ復旧に時間がかかったのか。こうした問いを立てることで、要求整理、テスト設計、自動化、品質ゲート、監視、ドキュメント、開発プロセスの改善につなげられる。

品質メトリクスを安全に使うには、次のような姿勢が重要である。

- 数字を結論ではなく、問いの入口として扱う
- 単一指標ではなく、複数の情報を組み合わせて読む
- 件数だけでなく、影響度や文脈を見る
- チーム間比較よりも、改善の方向を見る
- 個人評価ではなく、プロセス改善に使う
- 測りやすいものだけでなく、測りにくい品質にも注意を向ける
- 指標が人の行動を変えることを意識する

このように、品質メトリクスは、使い方によって価値が大きく変わる。

適切に使えば、品質活動を感覚や経験だけに依存させず、チームで観測し、対話し、改善するための材料になる。一方で、使い方を誤れば、数字だけが一人歩きし、現場の判断や品質改善を妨げることもある。

品質メトリクスは、品質を数字で管理しきるためのものではない。

品質活動の結果を見える化し、次の改善へつなげるための観測情報として扱う必要がある。

### 8.12 Key Takeaways

本章では、品質メトリクスを、品質を数字だけで断定するためのものではなく、QA活動・開発活動・運用活動の結果を観測し、次の改善へ還元するための情報として整理した。

品質活動の結果は、欠陥票、テスト実行結果、品質ゲート結果、問い合わせ、インシデント、PR(Pull Request:プルリクエスト)、レビュー、リリース履歴など、さまざまな形で残る。これらを単発の記録として終わらせず、傾向を把握し、リスクを見つけ、テスト設計、自動化、品質ゲート、リリース判断、運用改善へ戻すことが重要である。

一方で、品質メトリクスは扱い方を誤ると、数字だけが目的化し、品質活動を歪める可能性がある。そのため、指標の定義、単位、前提、対象範囲、文脈を明確にし、数字を結論ではなく、品質について対話するための入口として扱う必要がある。

- 品質メトリクスは、品質を数字だけで断定するためのものではなく、品質活動・開発活動・運用活動を観測するための情報である。
- テスト結果、品質ゲート結果、欠陥、リリース後流出欠陥、インシデント、問い合わせ、PR・レビュー・リリースデータは、次の品質改善に還元できる。
- 欠陥数や問い合わせ件数などの単純な件数だけでは、品質状態を判断できない。
- 欠陥数が少ないことは、品質が安定している可能性もあるが、テスト不足や記録不足によって問題が見えていない可能性もある。
- リリース後流出欠陥は、単なる見逃しではなく、リリース前の想定と実利用・運用環境との差分を学ぶための重要な品質情報である。
- インシデントデータは、障害対応の記録にとどまらず、監視、ログ、復旧手順、テスト設計、品質ゲート、運用設計を改善する材料になる。
- 問い合わせ・サポートデータは、ユーザーがどこで迷い、何を理解しにくく感じているかを知るための重要な品質フィードバックである。
- PR・レビュー・リリースデータは、開発プロセスのどこで手戻りが起きやすいか、どの変更がレビューしにくいか、どのタイミングで品質リスクが表面化しやすいかを考える材料になる。
- 品質メトリクスを扱うときは、何を1件、1回、1対象として数えているのか、対象期間、対象チーム、対象機能、重要度分類、除外条件を明確にする必要がある。
- ダッシュボードは、品質状態を自動的に判断するものではなく、チームが同じ情報を見ながら品質について対話するための道具である。
- ダッシュボードでは、単月の数字だけでなく、継続的な推移、重要度、影響度、対象機能、リリースとの関係、運用変更の影響を見る必要がある。
- 指標は人の行動を変えるため、欠陥数、テストケース数、カバレッジ指標、リードタイムなどを目標化するときは、副作用に注意する必要がある。
- 品質メトリクスは、チームや個人を責めるための成績表ではなく、品質リスクを見つけ、改善の方向を考えるための材料である。
- 重要なのは、数字を結論として扱うことではなく、なぜその結果になっているのかを問い、次の品質活動へつなげることである。
