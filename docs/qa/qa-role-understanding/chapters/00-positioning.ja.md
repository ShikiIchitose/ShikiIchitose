# QA職能入門：品質を作り、判断し、改善へ戻す仕組み

## — 要求・テスト設計・自動化・品質メトリクス・DQA・AI時代のQA —

> **注意**
>
> この資料は、QA(Quality Assurance:品質保証)、Testing(テスト)、Quality Engineering(品質エンジニアリング)、DQA(Data Quality Assurance / Data Quality Assessment:データ品質保証 / データ品質評価)に関する理解を整理するために、個人が作成した学習・参照用資料です。
>
> 第三者機関、標準化団体、資格認定団体、企業などによって内容が保証・監修・認証された資料ではありません。
>
> 内容は公開情報および執筆時点での作成者の理解に基づくものであり、実務適用にあたっては各組織・プロダクト・ドメインの状況に応じた判断が必要です。
>
> **この資料におけるQAの扱い**
>
> この資料で単にQAと表記する場合、原則としてソフトウェアプロダクト開発におけるQAを指します。
>
> DQAは、データそのものを品質対象として扱う領域であり、ソフトウェアQAと関連しますが、本資料では区別して扱います。
>
> 本資料では、まずソフトウェアQAの基本概念を整理し、そのうえでDQAを、ソフトウェア品質、データ品質、分析、意思決定、AI評価を接続する観点として扱います。

---

## 0. この資料の位置づけ

### 0.1 目的

この資料は、QA(Quality Assurance:品質保証)初学者が、QA職能の全体像を体系的に理解するための入門・参照用資料である。

QAはしばしば「テストを実行して不具合を見つける仕事」として理解される。しかし、実務におけるQAの役割は、テスト実行だけに閉じない。要求や仕様の曖昧さを早期に見つけること、プロダクトにとって重要なリスクを整理すること、テスト設計や自動化を通じて継続的に品質を確認できる状態を作ること、開発チームが品質を扱いやすくなるよう支援することも、QAの重要な役割に含まれる。

この資料では、QAを単なる後工程の確認作業ではなく、**品質を作るための仕組み・プロセス・考え方**として整理する。

特に、以下の観点を重視する。

- Testing(テスト)とQAを同一視しないこと
- QA / QC(Quality Control:品質管理) / Testing / Quality Engineeringの違いを整理すること
- 現代的な開発において、QA、Testing、Quality Engineeringの関係が固定的な分業だけでは捉えにくくなっていることを理解すること
- 要求・仕様・設計段階から品質を考えること
- テスト設計を、網羅作業ではなくリスク判断として捉えること
- 自動テストやCI/CD(Continuous Integration / Continuous Delivery:継続的インテグレーション / 継続的デリバリー)を品質ゲートとして理解すること
- 品質メトリクスを、品質状態を観測するためのデータとして扱うこと
- DQAを、ソフトウェアQAとデータ領域を接続する重要な観点として扱うこと
- AI(Artificial Intelligence:人工知能)時代におけるQAの変化を、AI-assisted QA(AI支援QA)とAI Product QA(AIプロダクトQA)の両面から考えること

この資料の目的は、QA実務のすべてを網羅することではない。むしろ、QA初学者が実務に入る前に、どのような観点で品質を捉えればよいのかを整理することにある。あわせて、すでにQAとして実務に関わっている人が、日々の活動を振り返り、QAの基本的な考え方や全体像を確認する際の補助としても使えることを想定している。

また、開発、データ、分析、運用など、QA以外の領域から品質に関心を持つ人が、自分の経験や関心とQA職能との接点を考えるための入口になることも意図している。

---

### 0.2 想定読者

この資料の主な想定読者は、QA職能をこれから理解しようとしている人である。

具体的には、以下のような読者を想定している。

- QA職に関心を持ち始めた人
- QA未経験からQAエンジニア職を理解したい人
- 開発、データ、分析、バックエンド領域からQA職能との接点を探りたい人
- テスト設計、自動化、品質メトリクス、データ品質に関心がある人
- AI時代における評価、検証、品質保証の考え方を整理したい人

QAの実務では、プロダクト、開発体制、組織規模、リリース頻度、ドメインリスクによって、求められる活動が大きく変わる。そのため、この資料では特定企業や特定プロダクトに依存したQA組織論ではなく、より汎用的な考え方を扱う。

また、ソフトウェア開発やデータ領域の経験がある読者にとっては、既に知っている概念も含まれる。ただし、それらをQA職能の文脈で再整理することで、開発者視点やデータエンジニアリング視点とは異なる品質の見方を得ることを狙いとしている。

---

### 0.3 この資料で扱う範囲

この資料では、QA職能を理解するための基礎として、以下の範囲を扱う。

第一に、QA、QC、Testing、Quality Engineeringの違いを整理する。これにより、QAを単なるテスト実行ではなく、品質要求が満たされる状態を作るための活動として理解する。また、現代的な開発において、これらの関係が固定的な分業ではなく、連続的な役割領域として現れやすくなっている点も扱う。

第二に、ソフトウェア品質を複数の観点に分解する。機能が正しく動くかだけでなく、業務ルール、データ品質、権限、UX(User Experience:ユーザー体験)、運用品質、開発プロセス品質なども品質の一部として扱う。

第三に、QAが開発ライフサイクルのどこで関与するのかを整理する。後工程テストだけでなく、Shift Left Testing(開発初期段階へ品質活動を前倒しする考え方)、Shift Right Testing(リリース後の利用状況や運用情報から品質を確認する考え方)、Agile QA(アジャイル開発におけるQA)、DevOps(Development and Operations:開発と運用の連携)とContinuous Deliveryとの関係も扱う。

第四に、要求をテスト可能な形にする考え方を扱う。Acceptance Criteria(受け入れ条件)、Example Mapping(実例マッピング)、Specification by Example(SBE:実例による仕様記述)、TDD(Test-Driven Development:テスト駆動開発)、ATDD(Acceptance Test-Driven Development:受け入れテスト駆動開発)、BDD(Behavior-Driven Development:振る舞い駆動開発)などを、合意形成と検証可能性の観点から整理する。

第五に、テスト設計とテスト自動化を扱う。Risk-Based Testing(リスクベースドテスト)、Equivalence Partitioning(同値分割)、Boundary Value Analysis(境界値分析)、Decision Table Testing(デシジョンテーブルテスト)、State Transition Testing(状態遷移テスト)、Exploratory Testing(探索的テスト)などの基本的なテスト設計技法を扱う。また、Unit Test(単体テスト)、Integration Test(結合テスト)、API Test、E2E(End-to-End:エンドツーエンド) Test、Regression Test(回帰テスト)、Test Pyramid(テストピラミッド)、CI/CD上の品質ゲートについても整理する。

第六に、品質メトリクスとDQAを扱う。品質メトリクスは、QA活動や開発活動の状態を観測するためのデータである。一方、DQAは、プロダクト、業務、分析、意思決定に使われるデータそのものの品質を扱う。この2つは関連するが、同一ではない。本資料では、この違いを明確にする。

第七に、他職種連携とAI時代のQAを扱う。QAはQA担当者だけで完結する活動ではなく、プロダクトマネージャー(PM: Product Manager)、開発者、デザイナー、カスタマーサクセス(CS: Customer Success) / サポート、Data / Analytics(データ / 分析)などとの連携を通じて成立する。また、AIを使ったQA支援や、AIを組み込んだプロダクト自体のQAについても、基礎的な観点を整理する。

---

### 0.4 この資料で扱わない範囲

この資料では、以下の内容は主な対象としない。

- 特定企業のQA組織分析
- 特定企業への応募動機
- 特定プロダクトの品質戦略の断定
- QA実務経験者としての実績紹介
- 個人ポートフォリオの詳細な自己分析
- 特定のテスト自動化ツールの詳細な使い方
- ISO(International Organization for Standardization:国際標準化機構)規格やISTQB(International Software Testing Qualifications Board:国際ソフトウェアテスト資格認定委員会)シラバスの網羅的解説
- セキュリティテスト、性能テスト、アクセシビリティテストなどの専門領域の詳細

これらは、QAを深めるうえで重要な領域である。しかし、本資料の中心目的は、QA初学者が最初に持つべき全体像を整理することである。そのため、個別分野の詳細は必要に応じて別資料や専門文献に委ねる。

また、この資料は「QAとして何ができるか」を実績として主張する資料ではない。QA職能の基本構造を理解し、開発・データ・自動化・品質活動との接点を整理するための基礎資料である。

なお、個人ポートフォリオとQA / DQA / Quality Engineeringとの接続については、本資料では扱わず、別資料として整理する。

---

### 0.5 この資料の読み方

この資料は、前から順に読むことで、QA職能の理解が段階的に深まるように構成している。

まず、1〜2章では、QAとTestingの違い、QA / QC / Testing / Quality Engineeringの関係を整理する。ここでは、QAを「テスト実行」だけでなく「品質を作る仕組み」として捉えるための土台を作る。また、現代的な開発において、QA、Testing、Quality Engineeringの関係が固定的な分業だけでは捉えにくくなっていることも扱う。

次に、3〜7章では、ソフトウェア品質の分解、開発ライフサイクル上のQA関与、要求整理、テスト設計、テスト自動化を扱う。ここでは、QAがどのようにプロダクト開発の中で品質リスクを扱うのかを整理する。

8〜9章では、品質メトリクスとDQAを扱う。ここでは、品質を感覚だけでなくデータとして観測すること、またデータそのものを品質対象として扱うことを整理する。

10〜12章では、他職種連携、AI時代のQA、QA初学者が実務に入る際の学習観点を扱う。QAがチーム横断的な職能であり、今後も変化し続ける領域であることを確認する。

最後に、まとめでは、QAを「確認作業」ではなく、品質を扱いやすくする仕組みとして捉える視点を再確認する。
