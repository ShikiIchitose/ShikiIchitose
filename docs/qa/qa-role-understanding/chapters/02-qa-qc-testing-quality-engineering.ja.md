1章では、QA(Quality Assurance:品質保証)はTesting(テスト)を含むが、Testingそのものではないことを整理した。

この章では、QAと近い概念であるQC(Quality Control:品質管理)、Testing、Quality Engineering(品質エンジニアリング)、Quality Assistance / Quality Enablementを区別する。

これらの言葉は、組織や文脈によって使われ方が異なることがある。そのため、厳密な職務名として固定的に理解するよりも、品質活動の性質を整理するための概念として捉える方が実務に近い。

まずは、それぞれの基本的な意味を確認する。

---

### 2.1 QA(Quality Assurance:品質保証)

QA(Quality Assurance:品質保証)は、品質要求が満たされると判断できる状態を作るための活動である。

ここで重要なのは、QAを「最後に不具合を見つける活動」だけに限定しないことである。QAは、プロダクトが期待された品質を満たしているかを判断できるように、要求、仕様、設計、実装、テスト、リリース、運用後フィードバックの各段階に品質観点を組み込む活動として理解できる。

たとえば、QAには次のような活動が含まれる。

- 要求や仕様の曖昧さを見つける
- Acceptance Criteria(受け入れ条件)を明確にする
- 重要なリスクを整理する
- テスト観点を設計する
- テストしやすい設計を促す
- レビューや合意形成に品質観点を入れる
- 自動テストやCI/CD(Continuous Integration / Continuous Delivery:継続的インテグレーション / 継続的デリバリー)を品質ゲートとして活用する
- 不具合、問い合わせ、インシデント、利用ログなどを改善に還元する

QAの特徴は、予防的・仕組み化的な性質を持つことである。

不具合が発生した後に見つけることも重要だが、それだけでは品質活動が後工程に集中しやすい。QAでは、不具合が入り込みやすい条件、仕様の認識違いが生まれやすい箇所、テストしにくい設計、レビューされにくい変更、運用後に問題化しやすいリスクを早く見つけることも重視する。

その意味で、QAは「品質を保証する担当者が存在する」というよりも、「チームが品質要求を満たしていると判断できる状態を作る活動」と捉える方が自然である。

また、QAはQA担当者だけで完結するものではない。品質は、プロダクトマネージャー(PM: Product Manager)、開発者、デザイナー、カスタマーサクセス(CS: Customer Success) / サポート、営業、法務 / コンプライアンス、データ / 分析、SRE(Site Reliability Engineering:サイト信頼性エンジニアリング) / 運用など、複数の職種が関わって作られる。

QAエンジニアは、その中で品質に関する観点を整理し、リスクを言語化し、確認可能な形に落とし込み、チームが品質を継続的に扱えるよう支援する役割を持つ。

### 2.2 QC(Quality Control:品質管理)

QC(Quality Control:品質管理)は、作られた成果物が定められた基準を満たしているかを確認する活動である。

QAが品質を満たすためのプロセスや仕組みに重点を置くのに対し、QCは成果物そのものが期待された基準に合っているかを確認する性質が強い。

ソフトウェア開発の文脈では、QCには次のような活動が含まれる。

- 実装された機能が仕様を満たしているかを確認する
- テスト結果を確認する
- 不具合の有無を確認する
- レビュー結果を確認する
- リリース基準を満たしているかを確認する
- 欠陥数、重要度、修正状況などを確認する

QCは、検出的な性質を持つ。つまり、すでに作られたものに対して、期待される基準との差分を見つける活動である。

たとえば、ある機能について「承認済みの申請だけが次工程に進める」という仕様がある場合、実装後に実際の画面やAPIの挙動を確認し、未承認の申請が誤って次工程に進まないかを検査することはQC的な活動である。

ただし、QCはQAと対立するものではない。QCによって得られた不具合情報や品質情報は、QA活動の改善材料になる。たとえば、リリース直前に特定領域の不具合が多く見つかった場合、その情報は要求整理、設計レビュー、テスト設計、自動化、開発プロセス改善に還元できる。

つまり、QCは「成果物の確認」、QAは「品質を満たす状態を作る活動」と整理できる。ただし実務では、同じ担当者や同じチームがQA的活動とQC的活動の両方を担うことも多い。

### 2.3 Testing(テスト)

Testing(テスト)は、期待される挙動と実際の挙動を比較し、品質に関する情報を得る活動である。

Testingの目的は、単に「バグを見つけること」だけではない。欠陥を発見することは重要な目的の一つだが、それに加えて、プロダクトのリスクを明らかにすること、リリース判断に必要な情報を集めること、仕様や実装に対する理解を深めることもTestingの重要な役割である。

Testingには、さまざまな形がある。

- 手動テスト
- 探索的テスト
- Unit Test(単体テスト)
- Integration Test(結合テスト)
- API Test
- E2E(End-to-End:エンドツーエンド) Test
- Regression Test(回帰テスト)
- 受け入れテスト
- 性能、セキュリティ、アクセシビリティなどの専門的なテスト

TestingはQAの中核手段の一つである。しかし、TestingそのものがQA全体を意味するわけではない。

たとえば、あるAPIが不正な入力に対して適切なエラーを返すかを確認することはTestingである。一方、そのような入力条件を事前に洗い出し、仕様として明文化し、自動テストとして継続的に確認できるようにし、同様の不具合が再発しにくい状態を作ることは、より広いQA活動に含まれる。

また、Testingでは「何を確認するか」を決める前段階が非常に重要である。テストケースの数が多くても、重要なリスクを外していれば品質判断にはつながらない。逆に、テストケースの数が少なくても、業務上重要な条件、境界値、権限、状態遷移、障害時の挙動を的確に押さえていれば、品質リスクの把握に大きく貢献する。

したがって、Testingは「作られたものを動かして確認する作業」だけではなく、「品質に関する情報を得るための設計された活動」として捉える必要がある。

### 2.4 Quality Engineering(品質エンジニアリング)

Quality Engineering(品質エンジニアリング)は、品質をエンジニアリング上の設計対象として扱う考え方である。

QAが品質要求を満たす状態を作る活動だとすれば、Quality Engineeringは、その状態を技術的な仕組みとして支える側面が強い。品質を人間の注意力やリリース前の一括確認だけに依存させず、設計、自動化、CI/CD、可観測性、テスト容易性、開発者体験などに組み込む考え方である。

Quality Engineeringには、次のような観点が含まれる。

- テストしやすい設計にする
- 自動テストを設計・実装・保守する
- CI/CD上に品質ゲートを組み込む
- 変更時に素早くフィードバックを得られるようにする
- flaky testを減らし、テスト結果の信頼性を高める
- ログ、メトリクス、トレースなどの可観測性を整える
- リリース後の品質情報を継続的に取得する
- 開発者が品質を扱いやすい開発環境を整える

Quality Engineeringの特徴は、品質活動を「人が最後に頑張って確認するもの」ではなく、「開発プロセスとシステム設計に組み込むもの」として扱う点にある。

たとえば、毎回手動で確認していた回帰テストを自動化し、Pull Requestごとに実行する。APIの入力バリデーションを自動テストで保護する。リリース後のエラー率や異常ログを監視し、問題があれば早く検知できるようにする。これらはQuality Engineering的な活動である。

この領域では、QAと開発の距離が近くなる。QAエンジニアがテスト設計や品質観点の整理を担い、開発者が自動テストやテスト容易性の改善を担うこともある。逆に、QAエンジニアが自動化、CI/CD、ログ分析、品質メトリクスの整備に深く関わることもある。

SET(Software Engineer in Test) / SDET(Software Development Engineer in Test)は、このようなQuality Engineeringに近いDevelopment寄りの役割として理解しやすい。組織によって定義は異なるが、一般にはテスト実行そのものよりも、テスト自動化、テスト基盤、テスト容易性、CI/CD上の品質ゲート、開発者へのフィードバックを、コードや仕組みによって支える役割として扱われることが多い。

特に、Grey-box testing(グレーボックステスト)やWhite-box testing(ホワイトボックステスト)では、コード、アーキテクチャ、API(Application Programming Interface:アプリケーションプログラミングインターフェース)、DB(Database:データベース)スキーマ、ログ、状態遷移、データフローなどの理解が必要になりやすい。そのため、QA職能の中でも、SET / SDET的な開発寄り技能を持つ人材が重要になる場面がある。

ただし、SET / SDETという職務名の有無や責任範囲は組織によって異なる。そのため、本資料ではSET / SDETを独立した職種解説として深掘りするのではなく、Quality EngineeringのDevelopment寄りの一例として扱う。

このように、Quality Engineeringは、品質をチーム全体で継続的に扱うための技術的・構造的なアプローチである。

### 2.5 Quality Assistance / Quality Enablement

Quality Assistance / Quality Enablementは、QAがすべての確認を抱え込むのではなく、チーム全体が品質を扱えるように支援するためのアプローチである。

ここでいうQuality Assistance / Quality Enablementは、特定の職種名というより、QAの専門性を開発チーム全体へ広げるための支援モデルとして理解するとよい。組織によっては、Quality Assistance Engineerのように役職名やロール名として使われることもあるが、本資料では、固定的な職務名ではなく、現代的QAにおける運用スタイルの一つとして扱う。

組織によっては、Quality Assistance、Quality Enablement、Quality Coaching、Quality Advocacyなど、近い意味の言葉が使われることがある。いずれも共通しているのは、QA担当者が品質確認を一手に引き受けるのではなく、開発者、PM(Product Manager:プロダクトマネージャー)、Designer(デザイナー)、CS(Customer Success:カスタマーサクセス)、Support(サポート)などが、それぞれの立場から品質を考え、確認し、改善できる状態を目指す点である。

Quality Assistance / Quality Enablementには、次のような活動が含まれる。

- テスト観点をチームに共有する
- 仕様レビューやリファインメントで品質リスクを問いかける
- 開発者がテストを書きやすいように観点や例を整理する
- 受け入れ条件を明確にする支援を行う
- 不具合報告や再現手順の書き方を整える
- 品質メトリクスをチームで読める形にする
- 問い合わせやインシデントを品質改善の材料に変換する
- ドキュメントやチェックリストを整備する
- QAがボトルネックにならない確認フローを作る

このアプローチでは、QAは「最後に確認する人」ではなく、「チームが品質を扱えるようにする支援者」として動く。

たとえば、QAがすべてのテストケースを作成し、すべての確認を実行する体制では、機能追加やリリース頻度が増えるほどQAがボトルネックになりやすい。これに対して、Quality Assistance / Quality Enablementのアプローチでは、開発者、PM、デザイナー、サポート、CSなどがそれぞれの立場で品質観点を扱えるように、QAが観点、基準、仕組み、フィードバックを提供する。

これは、QAの役割が不要になるという意味ではない。むしろ、QAの専門性を、個別の確認作業だけでなく、チーム全体の品質能力を高める方向に使うというアプローチである。

Quality Assistance / Quality Enablementは、現代的QAにおける重要な方向性の一つである。プロダクトが複雑化し、リリース頻度が高まり、品質確認の対象が広がるほど、QAだけが品質を抱え込むのではなく、チーム全体で品質を扱える状態を作ることが重要になる。

### 2.6 現代的QAにおける役割領域の変化

ここまで、QA、QC、Testing、Quality Engineering、Quality Assistance / Quality Enablementを区別して整理した。

ただし、実務ではこれらが常に明確に分離されているわけではない。特に、アジャイル開発、DevOps(Development and Operations:開発と運用の連携)、Continuous Delivery(継続的デリバリー)、プロダクトの複雑化、リリース頻度の増加により、品質活動をリリース直前の確認だけに集約することは難しくなっている。

従来型の分業では、開発が完了した後にQAやテスト担当者が成果物を確認し、不具合を検出する流れが中心になることがあった。この形は、リリース前の欠陥検出や第三者的な確認という意味では今でも重要である。特に、安全性、法令、監査、契約、金銭、個人情報などに関わる領域では、独立性を持った確認や明確なリリース判定が必要になる。

一方で、現代的なソフトウェア開発では、品質リスクはリリース直前だけで発生するわけではない。要求が曖昧な段階、仕様の前提が関係者間でずれている段階、設計がテストしにくい段階、実装変更が既存機能に影響する段階、リリース後に実ユーザーの利用状況が明らかになる段階など、開発ライフサイクル全体に異なる品質リスクが存在する。

そのため、現代的QAでは、QAを「後工程で検査する役割」だけではなく、要求、仕様、設計、実装、テスト、自動化、リリース、運用後フィードバックにまたがって、品質を扱いやすくする活動として捉えることが重要になる。

#### 2.6.1 後工程集中型QAの限界

後工程集中型QAとは、開発や実装がある程度完了した後に、QAやテスト担当者がまとめて確認する形を指す。

この形には利点がある。実装済みの成果物を実際に操作し、仕様との差分や不具合を検出できる。また、開発者とは異なる視点から確認することで、思い込みや見落としを発見しやすくなる。リリース前に一定の品質情報を集めるという意味でも、後工程での確認は重要である。

しかし、後工程に品質確認が集中しすぎると、いくつかの問題が起きやすい。

第一に、仕様の曖昧さや認識違いが実装後に発見されると、手戻りが大きくなる。要求段階で確認できたはずの前提が、実装後のテストで初めて問題化すると、設計、実装、テストケース、ドキュメント、場合によってはリリース計画まで見直す必要が出る。

第二に、リリース直前に不具合が集中すると、QAがボトルネックになりやすい。機能追加や仕様変更が増えるほど、確認すべき対象は増える。すべての確認をQAが最後に抱える体制では、開発速度やリリース頻度に追従しにくくなる。

第三に、品質が個人の注意力に依存しやすくなる。経験豊富なQAがいれば多くのリスクを見つけられるが、その観点がテスト設計、自動テスト、ドキュメント、品質メトリクス、開発プロセスに組み込まれていなければ、再利用や継続的改善が難しい。

第四に、プロダクトの複雑化に対応しにくい。現代のソフトウェアでは、UI(User Interface:ユーザーインターフェース)、API(Application Programming Interface:アプリケーションプログラミングインターフェース)、DB(Database:データベース)、外部連携、権限、状態遷移、ログ、分析データ、AI(Artificial Intelligence:人工知能)機能などが複雑に関係する。後工程の画面確認だけでは、内部構造やデータフローに起因する品質リスクを十分に扱いきれないことがある。

そのため、後工程での確認は必要である一方、それだけに依存するのではなく、より早い段階から品質観点を組み込み、変更ごとに継続的に確認できる仕組みを作る必要がある。

#### 2.6.2 Shift Leftによる早期関与

Shift Left Testing(シフトレフトテスト)は、品質活動やテスト活動を開発ライフサイクルのより早い段階へ移す考え方である。

ここでいう「Left」は、開発工程を左から右へ進む流れとして見たときの左側、つまり要求、仕様、設計、実装初期の段階を指す。リリース直前にまとめて確認するのではなく、要求や仕様が固まる前から品質観点を入れることで、認識違い、曖昧な条件、未決定事項、テストしにくい設計を早く見つける。

Shift Leftの目的は、単にテスト開始時期を早めることではない。重要なのは、品質リスクを早い段階で見える化し、手戻りを減らすことである。

たとえば、要求整理の段階では、次のような問いが有効である。

- 何が満たされれば、この機能は完了と言えるのか
- 正常系だけでなく、異常系や境界条件は定義されているか
- 権限によって見える情報や実行できる操作は変わるか
- 状態遷移に不自然な抜けや戻りはないか
- 外部連携やデータ更新が失敗した場合、どう扱うか
- その仕様はテスト可能な形で表現されているか

このような問いは、5章で扱うAcceptance Criteria(受け入れ条件)、Example Mapping(実例マッピング)、Specification by Example(SBE:実例による仕様記述)、ATDD(Acceptance Test-Driven Development:受け入れテスト駆動開発)、BDD(Behavior-Driven Development:振る舞い駆動開発)とも接続する。

また、Shift Leftは開発者の活動とも密接に関わる。Unit Test(単体テスト)、Integration Test(結合テスト)、API Test、自動化されたRegression Test(回帰テスト)、Pull Requestレビュー、静的解析、型チェック、lintなどを早い段階で組み込むことで、変更に対するフィードバックを速く得られる。

この意味で、Shift LeftはQAだけの活動ではない。QA、開発者、PM、デザイナー、データ担当者などが、早い段階から品質に関する前提を揃えるための考え方である。

#### 2.6.3 Shift Rightによるリリース後の品質確認

Shift Right Testing(シフトライトテスト)は、リリース後の実利用環境や運用情報から品質を確認する考え方である。

リリース前のテストで多くのリスクを確認できたとしても、production環境でしか見えない品質がある。実ユーザーの利用パターン、実データの分布、外部サービスの遅延、アクセス集中、運用手順の抜け、問い合わせ傾向、予期しない入力や組み合わせは、事前のテスト環境だけでは完全には再現できない。

Shift Rightでは、リリース後の情報を品質改善に還元する。

たとえば、次のような情報が品質活動の材料になる。

- エラーログ
- パフォーマンスメトリクス
- 監視アラート
- インシデント記録
- 問い合わせやサポートチケット
- 利用ログ
- Feature flag(機能フラグ)による段階的リリース結果
- A/B testing(A/Bテスト)の結果
- ユーザーフィードバック

これらは、単に運用担当者だけが見る情報ではない。QAにとっても、リリース前のテスト設計では見えなかったリスクや、実利用における品質課題を知るための重要な情報である。

たとえば、問い合わせが多い箇所は、単なるサポート課題ではなく、仕様の分かりにくさ、UX(User Experience:ユーザー体験)上の問題、エラーメッセージの不十分さ、ドキュメント不足を示している可能性がある。特定のAPIでエラー率が高い場合、入力バリデーション、外部連携、リトライ設計、テストデータ、監視条件を見直す必要があるかもしれない。

Shift Rightは、Shift Leftと対立するものではない。早い段階で品質を作り込み、リリース後に実利用から学び、その学びを次の要求、設計、テスト、自動化、監視へ還元する。このフィードバックループが重要である。

#### 2.6.4 DevOps / Continuous Deliveryによる継続的フィードバック

DevOpsやContinuous Deliveryの考え方では、開発、テスト、リリース、運用を分断せず、変更を小さく継続的に届けられる状態を目指す。

この文脈では、品質確認もリリース直前の一括作業ではなく、開発プロセスの中に継続的に組み込まれる。変更が加わるたびに、自動テスト、静的解析、ビルド、セキュリティチェック、データテスト、デプロイ検証などを実行し、早い段階でフィードバックを得る。

CI/CD(Continuous Integration / Continuous Delivery:継続的インテグレーション / 継続的デリバリー)上の品質ゲートは、その代表例である。

品質ゲートには、次のようなものが含まれる。

- lint
- type check
- unit test
- integration test
- API test
- E2E(End-to-End:エンドツーエンド) Test
- regression test
- build check
- security scan
- schema validation
- dbt test
- smoke test
- deployment check

これらは、QA担当者の確認作業を単に置き換えるものではない。変更時に期待状態を継続的に確認し、リグレッションを早期に検知し、リリース可能な状態を保つための仕組みである。

Continuous Deliveryの文脈では、ソフトウェアをいつでも安全にリリースできる状態に保つことが重視される。そのためには、品質確認を人間の記憶やリリース直前の集中確認に依存させず、再現可能なテスト、自動化された検証、安定したデプロイ手順、監視とフィードバックの仕組みを整える必要がある。

この領域では、QA、開発者、SRE(Site Reliability Engineering:サイト信頼性エンジニアリング)、Platform Engineering(プラットフォームエンジニアリング)、Data Engineering(データエンジニアリング)などの関係が近くなる。品質は、単一の職種が最後に確認するものではなく、開発・運用・データ・プロセスに組み込まれるものとして扱われる。

#### 2.6.5 QA / Testing / Quality Engineeringの接近

Shift Left、Shift Right、DevOps、Continuous Delivery、自動化、可観測性が進むと、QA、Testing、Quality Engineeringの関係は近くなる。

Testingは、品質に関する情報を得るための重要な手段である。QAは、そのTestingを含みながら、品質要求が満たされる状態を作る活動である。Quality Engineeringは、その状態を技術的な仕組みとして支える考え方である。

従来の整理では、これらは区別して理解できる。

- Testingは、期待される挙動と実際の挙動を比較する活動である
- QAは、品質要求が満たされる状態を作る活動である
- Quality Engineeringは、品質を技術的な仕組みとして組み込む考え方である

しかし実務では、これらが重なって現れる。

たとえば、QAエンジニアがAcceptance Criteriaを整理し、テスト観点を設計し、APIテストを自動化し、CI上で実行し、リリース後のログを見て次のテスト設計を改善する場合、その活動はTesting、QA、Quality Engineeringの要素を同時に含んでいる。

また、開発者がUnit TestやIntegration Testを書き、テストしやすい設計にし、ログを整備し、Feature flagで段階的にリリースし、ユーザー影響を見ながら改善する場合も、開発活動の中にQuality Engineering的な品質活動が含まれている。

つまり、現代的な開発では、QA、Testing、Quality Engineeringを完全に分離された箱として見るよりも、品質活動の性質が重なり合う領域として捉える方が実務に近い。

### 2.7 QA / QE / Testingを固定的な役割ではなくスペクトラムとして捉える

QA、QE(Quality Engineering:品質エンジニアリング)、Testingの違いを理解することは重要である。概念を区別できなければ、QAを単なるテスト実行と誤解したり、TestingとQuality Engineeringの役割を混同したりしやすくなる。

一方で、それらを固定的な職務名としてだけ捉えると、現代的な開発現場で行われている品質活動を説明しにくくなる。

実務上は、QA、QE、Testingを「どの職種が担当するか」だけで見るのではなく、品質活動がどのような性質を持つかというスペクトラムとして捉える方が理解しやすい。

#### 2.7.1 固定的な職務名ではなく、品質活動の分布として見る

QA Engineer、Quality Engineer、Test Engineer、Test Automation Engineer、SET(Software Engineer in Test)、SDET(Software Development Engineer in Test)などの職務名は、組織によって意味が異なることがある。

ある組織では、QA Engineerが手動テスト、探索的テスト、不具合報告、リリース前確認を中心に担うかもしれない。別の組織では、同じQA EngineerがAPIテスト、自動テスト、CI/CD、ログ分析、品質メトリクスまで担うかもしれない。また、Quality EngineerやSET / SDETが、テスト基盤、自動化、テスト容易性、開発者支援を中心に担うこともある。

そのため、職務名だけを見て役割を決めつけると、実態を誤解しやすい。

より重要なのは、その人やチームがどのような品質活動を担っているかである。

- 不具合を検出する活動か
- 不具合が生まれにくい状態を作る活動か
- 人間の判断を中心とする活動か
- 自動化や仕組み化を中心とする活動か
- 後工程で確認する活動か
- 開発プロセスの中に品質を組み込む活動か
- プロダクトの外部挙動を見る活動か
- 内部構造、コード、API、DB、ログ、データフローまで見る活動か

このように見ると、QA / QE / Testingは単純な職務名ではなく、品質活動の分布として理解できる。

#### 2.7.2 検出寄りの活動と予防寄りの活動

現代的なQAを理解するうえでは、品質活動を「検出寄り」と「予防寄り」の連続的な軸で捉えると分かりやすい。

ここで注意すべきなのは、QAという概念そのものは、本来、品質要求が満たされる状態を作るための予防的・プロセス志向の活動であるという点である。一方で、従来型の運用では、QA担当者の活動がリリース前の確認、テスト実行、不具合検出といった後工程・検出寄りの作業に集中することがあった。

そのため、本節では「QAは検出寄りである」と整理するのではなく、実務上の品質活動には検出寄りの活動と予防寄りの活動があり、現代的QAではその両方を扱う必要がある、という観点で整理する。

この軸で見ると、検出寄りの活動は、すでに作られた成果物に対して、期待と実際の差分を見つける活動である。

たとえば、次のような活動が含まれる。

- 実装後の機能確認
- 手動テスト
- 探索的テスト
- リリース前の回帰テスト
- 不具合報告
- リリース判定に必要な品質情報の収集
- 障害発生後の再現確認

これらは、TestingやQCに近い性質を持つ。従来型のQA運用では、QA担当者の作業がこの検出寄りの活動に集中することもあった。

一方、予防寄りの活動は、不具合が入り込みにくい状態や、早く検知できる状態を作る活動である。

たとえば、次のような活動が含まれる。

- 要求や仕様の曖昧さを早期に見つける
- Acceptance Criteriaを明確にする
- Example Mapping(実例マッピング)でルール、例、質問を整理する
- テストしやすい設計を促す
- 自動テストを整備する
- CI/CD上に品質ゲートを組み込む
- リリース後の品質情報を次の改善に還元する
- よく起きる不具合を再発防止の仕組みに変える

これらは、QAやQuality Engineeringに近い性質を持つ。特に現代的QAでは、リリース前の検出だけでなく、要求、仕様、設計、実装、CI/CD、運用後フィードバックに予防的な品質活動を組み込むことが重要になる。

ただし、検出と予防は対立するものではない。検出によって得られた不具合情報は、予防のための改善材料になる。逆に、予防的な仕組みがあっても、実際の成果物を確認する活動は必要である。

重要なのは、品質活動が検出だけに偏っていないか、また予防だけを重視して実際のユーザー影響を見落としていないかを確認することである。

#### 2.7.3 人間の判断寄りの活動と自動化・仕組み化寄りの活動

二つ目の軸は、人間の判断寄りの活動と、自動化・仕組み化寄りの活動である。

人間の判断寄りの活動には、仕様の妥当性、業務上の自然さ、UX上の違和感、未知のリスク探索などが含まれる。

たとえば、次のような活動である。

- 探索的テスト
- 仕様レビュー
- 業務ルールの妥当性確認
- ユーザー導線の違和感の発見
- エラーメッセージが、ユーザーや運用担当者が次に取るべき行動を示しているかの確認
- 問い合わせ内容から品質課題を読み取る
- リスクの優先順位を関係者と議論する

これらは、自動化だけでは扱いにくい。人間のドメイン理解、文脈理解、違和感、仮説形成が重要になる。

一方、自動化・仕組み化寄りの活動には、繰り返し確認できる期待状態をコードやシステムに組み込む活動が含まれる。

たとえば、次のような活動である。

- Unit Test
- Integration Test
- API Test
- E2E Test
- Regression Test
- CI/CD上の品質ゲート
- static analysis
- type check
- lint
- schema validation
- alerting
- dashboard
- test data management
- flaky test対策

これらは、変更時に素早くフィードバックを得るために重要である。特に、リリース頻度が高いプロダクトでは、毎回人間が同じ確認を繰り返すだけでは限界がある。

SET / SDETのような役割は、この軸では自動化・仕組み化寄りに位置づく。テスト実行そのものよりも、テスト基盤、自動化、CI/CD、テスト容易性、開発者へのフィードバックをコードや仕組みによって支えるためである。

ただし、人間の判断と自動化は対立しない。人間が重要なリスクを発見し、そのうち繰り返し確認すべきものを自動化する。自動テストの結果から異常に気づき、人間が原因や業務影響を判断する。このように、両者は補完関係にある。

#### 2.7.4 後工程確認寄りの活動と開発プロセス組み込み寄りの活動

三つ目の軸は、後工程確認寄りの活動と、開発プロセス組み込み寄りの活動である。

後工程確認寄りの活動は、実装された成果物を対象に、リリース前またはリリース後に品質を確認する活動である。

たとえば、次のような活動が含まれる。

- 実装後のシステムテスト
- 受け入れテスト
- リリース前の回帰テスト
- 本番リリース後の確認
- 障害後の再現確認
- 問い合わせを受けた後の原因調査

これらは、成果物が実際に期待どおり動くかを確認するうえで重要である。

一方、開発プロセス組み込み寄りの活動は、要求、仕様、設計、実装、レビュー、CI/CD、運用フィードバックの中に品質観点を組み込む活動である。

たとえば、次のような活動が含まれる。

- 要求段階での曖昧さの発見
- 受け入れ条件の明確化
- 仕様レビュー
- テストしやすい設計の検討
- Pull Request単位の自動テスト
- CI/CD上の品質ゲート
- Feature flagを使った段階的リリース
- リリース後ログからの学習
- インシデントや問い合わせを次の改善に還元する

この軸は、Shift LeftとShift Rightの両方に関係する。Shift Leftは、要求や設計など早い段階に品質観点を入れる。Shift Rightは、リリース後の実利用や運用情報を品質改善に還元する。どちらも、品質活動を一回限りの後工程確認に閉じないための考え方である。

#### 2.7.5 実務ではプロダクト特性・組織体制・リスクによって形が変わる

QA / QE / Testingの分担は、プロダクト特性、組織体制、リリース頻度、ドメインリスクによって変わる。

小規模な組織や少人数のプロダクトチームでは、PdE(Product Engineer:プロダクトエンジニア)やBackend Engineer(バックエンドエンジニア)が、Quality EngineeringやSET / SDET的な活動を部分的に担うこともある。たとえば、自動テストの実装、CI/CD上の品質ゲート、ログを用いた不具合調査、テストしやすい設計、APIやDBを踏まえたGrey-box testing(グレーボックステスト)などである。

一方で、プロダクトや組織が大きくなるほど、テスト基盤、テストデータ、E2E Test、flaky test対策、横断的な品質メトリクス、複数チーム間の品質基準の整備が複雑になる。その場合は、Quality Engineer、SET、SDET、Test Automation Engineer(テスト自動化エンジニア)のような専門性を持つ役割が必要になりやすい。

また、業務ドメインによっても重視される品質活動は変わる。

金銭、給与、契約、法令、個人情報、医療、安全性などに関わる領域では、仕様の正確性、監査可能性、権限、履歴、データ整合性が重要になる。この場合、テスト実行だけでなく、要求整理、業務ルールの明文化、状態遷移、データ品質、証跡、レビュー手順が重要になる。

一方、ユーザー体験や高速な機能改善が重視されるプロダクトでは、探索的テスト、利用ログ、問い合わせ、A/B testing、Feature flag、リリース後の学習が重要になることもある。

つまり、QA / QE / Testingの理想的な分担は一つではない。重要なのは、職務名にとらわれすぎず、そのプロダクトにとって重要な品質リスクを誰が、どの段階で、どの仕組みを使って扱うのかを明確にすることである。

このように捉えると、QA / QE / Testingは固定的な箱ではなく、品質活動のスペクトラムとして理解できる。

### 2.8 Key Takeaways

この章では、QA(Quality Assurance:品質保証)、QC(Quality Control:品質管理)、Testing(テスト)、Quality Engineering(品質エンジニアリング)、Quality Assistance / Quality Enablementを、固定的な職務名ではなく、品質活動の性質を整理するための概念として扱った。

QAはTestingを含むが、Testingそのものではない。Testingは品質に関する情報を得るための重要な手段であり、QCは作られた成果物が基準を満たしているかを確認する活動である。一方で、QAは品質要求が満たされると判断できる状態を作る活動であり、Quality Engineeringはその状態を技術的な仕組みとして支える考え方である。

現代的な開発では、品質活動はリリース直前の確認だけに閉じない。要求、仕様、設計、実装、CI/CD、リリース後フィードバックまで品質活動の対象が広がるため、QA / QE / Testingは固定的な役割分担ではなく、検出寄り・予防寄り、人間の判断寄り・自動化寄り、後工程確認寄り・開発プロセス組み込み寄りといったスペクトラムとして理解する方が実務に近い。

- QA(Quality Assurance:品質保証)は、品質要求が満たされると判断できる状態を作るための活動であり、Testing(テスト)そのものではない。
- QC(Quality Control:品質管理)は、作られた成果物が基準を満たしているかを確認する活動であり、Testingはその主要な手段の一つである。
- Quality Engineering(品質エンジニアリング)は、品質を設計、自動化、CI/CD、可観測性、テスト容易性などの技術的な仕組みに組み込む考え方である。
- Quality Assistance / Quality Enablementは、QAがすべての確認を抱え込むのではなく、チーム全体が品質を扱えるよう支援するアプローチである。
- 現代的QAでは、後工程の確認だけでなく、要求、仕様、設計、実装、CI/CD、リリース後フィードバックまで品質活動の対象が広がっている。
- QA / QE / Testingは固定的な職務名だけで理解するよりも、検出寄り・予防寄り、人間の判断寄り・自動化寄り、後工程確認寄り・開発プロセス組み込み寄りといったスペクトラムで捉えると理解しやすい。
- 実務上の役割分担は、プロダクト特性、組織体制、リリース頻度、ドメインリスクによって変わる。
