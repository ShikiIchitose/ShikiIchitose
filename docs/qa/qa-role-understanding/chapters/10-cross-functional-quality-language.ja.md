## 10. 他職種連携と品質の言語化

9章では、DQA(Data Quality Assurance / Data Quality Assessment:データ品質保証 / データ品質評価)を、データそのものを品質対象として扱う活動として整理した。

データ品質の問題は、QA(Quality Assurance:品質保証)だけでは完結しない。データの欠損、不整合、定義の曖昧さ、更新遅延、指標の解釈違いは、入力仕様、業務ルール、画面設計、API(Application Programming Interface:アプリケーションプログラミングインターフェース)、データ連携、ダッシュボード、運用手順など、複数の領域にまたがって発生する。

この構造は、データ品質に限らない。ソフトウェア品質全体を見ても、機能が仕様どおりに動くか、業務ルールに合っているか、ユーザーが迷わず使えるか、データが信頼できるか、権限や監査に問題がないか、障害時に調査・復旧できるかは、複数の職種の視点によって見えてくる。

つまり、品質問題の多くは、一つの職種や一つの工程だけでは捉えきれない。

4章で扱ったように、QAの関与には、リリース前や受け入れ前に成果物を確認する後工程QA、開発プロセス内で継続的に品質観点を入れるインプロセスQA、リリース後の問い合わせ、ログ、監視、インシデント、ユーザーフィードバックから品質を確認するShift Rightの活動がある。これらは互いに排他的ではなく、いずれの形でも、QAは他職種との接点を持つ。

この章で扱うのは、QAがどのタイミングで関与するかという工程分類そのものではない。むしろ、後工程QA、インプロセスQA、Shift Rightの活動を横断して必要になる、品質情報・品質観点・判断基準をつなぐ活動である。

この考え方は、2章で扱ったQuality Assistance(品質支援) / Quality Enablement(品質を扱える状態にする支援)ともつながる。QAは、各職種が持つ情報、違和感、懸念、判断基準を品質観点として整理し、チームや組織が品質を扱いやすい状態を作る。

10章では、他職種連携を単なるコミュニケーションではなく、品質に関する情報を、関係者が判断・改善に使える言葉へ変換する活動として整理する。

---

### 10.1 品質はQAだけで決まらない: 職種ごとの品質観点

品質は、QAだけで決まるものではない。

QAは、品質リスクを見つけ、テスト観点を整理し、確認可能な形に落とし込み、リリース判断や改善に必要な情報を提供する。しかし、プロダクトの品質は、QA以外の職種が持つ視点や情報によっても支えられる。

プロダクトマネージャー(PM: Product Manager)は顧客価値や優先順位を見ている。開発者は実装品質、保守性、テスト容易性を見ている。デザイナーはUX(User Experience:ユーザー体験)や誤操作の防止を見ている。カスタマーサクセス(CS: Customer Success) / サポートは、顧客が実際にどこでつまずいているかを知っている。営業、法務 / コンプライアンス、データ / 分析、SRE(Site Reliability Engineering:サイト信頼性エンジニアリング) / 運用も、それぞれ異なる品質情報を持っている。

これは、どれか一つの視点が正しく、他が間違っているということではない。プロダクト品質が多面的であるため、立場によって見えやすい品質リスクが異なるということである。

これらを整理すると、次のようになる。

| 職種 | 重視しやすい品質観点 | QAとの接続 |
|---|---|---|
| プロダクトマネージャー(PM) | 顧客価値、スコープ、優先順位、リリース判断 | 要求、受け入れ条件、リスク、残課題を確認可能な形にする |
| 開発者 | 実装品質、保守性、テスト容易性、変更容易性 | テスト観点、自動化、品質ゲート、設計上のリスクを共有する |
| デザイナー | UX、誤操作防止、情報設計、分かりやすさ | ユーザーが迷う箇所、エラー時の行動、画面上の認識違いを確認する |
| CS / サポート | 顧客のつまずき、問い合わせ、運用上の困難 | 問い合わせを品質課題、テスト観点、改善候補へ変換する |
| 営業 | 顧客期待、導入時の懸念、契約・運用上の制約 | 期待値のずれ、制約説明、導入時リスクを要求整理へ戻す |
| 法務 / コンプライアンス | 法令、規約、監査、説明責任、リスク管理 | 権限、ログ、同意、証跡、データ保持などを品質観点として扱う |
| データ / 分析 | 指標定義、データ品質、集計条件、意思決定可能性 | データ品質、指標の意味、ダッシュボードの解釈可能性を確認する |
| SRE / 運用 | 監視、復旧性、障害対応、運用負荷、インシデントからの学習 | ログ、アラート、切り戻し、Postmortem(ポストモーテム)、運用改善へ接続する |

この表は、職種ごとの責任範囲を固定するためのものではない。

実務では、組織によって職種名や分担は異なる。小さなチームでは、一人が複数の役割を兼ねることもある。逆に、大きな組織では、セキュリティ(Security)、アクセシビリティ(Accessibility)、プライバシー(Privacy)、データガバナンス(Data Governance)、カスタマーオペレーション(Customer Operations)など、より専門的なチームが関わることもある。

重要なのは、職種名そのものではなく、品質に関する情報がどこに存在するかを理解することである。

QAが見るべきなのは、「誰が品質を担当しているか」だけではない。「どの品質情報が、どの職種や業務の中に埋もれているか」である。問い合わせの中にUX品質の問題が埋もれていることもあれば、商談時の懸念の中に要求や制約の問題が埋もれていることもある。インシデント対応の記録の中に、設計、監視、リリース判断の改善点が埋もれていることもある。

QAは、それらの情報を拾い上げ、品質観点として整理し、関係者が判断しやすい形にする。

そのため、他職種連携を単なるコミュニケーション能力の問題として扱うべきではない。重要なのは、品質に関する情報を、関係者間で共有可能な言葉、記録、判断材料、改善アクションへ変換することである。

次節では、このような職種ごとの言葉や違和感を、どのように品質観点へ変換するかを整理する。

---

### 10.2 品質観点を共通言語に変換する

10.1では、プロダクトマネージャー(PM: Product Manager)、開発者、デザイナー、カスタマーサクセス(CS: Customer Success) / サポート、営業、法務 / コンプライアンス、データ / 分析、SRE(Site Reliability Engineering:サイト信頼性エンジニアリング) / 運用など、職種ごとに見えやすい品質情報が異なることを整理した。

次に重要なのは、それらの情報を、関係者が議論し、判断し、改善できる言葉に変換することである。

ここでいう共通言語とは、すべての職種に同じ専門用語を使わせることではない。ある職種で見えている違和感、困りごと、懸念を、他の職種も判断や改善に使える品質課題として整理することである。

品質に関する問題は、最初から「機能品質」「UX(User Experience:ユーザー体験)品質」「データ品質」「運用品質」のような整理された言葉で現れるとは限らない。むしろ、最初は次のような曖昧な言葉として出てくることがある。

- 使いにくい
- なんとなく不安
- 問い合わせが多い
- 数字が合わない
- 運用がつらい
- リリース後の手戻りが多い
- 顧客に説明しにくい
- 仕様としては正しいが、現場では使いづらい

これらは、単なる感想として流してしまうと扱いにくい。しかし、QA(Quality Assurance:品質保証)の観点では、こうした違和感の中に、重要な品質リスクが含まれている可能性がある。

たとえば、「使いにくい」という言葉には、画面導線の問題、情報設計の問題、エラーメッセージの分かりにくさ、業務フローとの不一致、ドキュメント不足などが含まれているかもしれない。

「数字が合わない」という言葉には、データ品質、指標定義、集計条件、対象期間、除外条件、更新タイミング、画面表示とダッシュボードの不一致などが含まれている可能性がある。

「運用がつらい」という言葉には、手作業が多すぎる、例外対応が多い、障害時の切り戻し手順が曖昧である、ログや監視が不足している、問い合わせ対応に必要な情報が画面上で確認しにくい、といった運用品質の問題が含まれていることがある。

このように、QAは、曖昧な言葉をそのまま受け取るのではなく、その背後にある品質観点を整理する必要がある。

整理の例を示すと、次のようになる。

| 現場で出てくる言葉 | 品質観点としての整理 | 確認すべき問い |
|---|---|---|
| 顧客が迷っている | UX品質、ドキュメント品質、仕様理解の問題 | どの画面、どの操作、どの用語で迷っているのか |
| 問い合わせが多い | 仕様の曖昧さ、導線不足、エラーメッセージ不足 | 問い合わせは特定機能、特定操作、特定ユーザー層に集中しているか |
| 数字が信用できない | データ品質、指標定義、集計条件の問題 | 何を数えているのか、対象期間や除外条件は明確か |
| 運用がつらい | 運用品質、保守性、例外対応の多さ | 手作業、判断待ち、障害対応、問い合わせ対応のどこに負荷があるか |
| 顧客に説明しにくい | 仕様理解、制約説明、ドキュメント品質 | 仕様、制約、既知の制限、回避策が説明可能な形になっているか |
| リリース後の手戻りが多い | 要求整理、テスト設計、品質ゲート、運用準備の問題 | どの段階で見つけられたはずの問題か、どの確認が不足していたか |

たとえば、CS / サポートから次のような情報が共有されたとする。

> 最近、管理者向けのユーザー招待・権限設定画面について問い合わせが増えている。  
> 特に「ユーザーを招待したのに、対象機能が使えない」という問い合わせが多い。

この情報は、そのままでは「問い合わせが多い」という粗い情報である。原因が仕様なのか、UX品質なのか、権限設計なのか、ドキュメント不足なのか、実装不具合なのかは分からない。

QAはまず、この情報を品質課題として扱える形に整理する。

この仮想例では、現行仕様として、ユーザー招待はアカウント作成・参加招待の操作であり、対象機能の利用権限は管理者が別途付与する必要があるとする。一方で、問い合わせ内容からは、管理者が「ユーザーを招待すれば、自動的に対象機能の利用権限も付与される」と理解している可能性が見えてくる。

このように整理すると、「問い合わせが多い」という情報は、次のような品質課題候補として扱えるようになる。

> 権限設定フローにおいて、ユーザー招待と権限付与の関係が分かりにくい。  
> その結果、管理者が必要な設定を完了できず、招待されたユーザーが対象機能を使えない。

この品質課題は、一つの職種だけで解決できるとは限らない。QAは、関係する職種がそれぞれ判断・改善に使える形へ変換する。

| 共有先 | 変換後の観点 |
|---|---|
| プロダクトマネージャー(PM) | 導入体験、顧客影響、改善優先度、仕様として招待と権限付与を分ける妥当性 |
| 開発者 | 権限状態、API(Application Programming Interface:アプリケーションプログラミングインターフェース)の認可、権限未付与時の挙動、テスト観点、調査用ログ |
| デザイナー | 招待完了後の導線、次に必要な操作の見え方、誤解しにくい文言、権限未付与状態の表示 |
| CS / サポート | 問い合わせ分類、FAQ(Frequently Asked Questions:よくある質問)改善、導入初期の顧客向け案内、再発傾向の把握 |
| 法務 / コンプライアンス | 自動権限付与の可否、管理者の明示的操作、権限変更履歴、監査ログ、利用規約や関連ポリシーへの影響 |
| データ / 分析 | 招待済みだが権限未付与のユーザー数、権限未付与によるアクセス拒否回数、導入初期顧客での発生傾向 |
| SRE / 運用 | 権限状態を調査できるログ、サポート調査手順、アクセス拒否の監視、運用負荷 |

この例で重要なのは、QAが各職種に別々の問題を投げているわけではないという点である。

中心にある品質課題は、「ユーザー招待と権限付与の関係が分かりにくく、管理者が設定を完了できていない」という一点である。ただし、その課題を改善するには、プロダクトマネージャーには優先度判断の材料として、開発者には実装・テスト・ログの観点として、デザイナーには導線や文言の問題として、CS / サポートには問い合わせ分類やFAQ改善として、法務 / コンプライアンスには権限・証跡・説明責任として、データ / 分析には発生傾向として、SRE / 運用には調査性や運用負荷として伝わる必要がある。

つまり、共通言語に変換するとは、各職種の言葉を一つの専門用語に統一することではない。各職種が持つ情報を、プロダクト品質を判断するための材料として接続し、関係者が同じ品質課題について会話できる状態を作ることである。

この例では、職種ごとの観点を分かりやすく一覧化している。実際には、すべての職種へ同時に同じ深さで確認するわけではない。QAが問い合わせ内容を一次整理し、関係度の高い職種へ順次または並行して確認し、得られた回答、制約、データ、改善案を整理したうえで、必要に応じて関係者MTG(Meeting:会議)で改善方針を調整する。

また、確認は会議だけで行うとは限らない。チャット、Issue Tracker、共有ドキュメントなどを使って、問い合わせ内容、仮説、確認事項、回答を非同期に整理することもある。たとえば、Slackのようなチャット、JiraやGitHub IssuesのようなIssue Tracker(課題管理ツール)、NotionやGoogle Docsのような共有ドキュメントが使われる場合がある。

より具体的な流れは、章末のAppendix 10-A『「問い合わせが多い」を品質課題へ変換する実務シミュレーション』を参照されたい。

このように整理することで、品質に関する会話は、感覚的な不満や個別の困りごとから、具体的な確認対象、改善対象、判断材料へ変わる。

品質観点を共通言語に変換する活動は、単なる説明能力ではない。品質リスクを見える化し、関係者の前提を揃え、改善に向けた会話を可能にするためのQA活動である。

### 10.3 顧客の困りごとを品質課題に変換する

10.2では、職種ごとに異なる言葉や違和感を、品質観点として整理する考え方を扱った。

その中でも、CS / サポートが持つ顧客接点情報は、QAにとって特に重要な入力情報になる。

なぜなら、顧客の問い合わせや困りごとは、リリース前のテストだけでは見えなかった品質問題を表していることがあるからである。画面やAPIが仕様どおりに動いていても、ユーザーが操作に迷っている、仕様を誤解している、エラーメッセージから次の行動を判断できない、権限設定でつまずいている、必要な情報にたどり着けない、ということは起こり得る。

このような情報を、単なる個別対応として終わらせると、同じ類の困りごとが繰り返されやすい。

たとえば、あるユーザーが操作方法を誤解した場合、その一件だけをサポートで解決することは必要である。しかし、同じ問い合わせが繰り返されているなら、それは個人の操作ミスだけではなく、仕様の分かりにくさ、画面導線、用語、ドキュメント、権限設計、エラーメッセージなどの品質課題として扱う余地がある。

顧客の困りごとを品質課題として扱うには、まず問い合わせを分類する必要がある。

分類の例を示すと、次のようになる。

| 顧客接点で見える困りごと | 品質課題としての見方 | 改善への戻し先 |
|---|---|---|
| 操作方法が分からない | UX品質、情報設計、ドキュメント品質 | 画面導線、ヘルプ、チュートリアル、用語説明 |
| 仕様を誤解している | 要求・仕様の説明不足、期待値のずれ | 仕様説明、受け入れ条件、FAQ、リリースノート |
| エラーの意味が分からない | エラーメッセージ、例外処理、回復可能性の問題 | エラー文言、入力補助、再試行手順、ログ |
| 権限設定でつまずく | セキュリティ・権限品質、管理画面の分かりにくさ | 権限設計、管理者向け説明、権限テスト観点 |
| 数値やレポートを信用できない | データ品質、指標定義、集計条件の問題 | データ定義、集計仕様、ダッシュボード説明 |
| 同じ作業を何度も手動で行っている | 運用品質、業務フロー、効率性の問題 | 業務フロー改善、自動化候補、管理機能改善 |
| リリース後に想定外の問い合わせが増えた | 事前の影響整理、テスト設計、周知不足 | リリース前確認、リリースノート、問い合わせ分類、回帰観点 |

ここで重要なのは、問い合わせを「ユーザーの理解不足」として処理しないことである。

もちろん、ユーザー側の操作ミスや確認漏れが原因になることもある。しかし、その操作ミスが起きやすい画面設計になっていないか、誤解しやすい用語を使っていないか、必要な制約が事前に説明されているか、エラー時に次の行動が分かるかを確認することは、QAの重要な観点である。

顧客接点情報は、Shift Rightの活動とも接続する。

Shift Rightでは、リリース後の実利用、問い合わせ、ログ、監視、インシデント、ユーザーフィードバックから品質を学び、次の要求、仕様、テスト、自動化、監視、運用改善へ戻す。顧客の困りごとは、その中でも、実際の利用文脈から得られる重要な品質情報である。

たとえば、問い合わせから得られた情報は、次のように開発プロセスへ戻せる。

- 要求整理へ戻す  
  顧客が本当に達成したい目的や、現在の仕様との期待値のずれを確認する。

- 仕様へ戻す  
  条件、制約、例外、権限、状態遷移、エラー時の挙動を明確にする。

- テスト観点へ戻す  
  実際に顧客が迷った操作、誤解した条件、問い合わせが多いパターンを、次回以降の確認観点に加える。

- ドキュメントへ戻す  
  FAQ、ヘルプ、リリースノート、管理者向け説明、エラーメッセージを見直す。

- 自動化や品質ゲートへ戻す  
  繰り返し発生する不具合やデータ不整合について、再発検知できる確認を追加する。

- 運用改善へ戻す  
  サポート時に必要なログ、管理画面、調査手順、切り戻し手順を整える。

このとき、QAがすべての問い合わせを直接処理する必要はない。

QAが担うべきなのは、CS / サポートが持つ顧客接点情報を、品質観点として読めるようにすることである。たとえば、問い合わせ分類に品質観点を加える、リリース後の問い合わせ傾向を振り返りに持ち込む、頻出問い合わせをテスト観点やドキュメント改善候補へ変換する、といった活動が考えられる。

顧客の困りごとは、プロダクトが実際の利用環境でどのように受け取られているかを示す情報である。

それを個別対応だけで終わらせず、要求、仕様、テスト設計、自動化、ドキュメント、運用改善へ戻すことで、QAはリリース後の学びを次の品質作りへ接続できる。

### 10.4 暗黙知を明文化する

10.2では、職種ごとに異なる言葉や違和感を、関係者が判断・改善に使える品質課題へ変換する考え方を扱った。

10.3では、顧客の問い合わせや困りごとを、単なる個別対応ではなく、要求、仕様、テスト観点、ドキュメント、自動化、品質ゲート、運用改善へ戻す品質情報として扱うことを整理した。

次に重要になるのは、その過程で分かったことを、会話や一時的な判断で終わらせず、誰が読んでも同じ意味に解釈できる形で残すことである。

実務では、品質に関する重要な情報が、暗黙知(tacit knowledge)として残っていることがある。

ここでいう暗黙知とは、特定の担当者や一部の関係者は知っているが、仕様書、受け入れ条件、テスト観点、運用手順、FAQ(Frequently Asked Questions:よくある質問)、リリースノート、データ定義などには明確に書かれていない知識である。

たとえば、本資料で扱ってきた権限、状態遷移、データ定義、運用条件、顧客説明などの観点では、次のような情報が暗黙知になりやすい。

- この操作は、管理者だけが実行できる
- この状態では、データを変更してはいけない
- このエラーは、ユーザー側の入力ミスではなく、権限不足を意味する
- この数値は、当月分だけでなく過去分の再集計も含む
- この機能は、特定の契約プランでは利用できない
- この制約は、法務 / コンプライアンス上の理由で意図的に入れている
- この処理は、外部サービス障害時には自動再試行せず、手動確認に回す
- この問い合わせ内容は、既知の仕様制約としてCS / サポートが説明している

これらの情報が明文化されていない場合、開発者、QA(Quality Assurance:品質保証)、プロダクトマネージャー(PM: Product Manager)、デザイナー、CS(Customer Success:カスタマーサクセス) / サポート、法務 / コンプライアンス、SRE(Site Reliability Engineering:サイト信頼性エンジニアリング) / 運用などの間で、前提がずれやすくなる。

前提がずれると、品質問題はさまざまな形で表面化する。

たとえば、プロダクトマネージャーは仕様上の制約として理解しているが、開発者は一時的な実装制約だと捉えているかもしれない。

また、権限に関する確認では、画面上でボタンが非表示になることと、API(Application Programming Interface:アプリケーションプログラミングインターフェース)を直接呼び出した場合にもサーバー側で操作が拒否されることは、別の確認観点である。

この前提が仕様や受け入れ条件に明記されていなければ、開発者、QA、関係者の間で「どこまで確認済みなのか」の認識がずれる可能性がある。

CS / サポートは顧客に説明しているが、その説明内容が仕様やFAQに反映されていないかもしれない。データ / 分析では特定の除外条件を前提に集計しているが、ダッシュボード利用者にはその前提が伝わっていないかもしれない。

このような状態では、品質判断が個人の記憶や経験に依存してしまう。

QAの観点では、暗黙知を明文化することは、単なるドキュメント作成ではない。品質に関する判断基準を、チームが再利用できる形にする活動である。

明文化すべき対象には、次のようなものがある。

| 明文化する対象 | 例 | 品質との関係 |
|---|---|---|
| 業務ルール | どの状態で、誰が、どの操作を実行できるか | ドメイン品質、権限品質、テスト観点に関わる |
| 受け入れ条件 | 何が満たされれば、機能を受け入れ可能とするか | 要求、仕様、テスト、受け入れ判断の基準になる |
| 判断基準 | どの欠陥をリリース前に必ず修正するか | リリース判断、リスク判断に関わる |
| 既知の制約 | 現時点で対応しない範囲、利用条件、制限事項 | 顧客説明、FAQ、リリースノートに関わる |
| テスト観点 | 次回以降も確認すべき条件、境界、状態、権限 | 回帰確認、自動化、探索的テストに関わる |
| データ定義 | 指標の意味、対象期間、除外条件、更新タイミング | データ品質、ダッシュボード解釈に関わる |
| 運用条件 | 障害時の調査手順、切り戻し条件、サポート時の確認項目 | 運用品質、調査性、復旧性に関わる |
| 権限・監査ルール | 権限付与、変更、削除、監査ログの記録条件 | セキュリティ・権限品質、説明責任に関わる |

重要なのは、すべてを一つの巨大なドキュメントにまとめることではない。

むしろ、情報の性質に応じて、適切な場所に残す必要がある。

たとえば、仕様として開発者やQAが参照すべき内容は、仕様書、ユーザーストーリー、Acceptance Criteria(受け入れ条件)、Issue Tracker(課題管理ツール)に残す方がよい。顧客や管理者に説明すべき内容は、FAQ、ヘルプ、管理者向けガイド、リリースノートに反映する必要がある。テストで継続的に確認すべき内容は、テスト観点、テストケース、自動テスト、品質ゲートに戻す必要がある。運用時に必要な内容は、調査手順、Runbook(運用手順書)、ログ設計、監視項目に反映する必要がある。

たとえば、10.2で扱った「ユーザー招待と権限付与の関係が分かりにくい」という品質課題を考える。

関係者で確認した結果、次のような方針になったとする。

> ユーザー招待時点では、対象機能の利用権限は自動付与しない。  
> 管理者は、ユーザー招待後にロールを選択し、対象機能へのアクセス権限を明示的に付与する必要がある。  
> 招待完了画面には、次に必要な権限付与操作への導線を表示する。  
> 権限未付与のユーザーが対象機能へアクセスした場合、画面には「管理者による権限付与が必要です」と表示する。  
> 権限付与・変更・削除は監査ログに記録する。

この内容は、会議やチャットで合意しただけでは不十分である。

少なくとも、次のような形に分解して残す必要がある。

| 反映先 | 明文化する内容 |
|---|---|
| 仕様 / ユーザーストーリー | ユーザー招待と権限付与は別操作である |
| 受け入れ条件 | 招待完了後に権限付与導線が表示されること、権限未付与時に適切なメッセージが表示されること |
| テスト観点 | 招待済み・権限未付与・権限付与済み・権限削除後の各状態を確認する |
| API仕様 / 認可テスト観点 | 画面上の表示だけでなく、API側でも権限未付与ユーザーの操作を拒否する |
| FAQ / 管理者向け説明 | 招待後に別途権限付与が必要であることを説明する |
| サポート手順 | 問い合わせ時に、招待状態、ロール、権限付与状態、監査ログを確認する |
| 監査 / ログ | 権限付与、変更、削除の操作履歴を確認できるようにする |

このように明文化することで、同じ品質課題が複数の成果物に接続される。

章末のAppendix 10-B「品質観点をチームで使うためのドキュメント例」では、共通参照ドキュメント、個別機能仕様 / 受け入れ条件メモ、リリース判断・既知リスク共有メモの例を通じて、品質観点をチームで再利用できる形へ落とし込む方法を示しているので、適宜参照されたい。

仕様だけに書かれていても、テスト観点に反映されなければ確認漏れが起きる可能性がある。テストケースだけに書かれていても、FAQに反映されなければ、顧客は同じ箇所でつまずく可能性がある。FAQだけに書かれていても、API側の認可や監査ログが不足していれば、セキュリティ・権限品質や運用品質の問題が残る。

したがって、暗黙知の明文化では、「どこかに書く」だけではなく、「誰が、どの判断や作業に使う情報なのか」を意識する必要がある。

QAは、この明文化を一人で完了させる必要はない。仕様の最終判断はプロダクトマネージャーや業務責任者が担うことが多い。実装上の詳細は開発者が確認する必要がある。画面上の文言や導線はデザイナーと調整する必要がある。顧客向け説明はCS / サポートと確認する必要がある。権限、監査、ログ、データ保持に関する事項は、法務 / コンプライアンスやSRE / 運用と確認する必要がある。

QAが担うのは、品質に関する重要な前提が、暗黙知のまま残っていないかを見つけることである。

具体的には、次のような問いを持つとよい。

- この判断基準は、どこに書かれているか
- 誰が読めば、同じ意味に解釈できるか
- 受け入れ条件として確認可能な形になっているか
- テスト観点や回帰確認に反映されているか
- 顧客向け説明やFAQに反映すべき内容はないか
- 問い合わせ対応時に、CS / サポートが確認できる情報になっているか
- リリース後に問題が起きた場合、ログや履歴から調査できるか
- 仕様変更が入った場合、どのドキュメント、テスト、運用手順に影響するか

暗黙知を明文化することには、もう一つ重要な効果がある。

それは、属人性を下げることである。

特定の担当者だけが仕様の背景を知っている状態では、その担当者が不在のときに判断が止まりやすい。過去の経緯を知らない開発者が変更を加えると、意図しない仕様変更が起きる可能性がある。QAが過去の不具合や問い合わせを覚えていなければ、同じリスクを再び見落とす可能性がある。CS / サポートの担当者が変わると、顧客への説明がぶれる可能性もある。

明文化された情報は、チームが品質を継続的に扱うための共有資産になる。

ただし、ドキュメントを作れば自動的に品質が上がるわけではない。古い情報、不正確な情報、参照されない情報が増えると、かえって混乱を生む。明文化した情報は、仕様変更、リリース、問い合わせ傾向、インシデント、データ定義の変更に応じて更新される必要がある。

そのため、暗黙知の明文化は、一回限りの整理ではなく、品質改善のフィードバックループの一部として扱う方がよい。

問い合わせから見つかった課題を、仕様に反映する。仕様として決まった内容を、受け入れ条件やテスト観点に反映する。テストで継続的に確認すべき内容を、自動化や品質ゲートに組み込む。顧客が迷いやすい内容を、FAQやヘルプに反映する。運用で調査しにくかった内容を、ログ設計やRunbookに反映する。

この流れを作ることで、品質情報は一時的な会話ではなく、次の開発、テスト、リリース、運用、顧客説明に再利用できる形になる。

10.5では、このような品質情報の整理、関係者間の前提合わせ、判断材料の準備を支えるQAのファシリテーション的役割について扱う。

### 10.5 組織横断のQuality EnablementとしてのQA

10.1から10.4では、品質がQA(Quality Assurance:品質保証)だけで決まるものではなく、複数の職種が持つ情報、違和感、判断基準、顧客接点情報、暗黙知を品質観点として整理する必要があることを扱った。

ここまでの内容は、単に「他職種とよく会話する」という話ではない。

重要なのは、品質に関する情報が、必要な関係者に届き、判断や改善に使える状態になっているかである。

たとえば、CS(Customer Success:カスタマーサクセス) / サポートが問い合わせ傾向を知っていても、それがプロダクトマネージャー(PM: Product Manager)や開発者、デザイナーに届かなければ、仕様改善や導線改善にはつながりにくい。開発者が実装上の制約やリスクを把握していても、それがリリース判断や顧客説明に反映されなければ、関係者間の期待値がずれる可能性がある。データ / 分析が指標定義や集計条件の前提を持っていても、それが利用者に共有されていなければ、ダッシュボードの数値が誤って解釈される可能性がある。

このように、品質情報は一箇所に集まっているとは限らない。

品質に関する情報は、仕様、Issue Tracker(課題管理ツール)、Pull Request(PR:プルリクエスト)、テスト結果、CI/CD(Continuous Integration / Continuous Delivery:継続的インテグレーション / 継続的デリバリー)、問い合わせ、FAQ(Frequently Asked Questions:よくある質問)、リリースノート、ログ、監視、インシデント記録、ダッシュボードなどに分散していることが多い。

QAの役割の一つは、これらに分散した情報を、品質観点としてつなぎ直すことである。

これは、後工程QA、インプロセスQA、Shift Right Testing(リリース後の利用状況や運用情報から品質を確認する考え方)のような工程分類とは少し異なる。

後工程QAは、リリース前や受け入れ前に成果物を確認し、欠陥や残リスクを整理する活動である。インプロセスQAは、要求、仕様、設計、実装、レビュー、テスト、リリース準備の中で、早い段階から品質観点を入れる活動である。Shift Rightは、リリース後の問い合わせ、ログ、監視、インシデント、利用状況から品質を学び、次の改善へ戻す活動である。

一方で、10章で扱っているのは、それらの工程を横断して必要になる活動である。

すなわち、品質情報、品質観点、判断基準が、職種や工程の間で分断されず、関係者が使える形で共有される状態を作ることである。

この考え方は、Quality Enablement(品質を扱える状態にする支援)として理解できる。

Quality Enablementでは、QAがすべての確認を一手に引き受けるのではなく、チームや組織が品質を自分たちの活動の中で扱える状態を目指す。

たとえば、開発者が実装やレビューの中で権限、状態遷移、データ整合性、エラー処理を意識できるようにする。プロダクトマネージャーが要求や受け入れ条件を整理するときに、顧客影響、既知の制約、リリース判断に必要な品質情報を扱えるようにする。デザイナーが画面導線や文言を検討するときに、問い合わせ傾向やユーザーの迷いやすい箇所を参照できるようにする。CS / サポートが問い合わせを分類するときに、それを仕様誤解、UX(User Experience:ユーザー体験)上の問題、ドキュメント不足、権限設定の分かりにくさなどの品質観点へつなげられるようにする。SRE(Site Reliability Engineering:サイト信頼性エンジニアリング) / 運用が監視やインシデント対応を考えるときに、リリース前に見えていたリスクや既知の制約を参照できるようにする。

このような状態を作ることは、QAが品質への関与を弱めるという意味ではない。

むしろ、品質をQAだけに閉じ込めないための活動である。

品質は、仕様、設計、実装、テスト、リリース、運用、顧客対応、データ活用のそれぞれで作られる。したがって、QAだけが最後に確認しても、すべての品質リスクを十分に扱えるとは限らない。また、プロダクトが大きくなり、改善頻度が高まるほど、品質確認をQAだけに集中させると、QAがボトルネックになりやすい。重要なのは、品質に関する情報が、それぞれの活動に適切に組み込まれていることである。

たとえば、権限に関するリスクは、要求段階では「誰が何をできるべきか」という業務ルールとして現れる。仕様段階では、ロール、状態、操作可否、監査ログの条件として具体化される。実装段階では、画面表示、API(Application Programming Interface:アプリケーションプログラミングインターフェース)側の認可、データ更新、ログ記録として扱われる。テスト段階では、正常系、権限不足、状態遷移、監査ログの確認観点になる。リリース後には、問い合わせ、アクセス拒否ログ、監査証跡、運用調査の対象になる。

この一連の流れが分断されると、品質リスクは途中で抜け落ちやすい。

要求では重要視されていた制約がテスト観点に反映されない。テストで見つかった懸念がFAQに反映されない。リリース後の問い合わせ傾向が次の仕様改善に戻らない。運用で調査しにくかった問題がログ設計やRunbook(運用手順書)の改善に反映されない。

Quality EnablementとしてのQAは、この分断を減らす方向に働く。

QAがすべてを直接確認するのではなく、品質情報が必要な場所へ流れ、関係者が自分の活動の中で品質を扱えるようにする。これにより、品質確認は一回限りのイベントではなく、要求、実装、テスト、リリース、運用、顧客対応をまたいだ継続的な活動になる。

この考え方は、10章後半の各節につながる。

10.6では、品質活動の価値をデータで説明することを扱う。品質活動は、「念のため確認する」「不安だから見る」という感覚だけでは、他職種に伝わりにくい場合がある。欠陥、問い合わせ、インシデント、テスト失敗、レビュー指摘、リリース後の手戻りなどを材料にすることで、なぜその確認や改善が必要なのかを説明しやすくなる。

10.7では、品質情報が自然に流れる状態を作ることを扱う。QAが毎回個別に聞き回らなければ情報が集まらない状態では、品質活動は属人的になりやすい。問い合わせ、仕様変更、リリース後問題、運用上の困りごと、データ不整合などが、必要な関係者に自然に届く流れを作ることが重要になる。

10.8では、避けられる業務を減らし、生産的な活動に時間を使うことを扱う。品質活動は、不具合を減らすためだけの活動ではない。仕様の認識違い、不要な手戻り、重複した確認、同じ問い合わせ、リリース後の緊急対応を減らすことで、チームが新しい価値提供、改善、設計、顧客理解に時間を使いやすくなる。

10.9では、QAのファシリテーション的役割を扱う。Quality Enablementを実際に進めるには、関係者間の前提を揃え、判断材料を用意し、不確実性やリスクを見える化し、職種ごとの言葉を共通の品質観点に変換する必要がある。この具体的な支援のあり方を、10.9で整理する。

QAは、品質を一人で保証する存在ではない。品質に関する情報が、必要な関係者に届き、それぞれの活動の中で使われ、次の改善へ還元される状態を支援する。その意味で、組織横断のQuality EnablementとしてのQAは、品質をQAだけの作業に閉じ込めず、チームや組織の共有活動にしていくための考え方として整理できる。

---

### 10.6 品質活動の価値をデータと具体例で共有する

10.5では、組織横断のQuality Enablement(品質を扱える状態にする支援)としてのQA(Quality Assurance:品質保証)を、品質情報、品質観点、判断基準が必要な関係者へ届き、それぞれの活動の中で使われる状態を支援する考え方として整理した。

10.6では、その前提をさらに進めて、品質活動の価値をどのように共有するかを扱う。

品質活動は、プロダクト品質を高めるために重要である。しかし、現場から見ると、短期的には追加作業として見えやすい。したがって、品質活動を広げるには、「品質のために大事だから」という抽象的な説明だけでは不十分である。

重要なのは、品質活動が各職種の業務や判断にどう関係するのかを、データと具体例を使って共有することである。

---

#### 10.6.1 品質活動は追加作業として見えやすい

品質活動は、短期的には追加作業として見えやすい。

たとえば、受け入れ条件を書く、問い合わせを分類する、テスト観点を明文化する、リリース後の問題を振り返る、既知の制約や運用条件をドキュメント化する、といった活動がある。

これらはいずれも品質改善にとって重要である。

しかし、プロダクトマネージャー(PM: Product Manager)、開発者、デザイナー、CS(Customer Success:カスタマーサクセス) / サポート、営業、SRE(Site Reliability Engineering:サイト信頼性エンジニアリング) / 運用、データ / 分析などにとっては、既存業務に加えて発生する作業のように見えることがある。

たとえば、プロダクトマネージャーにとって、受け入れ条件を詳しく書くことは、仕様整理の精度を上げる一方で、短期的には追加の整理作業に見えるかもしれない。開発者にとって、権限、状態遷移、異常系、ログ、監視まで意識したレビューやテスト観点の整理は、通常の実装作業に加わる負荷として見えるかもしれない。CS / サポートにとって、問い合わせを品質観点に分類することは、顧客対応に加えて入力作業が増えるように見えるかもしれない。

そのため、「品質のために大事だから」「不具合を減らすために必要だから」という抽象的な説明だけでは、品質活動の価値は伝わりにくい。

特に、品質活動がまだQA以外の職種の日常業務に十分に組み込まれていない段階では、品質活動は「本来業務とは別の追加作業」として受け取られやすい。

ここで重要なのは、品質活動の目的は、他職種にQAの仕事を肩代わりしてもらうことではないという点である。

QAが目指すべきなのは、各職種に追加の品質業務を一律に増やすことではない。むしろ、各職種が日々の業務の中ですでに見ている情報を、品質改善につながる手がかりとして扱える状態を作ることである。

---

#### 10.6.2 日常業務の中にある品質改善の手がかり

品質改善につながる情報は、QAだけが持っているわけではない。

各職種は、日々の業務の中で、品質改善につながる手がかりをすでに見ていることがある。

たとえば、CS / サポートが繰り返し受けている問い合わせは、単なる対応件数ではなく、仕様の分かりにくさ、画面導線、FAQ(Frequently Asked Questions:よくある質問)、権限設定、エラーメッセージの問題を示している可能性がある。

営業が商談時に感じている顧客の不安は、契約条件、導入時の説明、運用制約、期待値のずれ、将来的な問い合わせリスクを示している可能性がある。

開発者がレビュー時に気づいた実装上のリスクは、保守性、テスト容易性、権限境界、状態遷移、外部連携失敗時の挙動、ログ不足などの品質観点につながる可能性がある。

デザイナーが見つけた導線や文言の分かりにくさは、ユーザーが迷う箇所、誤操作しやすい箇所、エラー時に次の行動を判断しにくい箇所を示している可能性がある。

SRE / 運用が障害対応時に感じた調査のしにくさは、ログ、監視、アラート、Runbook(運用手順書)、切り戻し条件、影響範囲の特定方法に関する品質課題につながる可能性がある。

データ / 分析が見つけた指標定義や集計条件の曖昧さは、ダッシュボードの解釈違い、意思決定の誤り、データ品質、DQA(Data Quality Assurance / Data Quality Assessment:データ品質保証 / データ品質評価)の問題につながる可能性がある。

これらは、すべて正式な「品質報告」として提出してもらう必要はない。

むしろ重要なのは、各職種が日々の業務の中で見ている情報を、品質改善につながる手がかりとして共有しやすい状態を作ることである。

そうなれば、品質情報はQAが特別に探しに行くものではなく、日常業務の中から見つかりやすくなる。

ただし、このような状態は、「品質を意識しましょう」という呼びかけだけでは定着しにくい。

各職種が見ている情報が、どのように品質改善につながるのかを示す必要がある。そこで重要になるのが、データと具体例である。

---

#### 10.6.3 データと具体例を対話の材料にする

品質活動の価値を共有するときには、欠陥、問い合わせ、インシデント、テスト失敗、レビュー指摘、リリース後の手戻りなど、実際に発生しているデータや具体例を材料にすると伝わりやすい。

たとえば、ある機能について問い合わせが継続的に発生しているのであれば、単に「問い合わせが多い」と言うだけではなく、次のような情報を整理する。

- どの機能や画面に問い合わせが集中しているか
- 問い合わせ内容は、仕様理解、操作迷い、権限設定、データ不整合、エラー表示のどれに近いか
- 問い合わせは特定の顧客、契約プラン、導入初期、特定ロールに偏っているか
- 問い合わせ対応にどれくらいの時間が使われているか
- 同じ内容の問い合わせが繰り返されていないか
- FAQ、ヘルプ、画面文言、受け入れ条件、テスト観点へ戻せる内容はあるか

このように整理すると、問い合わせは単なるCS / サポートの業務ではなく、仕様、UX(User Experience:ユーザー体験)、ドキュメント、権限設計、テスト観点の改善材料として扱えるようになる。

同じように、リリース後に手戻りが多い場合も、単に「もっと慎重に確認するべきだった」とまとめるだけでは不十分である。

重要なのは、どの段階で見つけられた可能性があるのかを確認することである。要求段階で受け入れ条件が不足していたのか、仕様段階で状態遷移や権限条件が曖昧だったのか、テスト設計で異常系や境界条件が漏れていたのか、CI/CD(Continuous Integration / Continuous Delivery:継続的インテグレーション / 継続的デリバリー)上の品質ゲートに載せるべき確認だったのか、リリース後の監視や問い合わせ分類から早く気づけた問題だったのかを整理する。

品質活動の価値は、このような振り返りを通じて見えやすくなる。

「なぜこの確認が必要なのか」を説明するときには、過去の問題、発生傾向、影響範囲、再発防止の観点から話すとよい。

たとえば、権限に関する確認を厚くする理由は、「権限は重要だから」という抽象的な説明だけでは弱い。過去に権限設定の誤解による問い合わせが多かった、権限不足時のエラーメッセージが分かりにくかった、画面上の表示確認だけではAPI(Application Programming Interface:アプリケーションプログラミングインターフェース)側の認可確認が不足する可能性があった、監査ログがないと後から調査しにくかった、といった具体的な材料があれば、確認の必要性を共有しやすくなる。

ただし、数字は結論そのものではない。

問い合わせ件数、欠陥数、テスト失敗数、インシデント件数、レビュー指摘数などは、品質状態を考えるための材料である。数字が多いから悪い、少ないから良いと単純に判断するのではなく、どのような文脈で発生しているのか、どの品質観点に関係しているのか、どの改善につなげられるのかとあわせて読む必要がある。

たとえば、問い合わせ件数が増えている場合でも、それが新機能の利用増による自然な増加なのか、仕様が分かりにくいことによる増加なのか、特定の権限設定でつまずいているのかによって、取るべき対応は変わる。テスト失敗が多い場合でも、重要な不具合を早期に検出できているのか、flaky test(不安定なテスト)によるノイズなのかで、意味は大きく異なる。

したがって、品質活動の価値をデータで説明する目的は、他部署を一方的に説得することではない。

目的は、品質活動が各職種の業務や判断にどう関係するのかを共有し、関係者が自分たちの活動の中で品質情報を扱えるようにすることである。数字や具体例は、そのための対話の材料として使う。

一方で、品質活動の価値を共有できても、品質情報が特定の担当者や部署の中に留まったままでは、改善にはつながりにくい。

問い合わせ、レビュー指摘、インシデント、リリース後の問題、顧客からの不安や要望は、必要な関係者へ届いて初めて、仕様改善、テスト観点、ドキュメント改善、運用改善などに反映しやすくなる。

ただし、そのために各部署へ過剰な入力、分類、報告作業を求めすぎると、品質活動そのものが負担になり、形骸化する可能性もある。

そのため、10.7では、品質情報が特定の場所に滞留せず、必要な関係者へ自然に届き、それぞれの活動の中で判断や改善に使われる状態の価値を整理する。あわせて、その状態を作る際に、各部署への追加負荷や形骸化を防ぐ観点にも触れる。

---

### 10.7 品質情報が自然に流れる状態の価値

10.6では、品質活動の価値を、抽象的な呼びかけだけではなく、欠陥、問い合わせ、インシデント、テスト失敗、レビュー指摘、リリース後の手戻りなどのデータや具体例を通じて共有することを扱った。

ただし、品質活動の価値を共有できても、品質情報が特定の担当者や部署の中に留まったままでは、改善にはつながりにくい。

品質情報が自然に流れる状態の価値は、QA(Quality Assurance:品質保証)の作業を減らすことだけにあるのではない。

より重要なのは、問い合わせ、リリース後の問題、仕様変更、運用上の困りごと、データ不整合などが、特定の担当者や部署の中に滞留せず、必要な関係者へ届き、それぞれの活動の中で判断や改善に使われることである。

10.7では、まず品質情報が滞留しないことの価値を整理する。そのうえで、品質情報を流すために各部署へ過剰な入力や分類を求めすぎると、かえって負荷が増え、形骸化しやすいことも扱う。

---

#### 10.7.1 品質情報が滞留しないことの価値

品質情報は、発生した場所だけで完結させないことが重要である。

たとえば、CS(Customer Success:カスタマーサクセス) / サポートが把握している問い合わせ傾向が、プロダクトマネージャー(PM: Product Manager)やデザイナーに共有されれば、仕様説明、画面導線、FAQ(Frequently Asked Questions:よくある質問)、ヘルプの改善につながる可能性がある。

リリース後に発生した問題が開発者やQAへ戻れば、次回以降のテスト観点、回帰確認、自動テスト、品質ゲートの改善につながる可能性がある。

SRE(Site Reliability Engineering:サイト信頼性エンジニアリング) / 運用が障害対応時に感じた調査のしにくさが共有されれば、ログ、監視、アラート、Runbook(運用手順書)、切り戻し条件の改善につながる可能性がある。

データ / 分析が把握している指標定義、集計条件、除外条件の前提が共有されれば、ダッシュボードの誤解や意思決定上のずれを減らしやすくなる。

品質情報が特定の場所に滞留すると、次のような問題が起きやすい。

- 問題の発見が遅れる
- 改善に必要な関係者へ情報が届かない
- 同じ問題が別々の場所で繰り返し調査される
- 顧客対応、仕様改善、テスト観点、運用改善が分断される
- リリース後の問題が、次の要求整理やテスト設計に戻らない
- 既知の制約や注意点が、顧客説明やFAQに反映されない
- 運用上の困りごとが、ログ設計や監視改善に反映されない

QAが毎回個別に情報を集めなければならない状態は、QAの負荷が高いという問題だけではない。

情報共有が属人的になり、重要な品質リスクが埋もれやすくなることも問題である。ある担当者が気づいていた問い合わせ傾向が、仕様改善に使われない。運用担当者が感じていた調査上の不便さが、ログや監視の改善に反映されない。開発者がレビュー時に気づいたリスクが、テスト観点やリリース判断に残らない。このような状態では、品質改善の機会が失われやすい。

品質情報が自然に流れる状態とは、QAがすべての情報を集約して管理する状態ではない。

目指すのは、品質に関する情報が、必要な関係者へ自然に届き、それぞれの活動の中で判断や改善に使われる状態である。

たとえば、次のような仕組みが考えられる。

- 問い合わせ分類に、仕様誤解、UX(User Experience:ユーザー体験)問題、ドキュメント不足、権限設定、データ不整合などの品質観点を入れる
- リリース後の問題を、単なる障害対応記録ではなく、振り返り、テスト観点、自動化候補、運用改善へ戻す
- 仕様変更時に、影響するテスト観点、ドキュメント、FAQ、運用手順、データ定義を確認する
- ダッシュボードや品質メトリクスで、欠陥、問い合わせ、インシデント、テスト失敗、レビュー指摘の傾向を共有する
- 重要な業務ルール、既知の制約、判断基準を、仕様、受け入れ条件、FAQ、Runbookに明文化する
- 運用で調査しにくかった問題を、ログ設計、監視項目、アラート、Runbookの改善に戻す

このような流れがあると、関係者が早く気づき、早く判断し、早く改善しやすくなる。

たとえば、問い合わせが増えていることをCS / サポートだけが知っている状態では、問い合わせ対応は続いても、仕様や導線は改善されにくい。一方で、その問い合わせ傾向がプロダクトマネージャー、デザイナー、開発者、QAへ共有されれば、仕様説明、画面文言、エラーメッセージ、テスト観点、FAQの改善につなげやすくなる。

また、リリース後の障害対応で「ログが足りず、原因調査に時間がかかった」という情報が運用チーム内だけに留まっていると、次のリリースでも同じ調査上の困難が残る可能性がある。その情報が開発者、QA、SRE / 運用へ共有されれば、ログ出力、監視、アラート、Runbook、テスト観点の改善につなげやすくなる。

この意味で、品質情報が必要な関係者へ届く状態は、品質改善を一部の担当者の気づきや記憶に依存させないために重要である。

---

#### 10.7.2 負荷を増やしすぎずに品質情報を流す工夫

品質情報が必要な関係者へ届く状態は重要である。

ただし、品質情報を自然に流すために、各部署へ過剰なタグ付け、分類、詳細記入を求めすぎると、短期的には追加負荷となり、形骸化しやすい。

たとえば、CS / サポートに対して、すべての問い合わせに詳細な品質カテゴリ、影響範囲、再発防止観点、関連機能、関係部署を正確に入力してもらうよう求めるとする。理想的には有用な情報が集まるかもしれないが、現場の負荷が大きければ、入力が粗くなったり、分類が形式的になったり、運用そのものが続かなくなったりする可能性がある。

同じように、開発者にすべてのレビュー指摘を品質観点ごとに細かく分類してもらう、SRE / 運用にすべての調査メモを再発防止観点で構造化してもらう、データ / 分析にすべての指標定義変更を品質影響として記録してもらう、といった運用も、設計を誤ると追加作業だけが増えやすい。

そのため、重要なのは、品質情報を流すための仕組みを、既存の業務フローから大きく切り離さないことである。

問い合わせは、CS / サポートが普段使っている問い合わせ管理ツールの中で記録される。仕様変更は、Issue Tracker(課題管理ツール)やドキュメントの中で管理される。レビュー指摘は、Pull Request(PR:プルリクエスト)やコードレビューの中に残る。インシデントは、インシデント管理ツールやPostmortem(ポストモーテム)に残る。品質情報は、それらの既存の記録の中から拾える形にする方が、現場にとって無理が少ない。

この点で、AI(Artificial Intelligence:人工知能)や自動化を補助的に使うことも検討できる。

たとえば、問い合わせ本文、障害報告、チャット上の相談、レビューコメント、インシデント記録などを、AIや自動化によって要約し、機能領域、品質観点、重要度、関係しそうな職種ごとに分類することが考えられる。

このような仕組みは、他職種に追加の分類作業を大きく求めず、既存の業務フローから得られる情報を、品質改善に使いやすい形へ変換する補助になり得る。

たとえば、問い合わせ本文から対象機能、困っている操作、エラーメッセージを抽出する。レビューコメントから権限、状態遷移、データ整合性、テスト不足に関する指摘を拾う。インシデント記録から検知の遅れ、復旧の難しさ、監視不足に関する情報を抽出する、といった使い方が考えられる。このような整理ができれば、品質情報を人手で一から分類・集計する負荷を抑えながら、改善に使いやすい形に近づけられる可能性がある。

ただし、AIによる分類や要約は、品質判断そのものを代替するものではない。

AIの出力には、誤分類、重要な文脈の抜け落ち、過剰な要約、分類基準のぶれが含まれる可能性がある。また、問い合わせ、障害報告、ログ、顧客情報には、機密情報や個人情報が含まれることもある。そのため、AIや自動化を使う場合でも、入力データの扱い、確認手順、分類基準、レビュー方法、権限管理には注意が必要である。

AIは、品質情報を整理し、関係者へ届けやすくする補助として扱うべきである。最終的な品質判断、優先度判断、顧客影響の評価、リリース判断は、関係者が文脈を踏まえて行う必要がある。

AIを用いた品質情報の分類、要約、ルーティング、テスト観点生成などの詳細は、11章で扱う。

ここまでをまとめると、品質情報が自然に流れる状態とは、QAがすべての情報を抱え込む状態ではない。また、各部署に大量の追加報告作業を求める状態でもない。

品質に関する情報が、普段の業務の中から見つかり、必要な関係者へ届き、判断や改善に使われる状態である。

この状態を作ることで、問い合わせ、仕様変更、リリース後問題、運用上の困りごと、データ不整合などを、単発の対応で終わらせず、次の仕様改善、テスト観点、ドキュメント改善、運用改善へつなげやすくなる。

10.8では、このような品質活動によって、避けられる手戻り、重複した確認、同じ問い合わせ、リリース後の緊急対応を減らし、チームがより生産的な活動に時間を使いやすくするというテーマを扱う。

---

### 10.8 避けられる業務を減らし、生産的な活動に時間を使う

10.6では、品質活動の価値をデータと具体例で共有することを扱った。

10.7では、品質情報が特定の担当者や部署の中に滞留せず、必要な関係者へ自然に届き、それぞれの活動の中で判断や改善に使われる状態の価値を扱った。

10.8では、それらの品質活動が、結果としてどのような業務負荷を減らし、チームがどのような活動に時間を使いやすくするのかを整理する。

品質活動は、単に不具合を減らすためだけの活動ではない。

もちろん、不具合を減らすことは重要である。しかし、それだけでなく、仕様の認識違い、不要な手戻り、重複した確認、同じ問い合わせ、リリース後の緊急対応などを減らすことも、品質活動の重要な価値である。

これは、10.6で扱った「品質活動は短期的には追加作業として見えやすい」という問題とも関係する。

受け入れ条件を書く、テスト観点を明文化する、問い合わせを分類する、リリース後の問題を振り返る、既知の制約をドキュメント化する、といった活動は、短期的には作業量を増やすように見える。

しかし、適切に設計されれば、それらの活動は、将来の手戻り、重複確認、緊急対応、同じ問い合わせ対応を減らすための土台になり得る。

---

#### 10.8.1 避けられる業務を見つける

品質活動によって減らせる可能性があるのは、単純な作業時間だけではない。

むしろ重要なのは、前提整理、明文化、テスト観点、品質情報の共有によって減らせた可能性がある再確認、再実装、再調査、再説明、緊急対応を見つけることである。

たとえば、次のような業務は、品質活動によって減らせる可能性がある。

- 仕様の前提違いによる再実装
- 受け入れ条件の不足による手戻り
- 同じ問い合わせへの繰り返し対応
- 原因調査に必要な情報が不足していることによる長時間調査
- 既知の制約が共有されていないことによる説明のぶれ
- リリース後に発覚する確認漏れへの緊急対応
- 同じ品質リスクを複数部署が別々に調査する重複対応

これらの業務は、すべて不要というわけではない。

たとえば、複雑な仕様では、実装後に初めて見える問題もある。リリース後の問い合わせやインシデントも、完全になくせるものではない。顧客対応、障害対応、調査、再確認は、プロダクトを運用するうえで必要な活動である。

しかし、すべてを「仕方のない対応」として扱ってしまうと、同じ種類の手戻りや問い合わせが繰り返されやすくなる。

重要なのは、どの対応が本当に避けられなかったものか、どの対応は前提整理、明文化、テスト観点、品質情報の共有によって減らせた可能性があるかを見分けることである。

たとえば、同じ問い合わせが何度も発生しているなら、FAQ(Frequently Asked Questions:よくある質問)、画面文言、エラーメッセージ、導線、権限説明に改善余地があるかもしれない。

リリース後に同じ種類の不具合が繰り返し見つかっているなら、受け入れ条件、テスト設計、自動テスト、品質ゲート、レビュー観点に改善余地があるかもしれない。

障害調査に毎回時間がかかっているなら、ログ、監視、アラート、Runbook(運用手順書)、切り戻し条件に改善余地があるかもしれない。

品質活動は、このような「避けられる可能性がある業務」を見つけ、次の改善につなげるための活動でもある。

---

#### 10.8.2 生産的な活動に時間を使いやすくする

避けられる業務を減らすことには、単に忙しさを減らす以上の意味がある。

手戻り、重複確認、同じ問い合わせ、リリース後の緊急対応に使っていた時間を減らせれば、チームはより生産的な活動に時間を使いやすくなる。

また、避けられる業務を減らすことは、作業時間の削減だけでなく、心理的負荷の軽減にも関係する。同じ問い合わせへの繰り返し対応、謝罪や説明責任を伴う顧客対応、原因調査が難しい障害対応、リリース後の緊急対応は、単に時間を使うだけでなく、担当者に継続的な緊張や負担を与えやすい。

品質活動によって、仕様の認識違い、確認漏れ、情報不足、同じ問い合わせ、調査しにくい障害を減らせれば、チームが緊急対応や再対応に追われる状態を減らしやすくなる。その結果、長時間対応や突発的な残業を抑え、より安定した働き方を支える一因になり得る。

このようにして生まれた時間や余裕は、たとえば次のような活動に向けやすくなる。

- 新しい価値提供
- 仕様改善
- 設計改善
- 顧客理解
- テスト自動化や品質ゲートの改善
- 監視、ログ、運用手順の改善
- データ品質や指標定義の改善

ここでいう「生産的な活動」とは、単に新機能を多く作ることだけではない。

既存機能を分かりやすくすること、顧客が迷いやすい導線を改善すること、開発者が変更しやすい設計にすること、テストしやすい構造にすること、障害時に調査しやすいログを整えること、データや指標の意味を明確にすることも、生産的な活動に含まれる。

品質活動の価値は、将来の不具合や問い合わせを減らすことだけではない。

チームが、同じ問題の再対応に時間を使い続ける状態から、改善、設計、学習、顧客理解に時間を使える状態へ近づける点にもある。

たとえば、問い合わせ分類から「管理者が権限設定で迷いやすい」と分かった場合、それをFAQに追記するだけでなく、画面導線、権限付与フロー、エラーメッセージ、受け入れ条件、テスト観点に戻すことができる。

その結果、同じ問い合わせが減れば、CS(Customer Success:カスタマーサクセス) / サポートは個別対応だけでなく、より高度な顧客支援や導入支援に時間を使いやすくなる。開発者やデザイナーは、同じ問題への修正や説明の繰り返しではなく、根本的な体験改善に時間を使いやすくなる。QA(Quality Assurance:品質保証)も、同じ確認を繰り返すだけでなく、より重要なリスク分析、テスト設計、自動化、品質ゲート改善に時間を使いやすくなる。

このように、品質活動は、将来の無駄やリスクを減らし、生産的な活動に時間を使いやすくするための投資として説明できる。

ただし、ここでいう投資は、必ず短期的な工数削減として表れるとは限らない。

受け入れ条件の明確化、テスト観点の整理、問い合わせ分類、ドキュメント整備、ログ改善などは、短期的には時間を使う。しかし、それらが手戻り、重複確認、緊急対応、同じ問い合わせを減らす方向に働けば、長期的にはチーム全体の余裕を作りやすくなる。

---

#### 10.8.3 品質活動そのものを過剰にしない

一方で、品質活動そのものが過剰になると、逆にチームの負荷を増やす可能性がある。

品質活動は、目的を持って設計される必要がある。

たとえば、会議を増やしすぎる、チェックリストを細かくしすぎる、すべての作業に詳細な記録を求める、誰も読まないドキュメントを増やす、更新されない品質メトリクスを集め続ける、といった状態になると、品質活動は価値を生むどころか、追加負荷になりやすい。

品質活動は、単に「確認項目を増やすこと」ではない。

重要なのは、何を減らしたいのかを明確にすることである。

- どの手戻りを減らしたいのか
- どの問い合わせを減らしたいのか
- どの緊急対応を減らしたいのか
- どの認識違いを減らしたいのか
- どの調査時間を短くしたいのか
- どの品質リスクを早く見つけたいのか

この問いが曖昧なまま品質活動を増やすと、活動そのものが目的化しやすい。

たとえば、問い合わせ分類を行う場合も、単に分類項目を増やせばよいわけではない。その分類が、仕様改善、FAQ改善、テスト観点、リリース判断、顧客説明のどこで使われるのかを明確にする必要がある。

テスト観点を明文化する場合も、単に確認項目を増やすことが目的ではない。その観点が、どのリスクを見つけるためのものか、どのテストレベルで確認するのか、自動化すべきか、人間が探索的に見るべきかを考える必要がある。

品質メトリクスを集める場合も、数字を集めること自体が目的ではない。その数字を、どの判断、どの改善、どの対話に使うのかを明確にする必要がある。

したがって、品質活動は、目的、利用者、使われる場面、減らしたい手戻りやリスクを明確にしたうえで設計する必要がある。

品質活動の価値は、作業を増やすことではなく、避けられる業務を減らし、チームがより生産的な活動に時間を使いやすくすることにある。

10.9では、このような品質活動を進めるうえで、関係者間の前提を揃え、判断材料を用意し、不確実性やリスクを見える化するQAのファシリテーション的役割を扱う。

---

### 10.9 QAのファシリテーション的役割

10.5では、組織横断のQuality Enablement(品質を扱える状態にする支援)としてのQA(Quality Assurance:品質保証)を扱った。

10.6では、品質活動の価値をデータと具体例で共有することを扱った。10.7では、品質情報が特定の担当者や部署の中に滞留せず、必要な関係者へ自然に届く状態の価値を扱った。10.8では、品質活動によって避けられる業務を減らし、生産的な活動に時間を使いやすくすることを扱った。

10.9では、それらの活動を支えるQAのファシリテーション的役割を整理する。

ここでいうファシリテーション(facilitation:対話や合意形成を支援すること)は、単に会議を進行することではない。

品質に関する前提、論点、判断材料、未決定事項、不確実性、リスクを整理し、関係者が同じ土台で議論し、判断し、改善できる状態を作ることである。

QAは、品質を一人で決める役割ではない。プロダクトマネージャー(PM: Product Manager)、開発者、デザイナー、CS(Customer Success:カスタマーサクセス) / サポート、営業、法務 / コンプライアンス、データ / 分析、SRE(Site Reliability Engineering:サイト信頼性エンジニアリング) / 運用などは、それぞれ異なる品質情報と判断基準を持っている。

QAのファシリテーション的役割は、それらを整理し、品質に関する議論や判断が属人的な会話で終わらないようにすることである。

---

#### 10.9.1 関係者間の前提を揃える

品質に関する認識ずれは、同じ言葉を使っていても起こる。

関係者が同じように「管理者」「利用可能」「エラー」「完了」「リリース可能」「問い合わせが多い」と言っていても、それぞれが想定している意味は異なる場合がある。

たとえば、「管理者」と言ったときに、システム管理者を指しているのか、組織管理者を指しているのか、承認者ロールを指しているのかが曖昧なことがある。「利用可能」と言ったときに、画面に表示されることを指しているのか、API(Application Programming Interface:アプリケーションプログラミングインターフェース)側でも操作できることを指しているのか、契約プラン上利用できることを指しているのかがずれることもある。

このような前提のずれは、実装、テスト、顧客説明、運用判断に影響する。

QAは、要求、仕様、業務ルール、権限、状態遷移、データ定義、運用条件について、関係者間の前提が揃っているかを確認する役割を持つ。

ここで重要なのは、前提のずれを責めることではない。前提のずれは、職種ごとに見ている情報が異なるために自然に起こり得る。QAは、それを議論可能な形に見える化する。

具体的には、権限、状態遷移、データ整合性が関わる変更では、チーム内で「まずこの共通ドキュメントを参照する」と合意された参照先があるとよい。

この共通ドキュメントは、個別機能の詳細仕様を置き換えるものではない。役割は、権限ルール、状態遷移、データ整合性、監査ログ、テスト観点などの共通の判断基準を示し、個別機能の仕様、受け入れ条件、テスト観点と照合するための参照先になることである。

共通参照ドキュメントの具体例は、Appendix 10-Bを参照されたい。

このような参照先があれば、開発者はPR(Pull Request:プルリクエスト)レビュー時に、明文化された権限ルール、状態遷移、データ整合性の前提を参照し、実装変更による品質リスクを確認しやすくなる。これは、QAがすべてのレビューを代行するという意味ではない。開発者が通常のレビュー業務の中で品質観点を使える状態にするという意味である。

同じ考え方で、プロダクトマネージャーが受け入れ条件を書くときに、異常系、権限、既知の制約、顧客説明に関わる前提を確認できるようにする。CS / サポートが問い合わせを扱うときに、それが仕様誤解、UX(User Experience:ユーザー体験)問題、ドキュメント不足、権限設定問題のどれに近いかを判断しやすくする。

このように、QAは関係者が同じ前提を参照できる状態を支援する。

---

#### 10.9.2 判断材料を整理する

QAは、リリース可否、改善優先度、仕様変更、既知制約の扱いを一人で決める役割ではない。

しかし、関係者が判断するための材料を整理する役割を持つ。

たとえば、リリース判断の場面では、単に「テストが完了した」「不具合が残っている」と伝えるだけでは不十分である。重要なのは、関係者がリスクを理解したうえで判断できる状態を作ることである。

判断材料には、次のようなものがある。

- どのテストが完了しているか
- どのテストが未実施または制約付きで実施されたか
- 未解決欠陥はどの程度の顧客影響を持つか
- 影響範囲はどこまでか
- 回避策は存在するか
- 既知の制約として顧客に説明できるか
- 問い合わせが増える可能性はあるか
- 監視、ログ、アラート、Runbook(運用手順書)は準備されているか
- リリース後に確認すべき指標やログは何か
- 問題が起きた場合の切り戻し条件や対応手順はあるか

これらは、QAが結論を押しつけるための材料ではない。

品質に関する判断は、プロダクト価値、顧客影響、技術的制約、運用体制、法務 / コンプライアンス上の許容範囲などを踏まえて行われる。そのため、最終判断には複数の職種が関わる。

QAが担うのは、判断に必要な品質情報を整理し、関係者が同じ材料を見ながら議論できる状態を作ることである。

これは、10.6で扱った「数字は結論ではなく、対話の材料として使う」という考え方ともつながる。欠陥数、問い合わせ件数、テスト失敗数、インシデント件数、レビュー指摘数などは、それだけで結論を出すためのものではない。どの文脈で発生し、どの品質観点に関係し、どの改善や判断につながるのかとあわせて扱う必要がある。

---

#### 10.9.3 不確実性やリスクを見える化する

品質活動では、すべてを事前に確定できるとは限らない。

仕様がまだ決まっていないこともある。テスト環境では確認できない外部連携もある。本番利用後に初めて分かる利用傾向もある。問い合わせが増えるかどうかは、リリース後に観測しなければ分からないこともある。

そのため、QAの役割は、不確実性をすべてなくすことだけではない。不確実性を、関係者が扱える形に整理することも重要である。

たとえば、次のようなものは分けて扱うとよい。

- 仕様として未決定の条件
- 実装上の制約
- テスト環境では確認できなかった事項
- リリース後に観測すべき事項
- 既知の制約として顧客に説明する事項
- 監視、ログ、問い合わせ傾向で確認する事項
- 次回以降の改善候補

「なんとなく不安」「使いにくそう」「問い合わせが増えそう」という違和感は、品質リスクを見つける重要な出発点である。しかし、そのままでは、関係者が優先度、対応方針、リリース可否を判断しにくい。

QAは、その違和感を、確認すべき観点、想定される影響、未決定事項、追加で確認すべき情報に整理し、関係者が同じ土台で議論できる状態にする。

たとえば、「この権限設定画面は不安」という違和感がある場合、それを次のように分解できる。

- 管理者が次に何をすべきか分かりにくい
- 招待と権限付与の関係が明確でない
- 権限未付与時のエラーメッセージが行動につながらない
- API側の認可確認が必要である
- 権限変更の監査ログが必要である
- FAQや管理者向け説明に反映すべき内容がある

このように分解すると、不安は単なる感覚ではなく、仕様、UX、権限、テスト、監査、ドキュメントの論点として扱えるようになる。

---

#### 10.9.4 職種ごとの言葉を品質観点へ接続する

10.2では、職種ごとに異なる言葉や違和感を、関係者が判断・改善に使える品質課題へ変換する考え方を扱った。

10.9では、それをQAのファシリテーション行動として改めて位置づける。

プロダクトマネージャー、開発者、デザイナー、CS / サポート、営業、法務 / コンプライアンス、データ / 分析、SRE / 運用は、それぞれ異なる言葉で品質に関する情報を持っている。

たとえば、CS / サポートが「顧客が迷っている」と表現する問題は、UX品質、導線、文言、FAQ、受け入れ条件の問題かもしれない。

データ / 分析が「数字が合わない」と表現する問題は、データ品質、指標定義、集計条件、除外条件、更新タイミングの問題かもしれない。

SRE / 運用が「調査に時間がかかる」と表現する問題は、ログ、監視、アラート、Runbook、運用品質の問題かもしれない。

営業が「契約上説明しにくい」と感じている問題は、既知制約、顧客期待、法務 / コンプライアンス、リリースノート、FAQの問題かもしれない。

QAは、これらの言葉を無理にQA用語へ置き換えるのではない。

重要なのは、各職種が見ている違和感や判断基準を、品質改善に使える観点として整理することである。これにより、職種ごとの情報が、仕様、受け入れ条件、テスト観点、ドキュメント、運用改善、品質メトリクスへ接続しやすくなる。

この活動は、10.7で扱った品質情報が自然に流れる状態ともつながる。職種ごとの言葉が品質観点へ接続されることで、問い合わせ、レビュー指摘、インシデント、データ不整合、顧客からの不安が、単発の情報で終わらず、改善に使える情報として流れやすくなる。

---

#### 10.9.5 品質をチームが扱える状態に広げる

QAがすべての確認、判断、情報整理を抱え込むと、品質活動はQA依存になりやすい。

Quality Enablementの観点では、QAは品質確認を自分たちだけで抱え込むのではなく、チームや関係者が品質観点を自分たちの活動で使える状態を支援する。

たとえば、開発者がレビュー時に、明文化された権限ルール、状態遷移、データ整合性の前提を参照し、実装変更による品質リスクを確認できるようにする。

プロダクトマネージャーが受け入れ条件を書くときに、正常系だけでなく、異常系、権限、既知の制約、顧客説明に関わる観点を含められるようにする。

CS / サポートが問い合わせを扱うときに、それを単なる個別対応で終わらせず、仕様誤解、UX問題、ドキュメント不足、権限設定問題、データ不整合などの品質課題として共有できるようにする。

SRE / 運用がリリース前に見えていたリスクを、監視、ログ、アラート、Runbook、インシデント対応に反映できるようにする。

データ / 分析が指標定義、集計条件、除外条件、更新タイミングを明確にし、関係者が同じ意味で数値を解釈できるようにする。

これらは、QAの作業を他職種に肩代わりしてもらうことではない。

各職種が日々の業務の中で見ている情報を、品質改善につながる手がかりとして扱えるようにすることである。

品質をチームが扱える状態に広げるには、次のような支援が必要になる。

- 参照すべき仕様、判断基準、共通ドキュメントを明確にする
- テスト観点やリスク観点を共有する
- 問い合わせやインシデントを品質改善へ戻す流れを作る
- 品質メトリクスを対話の材料として使う
- 既知の制約や運用上の注意点を明文化する
- AI(Artificial Intelligence:人工知能)や自動化も含め、品質情報の分類や共有の負荷を増やしすぎない仕組みを検討する

このように、QAのファシリテーション的役割は、品質をQAだけの作業に閉じ込めず、チームの共有活動にしていくための支援である。

---

#### 10.9.6 QAがすべてを代行しない

QAがファシリテーション的役割を担うときには、役割境界にも注意する必要がある。

QAは、品質リスクや判断材料を整理できる。しかし、すべての意思決定を代行するわけではない。

仕様の優先順位、リリース判断、顧客説明、法務上の許容範囲、運用体制、データ定義の最終判断などは、それぞれの責任を持つ関係者と合意する必要がある。

QAがすべての判断を代行しようとすると、品質に関する情報と判断がQAに集中しすぎる可能性がある。その結果、他職種が品質を自分たちの活動として扱う機会が減り、チーム全体で品質を扱える状態から遠ざかる。

また、品質確認、情報整理、判断材料の準備、リスク指摘、関係者調整がQAに集中しすぎると、QA自身がボトルネックになりやすい。QAが確認しなければ進まない、QAが判断材料を整理しなければリリース判断できない、QAが問い合わせ傾向を拾わなければ改善につながらない、という状態では、品質活動の速度と継続性がQAの処理能力に依存してしまう。

さらに、QAがすべてを抱え込むと、品質活動そのものが属人的になりやすい。特定のQA担当者がいなければ判断材料が整理されない、品質情報が流れない、権限や状態遷移の観点が確認されない、という状態になると、品質活動は継続しにくい。一見すると品質確認を手厚くしているように見えても、長期的にはチーム全体が品質を扱う機会を減らしてしまう可能性がある。

そのため、QAの支援は、チームがQAに依存する方向ではなく、チームが品質観点を自分たちの活動の中で使えるような方向に向ける必要がある。

したがって、QAのファシリテーション的役割は、品質を一人で保証することではない。

品質に関する前提を揃え、判断材料を整理し、不確実性やリスクを見える化し、職種ごとの言葉を品質観点へ接続し、チームが品質を扱える状態を支援することである。

この役割によって、品質活動はQAだけの作業ではなく、チームや組織が継続的に扱う共有活動に近づいていく。

---

### 10.10 Key Takeaways

この章では、他職種連携を単なるコミュニケーションではなく、品質に関する情報を、関係者が判断・改善に使える形へ変換する活動として整理した。

品質はQA(Quality Assurance:品質保証)だけで決まるものではない。プロダクトマネージャー(PM: Product Manager)、開発者、デザイナー、CS(Customer Success:カスタマーサクセス) / サポート、営業、法務 / コンプライアンス、データ / 分析、SRE(Site Reliability Engineering:サイト信頼性エンジニアリング) / 運用などは、それぞれ異なる品質情報を持っている。

QAの重要な役割は、それらの情報を拾い上げ、品質観点として整理し、必要な関係者へ届くようにし、チームや組織が品質を継続的に扱える状態を支援することである。

- 品質情報は、QAだけが持っているものではない。問い合わせ、商談、レビュー、障害対応、データ分析、運用上の困りごとの中にも、品質改善につながる手がかりが含まれている。

- QAは、職種ごとの言葉や違和感を、議論・判断・改善に使える品質観点へ変換する。たとえば、「問い合わせが多い」「数字が合わない」「調査に時間がかかる」といった言葉は、仕様、UX(User Experience:ユーザー体験)、データ品質、運用品質、テスト観点の問題として整理できる。

- 品質に関する暗黙知は、仕様、受け入れ条件、テスト観点、FAQ(Frequently Asked Questions:よくある質問)、Runbook(運用手順書)、ログ、品質メトリクスなど、使われる場所に応じて明文化する必要がある。

- Quality Enablement(品質を扱える状態にする支援)としてのQAは、品質確認をQAだけに集中させるのではなく、各職種が日常業務の中で品質観点を扱える状態を目指す。そのためには、品質活動の価値をデータと具体例で共有し、品質情報が自然に流れる状態を作ることが重要である。

- QAのファシリテーション的役割は、関係者間の前提を揃え、判断材料を整理し、不確実性やリスクを見える化することである。ただし、QAがすべてを代行するのではなく、チームが品質を自分たちの活動として扱える状態を支援することが重要である。

### Appendix 10-A: 「問い合わせが多い」を品質課題へ変換する実務シミュレーション

Appendix 10-Aでは、10.2で扱った「品質観点を共通言語に変換する」活動を、仮想的な実務の流れとして整理する。

ここで示す内容は、特定企業の実務事例や標準テンプレートを再現したものではない。本章で扱った、職種ごとの品質観点、品質観点の共通言語化、顧客の困りごとの品質課題化、暗黙知の明文化、Quality Enablement(品質を扱える状態にする支援)の考え方をもとに、「問い合わせが多い」という情報をどのように品質課題へ変換できるかを示す仮想シミュレーションである。

また、QA(Quality Assurance:品質保証)がすべての部署に同時に指示を出す、という意味でもない。問い合わせ内容を一次整理し、関係度の高い職種へ順次または並行して確認し、得られた情報をもとに改善方針を調整する流れを例として示す。

題材として、CS(Customer Success:カスタマーサクセス) / サポートから、次のような情報が共有された状況を考える。

> 最近、管理者向けのユーザー招待・権限設定画面について問い合わせが増えている。  
> 特に「ユーザーを招待したのに、対象機能が使えない」という問い合わせが多い。

この段階では、まだ品質課題としては粗い。

単に「問い合わせが多い」だけでは、原因が仕様なのか、UX(User Experience:ユーザー体験)なのか、権限設計なのか、ドキュメント不足なのか、実装不具合なのかは分からない。そのため、QAはまず、問い合わせ内容を品質観点として扱える形に整理する。

#### 1. 問い合わせ内容を一次整理する

最初に、QAは問い合わせをそのまま関係者へ転送するのではなく、何が起きているのかを整理する。

| 整理する観点 | 内容 |
|---|---|
| 対象機能 | 管理者向けのユーザー招待・権限設定画面 |
| 対象ユーザー | 管理者、招待されたユーザー |
| 現行仕様・期待される挙動 | ユーザー招待はアカウント作成・参加招待の操作であり、対象機能の利用権限は管理者が別途付与する必要がある |
| 発生している困りごと | 管理者はユーザーを招待したつもりでいるが、招待されたユーザーには対象機能の権限が付与されておらず、機能を利用できない |
| 想定される誤解 | 管理者が「ユーザーを招待すれば、自動的に対象機能の利用権限も付与される」と理解している可能性がある |
| 品質課題候補 | ユーザー招待と権限付与の関係が分かりにくく、管理者が必要な設定を完了できていない |

ここで重要なのは、実装が仕様どおりに動いている場合でも、ユーザーが本来の仕様を理解できず、業務上の目的を達成できていないなら、それは品質課題として扱う余地があるという点である。

この時点で、問い合わせは次のような品質課題候補として表現できる。

> 権限設定フローにおいて、ユーザー招待と権限付与の関係が分かりにくい。  
> その結果、管理者が必要な設定を完了できず、招待されたユーザーが対象機能を使えない。

#### 2. 品質観点へ分解する

次に、QAはこの問題を一つの観点に決めつけず、複数の品質観点に分解する。

| 品質観点 | 確認したいこと |
|---|---|
| 機能品質 | 招待後に権限付与が正しく動作しているか |
| ドメイン品質 | 業務上、「招待」と「権限付与」は別操作でよいのか |
| UX品質 | 管理者が次に何をすればよいか分かる画面になっているか |
| セキュリティ・権限品質 | 意図しない権限付与を防げているか |
| ドキュメント品質 | 管理者向け説明、FAQ(Frequently Asked Questions:よくある質問)、ヘルプで手順が明確か |
| テスト観点 | 招待のみ、招待後の権限付与、権限未付与時の表示やAPI(Application Programming Interface:アプリケーションプログラミングインターフェース)応答を確認しているか |
| 運用品質 | サポートが調査しやすいログや管理画面情報があるか |

ここでの目的は、「これはUXの問題である」「これは仕様の問題である」と早く決めることではない。関係する職種が、自分たちの判断や改善に使える形で問題を見られるようにすることである。

#### 3. 関係する職種へ確認する

一次整理の後、QAは関係する職種へ確認を行う。

この確認は、すべての職種へ同時に、同じ深さで行うとは限らない。まずCS / サポート、プロダクトマネージャー(PM: Product Manager)、開発者、デザイナーなど、関係度の高い職種へ確認し、必要に応じて法務 / コンプライアンス、データ / 分析、SRE(Site Reliability Engineering:サイト信頼性エンジニアリング) / 運用にも接続する。

また、この確認は、必ずしも最初から会議で行う必要はない。組織によって進め方は異なるが、Slackのようなチャット、JiraやGitHub IssuesのようなIssue Tracker(課題管理ツール)、NotionやGoogle Docsのような共有ドキュメントを使い、問い合わせ内容、仮説、確認したい観点、各職種からの回答を非同期に整理することも考えられる。

非同期で一次確認を行うと、関係者MTG(Meeting:会議)の前に、事実、仮説、制約、未決定事項をある程度そろえやすい。会議は、情報を初めて集める場というより、集まった情報をもとに改善方針、優先度、担当、残課題を調整する場として位置づけやすくなる。

| 確認先 | 初期調査で確認したいこと | 改善後に確認したいこと |
|---|---|---|
| CS / サポート | 問い合わせ件数、顧客層、導入フェーズ、FAQで解決できているか | 問い合わせ件数・問い合わせ率の推移、FAQや案内で自己解決できる割合を見る |
| プロダクトマネージャー(PM) | 顧客影響、導入体験上の優先度、仕様変更の必要性 | 改善が期待した顧客影響を軽減したか、追加対応が必要か |
| 開発者 | 現行仕様、API応答、権限状態、テスト、ログ | 追加した実装・テスト・ログが期待どおり機能しているか |
| デザイナー | 導線、文言、権限未付与状態の表示が誤解を誘発していないか | 画面改善後に迷いが減ったか、ユーザーが次の操作を理解できているか |
| 法務 / コンプライアンス | 自動権限付与、明示操作、監査ログ、利用規約や関連ポリシーへの影響 | 決定した仕様が合意済みの制約や証跡要件を満たしているか |
| データ / 分析 | 権限未付与ユーザー数、アクセス拒否回数、導入初期顧客での偏り | 問い合わせ率、権限未付与ユーザーの割合、アクセス拒否回数、権限付与完了までの時間の推移を見る |
| SRE / 運用 | 調査ログ、監視、サポート調査手順、運用負荷 | 調査時間や運用負荷が減ったか、監視・ログで状況を追えるか |

この表は、確認観点の整理である。実際には、相手の職種に応じて、次のように確認内容を言い換えて渡す。

##### プロダクトマネージャー(PM)向け

プロダクトマネージャーには、顧客影響、導入体験、改善優先度、スコープ判断に使える形で共有する。

```text
権限設定画面について、管理者からの問い合わせが増えています。
主な内容は「ユーザーを招待したが、対象機能が使えない」というものです。

現状では、ユーザー招待と権限付与が別操作であることが管理者に伝わりにくく、導入初期の設定完了を妨げている可能性があります。

確認したい点:
- 招待と権限付与を別操作にする仕様は妥当か
- 初期設定フローとして改善優先度は高いか
- 次回リリースで画面改善、説明追加、権限付与フロー変更のどこまで扱うか
```

##### 開発者向け

開発者には、実装、テスト、API(Application Programming Interface:アプリケーションプログラミングインターフェース)、ログ調査に落とし込める形で共有する。

```text
権限設定画面で、招待済みユーザーが対象機能を利用できないという問い合わせが増えています。

確認したい技術観点:
- ユーザー招待時にデフォルト権限は付与される設計か
- 権限未付与の場合、APIは期待どおり403を返しているか
- 画面側で権限未付与の理由を表示できているか
- 招待済みだが権限未付与の状態をテストで確認しているか
- 調査用ログに、招待状態と権限状態を追える情報が残っているか
```

##### デザイナー向け

デザイナーには、画面導線、表示、文言、ユーザーの誤解として共有する。

```text
管理者が「ユーザーを招待すれば、そのまま対象機能を使える」と理解しているケースが多いようです。

確認したいUX観点:
- 招待完了画面で、次に権限付与が必要だと分かるか
- 権限未付与ユーザーが一覧上で識別できるか
- 管理者が「招待済み」と「利用可能」を混同しない表示になっているか
- エラー表示や案内文は、次に取るべき行動を示しているか
```

##### CS / サポート向け

CS / サポートには、問い合わせ分類、FAQ(Frequently Asked Questions:よくある質問)、顧客影響、再発傾向として共有する。

```text
この問い合わせは、単なる操作ミスとして扱うだけでなく、
「招待」と「権限付与」の関係が分かりにくいことに起因している可能性もあります。

今後の分類案:
- 権限設定
- 初期設定
- 招待済みだが利用不可
- 管理者向け設定理解
- ドキュメント・FAQ不足

確認したいこと:
- 同じ問い合わせがどの顧客規模・導入段階で多いか
- 管理者がどの画面を見て誤解しているか
- FAQで解決できているか、サポート対応が必要になっているか
```

##### 法務 / コンプライアンス向け

法務 / コンプライアンスには、特定の改善案がすでに決まっているように伝えるのではなく、権限設計上の制約や必要な証跡を確認する形で共有する。

```text
現行仕様では、ユーザー招待と対象機能の権限付与は別操作になっています。

一方で、問い合わせ状況を見ると、管理者が「招待すれば対象機能も利用可能になる」と誤解している可能性があります。

今後、招待時の自動権限付与、初期ロールの設定、明示的な権限付与フローの維持などが改善候補になる可能性があります。

対象機能に個人情報や機密情報が含まれる場合、どの設計が許容されるか確認したいです。

確認したい観点:
- 招待時にデフォルト権限を付けてよい機能か
- 管理者の明示的な操作や同意が必要か
- 権限付与の監査ログが必要か
- 権限変更履歴をどの程度保持すべきか
- 利用規約、プライバシーポリシー、管理者向け説明、契約条件への影響があるか
```

##### データ / 分析向け

データ / 分析には、問い合わせ件数だけでなく、実際の利用状態や発生傾向を確認するためのデータ観点として共有する。

```text
権限設定に関する問い合わせが増えているため、問い合わせ件数だけでなく、実際の利用データと合わせて確認したいです。

確認したいデータ観点:
- 招待済みだが権限未付与のユーザー数
- 招待から権限付与までの平均時間
- 権限未付与によるアクセス拒否回数
- 導入初期の顧客でこの問題が多いか
```

##### SRE / 運用向け

SRE / 運用には、調査容易性、ログ、監視、運用負荷として共有する。

```text
権限未付与による問い合わせが増えており、サポート調査に時間がかかっています。

確認したい運用観点:
- 管理者、招待ユーザー、権限状態を調査できるログがあるか
- サポート担当者が管理画面上で権限状態を確認できるか
- 権限不足によるアクセス拒否を監視・集計できるか
- 問い合わせ対応時の調査手順を標準化できるか
```

ここで重要なのは、QAが各職種に別々の問題を投げているわけではないという点である。

中心にある品質課題は、「ユーザー招待と権限付与の関係が分かりにくく、管理者が設定を完了できていない」という一点である。ただし、その課題を改善するには、プロダクトマネージャーには優先度判断の材料として、開発者には実装・テスト・ログの観点として、デザイナーには導線や文言の問題として、CS / サポートには問い合わせ分類やFAQ改善として、法務 / コンプライアンスには権限・証跡・説明責任として、データ / 分析には傾向把握として、SRE / 運用には調査性や運用負荷として伝わる必要がある。

これが、10.2でいう「品質観点を共通言語に変換する」活動である。

#### 4. 回答・制約・データを集約する

各職種から情報が集まったら、QAまたはプロダクトマネージャー(PM)は、論点を整理する。

たとえば、次のような確認結果が得られたとする。

| 確認結果 | 内容 |
|---|---|
| 実装状況 | 実装は現行仕様どおりであり、招待だけでは対象機能の権限は付与されない |
| 問い合わせ傾向 | 導入初期の顧客で問い合わせが多い |
| UX上の課題 | 招待完了後に、次に権限付与が必要であることが画面上で分かりにくい |
| 権限上の制約 | 対象機能には機密情報が含まれるため、無条件の自動権限付与は望ましくない |
| データ上の傾向 | 招待済みだが権限未付与のユーザーが一定数存在する |
| 運用上の課題 | サポート担当者が権限状態を確認するために複数画面を確認している |

この整理により、「問い合わせが多い」という曖昧な情報は、改善方針を検討できる論点へ変わる。

#### 5. 必要に応じて関係者MTGで調整する

回答や制約が集まったら、必要に応じて関係者の代表者を集めて調整する。

以下は、あくまで仮想例における調整の流れである。実際の進め方は、組織体制、プロダクトの性質、リリース判断の権限、顧客影響の大きさによって変わる。

ここでのMTG(Meeting:会議)は、単なる情報共有ではなく、改善方針、優先度、担当、テスト観点、ドキュメント更新、運用改善を整理・合意する場として想定する。

参加者は、すべての職種の全員である必要はない。

この仮想例では、プロダクトマネージャー(PM)、開発者代表、デザイナー、QA、CS / サポート代表を中心に、必要に応じて法務 / コンプライアンス、セキュリティ(Security)、データ / 分析、SRE / 運用を加える形で考える。

ただし、実際の参加者は、組織体制、プロダクトの性質、権限設計の重要度、顧客影響、扱うデータの機密性、改善案の内容によって変わる。

この場で扱う論点は、たとえば次のようになる。

| 論点 | 確認内容 |
|---|---|
| 仕様方針 | 招待と権限付与を別操作のまま維持するか |
| UX改善 | 招待完了後に権限付与を促す導線を追加するか |
| 権限設計 | デフォルトロールや初期権限を導入するか |
| ドキュメント | FAQ、管理者向けヘルプ、リリースノートを更新するか |
| テスト観点 | 招待のみ、招待後の権限付与、権限未付与時の表示、API応答、監査ログを追加確認するか |
| 運用改善 | サポート担当者が権限状態を確認しやすい画面や手順を整えるか |
| データ確認 | 改善後に問い合わせ率、権限未付与ユーザーの割合、アクセス拒否回数、権限付与完了までの時間の推移を見るか |

#### 6. 決定事項を改善へ戻す

調整の結果、たとえば次のような改善方針が決まる。

| 改善対象 | 決定事項 |
|---|---|
| 仕様 | 招待と権限付与は別操作のまま維持する |
| UI(User Interface:ユーザーインターフェース) | 招待完了画面に、次に必要な権限付与操作への導線を追加する |
| エラーメッセージ | 権限未付与のユーザーが対象機能へアクセスした場合、「管理者による権限付与が必要です」と表示する |
| ドキュメント | 管理者向けヘルプとFAQに、招待と権限付与の違いを追記する |
| テスト | 招待のみ、招待後の権限付与、権限未付与時の表示、API応答、監査ログをテスト観点に追加する |
| 運用 | サポート担当者が招待状態と権限状態を確認できる手順を整える |
| データ確認 | 改善後に、権限設定に関する問い合わせ率、権限未付与ユーザーの割合、アクセス拒否回数、権限付与完了までの時間の推移を見る |

ここまで進むと、最初の「問い合わせが多い」という情報は、要求、仕様、画面、テスト、ドキュメント、運用、データ確認へ戻っている。

#### 7. 10.4「暗黙知の明文化」へ接続する

最後に、決定事項を一時的な会話で終わらせず、誰が読んでも同じ意味に解釈できる形で残すことが重要である。

たとえば、次のように明文化する。

> ユーザー招待時点では、対象機能の利用権限は自動付与しない。  
> 管理者は、ユーザー招待後にロールを選択し、対象機能へのアクセス権限を明示的に付与する必要がある。  
> 招待完了画面には、次に必要な権限付与操作への導線を表示する。  
> 権限未付与のユーザーが対象機能へアクセスした場合、画面には「管理者による権限付与が必要です」と表示する。  
> 権限付与・変更・削除は監査ログに記録する。

これは、10.4で扱う「暗黙知を明文化する」活動にあたる。

10.2では、曖昧な問い合わせや違和感を、各職種が扱える品質課題へ変換した。10.4では、その結果として合意された業務ルール、仕様、判断基準、運用条件を、誰が読んでも同じ意味に解釈できる形で残す。

この一連の流れを整理すると、次のようになる。

| 段階 | QAが行うこと |
|---|---|
| 問い合わせの検知 | CS / サポートから共有された情報を受け取る |
| 一次整理 | 対象機能、対象ユーザー、現行仕様、想定される誤解、困りごとを整理する |
| 品質課題化 | 「問い合わせが多い」を、品質課題候補として表現する |
| 職種別確認 | 関係する職種へ、判断・改善に使える形で確認する |
| 集約 | 回答、制約、データ、改善案を整理する |
| 調整 | 必要に応じて関係者MTGで方針、優先度、担当を整理・合意する |
| 改善への反映 | 仕様、UI、テスト、ドキュメント、運用、データ確認へ戻す |
| 明文化 | 決定事項を、誰が読んでも同じ意味になる形で残す |

このAppendixの例は、QAが他職種に単に情報を転送するのではなく、品質情報を構造化し、関係者が判断できる形に変換し、改善へ接続する活動を示している。

#### 10-B.1 権限・状態遷移・データ整合性の共通参照ドキュメント例

このドキュメントは、特定の1機能だけの詳細仕様ではなく、権限、状態遷移、データ整合性が関わる機能や変更を扱うときに共通して参照するための文書である。

たとえば、新機能の仕様検討、PR(Pull Request:プルリクエスト)レビュー、テスト設計、不具合調査、問い合わせ対応、リリース判断の場面で、「まずこのドキュメントを確認する」とチーム内で合意しておく。

この共通参照ドキュメントは、個別機能の仕様書を置き換えるものではない。役割は、権限ルール、状態遷移、データ整合性、監査ログ、テスト観点などの共通の判断基準を示し、個別機能の仕様、受け入れ条件、テスト観点と照合するための参照先になることである。

---

##### 目的

このドキュメントの目的は、権限、状態遷移、データ整合性に関する前提を、チーム内で共有可能な形にすることである。

特に、次のような認識ずれを防ぐことを目的とする。

- 画面上でボタンが非表示であれば、API(Application Programming Interface:アプリケーションプログラミングインターフェース)側の認可確認も十分だと誤解する
- ユーザーを招待すれば、対象機能の利用権限も自動的に付与されると誤解する
- 状態によって実行できる操作が変わるにもかかわらず、その条件が仕様やテスト観点に反映されない
- 権限変更や重要操作の監査ログが必要かどうか、職種ごとに認識がずれる
- データの重複禁止、必須条件、削除可否、履歴保持条件が明文化されていない

##### 共通ルール

| 観点 | 共通ルール |
|---|---|
| 権限 | 操作できるロール、操作できないロール、例外条件を明示する |
| UI(User Interface:ユーザーインターフェース) | 権限のないユーザーには、不要な操作導線を表示しない、または操作できない理由を明示する |
| API認可 | UI上の制御とは別に、API側でも権限未付与ユーザーの操作を拒否する |
| 状態遷移 | 現在状態、操作、次状態、実行可能ロールを明示する |
| データ整合性 | 必須項目、参照関係、重複禁止、削除可否、履歴保持条件を明示する |
| 監査ログ | 権限付与、権限変更、権限削除、重要な状態変更は監査ログの対象とする |
| エラー表示 | 権限不足、状態不一致、データ不整合などは、ユーザーが次に何をすべきか分かる形で表示する |
| テスト観点 | 正常系だけでなく、権限不足、禁止状態、重複、削除後、API直接呼び出しを確認する |

##### 権限ルールの例

| ロール / 状態 | できること | できないこと |
|---|---|---|
| 組織管理者 | ユーザー招待、ロール付与、ロール変更、権限削除 | 監査ログの改ざん |
| 承認者 | 自分が担当する申請の承認、却下 | ユーザー招待、組織全体の権限変更 |
| 一般ユーザー | 自分に付与された機能の利用、自分の申請状況の確認 | 他ユーザーの権限変更、未付与機能の利用 |
| 権限未付与ユーザー | 基本画面の閲覧、必要に応じた権限申請 | 対象機能の実行、管理操作 |

##### 状態遷移ルールの例

| 現在状態 | 操作 | 次状態 | 実行可能ロール | アクセス制御 / 備考 |
|---|---|---|---|---|
| 招待前 | ユーザーを招待する | 招待済み | 組織管理者 | 招待時点では対象機能の権限は付与しない |
| 招待済み | 権限を付与する | 権限付与済み | 組織管理者 | 権限付与操作を監査ログに記録する |
| 招待済み | 対象機能へアクセスする | 状態変化なし | 権限未付与ユーザー | UIとAPIの両方で拒否する |
| 権限付与済み | 権限を削除する | 権限未付与 | 組織管理者 | 権限削除操作を監査ログに記録する |
| 権限未付与 | 対象機能へアクセスする | 状態変化なし | 権限未付与ユーザー | 管理者による権限付与が必要であることを表示する |

##### データ整合性ルールの例

| 対象 | ルール |
|---|---|
| user_id | 存在するユーザーを参照する |
| role_id | 定義済みのロールを参照する |
| permission_id | 定義済みの権限を参照する |
| user_id + permission_id | 同一ユーザーに同じ権限を重複付与しない |
| granted_at | 権限付与時に記録する |
| granted_by | 権限を付与した管理者を記録する |
| revoked_at | 権限削除時に記録する |
| audit_log | 権限付与、変更、削除の操作履歴を保持する |

##### PRレビュー時に確認する観点

PRレビューでは、次の観点を確認する。

- 今回の変更は、既存の権限ルールと矛盾していないか
- UI上の表示制御だけでなく、API側の認可制御も実装されているか
- 権限未付与ユーザーがAPIを直接呼び出した場合に拒否されるか
- 状態によって実行できる操作、実行できない操作が明確か
- 禁止された状態遷移が追加されていないか
- データの重複、参照切れ、不整合が発生しないか
- 権限付与、変更、削除の監査ログが残るか
- エラー時に、ユーザーや管理者が次に何をすべきか分かるか
- テスト観点または自動テストに反映すべき内容があるか

##### 更新が必要になるタイミング

このドキュメントは、一度作って終わりではない。次のような変更がある場合は、更新を検討する。

- 新しいロールが追加された
- 既存ロールの権限範囲が変わった
- 新しい状態や状態遷移が追加された
- 既存の禁止操作が許可されるようになった
- API認可の方式が変わった
- 監査ログの対象操作が変わった
- 問い合わせや障害対応から、既存ルールの分かりにくさが見つかった
- 法務 / コンプライアンス上の要件が変更された

##### このドキュメントの使い方

このドキュメントは、次のような場面で参照する。

- 新機能の仕様検討時
- ユーザーストーリーや受け入れ条件を書くとき
- PRレビュー時
- テスト観点を作るとき
- 権限まわりの不具合を調査するとき
- CS / サポートが問い合わせ対応を行うとき
- リリース前に既知リスクを整理するとき

---

このような共通参照先があることで、権限、状態遷移、データ整合性に関する判断が、個人の記憶や暗黙知に依存しにくくなる。

#### 10-B.2 個別機能仕様 / 受け入れ条件メモの例

このメモは、Appendix 10-Aで扱った「ユーザーを招待したのに対象機能が使えない」という問い合わせを受けて、ユーザー招待と権限付与の関係を明文化するための個別機能メモの例である。

10-B.1が横断的な共通参照ドキュメントであるのに対し、10-B.2は特定機能に対する仕様、受け入れ条件、テスト観点、顧客説明、運用確認項目を整理するための文書である。

---

##### 対象機能

管理者向けのユーザー招待・権限付与機能。

##### 背景

CS / サポートから、次の問い合わせが継続的に発生していると共有された。

> ユーザーを招待したのに、対象機能が使えない。

確認の結果、管理者が「ユーザーを招待すれば、対象機能の利用権限も自動的に付与される」と理解している可能性があることが分かった。

現在の仕様では、ユーザー招待と対象機能の権限付与は別操作である。ユーザーを招待しただけでは、対象機能の利用権限は付与されない。

そのため、招待完了後に管理者が次に行うべき権限付与操作を分かりやすくする必要がある。

##### 目的

この改善の目的は、管理者がユーザー招待後に必要な権限付与操作を理解し、対象ユーザーが必要な機能を利用できる状態まで設定を完了しやすくすることである。

また、権限未付与状態のユーザーが対象機能へアクセスした場合に、なぜ利用できないのか、次に何が必要なのかを分かりやすくする。

##### 対象外

この改善では、次の内容は対象外とする。

- ユーザー招待時に、対象機能の権限を自動付与すること
- 既存のロール体系を全面的に変更すること
- すべての契約プランで対象機能を利用可能にすること
- 監査ログの保存期間を変更すること

##### 業務ルール

| ルール | 内容 |
|---|---|
| ユーザー招待 | 管理者は、ユーザーを組織へ招待できる |
| 権限付与 | 対象機能を利用するには、管理者による明示的な権限付与が必要である |
| 自動付与 | ユーザー招待時点では、対象機能の権限は自動付与しない |
| 権限未付与時 | 権限未付与ユーザーは、対象機能を利用できない |
| API認可 | 権限未付与ユーザーがAPIを直接呼び出した場合も、操作を拒否する |
| 監査ログ | 権限付与、変更、削除は監査ログに記録する |
| 顧客説明 | 招待と権限付与が別操作であることを、FAQと管理者向け説明に反映する |

##### 状態と操作

| 状態 | 説明 | 可能な操作 | アクセス制御 |
|---|---|---|---|
| 未招待 | ユーザーがまだ組織に招待されていない | 管理者がユーザーを招待する | 対象機能へのアクセス対象外 |
| 招待済み・権限未付与 | 組織には招待済みだが、対象機能の権限は付与されていない | 管理者が権限を付与する | 対象機能へのアクセスはUI / APIの両方で拒否する |
| 権限付与済み | 対象機能の利用権限が付与されている | ユーザーが対象機能を利用する。管理者が権限を変更・削除する | 対象機能へのアクセスを許可する |
| 権限削除済み | 以前は権限があったが、現在は削除されている | 管理者が必要に応じて権限を再付与する | 対象機能へのアクセスはUI / APIの両方で拒否する |

##### 受け入れ条件

| ID | 受け入れ条件 |
|---|---|
| AC-01 | 管理者がユーザーを招待した後、招待完了画面に「対象機能を利用するには権限付与が必要です」という案内が表示される |
| AC-02 | 招待完了画面から、対象ユーザーの権限付与画面へ遷移できる |
| AC-03 | 招待済み・権限未付与ユーザーが対象機能へアクセスした場合、「管理者による権限付与が必要です」というメッセージが表示される |
| AC-04 | 権限未付与ユーザーが対象機能のAPIを直接呼び出した場合、403 Forbiddenを返す |
| AC-05 | 権限付与済みユーザーは、対象機能を利用できる |
| AC-06 | 権限削除後のユーザーは、対象機能を利用できない |
| AC-07 | 権限付与、変更、削除の操作は監査ログに記録される |
| AC-08 | FAQまたは管理者向けヘルプに、ユーザー招待と権限付与が別操作であることが記載される |

ここでは、画面やAPIの挙動だけでなく、顧客説明やサポートに必要なドキュメント反映も、受け入れ判断に含める例として示す。

##### テスト観点

| 観点 | 確認内容 |
|---|---|
| 招待完了後の導線 | 招待完了画面から権限付与画面へ進めるか |
| 権限未付与状態 | 招待済みだが権限未付与のユーザーが対象機能を利用できないか |
| UI表示 | 権限未付与時に、ユーザーや管理者が次に何をすべきか分かるメッセージが表示されるか |
| API認可 | APIを直接呼び出しても、権限未付与ユーザーの操作が拒否されるか |
| 権限付与後 | 権限付与後に対象機能を利用できるか |
| 権限削除後 | 権限削除後に対象機能を利用できなくなるか |
| 監査ログ | 権限付与、変更、削除がログに記録されるか |
| FAQ / ヘルプ | 招待と権限付与が別操作であることが説明されているか |

##### 追加で確認すべき観点

- 招待完了後に権限付与を行わず画面を閉じた場合、管理者が後から権限未付与ユーザーを見つけられるか
- 一括招待時に、権限付与導線をどのように表示するか
- 権限付与できるロールとできないロールが明確か
- 契約プラン上、対象機能を利用できない場合の表示はどうするか
- 権限未付与と契約プラン対象外を、ユーザーに区別して説明する必要があるか
- 監査ログをCS / サポートが問い合わせ対応時に参照できるか
- 招待済み・権限未付与ユーザー数をダッシュボードで確認できるか

##### CS / サポート向け確認項目

問い合わせがあった場合、CS / サポートは次の内容を確認する。

- 対象ユーザーは組織に招待済みか
- 対象ユーザーに対象機能の権限が付与されているか
- 対象ユーザーのロールは何か
- 契約プラン上、対象機能を利用できるか
- 権限付与、変更、削除の監査ログが存在するか
- エラーメッセージは何と表示されているか
- 同じ問い合わせが同一顧客または複数顧客で繰り返されているか

##### FAQ / 管理者向け説明に反映する内容

FAQや管理者向けヘルプには、次の内容を反映する。

- ユーザー招待と対象機能の権限付与は別操作である
- ユーザーを招待しただけでは、対象機能の利用権限は付与されない
- 対象機能を利用させるには、管理者が権限付与を行う必要がある
- 権限未付与ユーザーが対象機能へアクセスした場合、管理者による権限付与が必要である
- 権限付与後も利用できない場合は、契約プラン、ロール、監査ログ、エラー表示を確認する

##### リリース後に確認する指標

| 指標 | 目的 |
|---|---|
| 招待済み・権限未付与ユーザー数 | 招待後に権限付与が完了していないユーザーがどれくらいいるかを確認する |
| 権限未付与によるアクセス拒否回数 | 権限付与忘れによる利用失敗が発生していないかを確認する |
| 関連問い合わせ件数 | 改善後に同じ問い合わせが減っているかを確認する |
| 招待完了画面から権限付与画面への遷移率 | 管理者が次の操作へ進んでいるかを確認する |
| 権限付与操作の完了率 | 招待後に権限付与まで完了しているかを確認する |

##### このメモの使い方

このメモは、次の場面で参照する。

- 仕様確認
- 受け入れ条件の確認
- PRレビュー
- テスト設計
- QAレビュー
- FAQ / ヘルプ更新
- CS / サポート問い合わせ対応
- リリース後の問い合わせ傾向確認

---

このように、個別機能の仕様、受け入れ条件、テスト観点、顧客説明、運用確認項目を一つの流れで整理しておくことで、問い合わせから見つかった品質課題を、次の開発、テスト、運用、顧客説明に再利用しやすくなる。

#### 10-B.3 リリース判断・既知リスク共有メモの例

このメモは、リリース前に、確認済み範囲、未確認範囲、既知リスク、顧客影響、回避策、リリース後に確認すべき情報を整理するための文書例である。

QA(Quality Assurance:品質保証)がリリース可否を一人で決めるためのものではない。関係者が同じ判断材料を見ながら、リリース判断、顧客説明、監視、問い合わせ対応、リリース後確認を行いやすくするための補助資料である。

ここでは、管理者向け利用状況ダッシュボードの集計条件を変更するリリースを題材にする。

ここでいう「顧客向けダッシュボード」とは、サービスを契約している顧客企業の管理者が、プロダクト内で閲覧する利用状況画面を指す。

一方、「社内確認用レポート」とは、サービス提供会社側のCS / サポート、PM、データ / 分析などが、特定顧客の利用状況の把握や問い合わせ対応に使う社内向けレポートを指す。

この仮想例では、顧客向けダッシュボードと社内確認用レポートは同じ利用実績データをもとにしているが、集計条件が異なっていたものとする。差分の主な原因は更新タイミングではなく、削除済みユーザーと一時停止中ユーザーを集計対象に含めるかどうかの違いである。

---

##### 対象リリース

管理者向け利用状況ダッシュボードの集計条件変更。

##### 背景

CS / サポートから、次のような問い合わせが共有された。

> 管理画面の利用状況ダッシュボードに表示される「月間アクティブユーザー数」と、サポート担当者が社内確認用レポートをもとに説明した数値が一致しない。

確認の結果、社内確認用レポートで使われている「削除済みユーザーと一時停止中ユーザーを除外する」集計条件が、月間アクティブユーザー数の正式な指標定義として合意されていた。一方で、顧客向けダッシュボードでは古い集計条件が残っており、削除済みユーザーや一時停止中ユーザーを一部含んでいた。

今回のリリースでは、顧客向けダッシュボード側の集計条件を、合意済みの指標定義に合わせる。これは社内確認用レポートに機械的に合わせるという意味ではなく、同じ「月間アクティブユーザー数」という指標名で異なる定義が使われていた状態を解消するためである。

##### リリースの目的

このリリースの目的は、顧客向けダッシュボードの月間アクティブユーザー数を、合意済みの正式な指標定義に揃え、顧客や社内関係者が同じ意味で数値を解釈できるようにすることである。

また、集計条件を明文化し、問い合わせ対応時にCS / サポートが説明できる状態にする。

##### 対象範囲

| 項目 | 内容 |
|---|---|
| 対象画面 | 管理者向け利用状況ダッシュボード |
| 対象指標 | 月間アクティブユーザー数 |
| 変更内容 | 削除済みユーザー、一時停止中ユーザーを集計対象から除外する |
| 対象期間 | リリース後に表示されるダッシュボード値。過去期間を表示する場合も、新しい集計条件で再計算される |
| 反映対象 | ダッシュボード表示、CSVエクスポート、管理者向けヘルプ、リリースノート |
| 反映対象外 | 過去に顧客へ共有済みの利用状況レポート、請求金額計算、契約プラン判定 |

ここでいう「利用状況レポート」とは、サービス提供会社側が顧客支援や定例報告のために、過去の時点の利用状況をまとめて顧客へ共有した資料を指す。すべてのSaaSで必ず提供されるものではなく、契約形態やCSの運用によって提供有無や頻度は異なる。

##### 関係者

| 職種 / 役割 | 確認観点 |
|---|---|
| プロダクトマネージャー(PM: Product Manager) | 変更の目的、顧客影響、リリース可否 |
| 開発者 | 集計ロジック、表示、CSVエクスポート、既存データへの影響 |
| QA | テスト済み範囲、未確認範囲、既知リスク、回帰確認 |
| CS / サポート | 顧客説明、問い合わせ対応、FAQ(Frequently Asked Questions:よくある質問)更新 |
| データ / 分析 | 指標定義、除外条件、社内確認用レポートとの整合性 |
| SRE(Site Reliability Engineering:サイト信頼性エンジニアリング) / 運用 | リリース後の監視、エラー発生時の確認、切り戻し手順 |

##### テスト済み範囲

| 観点 | 確認内容 | 結果 |
|---|---|---|
| 集計条件 | 削除済みユーザーが月間アクティブユーザー数から除外される | 確認済み |
| 集計条件 | 一時停止中ユーザーが月間アクティブユーザー数から除外される | 確認済み |
| 集計条件 | 有効ユーザーは月間アクティブユーザー数に含まれる | 確認済み |
| 画面表示 | ダッシュボード上の月間アクティブユーザー数が新しい条件で表示される | 確認済み |
| CSVエクスポート | CSV出力でも同じ集計条件が使われる | 確認済み |
| 権限 | 管理者のみが対象ダッシュボードを閲覧できる | 確認済み |
| 回帰確認 | 関連する主要指標に意図しない差分が出ていない | 確認済み |
| ヘルプ | 管理者向けヘルプに集計条件が記載されている | 確認済み |

##### 未確認範囲

| 未確認事項 | 理由 | 対応方針 |
|---|---|---|
| 全顧客の過去全期間データでの完全照合 | データ量が多く、全期間の手動照合は現実的でない | 代表顧客、代表期間、異常値がある期間を抽出して確認済み |
| 顧客側の独自集計との一致 | 顧客側で独自に使っている集計条件は把握できない | ヘルプに集計条件を明記し、問い合わせ時に説明する |
| リリース後の問い合わせ傾向 | リリース後でないと、顧客影響、説明不足、想定外の混乱、実装不具合の兆候を確認できない | リリース後1週間、必要に応じて次回月次確認タイミングまで確認する |
| 一部の古いCSV利用手順への影響 | 顧客が独自にCSVを加工している可能性がある | リリースノートで集計条件変更を通知する |

リリース直後に関連問い合わせが増えた場合、それが仕様どおりの変更に対する説明不足なのか、集計定義の不一致なのか、実装不具合なのかを切り分ける必要がある。そのため、問い合わせ件数は単なるサポート負荷の指標ではなく、リリース後の品質影響を確認するためのシグナルとして扱う。

##### 既知リスク

| リスク | 影響 | 対応 |
|---|---|---|
| リリース後に月間アクティブユーザー数が下がって見える | 管理者が「利用者が急に減った」と誤解する可能性がある | ヘルプ、リリースノート、CS / サポート向け説明に、集計条件変更であることを明記する |
| 過去のダッシュボード値と新しい表示値が一致しない | 過去値との比較時に混乱が起きる可能性がある | 変更日以降の集計条件を明記し、必要に応じて注記を表示する |
| CSVを使った顧客側レポートに差分が出る | 顧客側の社内報告値が変わる可能性がある | CSV出力の集計条件変更をリリースノートに記載する |
| 社内確認用レポートと一時的に差分が残る | 集計条件を揃えても、更新タイミング、対象期間、タイムゾーン、データ反映遅延によって差分が残る可能性がある | 差分が残る条件をデータ / 分析と確認し、FAQに反映する |

##### 顧客影響

この変更により、対象顧客の管理画面で表示される月間アクティブユーザー数が、リリース前より小さくなる可能性がある。

これは利用者数が実際に減ったことを意味するとは限らない。削除済みユーザーと一時停止中ユーザーを除外するように集計条件を変更したためである。

顧客への説明では、次の点を明確にする。

- 集計条件を明確化したこと
- 削除済みユーザーと一時停止中ユーザーを除外するようにしたこと
- 過去の表示値と差分が出る可能性があること
- 請求金額や契約プラン判定には影響しないこと
- 詳細な集計条件は管理者向けヘルプで確認できること

##### 回避策 / 問い合わせ対応

問い合わせが発生した場合、CS / サポートは次の順に確認する。

- 対象顧客のダッシュボード表示期間
- リリース前後で月間アクティブユーザー数に差分が出ているか
- 削除済みユーザー、一時停止中ユーザーがどれくらい含まれていたか
- CSVエクスポートでも同じ差分が出ているか
- 請求金額や契約プラン判定に関する問い合わせではないか
- 顧客が独自に使っている集計条件があるか

説明時には、次のように伝える。

> 今回のリリースでは、月間アクティブユーザー数の集計条件を明確化し、削除済みユーザーと一時停止中ユーザーを除外するように変更しました。  
> そのため、リリース前後で表示される数値に差分が出る場合があります。  
> この変更は、ダッシュボード表示とCSVエクスポートの集計条件に関するものであり、請求金額や契約プラン判定には影響しません。

##### リリース後に確認する項目

| 確認項目 | 確認目的 | 確認期間 |
|---|---|---|
| 関連問い合わせ件数 | 集計条件変更による顧客影響、説明不足、想定外の混乱、実装不具合の兆候を確認する | リリース後1週間、必要に応じて次回月次確認タイミングまで |
| ダッシュボード表示エラー | 表示や集計処理にエラーが出ていないか確認する | リリース後3日間 |
| CSVエクスポートエラー | CSV出力に失敗していないか確認する | リリース後3日間 |
| 月間アクティブユーザー数の異常値 | 想定外に大きな差分が出ていないか確認する | リリース後1週間、および次回月次集計時 |
| CS / サポートからの追加報告 | 顧客説明で分かりにくい点がないか確認する | リリース後1週間 |

確認期間は固定値ではなく、リスクが表面化しやすいタイミング、データ更新サイクル、顧客が対象機能やレポートを確認する頻度に応じて設定する。ここでは、技術的な表示・出力エラーはリリース直後、問い合わせや月次指標の違和感は数日遅れて表面化する可能性があるため、確認期間を分けている。

##### 切り戻し条件

次のいずれかに該当する場合、切り戻しまたは一時的な表示停止を検討する。

- ダッシュボード表示に重大なエラーが発生している
- CSVエクスポートが継続的に失敗している
- 集計結果に明らかな誤りがある
- 複数顧客で業務上重大な混乱が発生している
- CS / サポートで説明不能な差分が多数発生している

##### リリース判断に必要な確認

| 確認事項 | 担当 | 状態 |
|---|---|---|
| 集計ロジックの変更内容を確認した | 開発者 / データ | 確認済み |
| 主要なテスト観点を確認した | QA | 確認済み |
| 管理者向けヘルプを更新した | CS / サポート / PM | 確認済み |
| リリースノートに集計条件変更を記載した | PM | 確認済み |
| リリース後の監視項目を決めた | SRE / 運用 / QA | 確認済み |
| 問い合わせ時の説明方針を共有した | CS / サポート | 確認済み |
| 既知リスクを関係者で確認した | PM / QA / 開発者 / CS / データ | 確認済み |

##### リリース判断

現時点では、主要な集計条件、画面表示、CSVエクスポート、ヘルプ更新、問い合わせ対応方針は確認済みである。

一方で、顧客独自の集計条件との一致や、リリース後の問い合わせ件数は事前に完全には確認できない。そのため、これらは既知リスクとして扱い、リリース後1週間は問い合わせ傾向とダッシュボード表示の異常値を確認する。

上記を前提として、関係者間でリリース可否を判断する。

---

このようなメモを用意しておくことで、リリース判断が「なんとなく不安」「テストは終わった」という曖昧な会話だけで進むことを防ぎやすくなる。

QAがリリース可否を一人で決めるのではなく、テスト済み範囲、未確認範囲、既知リスク、顧客影響、問い合わせ対応、リリース後確認を整理し、関係者が同じ判断材料を見ながら合意できる状態を支援することが重要である。
