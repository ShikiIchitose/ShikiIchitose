# AE / DEポートフォリオを品質の観点から読み直す

**QA / DQA / QE / 運用品質から見たポートフォリオ再解釈**

## 概要

この資料は、AE(Analytics Engineering:分析エンジニアリング) / DE(Data Engineering:データエンジニアリング)を主軸として作成したポートフォリオ群を、品質・検証・データ品質・運用品質の観点から読み直すための概要版である。

ここで示したいのは、QA(Quality Assurance:品質保証)専任の実務経験ではない。すでに作成したポートフォリオに含まれる設計判断を、QA、DQA(Data Quality Assurance:データ品質保証)、QE(Quality Engineering:品質エンジニアリング)、運用品質の観点から整理し直し、どのような品質意識と接続して説明できるかを示すことである。

詳細な背景、個別リポジトリごとの設計判断、言いすぎないための補足は詳細版にまとめている。本資料は、その詳細版と各リポジトリを読む前に、全体像を短時間で把握するための入口として位置づける。

## 1. この資料の目的

本資料の目的は、AE / DEポートフォリオとして作成してきた内容を、品質観点から再解釈することである。具体的には、業務フロー、入力契約、データの意味、指標定義、期待出力、回帰確認、関係者への共有といった要素を、QA / DQA / QE / 運用品質と接続して整理する。

この資料では、品質を「最後に確認するもの」としてではなく、設計・実装・テスト・データ・ドキュメント・成果物の中に組み込まれるものとして扱う。つまり、期待される状態を明確にし、変更後も確認できる形にし、関係者が同じ情報をもとに判断できる状態を作ることに焦点を置く。

## 2. ポートフォリオ群の全体像

このポートフォリオ群は、AIツール利用ガバナンスを題材に、業務データの発生源から、イベント取り込み境界、rawデータ、warehouseモデリング、mart / BI(Business Intelligence:ビジネスインテリジェンス)出力、分析API、外部から見えるサービス状態の確認までを、小さく表現したものである。

中心となるのは、AIツール利用申請・承認フロー、利用イベントの取り込み、dbtによるwarehouseモデリング、業務向けmart、BI出力、分析APIである。`url-monitor` は中心ポートフォリオではないが、HTTPステータス、レイテンシ、エラー、p95などを記録する点で、運用品質への関心を示す補助線として扱う。

- `ai-tool-access-requests`: 業務アプリケーション
- `go-ingestion-api`: イベント取り込み境界
- `access-governance-warehouse`: dbt warehouse / BI出力
- `analytics-metrics-api`: 分析API
- `url-monitor`: 運用品質への補助線

## 3. 品質観点で見た接続

本資料では、各ポートフォリオを、QA / DQA / QE / 運用品質の4つの観点から読み直す。

QA軸では、業務フロー、権限、状態遷移、禁止操作を明確にし、期待されるふるまいを確認可能にする。  
DQA軸では、データの意味、粒度、source contracts、指標定義を明確にし、データが意図された用途に対して信頼できるかを見る。  
QE軸では、テスト、自動化、CI(Continuous Integration:継続的インテグレーション)、期待出力、再現性を仕組みに組み込み、変更後も確認しやすい状態を作る。  
運用品質軸では、HTTPステータス、レイテンシ、エラー、p95など、外部から見える状態を確認・記録する。

## 4. ポートフォリオ別対応表

| ポートフォリオ | 本来の位置づけ | 品質観点で説明できること |
|---|---|---|
| `ai-tool-access-requests` | AIツール利用申請・承認フロー | 業務フロー、権限、状態遷移、自己承認禁止、禁止操作の保護 |
| `go-ingestion-api` | 利用イベントの取り込みAPI | 入力契約、JSON検証、参照データ照合、rawデータ保存 |
| `access-governance-warehouse` | dbtによるwarehouse / BI出力 | model grain、source contracts、dbt data tests、mart、BI出力によるデータ品質の整理 |
| `analytics-metrics-api` | 読み取り専用の分析API | 指標定義、期待出力、外部依存を避けたテスト、SQLからAPI出力までの追跡可能性 |
| `url-monitor` | URL監視補助CLI | HTTPステータス、レイテンシ、エラー、p95を記録する運用品質への補助線 |

## 5. この資料から説明できること

このポートフォリオ群から説明できるのは、個別の技術スタックやツールの利用経験だけではない。期待状態、入力契約、データの意味、指標定義、期待出力を確認可能な形にし、変更後も重要な前提や出力を確認できるようにしようとしている点である。

また、構造的な不整合と、業務上確認すべきレビュー対象を分けて扱っている。たとえば、壊れているデータや前提に反する入力は、テストや検証で検出する。一方で、業務判断が必要な状態は、martやBI出力を通じて関係者が確認できる形にする。このように、止めるべきものと、可視化して判断すべきものを分けて扱う姿勢を示せる。

さらに、テスト、CI、dbt data tests、期待出力、ドキュメント、レポート、BI出力を通じて、品質確認を一回限りの手作業に閉じないことを重視している。品質を最後の確認作業としてではなく、設計・実装・データ・成果物の中に組み込む姿勢として説明できる。

## 6. 限界と今後の方向性

本資料は、QA専任実務経験、本番水準のQA活動、ISO(International Organization for Standardization:国際標準化機構)規格準拠、本格的なSRE(Site Reliability Engineering:サイト信頼性エンジニアリング)監視基盤を主張するものではない。各ポートフォリオは、あくまでAE / DEを主軸として作成した実装を、品質観点から再解釈したものである。

また、個人ポートフォリオという性質上、実際のプロダクト運用から得られる品質課題までは十分に示せない。リリース後の利用状況、問い合わせ、不具合、障害、ログ、監視データをもとに改善サイクルへ戻すShift Right(リリース後や運用中の観測・学習を品質改善へ戻す考え方)の活動や、PM、開発者、デザイナー、CS、サポートなどと品質リスクを共有して進めるチームとしてのQA活動は、今後実務の中で深めたい領域である。

今後は、これまでポートフォリオで扱ってきたデータ品質、入力契約、指標定義、テスト自動化、再現性への関心を土台にしながら、QA / DQA / QE実務の中で、品質をどのように定義し、確認し、改善していくのかを学びたい。また、Quality Assistance(品質支援) / Quality Enablement(品質活動を可能にする支援)のように、品質をQA担当者だけで抱えるのではなく、チーム全体で扱える状態にする考え方にも関心がある。
