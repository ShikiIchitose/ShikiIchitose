# 顧客ライフサイクルと収益化分析のケーススタディ

> English version: [`02_customer_lifecycle_and_monetization_case_study.md`](02_customer_lifecycle_and_monetization_case_study.md)

## 1. このケーススタディの目的

このケーススタディでは、共通編で整理した dbtモデリング原則を、再利用可能な業務領域である顧客ライフサイクルと収益化分析に適用します。

目的は、特定企業向けの完全な本番アーキテクチャを提案することではありません。事業上の問いを、ソースデータ、業務プロセス、model grain、ファクト、ディメンション、BI / semantic layer への公開、dbtレポーティングマート、テスト、意思決定支援のための出力へどのように接続できるかを示す、モデリングの考え方を提示することです。

このケーススタディは、複数の業務領域に適用できる程度に汎用的でありながら、実務的なアナリティクスエンジニアリングの考え方を示せる程度に具体的であることを目指しています。

この領域は、企業によって異なる意味を持ちます。

- SaaS では、アカウントの有効化、プロダクト利用、サブスクリプション収益、アップセル / 拡張、チャーンを意味する場合があります。
- Fintech では、オンボーディング、口座やアカウントの活動、取引量、収益化、継続、業務レビューやリスクレビューを意味する場合があります。
- e-commerce / marketplace では、獲得、初回購入、リピート購入、注文金額、出品者活動、GMV（Gross Merchandise Value: 流通取引総額）、顧客継続を意味する場合があります。
- B2B services では、アカウントのオンボーディング、契約活動、プロダクト利用、更新、サポート負荷、アカウントヘルスを意味する場合があります。

共通するモデリング上の考え方は、多くの事業において、顧客やアカウントが、獲得、有効化、利用、収益化、継続、フォローアップへどのように進むのかを理解する必要があるという点です。

## 2. この領域が再利用可能なモデリング原型として有用な理由

顧客ライフサイクルと収益化分析は、多くの事業モデルに現れるため、再利用可能なモデリング原型として有用です。

業界によって使われる言葉は異なりますが、背後にある分析構造は似ていることが多いです。

通常、事業では次のような点を理解したいと考えます。

- 顧客、アカウント、購入者、出品者、ユーザー、組織が誰なのか
- そのエンティティがどのように獲得、またはオンボーディングされたのか
- 有効化のマイルストーンに到達したか
- その後もプロダクト、プラットフォーム、アカウント、サービスを利用し続けているか
- 利用や取引が収益とどのように接続しているか
- どのライフサイクル状態にフォローアップが必要か
- どの指標をチーム横断で信頼できるものにする必要があるか

この領域は、dbtモデリングを示すのに適しています。なぜなら、自然に次の要素を含むためです。

- エンティティディメンション
- イベントファクトと取引ファクト
- スナップショットファクト
- stock metrics と flow metrics
- コホート分析とライフサイクル分析
- 業務レビューシグナル
- BI / semantic layer での利用
- 安定した grain と繰り返し使うロジックが重要になるレポーティングマート

この領域における dbtモデリングの価値は、単にテーブルを作ることではありません。顧客行動、エンゲージメント、収益、フォローアップ優先度について、事業チームと分析チームが一貫して考えられるように、テストされ、ドキュメント化され、再利用可能な分析モデルを作ることにあります。

## 3. 想定されるステークホルダーの問い

この領域における中心的なステークホルダーの問いは、例えば次のようになります。

> どの顧客セグメント、アカウント、プロダクト、プラン、チャネルが、有効化、利用、収益、継続を生み出しているのか。また、どのライフサイクル状態にフォローアップが必要なのか。

この問いは、より具体的な事業上の問いに分解できます。

### 3.1 獲得とオンボーディング

例示的な問いは次の通りです。

- どの獲得チャネルや顧客セグメントが、有効化された顧客やアカウントを生み出しているのか
- signup から activation までにどのくらい時間がかかるのか
- どのオンボーディング手順で離脱が最も大きいのか
- signup はしたが、意味のある activation event に到達していない顧客やアカウントは存在するか

### 3.2 利用とエンゲージメント

例示的な問いは次の通りです。

- どの顧客、アカウント、プロダクト、プランが active usage を生み出しているのか
- どの機能やプロダクト領域が継続的なエンゲージメントと関係しているのか
- アクセス権はあるが、利用が少ない、または利用がないアカウントは存在するか
- 利用指標は増加しているのか、減少しているのか、あるいは一部のセグメントに集中しているのか

### 3.3 収益化

例示的な問いは次の通りです。

- どの顧客、アカウント、プラン、プロダクト、チャネルが収益を生み出しているのか
- 利用状況は、サブスクリプション収益、取引収益、手数料、注文金額とどのように関係しているのか
- コストが高い、または high-touch であるにもかかわらず、収益化が弱いアカウントは存在するか
- active usage without billing や paid access without usage のような、利用と課金のズレは存在するか

### 3.4 継続とライフサイクル上のフォローアップ

例示的な問いは次の通りです。

- どの顧客やアカウントが継続、非アクティブ、休眠、またはチャーンリスク状態にあるのか
- どのライフサイクル状態に、営業、カスタマーサクセス、オペレーション、リスク、ファイナンスによるフォローアップが必要なのか
- activation は強いが retention が弱いセグメントはどこか
- 更新やリピート購入の前に、利用低下を示しているアカウントは存在するか

### 3.5 経営・業務レポーティング

例示的な問いは次の通りです。

- どの KPI（key performance indicator: 重要業績評価指標）をチーム横断で信頼できるものにする必要があるか
- どのダッシュボードに、安定し管理された定義が必要か
- どの業務レビューリストを定期的に更新する必要があるか
- 指標を意思決定に使う前に、どの前提をテストする必要があるか

## 4. モデル化する業務プロセス

ファクトとディメンションを設計する前に、モデル化する必要がある業務プロセスを特定します。

この領域では、一般に次のような業務プロセスが考えられます。

| 業務プロセス | 説明 | 想定モデル |
|---|---|---|
| Signup / registration | 顧客、アカウント、ユーザー、購入者、出品者がシステムに入る | `fct_signup` |
| Onboarding / activation | エンティティが意味のある first-value milestone に到達する | `fct_activation_event` |
| Product usage | エンティティがプロダクト、機能、アカウント、サービスを利用する | `fct_usage_event` / `fct_usage_daily` |
| Transaction / order | エンティティが取引、注文、送金、購入を行う | `fct_transaction` / `fct_order` |
| Subscription lifecycle | サブスクリプションが開始、更新、拡張、縮小、解約、または継続される | `fct_subscription_event` / `fct_subscription_snapshot_monthly` |
| Billing / invoicing | 請求、インボイス、入金、返金、収益認識を追跡する | `fct_invoice` / `fct_payment` |
| Support / service interaction | 顧客、ユーザー、アカウントがサポートへ連絡する、または業務対応を必要とする | `fct_support_case` |
| Lifecycle review signal | 顧客、アカウント、セグメントをフォローアップ状態に分類する | `fct_lifecycle_review_signal` または `lifecycle_review_candidates` mart |

正確なプロセスは、企業やソースシステムによって異なります。重要なモデリング上の手順は、すべての raw tables を1つの広い分析テーブルに結合するのではなく、業務プロセスを分けて考えることです。

ファクトテーブルは、業務プロセスにおける測定可能なイベント、取引、状態を表すべきです。利用可能な raw sources を都合よく結合しただけのものにするべきではありません。

## 5. ソースデータのカテゴリ

本番運用を意識した実装では、利用可能なソースシステム、その所有チーム、grain、更新パターン、データ品質を理解するところから始めます。

例示的なソースカテゴリは次の通りです。

| ソースカテゴリ | ソースデータの例 | 主なモデリング上の役割 |
|---|---|---|
| 顧客 / アカウントのマスタデータ | 顧客レコード、アカウントレコード、組織レコード | 安定したエンティティディメンションを定義する |
| ユーザー / メンバーデータ | ユーザー、seat、チームメンバー、購入者 / 出品者プロフィール | ユーザーレベル、またはロールレベルの分析を支える |
| 獲得データ | キャンペーン、チャネル、紹介、流入元 | 獲得品質を分析する |
| プロダクト / サービスカタログ | プロダクト、プラン、機能、SKU、サービス | 何が利用・購入されているかを定義する |
| Signup / onboarding events | 登録、認証、初回ログイン、初回の主要アクション | activation funnel をモデル化する |
| 利用 / 行動イベント | セッション、機能利用、API call、ページビュー、プロダクトイベント | エンゲージメントと活動をモデル化する |
| 注文 / 取引 | 購入、送金、取引、注文、取引イベント | 事業活動と取引行動をモデル化する |
| サブスクリプション / 契約データ | プラン、更新、解約、拡張、契約条件 | 継続収益のライフサイクルをモデル化する |
| 請求 / 収益データ | invoice、入金、手数料、返金、credit | 収益化と照合をモデル化する |
| サポート / オペレーションデータ | ticket、case、手動レビュー、介入 | フォローアップと業務負荷をモデル化する |

source layer では、raw source grain を保ち、必要に応じて source contracts を公開するべきです。staging models では、重い業務ロジックを避けながら、名前、型、タイムスタンプ、軽量なソースレベルの補助フィールドを標準化します。

## 6. 再利用可能なファクトとディメンション

再利用可能なモデル構造には、通常、安定した業務エンティティを表すディメンションと、測定可能な業務プロセスを表すファクトモデルが含まれます。

以下のモデルは例示的な候補であり、必ず実装すべき要件ではありません。実際のモデル設計は、企業のソースシステム、業務プロセス、BI / semantic layer、ステークホルダーの優先度によって変わります。

ここで使うレイヤー名は、意図的に汎用的なものにしています。一般的な本番運用を意識した dbt構成では、再利用可能な `dim_*` と `fct_*` モデルが `marts / dimensional models` 配下に置かれ、それらが参照するロジックを intermediate models が準備する場合があります。

私のポートフォリオでは、再利用可能なファクトとディメンションのために独立した `core` レイヤーを使い、`core` の下流にある intermediate models で re-graining、stock logic、mart support logic を分離しました。重要なのはフォルダ名そのものではなく、各レイヤーの責任が明確であり、依存方向が理解しやすいことです。

### 6.1 ディメンションモデルの候補

| モデル | grain の例 | 目的 |
|---|---|---|
| `dim_customer` | 顧客ごとに1行 | 顧客属性とセグメンテーション |
| `dim_account` | アカウント、または組織ごとに1行 | B2B や複数ユーザー型プロダクトのアカウントレベル分析 |
| `dim_user` | ユーザー、またはメンバーごとに1行 | ユーザーレベルの活動やロール分析 |
| `dim_product` | プロダクト、またはサービスごとに1行 | プロダクトレベルのパフォーマンス分析 |
| `dim_plan` | プラン、または価格ティアごとに1行 | サブスクリプションと収益化分析 |
| `dim_channel` | 獲得チャネル、または販売チャネルごとに1行 | 獲得とチャネル別パフォーマンス |
| `dim_date` | カレンダー日付ごとに1行 | 一貫した時系列レポーティング |

領域によっては、`customer`、`account`、`organization`、`buyer`、`seller` が別々のエンティティになる場合があります。一方で、これらの概念の一部が統合される場合もあります。

### 6.2 ファクトモデルの候補

| モデル | grain の例 | 目的 |
|---|---|---|
| `fct_signup` | signup event ごとに1行 | 獲得と登録の分析 |
| `fct_activation_event` | activation event ごとに1行 | activation と time-to-value の分析 |
| `fct_usage_daily` | 顧客、アカウント、またはユーザー、プロダクト、日付ごとに1行 | エンゲージメントと利用分析 |
| `fct_transaction` | 取引ごとに1行 | 取引量、取引金額、取引行動の分析 |
| `fct_order` / `fct_order_line` | 注文ごと、または注文明細ごとに1行 | コマース型の購入分析 |
| `fct_subscription_snapshot_monthly` | アカウント、月ごとに1行 | 継続収益ライフサイクルとチャーン分析 |
| `fct_invoice` | invoice ごとに1行 | 請求、インボイス、請求金額の分析 |
| `fct_payment` | payment ごとに1行 | 入金回収と支払いステータスの分析 |
| `fct_support_case` | サポート、またはオペレーションケースごとに1行 | サービス負荷と顧客フォローアップ分析 |

### 6.3 再利用可能な中間モデルの候補

intermediate models は、有用だが必ずしも最終利用者向けではないロジックを分離するために使います。

例は次の通りです。

| モデル | grain の例 | 目的 |
|---|---|---|
| `int_usage_aggregated_to_month` | 顧客、アカウント、またはユーザー、プロダクト、月ごとに1行 | 下流 marts 向けに月次利用指標を準備する |
| `int_customer_revenue_monthly` | 顧客、またはアカウント、月ごとに1行 | invoice、payment、取引収益を集計する |
| `int_account_status_as_of_month_end` | アカウント、月ごとに1行 | 月末時点のライフサイクル状態を導出する |
| `int_recent_activity_30d` | 顧客、アカウント、またはユーザーごとに1行 | 直近活動状態を導出する |
| `int_lifecycle_review_signals` | 顧客、またはアカウント、シグナルごとに1行 | mart へ公開する前にフォローアップロジックを分離する |

intermediate models は、re-graining、stock logic、ライフサイクル分類、繰り返し使う mart support logic に有用です。複雑な変換を確認しやすく、テストしやすい形にします。

特に、イベントレベルのデータを日次 grain へ集計する、注文明細データを注文 grain へ集計する、月末時点の状態を導出する、複数の下流 marts で使う入力を準備する、といった変換を分離する場所として適しています。

### 6.4 grain と re-graining の方針

staging models と異なり、ファクトモデルやディメンションモデルは、必ずしも raw source grain を保つとは限りません。代わりに、公開する各モデルは、明確に定義された business grain を持つべきです。

ディメンションモデルは、安定した業務エンティティ、またはエンティティのバージョンを表すべきです。例えば、`dim_customer` は顧客ごとに1行を持つ場合があります。一方、履歴を考慮した顧客ディメンションでは、顧客バージョン、または有効期間ごとに1行を持つ場合があります。

ファクトモデルは、測定可能な業務プロセス、イベント、取引、スナップショットを表すべきです。例えば、`fct_transaction` は取引ごとに1行を持つ場合があり、`fct_usage_daily` は顧客、アカウント、またはユーザー、プロダクト、日付ごとに1行を持つ場合があります。

ファクトモデルで re-graining が必要な場合、そのロジックが複雑である、複数の下流モデルで再利用される、または指標の解釈を守る上で重要であるなら、通常は intermediate model に分離する方がよいです。

例は次の通りです。

| ソースの grain | 中間ロジック | 公開モデルの grain |
|---|---|---|
| usage event ごとに1行 | イベントを選択したエンティティ・プロダクト・日付 grain に集計する | `fct_usage_daily`: 顧客、アカウント、またはユーザー、プロダクト、日付ごとに1行 |
| 注文明細ごとに1行 | 注文明細を注文単位に集計する | `fct_order`: 注文ごとに1行 |
| 取引ごとに1行 | 取引をアカウント月次に集計する | `fct_account_activity_monthly`: アカウント、月ごとに1行 |
| サポートケースごとに1行 | サポートケースをアカウント月次に集計する | `fct_account_support_monthly`: アカウント、月ごとに1行 |
| サポート活動にプランと収益文脈を加えたもの | サポート負荷、プランティア、収益文脈を組み合わせる | `account_support_monetization_monthly` mart: アカウント、月ごとに1行 |

下流利用が1つだけの単純な変換であれば、re-graining ロジックを公開ファクトモデルの中に直接実装してもよい場合があります。しかし、ロジックが再利用される、複雑である、または解釈上重要である場合は、変換を見える形にし、テスト可能で再利用可能にするため、intermediate model に分離する方が望ましいです。

重要なのは、すべての変換に intermediate model が必要ということではありません。重要なのは、公開されるファクト、ディメンション、mart が documented grain を持ち、grain を変更するロジックが確認・テストしやすいことです。

## 7. grain に関する判断

grain は、この領域において最も重要なモデリング判断の1つです。

各モデルは、1行が何を表すかを明確に定義する必要があります。指標は、そのモデルが公開している grain においてのみ解釈するべきです。同じ業務領域で複数の分析観点が必要な場合は、複数の grain を1つのモデルに混在させるのではなく、grain ごとに別のモデルを公開する方が望ましいです。

### 7.1 grain の例

| モデル | grain | 解釈 |
|---|---|---|
| `dim_customer` | 顧客ごとに1行 | 顧客レベルの属性とセグメンテーション |
| `dim_account` | アカウント、または組織ごとに1行 | アカウントレベルの属性と B2B 分析 |
| `fct_signup` | signup event ごとに1行 | 登録と獲得の flow |
| `fct_activation_event` | activation event ごとに1行 | first-value、またはマイルストーン達成 |
| `fct_usage_daily` | 顧客、アカウント、またはユーザー、プロダクト、利用日ごとに1行 | 定義されたエンティティ・プロダクト grain における日次エンゲージメント |
| `fct_transaction` | 取引ごとに1行 | 取引レベルの活動と金額 |
| `fct_order` | 注文ごとに1行 | 注文レベルの購入行動 |
| `fct_order_line` | 注文明細ごとに1行 | アイテムレベル、または SKU レベルの購入行動 |
| `fct_subscription_snapshot_monthly` | アカウント、月ごとに1行 | 月次期間における継続収益ライフサイクル状態 |
| `customer_lifecycle_monthly` | レポート月、セグメント、ライフサイクル状態ごとに1行 | 集計済みライフサイクルレポーティング |
| `account_health_current` | 現在のアカウントごとに1行 | 現在のアカウントレベルのヘルスレビュー |
| `churn_risk_candidates_current` | レビューが必要な現在のアカウント、または顧客ごとに1行 | 現在のレビュー候補一覧 |

### 7.2 grain が重要な理由

複数の grain が1つのモデルに混在すると、指標の解釈が難しくなります。

例えば、次のような問題があります。

- `active_users_total` はプロダクトレベルの grain では妥当でも、同じユーザーが複数プロダクトを使える場合、プロダクト行をまたいで合計すると危険です。
- `monthly_revenue` はアカウント月次 grain では妥当でも、慎重な re-graining なしにユーザーレベルの利用データと結合すると二重計上される可能性があります。
- `transactions_total` は月次の flow metric である一方、`active_accounts_at_month_end` は月末時点の stock metric です。

良いモデルは、こうした境界を明示します。新しい事業上の問いが別の grain を必要とする場合、集計済みの行から BI層の計算で存在しない詳細を推測させるのではなく、その grain を持つ別のドキュメント化されたモデルや mart を公開する方が望ましいです。

## 8. stock metrics と flow metrics

顧客ライフサイクルと収益化分析では、stock metrics と flow metrics が自然に組み合わさります。これらは慎重にモデル化する必要があります。

### 8.1 flow metrics

flow metrics は、ある期間中の活動量を表します。

例は次の通りです。

| 指標 | 意味 |
|---|---|
| `signups_total` | 期間中の signup 数 |
| `activations_total` | 期間中の activation 数 |
| `sessions_total` | 期間中の合計 session 数 |
| `transactions_total` | 期間中の合計 transaction 数 |
| `orders_total` | 期間中の合計 order 数 |
| `revenue_amount` | 期間中に測定、または認識された revenue |
| `payments_total` | 期間中に記録された payment 数 |
| `payment_amount` | 期間中に回収された payment amount |
| `support_cases_opened` | 期間中に開始された support case 数 |

### 8.2 stock metrics

stock metrics は、ある時点の状態を表します。

例は次の通りです。

| 指標 | 意味 |
|---|---|
| `active_accounts_at_month_end` | 月末時点で active な account |
| `active_subscriptions_at_month_end` | 月末時点で active な subscription |
| `open_support_cases_at_month_end` | 月末時点で未解決の support case |
| `dormant_accounts_at_month_end` | 月末時点で dormant と分類された account |
| `at_risk_accounts_at_month_end` | 月末時点で at risk と分類された account |

### 8.3 モデリング上の含意

stock metrics と flow metrics を1つの mart に組み合わせる場合、レポート上の grain と時間の意味を明示する必要があります。

例えば、月次アカウントライフサイクル mart には、次の指標が含まれる場合があります。

- 月中の signup
- 月中の activation
- 月中の利用
- 月中の revenue
- 月末時点の active account
- 月末時点の dormant account

これらの指標はすべて有用ですが、同じ時間的意味を持っているわけではありません。mart のドキュメンテーションでは、どの指標が期間中の flow であり、どの指標が特定時点の stock であるかを説明する必要があります。

収益関連指標についても、それが請求額、入金額、収益認識額、または別の事業固有の収益定義を表すのかを明確にする必要があります。

## 9. 業務レビューシグナル

望ましくない業務状態がすべて pipeline を失敗させるべきとは限りません。

この領域では、珍しい状態や望ましくない状態の多くが、妥当な分析出力である場合があります。それらは変換処理の失敗として扱うのではなく、レビューシグナルとして表示するべきです。

例示的な業務レビューシグナルは次の通りです。

| レビューシグナル | 想定される解釈 |
|---|---|
| signup without activation | オンボーディングのフォローアップ候補 |
| activated account with no recent usage | エンゲージメント、またはカスタマーサクセスのフォローアップ候補 |
| high usage with low monetization | 価格設定、パッケージング、または請求のレビュー候補 |
| paying account with no recent usage | 更新、またはカスタマーサクセスのレビュー候補 |
| active usage without expected billing | ファイナンス、または契約のレビュー候補 |
| high support load with low retention | 顧客体験のレビュー候補 |
| declining usage before renewal | チャーンリスクのレビュー候補 |
| dormant customer with prior high value | 再活性化候補 |

これらのシグナルは、意思決定支援のための出力としてモデル化するべきです。必ずしもデータ品質上の失敗を示すものではありません。

### 9.1 レビューシグナルは自動的な業務アクションではない

業務レビューシグナルは、自動的な業務アクションとして扱うべきではありません。

例えば、`dormant_customer_with_prior_high_value` というシグナルは、自動的に割引、キャンペーン、または outreach action を送るべきだという意味ではありません。これは、その顧客が過去に高い価値を持っていた一方で現在は非アクティブであるため、再活性化候補としてレビューする価値があるかもしれない、という意味です。

アナリティクスエンジニアリングは、レビュー対象の顧客リスト、指標定義、関連する文脈を提供できます。ただし、実際のキャンペーン、オファー、outreach strategy、除外ルール、優先順位付けロジックは、適切な事業ステークホルダーが決めるべきです。

この区別が重要なのは、レビューシグナルは業務状態を見えるようにし、議論可能にするために設計されるものだからです。レビューシグナルは意思決定を支援するものであり、黙って置き換えるものではありません。

### 9.2 文脈フィールドとステークホルダーとの認識合わせ

アナリティクスエンジニアリングは、単純なレビューフラグだけではアクションに不十分だと判断する場合があります。

例えば、`is_reactivation_candidate = true` は、マーケティング、営業、カスタマーサクセス、オペレーションチームが責任を持って使うには、追加の文脈を必要とする場合があります。有用な文脈には、次のようなものがあります。

- `contact_permission_status`
- `unsubscribe_flag`
- 過去の苦情履歴
- 過去の margin
- 直近のキャンペーン接触
- 直近のサポート状態
- 現在のアカウント、または顧客ステータス
- 最終活動日
- 最終活動からの経過日数

これらの文脈フィールドは、ステークホルダーがより適切な判断をする助けになります。ただし、それらが黙って公式のキャンペーン適格条件、除外ルール、優先順位付けルールになるべきではありません。

例えば、アナリティクスエンジニアリングは、`contact_permission_status` と `unsubscribe_flag` を reactivation candidate mart に含めることを提案できます。これは、ステークホルダーが outreach の適切性を理解する助けになるためです。ただし、それらのフィールドによって顧客をキャンペーンから除外するべきか、優先順位に影響させるべきか、outreach eligibility を定義するべきかは、関連する business owners とすり合わせる必要があります。

この意味で、アナリティクスエンジニアリングは、モデリング上の制約を特定し、有用な文脈を提案し、補助フィールドを公開し、解釈上の注意をドキュメント化できます。最終的な inclusion、exclusion、prioritization、outreach rules は、公式なレビュー logic に組み込む前に、適切な事業ステークホルダーと決めるべきです。

また、変換処理の失敗は、次のような構造上、契約上の問題に限定するべきです。

- 必須キーの欠損
- 一意であるべき primary key の重複
- 不正な許可値
- 必須ディメンションに解決できないリレーションシップ
- 不可能、または一貫しないタイムスタンプ
- ソースと変換後の合計値の照合不一致

この分離により、dbtテストは構造上・意味上の前提に集中し、marts やダッシュボードはレビューを必要とする妥当な業務状態を表示できます。

次のセクションでは、この区別を、アナリティクスエンジニアリングと事業ステークホルダーのより広い責任境界へ一般化します。

---

## 10. アナリティクスエンジニアリングの責任範囲とステークホルダーとの認識合わせ

アナリティクスエンジニアリングは、信頼できる意思決定支援モデルを提供できます。ただし、価格設定、サポート、カスタマーサクセス、リスク、ファイナンス、プロダクトに関する事業上の意思決定を置き換えるべきではありません。

この領域では、dbt mart が顧客やアカウントを次のようなレビュー向け状態に分類する場合があります。

- `high_touch_high_revenue`
- `high_touch_low_revenue`
- `low_touch_high_revenue`
- `low_touch_high_support_load`

これらの分類は、顧客ライフサイクル、サポート負荷、収益化パターンを確認しやすくするため有用です。ただし、自動的な業務判断ではなく、意思決定支援のための出力として扱うべきです。

例えば、`high_touch_low_revenue` のアカウントは、価格設定、パッケージング、サポート方針、カスタマーサクセスの動き方、アカウント戦略についての議論を必要とするかもしれません。分析モデルは、その状態を表示し、指標ロジックを定義し、パターンを見えるようにできます。しかし、実際の意思決定は、経営、カスタマーサクセス、営業、サポート、ファイナンス、プロダクト、リスクチームなど、関連する business owners が持つべきです。

### 10.1 アナリティクスエンジニアリングが担うべきこと

この文脈では、アナリティクスエンジニアリングは次の領域を担う、または強く貢献するべきです。

- ステークホルダーの問いを、モデル化可能な業務概念へ翻訳すること
- 指標定義と model grain を明確にすること
- 必要なソースデータと source contracts を特定すること
- 再利用可能なファクト、ディメンション、intermediate models、marts を設計すること
- 構造上・意味上の前提に対する dbtテストを実装すること
- 前提、制約、解釈上の注意をドキュメント化すること
- 安定したモデルを BIツール、semantic layer、ダッシュボード、レポート、レビュー workflow へ公開すること
- 変換ロジックの再現性、lineage、追跡可能性を維持すること

目的は、業務状態を測定可能で、説明可能で、再利用可能にすることです。

本番環境では、この責任は構造化された dbt change workflow によって支えられる場合もあります。公開されている例として、GitLab の dbt change workflow があります。これは、dbt変更を計画、作成、検証の段階に分け、scope の定義、test の定義、環境の準備、ローカルおよびリモートでの検証、下流テーブルやレポートへの影響確認、業務ロジックの整合性確認を含むものです。

このような workflow は、アナリティクスエンジニアリングが単に transformation SQL を書くことではないことを補強します。モデル変更をテスト可能、レビュー可能、ドキュメント化済み、下流利用者にとって理解可能な状態にすることも含まれます。

### 10.2 アナリティクスエンジニアリングの外に残すべきこと

アナリティクスエンジニアリングが一方的に決めるべきではないものには、次のようなものがあります。

- 価格プランを変更するかどうか
- 電話サポートを有料機能にするかどうか
- 顧客を別プランへ移すかどうか
- サポート方針を制限、または拡大するかどうか
- 営業、カスタマーサクセス、ファイナンス、プロダクト、リスクチームが具体的なアクションを取るべきかどうか
- レビュー候補が確定的な問題であるかどうか

これらは事業上の意思決定です。アナリティクスエンジニアリングは根拠をより明確にできますが、解釈とアクションは適切な domain stakeholders が持つべきです。

### 10.3 モデル化前に確認すべきステークホルダーへの問い

レビュー向けの分類を実装する前に、まず重要な用語の意味をステークホルダーとすり合わせます。

例えば、事業側が high-touch accounts を特定したい場合、次の点を確認します。

- high-touch は、電話サポート、専任カスタマーサクセス支援、手動オンボーディング、アドバイザリーサービス、総サポート負荷のどれを意味するのか
- サポート負荷は、case count、対応時間、エスカレーション数、電話分数、推定サポートコストのどれで測るべきか
- しきい値は、プラン、セグメント、地域、アカウント規模、契約種別によって変えるべきか
- 一時的なオンボーディング支援は、継続的なサポート負荷と別扱いにするべきか

事業側が low monetization を特定したい場合、次の点を確認します。

- monetization は、サブスクリプション収益、取引収益、手数料、gross revenue、net revenue、gross margin、contribution margin のどれを意味するのか
- 指標は、月次、四半期、直近12か月、顧客生涯のどの期間で測るべきか
- 割引、返金、credit、プロモーション価格を差し引くべきか
- 比較対象は、サポートコスト、プラン上の期待値、顧客セグメント、獲得チャネルのどれにするべきか

事業側が review candidates を定義したい場合、次の点を確認します。

- 出力は、経営レポーティング、カスタマーサクセスの優先順位付け、サポートオペレーション、ファイナンスレビュー、プロダクト戦略、リスク監視のどれを目的としているのか
- mart は、説明的な status label、priority score、業務キューのどれを出すべきか
- どの false positive は許容でき、どの false negative は重大か
- 候補が表示された後のフォローアップアクションは誰が持つのか

### 10.4 初期検出ルールから公式レビュー logic へ

レビューシグナルの中には、一時的な変動、文脈不足、ライフサイクル上のタイミングに影響されるものがあります。

例えば、ある low-touch account が月次 mart で `high_support_load` としてフラグされる場合があります。その月にサポート活動が増えたためです。この分類はその月については技術的に正しいかもしれません。しかし、その増加がすでに解決済みの一時的なオンボーディング問題によるものであれば、誤解を招く可能性があります。

このような状況では、アナリティクスエンジニアリングが初期検出ルールを黙って事業判断ルールに変えるべきではありません。

代わりに、制約を表示し、次のような追加文脈を提案するべきです。

- 直近3か月、または6か月の support load
- 最近の期間内で high-support-load だった月数
- オンボーディング期間フラグ
- サポートケースカテゴリ
- 解決済み、未解決の case count
- 推定サポートコスト
- plan tier と期待される support level
- 前月・翌月との比較

公式レビュー mart にロジックを昇格させる前に、`account_support_load_trend_monthly` のような診断用モデルが有用な場合があります。

この診断用モデルは、ステークホルダーが次の状態を区別する助けになります。

- 一時的なオンボーディング上の増加
- 継続的な高サポート負荷
- 未解決の業務上の問題
- 想定された high-touch support
- low-touch account であるにもかかわらず、想定外に高いサポート負荷を生み出している状態

business owners が定義、しきい値、時間窓、想定用途に合意した後、そのロジックを公式レビュー mart、または governed metric へ昇格できます。

この区別が重要なのは、アナリティクスエンジニアリングはモデリング上の制約を特定し、より良い分析文脈を提案できますが、何を公式レビュー条件にするかの定義は、関連するステークホルダーとすり合わせるべきだからです。

### 10.5 レビュー分類の例

ステークホルダーとの認識合わせ後、レポーティングマートは `support_monetization_status` のようなレビュー向けフィールドを公開できます。

例示的な status は次の通りです。

| Status | 意味 | 想定されるフォローアップ担当 |
|---|---|---|
| `high_touch_high_revenue` | アカウントは high-touch support を受けており、高い revenue も生み出している | 経営 / 営業 / カスタマーサクセス |
| `high_touch_low_revenue` | アカウントは high-touch support を受けているが、収益化が弱い | カスタマーサクセス / ファイナンス / 営業 |
| `low_touch_high_revenue` | アカウントは限定的な手動サポートで高い revenue を生み出している | 経営 / 営業 / プロダクト |
| `low_touch_high_support_load` | low-touch が期待されるアカウントだが、高い support load を生み出している | サポート / プロダクト / カスタマーサクセス |
| `aligned` | 現時点でレビュー条件に該当しない | ただちに必要なフォローアップはない |

モデルでは、それぞれの status がどのように導出されるかをドキュメント化するべきです。例えば、`high_touch` が plan tier、サポート接点、電話サポート利用、推定サポートコスト、またはそれらの組み合わせに基づくのかを明示する必要があります。

これにより、mart は意思決定支援に有用になりつつ、事業上の意思決定の責任範囲を明確に保てます。

## 11. BI / semantic layer への公開

本番運用を意識した環境では、一般に、十分な機能を持つ BI / semantic layer を、再利用可能な dimensional models の主な利用層として扱います。

この層の目的は、dbtモデルを可視化することだけではありません。事業ユーザー向けに、管理されたリレーションシップ、measure、explore、ダッシュボード、セルフサービス分析体験を提供することにもあります。

### 11.1 本番運用を意識した公開パターン

典型的な公開パターンは次のようになります。

```text
sources
  ↓
staging
  ↓
intermediate
  ↓
marts / dimensional models
  - dim_*
  - fct_*
  ↓
BI / semantic layer
  - customer lifecycle explore / data model
  - account health explore / data model
  - product usage explore / data model
  - revenue and retention measures
  ↓
dashboards / self-service BI / stakeholder reporting
```

この構造では、dbt がテストされ、ドキュメント化されたファクトとディメンションを提供します。その上で、BI / semantic layer が、利用者向けのリレーションシップ、管理された measure、explore、ダッシュボード、セルフサービス分析経路を定義します。

この構成により、結合条件や指標計算を各ダッシュボード内の個別 SQL に分散させることを避けられます。dbt側で信頼できるモデルを提供し、BI / semantic layer 側で利用者向けの関係性や指標を定義することで、事業ユーザーが安全に複数の切り口からデータを探索できるようになります。

### 11.2 管理されたリレーションシップと探索

顧客、アカウント、プロダクト、プラン、利用、取引、サブスクリプション、請求、入金などの再利用可能な dimensional models は、管理された探索のために BI / semantic layer へ公開できます。

重要なのは、BI層で変換ロジックを重複実装しないことです。BI / semantic layer は、テスト済みの dbtモデルの上に置き、事業ユーザーがそれらを安全に探索する方法を定義するべきです。

例えば、BI / semantic layer では次のような内容を定義できます。

- 顧客、またはアカウントディメンションが、利用、取引、サブスクリプション、請求、サポートのファクトとどのように関係するか
- 探索に有効な join はどれか
- 事業ユーザーが利用できる measure はどれか
- 指標を切り分けるのに適した dimension はどれか
- grain と集計上の注意点を、下流利用者にどのように明示するか

これにより、中心的な変換ロジックを dbt に保ちながら、事業ユーザーが管理されたインターフェースを通じて、顧客ライフサイクル、利用、収益化、継続、レビュー状態を探索できるようになります。

### 11.3 管理された measure と指標定義

BI / semantic layer では、テスト済みの dbtモデルの上に、管理された measure を定義できます。

管理された measure の例は次の通りです。

| Measure | 想定される定義領域 |
|---|---|
| `activated_customers` | 定義済みマイルストーンに基づく activation logic |
| `active_accounts` | account status、usage threshold、または subscription state |
| `monthly_active_users` | レポート期間内の distinct active users |
| `revenue_amount` | 請求、入金、収益認識、取引ベース、または margin ベースの revenue logic |
| `churned_accounts` | サブスクリプションベース、または活動ベースの churn definition |
| `retention_rate` | コホートベース、または期間ベースの retained account logic |
| `average_revenue_per_account` | revenue を active、paying、または eligible accounts で割ったもの |

正確な定義は、事業ステークホルダーとすり合わせ、dbt model documentation、semantic layer、またはその両方にドキュメント化するべきです。

収益関連の measure は特に明示的である必要があります。その指標が、請求 revenue、入金額、収益認識額、取引手数料、gross revenue、net revenue、gross margin、または別の事業固有の収益化概念を表すのかを明確にするべきです。

### 11.4 ダッシュボードとセルフサービスBIでの利用

ダッシュボードとセルフサービスBIは、事業上の問いに合った grain のモデルを利用するべきです。

例えば、顧客ライフサイクルダッシュボードは、獲得、activation、利用、収益化、継続の傾向を監視する場合があります。アカウントヘルスダッシュボードは、現在のアカウントレベルのライフサイクル状態やサポート状態に焦点を当てる場合があります。プロダクト利用ダッシュボードは、プロダクト、機能、プラン、セグメント、アカウント種別ごとのエンゲージメントを分析する場合があります。業務レビューダッシュボードは、フォローアップが必要なアカウントや顧客を表示する場合があります。

BI / semantic layer は、model grain と指標の解釈を下流利用者に明確にするべきです。例えば、SaaS のプロダクトレベルの active user counts や、e-commerce のカテゴリレベルの buyer counts は、それぞれの product-month 行、または category-month 行の中では妥当な場合があります。しかし、同じユーザーや顧客が複数行に現れる可能性がある場合、それらをグローバルな distinct user count や customer count として安易に合計するべきではありません。

これは、ダッシュボードがライフサイクル、利用、収益、サポート、レビュー状態の指標を組み合わせる場合に特に重要です。ダッシュボードは指標を利用しやすくできますが、その指標を妥当にする前提を隠すべきではありません。

### 11.5 解釈上の注意とレポーティングマートへの橋渡し

BI / semantic layer は、業務指標を使いやすい形で公開するべきですが、重要なモデリング上の前提を隠すべきではありません。

ドキュメンテーションでは、次の内容を説明するべきです。

- model grain
- 指標定義
- stock と flow の時間的意味
- ソースシステム上の前提
- 既知の制約
- 有効な集計経路
- 業務定義の所有者
- レビュー状態に関する解釈上の注意

ライフサイクルレビュー出力については、BI層はレビュー状態を見えるようにし、説明可能にするべきです。ただし、それらの状態を、自動的な価格設定、キャンペーン、サポート、ファイナンス、カスタマーサクセス、プロダクト施策へ黙って変換するべきではありません。

例えば、`churn_risk_candidate` や `dormant_customer_with_prior_high_value` という status は、アカウントをレビューする価値があることを示す場合があります。しかし、それ自体が、キャンペーン、割引、outreach action、価格変更、サポート介入を行うべきかどうかを決めるわけではありません。

それらのフォローアップ判断は、適切な事業ステークホルダーとすり合わせるべきです。

実務上、このドキュメンテーションは、ダッシュボード説明、指標定義、semantic model descriptions、データカタログ、BIツールのツールチップによって支援できます。例えば、dbt exposures はダッシュボードのような下流利用をドキュメント化でき、semantic layer や BIツールは、指標定義、説明、リレーションシップ、解釈文脈を data consumers に直接公開できます。

アナリティクスエンジニアリングは、model grain、指標ロジック、lineage、ダッシュボード解釈を接続するため、このドキュメンテーションを担う、または強く貢献できます。ただし、指標が公式レポーティング、レビュー workflow、業務アクションルールに影響する場合、指標ドキュメンテーションは事業ステークホルダーともすり合わせるべきです。

十分な機能を持つ BI / semantic layer がある場合でも、一部のロジックは dbtレポーティングマートとして materialize する方が適していることがあります。これは、繰り返し集計、stock-and-flow logic、review candidate classification、ダッシュボード性能最適化、複数ツールをまたいだ再利用が必要な場合に特に当てはまります。

次のセクションでは、dbtレポーティングマートがどこで価値を持つかを説明します。

## 12. dbtレポーティングマートが有用な場面

十分な機能を持つ BI / semantic layer がある場合でも、繰り返し使われる、複雑である、またはレビュー向けであるロジックを materialize すべき場面では、dbtレポーティングマートが価値を持ちます。

例えば、次のような場合には dbtレポーティングマートを検討します。

- 重い、または繰り返し実行される集計
- 複雑な stock-and-flow metrics
- ダッシュボード性能の最適化
- 安定したダッシュボード向け抽出データ
- 業務レビュー候補テーブル
- BI、notebook、SQL、script、report をまたいだ再利用
- 単一のBIツールの外側でテスト・レビューすべき業務ロジック

例示的なレポーティングマート候補は次の通りです。

| Mart | grain の例 | 目的 |
|---|---|---|
| `customer_lifecycle_monthly` | レポート月、セグメント、ライフサイクル状態ごとに1行 | ライフサイクルの動きとアカウント / 顧客状態を要約する |
| `activation_funnel_weekly` | signup week、funnel step ごとに1行 | オンボーディングの conversion と drop-off を分析する |
| `usage_engagement_monthly` | レポート月、セグメント、プロダクト、プランごとに1行 | プロダクトエンゲージメントと利用強度を分析する |
| `revenue_retention_monthly` | レポート月、セグメント、プロダクト、プランごとに1行 | revenue、retention、expansion、churn を比較する |
| `account_health_current` | 現在のアカウントごとに1行 | 現在のアカウント状態とヘルス指標を公開する |
| `churn_risk_candidates` | レビューが必要なアカウント、または顧客ごとに1行 | カスタマーサクセス、または継続フォローアップを支援する |
| `monetization_review_candidates` | レビューが必要なアカウント、顧客、またはプロダクトごとに1行 | 利用、収益、請求の整合性上の論点を表示する |
| `operational_review_candidates` | 業務レビュー候補ごとに1行 | 部門横断のフォローアップを支援する |

これらの marts の目的は、BI / semantic layer を置き換えることではありません。安定し、再利用可能で、テスト可能で、追跡可能な業務ロジックを materialize することに明確な価値がある場合に、それを実現することです。

## 13. 業界別の解釈

同じモデリング原型でも、業界によって異なる解釈ができます。

以下の対応表は例示です。実際の実装は、企業のソースシステム、事業モデル、データ品質、ステークホルダーの優先度によって変わります。

| 汎用概念 | SaaSでの解釈 | Fintechでの解釈 | e-commerce / marketplaceでの解釈 | B2B serviceでの解釈 |
|---|---|---|---|---|
| 顧客 / アカウント | アカウント、ワークスペース、組織、ユーザー | 顧客、口座 / アカウント、ウォレット、加盟店 | 顧客、購入者、出品者、ショップ | アカウント、クライアント、契約、組織 |
| プロダクト / プラン | プロダクト、モジュール、機能、サブスクリプションプラン | 口座種別、金融商品、カード、ウォレット機能 | 商品、SKU、カテゴリ、出品、マーケットプレイスサービス | サービスプラン、契約種別、ソリューション領域 |
| 獲得 | signup、トライアル開始、リード獲得元 | 申込開始、口座開設、キャンペーン流入元 | 登録、初回訪問、出品者オンボーディング | リード作成、契約開始、オンボーディング依頼 |
| 有効化 | 初回の主要アクション、オンボーディング完了、初回チーム招待 | KYC（Know Your Customer: 本人確認）完了、初回入金、初回取引 | 初回購入、初回出品、初回販売 | 初回サービス利用、初回プロジェクト開始 |
| 利用 / 活動 | セッション、機能利用、API call、seat 利用 | 取引、送金、残高変動、カード利用 | 注文、セッション、出品、カート行動、出品者活動 | サービス利用、業務フロー上の活動、サポート接点 |
| 収益化 | サブスクリプション収益、MRR（Monthly Recurring Revenue: 月次経常収益）、ARR（Annual Recurring Revenue: 年間経常収益）、アップセル / 拡張 | 手数料、インターチェンジフィー、取引収益、利息収益 | GMV（Gross Merchandise Value: 流通取引総額）、net revenue、take rate、注文金額 | 契約収益、月額料金、従量課金収益 |
| 継続 | 契約更新、継続利用、チャーンリスク | 継続的な口座 / アカウント活動、休眠アカウント | リピート購入、リピート販売、購入者 / 出品者の継続 | 契約更新、継続的な契約利用、アカウントヘルス |
| レビューシグナル | オンボーディング後の低利用、有料アカウントだが利用がない状態 | オンボーディング失敗、休眠アカウント、通常とは異なる非アクティブ状態 | 高い返品率、リピート購入なし、非アクティブな出品者 | 高いサポート負荷、低いサービス利用、更新リスク |

この対応表が有用なのは、一般的なモデリングケーススタディを広く適用可能なままにしつつ、読者が自社や対象業務に置き換えて理解しやすくするためです。

## 14. まとめ

顧客ライフサイクルと収益化分析は、多くの事業モデルに現れながらも、具体的なモデリング判断を必要とするため、対象業務領域のケーススタディとして有用です。

中心となるモデリングの流れは次の通りです。

```text
ステークホルダーの問い
  → 業務プロセス
  → ソースデータ
  → model grain
  → ファクトとディメンション
  → intermediate logic
  → テストとドキュメンテーション
  → BI / semantic layer またはレポーティングマート
  → 意思決定支援のための出力
```

最も重要なモデリング判断は、正確なモデル名ではありません。重要なのは次の点です。

- どの業務プロセスをファクトとしてモデル化するべきか
- どのエンティティを再利用可能なディメンションにするべきか
- 各モデルがどの grain を公開するべきか
- stock metrics と flow metrics をどのように分離、または組み合わせるべきか
- どの前提をテストするべきか
- どの業務レビューシグナルを出力として表示するべきか
- どのロジックを dbt に置き、どのロジックを BI / semantic layer に置くべきか

このケーススタディは、一般的な dbtモデリング原則と、企業・業務領域ごとのモデリング仮説をつなぐ、再利用可能な橋渡しとして設計しています。
