## 6. テスト設計の基本

5章では、要求をテスト可能な形にする考え方を整理した。具体的には、Acceptance Criteria(受け入れ条件)、具体例、Example Mapping(実例マッピング)、Specification by Example(SBE:実例による仕様記述)、Three Amigos(スリーアミーゴス)、ATDD(Acceptance Test-Driven Development:受け入れテスト駆動開発)、BDD(Behavior-Driven Development:振る舞い駆動開発)、TDD(Test-Driven Development:テスト駆動開発)を通じて、要求を確認可能な形に近づける方法を扱った。

6章では、その次の段階として、要求、受け入れ条件、具体例、期待される振る舞いをもとに、どの観点で確認するか、どの条件を代表として選ぶか、どこを重点的に確認するかを整理する。

言い換えると、5章が「何を満たせば受け入れ可能か」を明確にする章だとすれば、6章は「その受け入れ可能性を、どの観点・条件・確認範囲で確認するか」を扱う章である。

テスト設計は、単にテストケースを大量に作る作業ではない。重要なのは、品質判断に必要な情報を得るために、確認すべき対象、条件、リスク、期待結果を整理することである。

たとえば、「50,000円以上の申請には追加承認が必要である」という受け入れ条件がある場合、単に「追加承認されることを確認する」と書くだけでは不十分である。

少なくとも、次のような観点が考えられる。

- 49,999円の場合は追加承認が不要か
- 50,000円ちょうどの場合は追加承認が必要か
- 50,001円の場合は追加承認が必要か
- 複数明細の合計で50,000円以上になる場合はどう扱うか
- 申請後に金額が変更された場合、追加承認の要否を再判定するか
- 承認済みの申請について、金額変更を許可するか
- 追加承認者が存在しない場合、申請はどう扱われるか
- 権限のないユーザーが追加承認を実行しようとした場合、どうなるか

このように、受け入れ条件や具体例を起点にして、境界値、異常系、権限、状態遷移、データ整合性、業務上の影響を整理していくことが、テスト設計の基本になる。

また、すべての条件を同じ深さで確認することは現実的ではない。時間、人数、リリース期限、環境、テストデータ、外部連携の制約がある中で、どこを厚く確認し、どこを代表値で確認し、どこを自動テストで継続的に確認し、どこを人間が探索的に見るかを判断する必要がある。

その判断には、リスクが関わる。

金銭、契約、個人情報、権限、承認、外部連携、監査証跡、業務上の重要フローなどは、不具合が起きたときの影響が大きい。そのため、正常系だけでなく、境界条件、異常系、不正操作、状態遷移の抜け、データ不整合まで含めて厚く確認する必要がある。

一方で、影響が小さく、仕様も単純で、過去に大きな問題が出ていない領域では、代表値による確認や既存の自動テストを中心にして、確認の深さを調整することもある。

QA(Quality Assurance:品質保証)にとって重要なのは、「テストケースが多いから安心」と考えないことである。テストケースの数が多くても、重要なリスクを外していれば、品質判断にはつながらない。逆に、テストケースの数が多くなくても、業務上重要な条件、境界値、権限、状態遷移、異常系を適切に押さえていれば、リスク把握に大きく貢献できる。

この章では、QA初学者が最低限知っておきたいテスト設計の基本として、次の観点を扱う。

- テスト設計とは何か
- テスト設計の入力情報
- テスト対象・テストレベル・確認観点の整理
- Risk-Based Testing(リスクベースドテスト)
- Equivalence Partitioning(同値分割)
- Boundary Value Analysis(境界値分析)
- Decision Table Testing(デシジョンテーブルテスト)
- State Transition Testing(状態遷移テスト)
- Scenario Testing / Use Case Testing(シナリオテスト / ユースケーステスト)
- Exploratory Testing(探索的テスト)
- 実装例に対するテスト設計技法の適用例

ここで扱う考え方や技法は、名前を覚えること自体が目的ではない。重要なのは、それぞれが、どのような品質リスクを明らかにし、品質判断に必要な情報を得るためにどのように役立つのかを理解することである。

なお、本章で扱うRisk-Based Testing(リスクベースドテスト)は、同値分割や境界値分析のような個別のテスト設計技法というより、リスクに応じてテストの優先度や確認の深さを決めるテストアプローチである。

また、ISTQB CTFLでは、テスト技法をBlack-box Test Techniques(ブラックボックステスト技法)、White-box Test Techniques(ホワイトボックステスト技法)、Experience-based Test Techniques(経験ベースのテスト技法)に分類している。

本章では、QA初学者が要求、仕様、受け入れ条件、業務ルールからテスト観点を設計しやすいように、6.5〜6.8で主にブラックボックステスト技法を扱う。また、固定されたテストケースだけでは見つけにくいリスクを扱うため、6.10ではExploratory Testing(探索的テスト)のような経験ベースの技法にも触れる。コード内部構造やカバレッジに基づくホワイトボックステスト技法は、本章では詳細に扱わず、7章のテスト自動化や品質ゲートの文脈で必要な範囲を扱う。

### 6.1 テスト設計とは何か

テスト設計とは、品質に関する情報を得るために、何を、どの条件で、どの深さで確認するかを決める活動である。

テストという言葉からは、実際に画面を操作すること、API(Application Programming Interface:アプリケーションプログラミングインターフェース)を実行すること、自動テストを走らせることを想像しやすい。しかし、それらを実行する前に、そもそも何を確認すべきかを考える必要がある。

たとえば、ある申請機能を確認する場合、単に「申請できること」を確認するだけでは不十分である。

次のような観点を考える必要がある。

- 誰が申請できるのか
- どの項目が必須なのか
- 入力値の上限・下限はどこか
- どの状態の申請を編集できるのか
- 申請後に誰が承認できるのか
- 権限のないユーザーは何をできないのか
- 外部連携や通知に失敗した場合、どう扱うのか
- 作成者、承認者、更新時刻、履歴は記録されるのか
- 申請データは集計や監査に使われるのか

これらを整理せずにテストケースを書き始めると、正常系の操作確認だけに偏りやすい。結果として、業務上重要な例外、境界条件、権限、状態遷移、データ整合性を見落とす可能性がある。

テスト設計では、まず確認対象を分解する。

確認対象には、画面、API、バッチ処理、データ、権限、状態遷移、通知、ログ、外部連携、業務フローなどが含まれる。どの対象を確認するかによって、使いやすいテスト技法や確認方法は変わる。

たとえば、入力フォームの文字数や金額の制限であれば、Equivalence Partitioning(同値分割)やBoundary Value Analysis(境界値分析)が使いやすい。複数条件によって結果が変わる業務ルールであれば、Decision Table Testing(デシジョンテーブルテスト)が向いている。申請、承認、却下、取消のように状態が変化する機能であれば、State Transition Testing(状態遷移テスト)が重要になる。

また、テスト設計では、確認の深さも考える必要がある。

すべての入力値、すべての権限、すべての状態、すべての操作順序を完全に確認しようとすると、テストケースは膨大になる。実務では、限られた時間の中で、どこを重点的に確認するかを判断する必要がある。

そのため、テスト設計は、網羅作業というよりもリスク判断である。

もちろん、網羅性も重要である。重要な条件を抜けなく確認するために、同値分割、境界値分析、デシジョンテーブル、状態遷移図などの技法を使う。しかし、網羅性だけを追求すると、低リスクの細部に時間を使いすぎ、高リスクの業務フローや異常系を十分に確認できないことがある。

QAは、要求、仕様、受け入れ条件、具体例、過去の不具合、ユーザー影響、業務上の重要度を踏まえ、どのリスクを優先的に確認するかを整理する。

したがって、テスト設計の目的は、テストケース表を埋めることではない。品質判断に必要な情報を得るために、確認対象、確認条件、期待結果、優先度を整理することである。

### 6.2 テスト設計の入力情報

テスト設計は、何もないところから始めるものではない。テスト設計には、入力情報がある。

主な入力情報には、次のようなものがある。

- 要求
- ユーザーストーリー
- Acceptance Criteria(受け入れ条件)
- 具体例
- Example Mapping(実例マッピング)で整理されたRule(ルール)、Example(具体例)、Question(質問)
- BDD(Behavior-Driven Development:振る舞い駆動開発)シナリオ
- 仕様書
- 画面設計
- API仕様
- データ定義
- 状態遷移
- 権限ルール
- 外部連携仕様
- ログ、監視、通知の仕様
- 過去の不具合
- 問い合わせ
- インシデント
- 運用上の制約やリスク

このような、テスト設計の根拠になる情報は、Test Basis(テストベース)と呼ばれることがある。テストベースは、テストケースやテスト観点を考えるための出発点である。QAは、テストベースをもとに、何を確認すべきか、どこに曖昧さがあるか、どのリスクを優先的に扱うべきかを整理する。

5章で扱った受け入れ条件や具体例は、テスト設計の重要な材料になる。

たとえば、「50,000円以上の申請には追加承認が必要である」という受け入れ条件がある場合、それはそのままテスト観点につながる。ただし、この条件をそのまま1つのテストケースに変換するだけでは不十分である。

実際には、次のように分解する必要がある。

- 50,000円未満の場合
- 50,000円ちょうどの場合
- 50,000円を超える場合
- 複数明細の合計で判定する場合
- 申請後に金額が変更される場合
- 追加承認者が存在しない場合
- 権限のないユーザーが承認しようとする場合
- 承認済みの申請を変更しようとする場合

この分解により、受け入れ条件は、入力値、境界値、状態、権限、例外条件に展開される。

一方で、5章で出てきた具体例をすべて機械的にテストケース化する必要はない。具体例には、仕様理解のための例、関係者の認識合わせのための例、未決定事項を見つけるための例、実際にテストケースとして使う例が混ざっている。

テスト設計では、それらを整理し、どの例をテストケースにするか、どの例は仕様確認や補足説明として扱うか、どの例は追加確認が必要な質問として残すかを判断する。

また、仕様書や画面設計だけを見てテスト設計を行うと、実務上の重要なリスクを見落とすことがある。

たとえば、画面設計には「申請ボタン」が記載されていても、そのボタンを誰が押せるのか、どの状態で押せるのか、二重クリックされた場合にどうなるのか、外部連携に失敗した場合にどうなるのかまでは書かれていないかもしれない。

API仕様には、正常なリクエストとレスポンスが書かれていても、不正なIDを指定した場合、他人のデータを指定した場合、無効なステータスで更新しようとした場合、タイムアウトした場合の挙動が十分に記載されていないこともある。

そのため、テスト設計では、書かれている仕様だけでなく、書かれていないが確認すべきリスクも考える必要がある。

過去の不具合や問い合わせも重要な入力情報である。過去に同じような機能で権限漏れが起きていた場合、新しい機能でも権限確認を厚くする必要がある。外部連携失敗による問い合わせが多かった場合、正常系だけでなく失敗時の挙動やリカバリ手順を確認する必要がある。

運用上の制約も、テスト設計に影響する。たとえば、本番環境に近い外部サービスを使えない場合、どのように失敗状態を再現するかを考える必要がある。十分なテストデータを用意できない場合、代表的な条件をどのように選ぶかを考える必要がある。

このように、テスト設計では、明示された要求や仕様だけでなく、受け入れ条件、具体例、業務ルール、状態遷移、権限、データ、過去の不具合、問い合わせ、運用リスクを組み合わせて、確認すべき観点を整理する必要がある。

### 6.3 テスト対象・テストレベル・確認観点の整理

テスト設計では、何を確認するかだけでなく、どの対象に対して、どの粒度で確認するかを考える必要がある。

ここでいうテストの粒度とは、確認対象の範囲の大きさを指す。本資料では、関数、メソッド、小さなロジックなど狭い範囲を確認するテストを「粒度の細かいテスト」と呼び、API、DB、画面、外部連携、ユーザー操作を含む広い範囲を確認するテストを「粒度の粗いテスト」と呼ぶ。

粒度の細かいテストは、実行が速く、失敗時の原因を特定しやすい。一方で、業務フロー全体の確認には向かない。粒度の粗いテストは、実利用に近い流れを確認しやすい一方で、実行時間や保守負荷が大きくなりやすい。

テスト設計時に確認単位を整理するうえで、実務上よく意識される分類には、次のようなものがある。

| 種類 | 確認粒度の目安 | 主な確認対象 | 確認しやすい観点 |
|---|---|---|---|
| Unit Test(単体テスト) | 細かい | 関数、メソッド、クラス、小さなロジック | 計算、入力バリデーション、分岐、境界値 |
| API Test | 中程度 | APIの入力、出力、認可、エラー応答 | リクエスト検証、レスポンス、権限、異常系 |
| Integration Test(結合テスト) | 中程度〜粗い | 複数コンポーネント、DB(Database:データベース)、外部サービス連携 | データ保存、連携、トランザクション、コンポーネント間の整合性 |
| E2E(End-to-End:エンドツーエンド) Test | 粗い | ユーザーに近い一連の操作フロー | 主要業務フロー、画面遷移、複数機能の連携 |
| Manual Test(手動テスト) | 可変 | 画面、業務フロー、UX(User Experience:ユーザー体験)、例外条件 | 視覚的違和感、操作性、業務上の自然さ、探索的確認 |
| Exploratory Testing(探索的テスト) | 可変 | 仕様や既存ケースから漏れやすい領域 | 仕様抜け、未知リスク、想定外操作、UX上の違和感 |

なお、これらは厳密には同じ分類軸の言葉ではない。Unit TestやIntegration Testは主に確認粒度を表し、API Testは確認対象、Manual Testは実行方法、Exploratory Testingはテストの進め方を表す。そのため、表中の「確認粒度の目安」は絶対的な分類ではなく、テスト設計時に確認範囲を整理するための目安である。

ここで重要なのは、どの確認単位が優れているかではない。確認したいリスクに対して、どの確認範囲で見るのが適切かを考えることである。

たとえば、金額が50,000円以上かどうかを判定する単純なロジックであれば、Unit Testで境界値を確認しやすい。49,999円、50,000円、50,001円のような値を使えば、境界値の挙動を素早く確認できる。

一方で、申請金額が50,000円以上になったときに、追加承認フローが作成され、承認者に通知され、申請画面のステータスが変わり、履歴が残ることを確認する場合は、Unit Testだけでは不十分である。API、DB、通知、画面表示など、複数の要素が関わるため、Integration Test、API Test、E2E Test、Manual Testを組み合わせて確認する必要がある。

また、権限に関する確認では、API Testが重要になることが多い。画面上でボタンが非表示になっていても、APIを直接呼び出したときに操作できてしまえば、権限品質として問題がある。そのため、画面表示だけでなく、サーバー側で認可が正しく行われているかを確認する必要がある。

E2E Testは、ユーザーの主要な業務フローが壊れていないことを確認するうえで有効である。たとえば、ユーザーが申請を作成し、承認者が承認し、通知が送られ、履歴が残るという流れを確認できる。ただし、すべての境界値やすべての条件分岐をE2E Testで確認しようとすると、テストの実行時間や保守負荷が大きくなりやすい。

そのため、細かいロジックや境界値はUnit TestやAPI Testで確認し、主要な業務フローはE2E TestやManual Testで確認する、といった分担が必要になる。

Manual TestやExploratory Testingも重要である。自動テストは、期待される条件を繰り返し確認するのに向いている。一方で、仕様の違和感、ユーザーが迷いやすい画面、エラーメッセージの分かりにくさ、想定外の操作、業務上の不自然さは、人間が実際に触りながら気づくことも多い。

したがって、テスト設計では、次のような問いを持つ必要がある。

- この確認は、どの確認単位で行うのが適切か
- 小さなロジックとして確認できるか
- API単位で確認すべきか
- 画面を通して確認する必要があるか
- ユーザーの一連の業務フローとして確認すべきか
- 自動テストで継続的に確認すべきか
- 人間が探索的に確認すべきか
- 同じ観点を複数のレベルで重複して確認しすぎていないか
- 逆に、どのレベルでも確認されていない重要リスクはないか

6章では、主に「何を確認するか」「どの観点をどの対象・段階に割り当てるか」を扱う。自動化の具体的な設計、CI/CD(Continuous Integration / Continuous Delivery:継続的インテグレーション / 継続的デリバリー)上の品質ゲート、テストピラミッド、回帰テストの運用については、7章で詳しく扱う。

この切り分けにより、6章ではテスト設計そのものに集中できる。つまり、要求や受け入れ条件をもとに、どの品質リスクを、どのテスト観点で、どの確認単位・確認範囲で扱うかを整理することが、6章の中心である。

次節からは、そのためにQA初学者がまず押さえておきたい代表的なテスト設計技法を見ていく。最初に、限られた時間の中でどこを重点的に確認するかを考えるRisk-Based Testing(リスクベースドテスト)を扱う。

### 6.4 Risk-Based Testing(リスクベースドテスト)

Risk-Based Testing(リスクベースドテスト)は、品質リスクに基づいて、何を優先的に確認するかを決める考え方である。

ここでいうリスクとは、不具合が起きる可能性と、不具合が起きた場合の影響の組み合わせとして考えられる。発生する可能性が高く、かつ影響も大きい領域は、重点的に確認する必要がある。一方で、影響が小さく、発生可能性も低い領域は、代表的な条件だけを確認する、既存の自動テストに任せる、後続の監視や運用で補う、といった判断を行うことがある。

重要なのは、すべてを同じ深さで確認しようとしないことである。

実務では、確認に使える時間、人数、環境、テストデータ、外部連携先、リリース期限には制約がある。その中で、すべての条件、すべての画面、すべての権限、すべての状態遷移を同じ深さで確認しようとすると、重要なリスクに十分な時間を使えなくなる可能性がある。

たとえば、次のような領域は、一般にリスクが高くなりやすい。

- 金銭、請求、支払い、契約に関わる処理
- 個人情報、機密情報、権限に関わる処理
- 承認、取消、締め処理、監査証跡に関わる業務フロー
- 外部サービスや外部システムとの連携
- 多くのユーザーが利用する主要フロー
- 過去に不具合や問い合わせが多かった領域
- 変更範囲が大きい、または影響範囲が読みづらい領域
- 仕様が曖昧、または関係者間で認識が揃っていない領域

これらの領域では、正常系だけでなく、異常系、境界条件、権限違反、状態遷移の不正、外部連携失敗、データ不整合まで含めて確認する必要がある。

一方で、表示文言の軽微な変更、影響範囲が限定されたUI(User Interface:ユーザーインターフェース)変更、既存ロジックを再利用している低リスクな変更などでは、確認範囲を絞ることもある。ただし、低リスクに見える変更でも、共通コンポーネント、権限、データ、主要導線に影響する場合は、想定よりリスクが高いことがある。

Risk-Based Testingでは、たとえば次のような観点で優先度を考える。

| 観点 | 確認する内容 |
|---|---|
| 影響度 | 不具合が起きた場合、ユーザー、業務、金銭、法令、信頼性にどの程度影響するか |
| 発生可能性 | 仕様の複雑さ、変更量、過去不具合、技術的難易度から見て、不具合が起きやすいか |
| 検出しにくさ | 通常の確認では見つけにくいか、本番環境で初めて表面化しやすいか |
| 回復しにくさ | 不具合が起きた後、データ修正、ユーザー対応、ロールバックが難しいか |
| 利用頻度 | 多くのユーザーが使うか、業務上頻繁に使われるか |
| 変更範囲 | 変更が複数機能、複数画面、複数API、複数データにまたがるか |

たとえば、「50,000円以上の申請には追加承認が必要である」という業務ルールを考える。このルールが経費精算や購買申請に関わる場合、閾値判定の誤りは金銭的な影響や承認統制上の問題につながる可能性がある。そのため、単に50,000円を超えるケースだけを確認するのではなく、49,999円、50,000円、50,001円のような境界値、複数明細の合計、申請後の金額変更、承認済み申請の変更可否、権限のないユーザーによる承認などを重点的に確認する必要がある。

Risk-Based Testingは、テストを減らすための言い訳ではない。限られた条件の中で、重要な品質リスクに確認資源を集中させるための考え方である。

QA(Quality Assurance:品質保証)は、リスクの高い領域を一人で決めるのではなく、PM(Product Manager:プロダクトマネージャー)、開発者、業務担当者、CS(Customer Success:カスタマーサクセス)、サポート、SRE(Site Reliability Engineering:サイト信頼性エンジニアリング)などと連携しながら、どのリスクをリリース前に確認すべきか、どのリスクを監視や段階的リリースで扱うか、どの残リスクを関係者に共有すべきかを整理する。

このように、Risk-Based Testingは、6.5以降で扱う個別のテスト設計技法を、どこにどの深さで適用するかを決める前提になる。

### 6.5 Equivalence Partitioning(同値分割)

Equivalence Partitioning(同値分割)は、同じように扱える入力値や条件をグループに分け、それぞれのグループから代表値を選んで確認するテスト設計技法である。

すべての入力値を確認することは現実的ではない。たとえば、申請金額に1円から999,999円まで入力できる場合、すべての金額を確認することはできない。しかし、システムが同じルールで扱う範囲をグループ化すれば、代表値を使って効率的に確認できる。

このようなグループをEquivalence Partition(同値パーティション)または同値クラスと呼ぶ。

たとえば、ある入力項目について、申請金額は1円以上、999,999円以下でなければならないという仕様があるとする。この場合、次のような同値クラスを考えられる。

| 区分 | 入力値の範囲 | 代表値の例 | 期待結果 |
|---|---:|---:|---|
| 無効同値クラス | 0円以下 | 0円 | エラー |
| 有効同値クラス | 1円〜999,999円 | 50,000円 | 保存できる |
| 無効同値クラス | 1,000,000円以上 | 1,000,000円 | エラー |

このように分けると、すべての金額を確認しなくても、少なくとも有効な範囲と無効な範囲を代表値で確認できる。

同値分割は、入力バリデーションで特に使いやすい。たとえば、次のような対象に向いている。

- 金額、数量、年齢、日数などの数値入力
- 文字数制限
- 日付範囲
- ステータス
- ユーザー種別
- 選択肢
- 検索条件
- API(Application Programming Interface:アプリケーションプログラミングインターフェース)のリクエストパラメータ

同値分割で重要なのは、有効な値だけでなく、無効な値のグループも考えることである。

たとえば、メールアドレス入力欄であれば、「有効なメールアドレス」だけを確認するのではなく、空文字、@がない文字列、長すぎる文字列、使用できない文字を含む文字列なども無効同値クラスとして考える必要がある。

また、ステータスやユーザー種別のようなカテゴリ値でも同値分割は使える。

たとえば、申請ステータスが「下書き」「申請中」「承認済み」「却下」「取消済み」を取り得る場合、同じ操作が許可されるステータス群と、許可されないステータス群に分けて考えることができる。

| 操作 | 同じように扱える状態 | 期待結果 |
|---|---|---|
| 申請内容を編集する | 下書き | 編集できる |
| 申請内容を編集する | 申請中、承認済み、却下、取消済み | 編集できない、または制限される |

ただし、同値分割では、グループの分け方を誤ると重要な不具合を見落とす可能性がある。

たとえば、「50,000円以上なら追加承認が必要」というルールがある場合、単に「有効な金額」と「無効な金額」に分けるだけでは不十分である。この場合、50,000円未満と50,000円以上では業務上の扱いが変わるため、別の同値クラスとして分ける必要がある。

| 区分 | 金額 | 期待結果 |
|---|---:|---|
| 有効同値クラス | 1円〜49,999円 | 通常承認 |
| 有効同値クラス | 50,000円〜999,999円 | 追加承認 |
| 無効同値クラス | 0円以下 | エラー |
| 無効同値クラス | 1,000,000円以上 | エラー |

このように、同値分割では、単に入力値が形式的に有効かどうかだけでなく、業務ルール上同じ扱いになるかどうかを考える必要がある。

同値分割は、確認量を減らすためだけの技法ではない。入力値や条件が、どのルールで同じ扱いになり、どこから扱いが変わるのかを明確にするための技法である。

### 6.6 Boundary Value Analysis(境界値分析)

Boundary Value Analysis(境界値分析)は、同値クラスの境界や、業務ルール上の閾値の周辺を重点的に確認するテスト設計技法である。

不具合は、入力範囲の中央よりも、上限、下限、閾値、その直前、その直後で発生しやすい。これは、比較演算子の誤り、以上と超過の取り違え、未満と以下の取り違え、配列や件数の上限処理、日付範囲の扱いなどで起きやすい。

たとえば、「50,000円以上なら追加承認が必要」という仕様がある場合、重要なのは50,000円を大きく超える値だけではない。むしろ、次の3つが重要になる。

| 金額 | 期待結果 |
|---:|---|
| 49,999円 | 追加承認は不要 |
| 50,000円 | 追加承認が必要 |
| 50,001円 | 追加承認が必要 |

この例では、50,000円が境界値である。  
もし実装で `amount > 50000` のように書かれていれば、50,000円ちょうどの申請が誤って通常承認になってしまう。このような不具合は、境界値を確認しないと見落としやすい。

境界値分析は、次のような対象で有効である。

- 金額の上限・下限
- 数量、人数、回数の上限・下限
- 文字数制限
- 年齢制限
- 日付範囲
- パスワード長
- ファイルサイズ
- 検索期間
- ページング件数
- 割引率や手数料率の閾値
- 承認が必要になる金額や条件

たとえば、パスワードが8文字以上、64文字以下でなければならない場合、次の値を確認候補にできる。

| 文字数 | 期待結果 |
|---:|---|
| 7文字 | エラー |
| 8文字 | 有効 |
| 9文字 | 有効 |
| 63文字 | 有効 |
| 64文字 | 有効 |
| 65文字 | エラー |

境界値分析では、最小値、最大値、その直前、その直後を確認することが多い。ただし、どの値を選ぶべきかは、仕様、データ型、入力単位、業務ルールによって変わる。

たとえば、金額が1円単位で扱われるなら、49,999円、50,000円、50,001円が自然である。一方で、日付であれば、締切日の前日、当日、翌日が重要になる。時刻を含む場合は、日付の境界だけでなく、23:59:59や00:00:00のような時刻境界も問題になることがある。

境界値分析は、同値分割と組み合わせて使うことが多い。

まず同値分割で、どの範囲が同じ扱いになるかを整理する。そのうえで、扱いが変わる境界の周辺を境界値分析で重点的に確認する。

ここでは、表を読みやすくするため、次の略号を使う。

- E: Equivalence Partitioning(同値分割)
- B: Boundary Value Analysis(境界値分析)

たとえば、「1円〜49,999円は通常承認」「50,000円〜999,999円は追加承認」「0円以下と1,000,000円以上はエラー」という仕様であれば、まず同値分割で同じ扱いになる範囲を整理する。次に、境界値分析でそれぞれの範囲の端や、扱いが変わる境界周辺の値を確認候補として選ぶ。

| Step | 技法 | 見ているもの | 具体例 | 期待結果 |
|---|---|---|---:|---|
| 1 | E | 無効な金額の範囲 | 0円以下 | エラー |
| 1 | E | 通常承認になる有効範囲 | 1円〜49,999円 | 通常承認 |
| 1 | E | 追加承認になる有効範囲 | 50,000円〜999,999円 | 追加承認 |
| 1 | E | 無効な金額の範囲 | 1,000,000円以上 | エラー |
| 2 | B | 下限の外側 | 0円 | エラー |
| 2 | B | 下限 | 1円 | 通常承認 |
| 2 | B | 追加承認境界の直前 | 49,999円 | 通常承認 |
| 2 | B | 追加承認境界 | 50,000円 | 追加承認 |
| 2 | B | 追加承認境界の直後 | 50,001円 | 追加承認 |
| 2 | B | 上限 | 999,999円 | 追加承認 |
| 2 | B | 上限の外側 | 1,000,000円 | エラー |

この表で見ると、同値分割は「どの範囲が同じ扱いになるか」を整理し、境界値分析は「その範囲の端や、扱いが変わる境界周辺の具体値」を選ぶ役割を持つことが分かる。

このように、境界値分析は、単に端の値を確認する技法ではない。仕様上、扱いが変わる境界を見つけ、その周辺で期待どおりの挙動になるかを確認する技法である。

### 6.7 Decision Table Testing(デシジョンテーブルテスト)

Decision Table Testing(デシジョンテーブルテスト)は、複数の条件と、その組み合わせに対する期待結果を表として整理するテスト設計技法である。

単一の入力値や単一の境界だけで判断できる場合は、同値分割や境界値分析で整理しやすい。しかし、実務上の業務ルールでは、複数の条件が組み合わさって結果が決まることが多い。

たとえば、次のようなルールを考える。

> 申請金額が50,000円以上で、申請者が一般ユーザーで、申請が下書き状態の場合、申請すると追加承認が必要になる。  
> ただし、管理者が代理申請する場合は、通常とは異なる承認ルートになる。

このような仕様を文章だけで扱うと、条件の組み合わせ漏れや、例外条件の見落としが起きやすい。

デシジョンテーブルでは、条件と結果を表にすることで、どの条件の組み合わせでどの結果になるべきかを整理する。

たとえば、追加承認の要否について、重要な条件の組み合わせを抜き出すと、次のように整理できる。ここでは説明を簡単にするため、すべての可能な組み合わせではなく、結果が変わる代表的な組み合わせを示す。表中の「-」は、そのルールでは結果に影響しない、またはここでは問わない条件を表す。

| 条件 / ルール | R1 | R2 | R3 | R4 |
|---|---:|---:|---:|---:|
| 申請金額が50,000円以上 | No | Yes | Yes | - |
| 操作ユーザーが一般ユーザー | Yes | Yes | No | - |
| 管理者による代理申請 | No | No | Yes | - |
| 申請状態が下書き | Yes | Yes | Yes | No |
| 期待結果 | 通常承認 | 追加承認 | 管理者代理申請ルート | 申請不可 |

この表では、R1、R2、R3、R4が条件の組み合わせを表す。各列を1つのルールとして読み、操作ユーザー、申請状態、申請金額などの組み合わせに対して期待結果が定まる。

デシジョンテーブルは、次のような対象に向いている。

- 権限によって操作可否が変わる機能
- 申請、承認、差戻し、取消などの業務ルール
- 割引、料金、手数料、キャンペーン条件
- 通知の送信条件
- 外部連携時の分岐
- 複数のフラグやステータスで結果が変わる処理
- 入力条件とユーザー種別の組み合わせで結果が変わるAPI

たとえば、権限管理では、ユーザー種別、所属組織、申請状態、操作種別によって、操作可否が変わることがある。ここでも、すべての組み合わせを列挙するのではなく、結果の違いを理解しやすい代表的な組み合わせを示す。

| 条件 / ルール | R1 | R2 | R3 | R4 |
|---|---:|---:|---:|---:|
| ユーザーは申請者本人である | Yes | No | No | No |
| ユーザーは承認者である | No | Yes | No | No |
| ユーザーは管理者である | No | No | Yes | No |
| 申請状態は申請中である | Yes | Yes | Yes | Yes |
| 期待結果 | 閲覧のみ | 承認できる | 管理操作できる | アクセス不可 |

このように整理すると、「誰が、どの状態で、何をできるのか」が見えやすくなる。  
また、仕様に矛盾がある場合や、結果が未定義の組み合わせがある場合も発見しやすくなる。

ただし、条件が増えると、組み合わせ数は急激に増える。

たとえば、Yes / Noで表せる条件が5個ある場合、単純には2の5乗、つまり32通りの組み合わせが存在する。すべてをテストケース化すると、確認量が大きくなりすぎることがある。

そのため、実際のテスト設計では、これらの表を出発点として、あり得ない組み合わせ、同じ結果になる組み合わせ、業務上重要な組み合わせ、リスクが高い組み合わせを整理する。

デシジョンテーブルは、テストケースを増やすための表ではない。複数条件が絡む業務ルールを整理し、条件の組み合わせ漏れ、結果の未定義、仕様の矛盾を見つけるための技法である。

### 6.8 State Transition Testing(状態遷移テスト)

State Transition Testing(状態遷移テスト)は、システムやデータが取り得る状態と、状態を変化させるイベントを整理し、期待される状態遷移を確認するテスト設計技法である。

業務アプリケーションでは、多くのデータが状態を持つ。たとえば、申請、注文、契約、チケット、請求、在庫、ユーザーアカウントなどは、作成されてから完了・取消・失効などに至るまで、複数の状態を取ることが多い。

たとえば、申請データには次のような状態が考えられる。

- 下書き
- 申請中
- 承認済み
- 却下
- 取消済み
- 期限切れ

状態遷移テストでは、どの状態から、どのイベントによって、どの状態へ移るのかを確認する。

たとえば、申請フローでは次のような遷移が考えられる。

| 現在の状態 | イベント | 次の状態 | 期待結果 |
|---|---|---|---|
| 下書き | 申請する | 申請中 | 申請が受け付けられる |
| 申請中 | 承認する | 承認済み | 承認履歴が残る |
| 申請中 | 却下する | 却下 | 却下理由が記録される |
| 申請中 | 取消する | 取消済み | 取消履歴が残る |
| 申請中 | 期限を過ぎる | 期限切れ | 操作が制限される |
| 却下 | 再申請する | 申請中 | 再申請として扱われる |

このような表を作ると、状態とイベントの組み合わせが整理しやすくなる。

状態遷移テストで重要なのは、許可される遷移だけでなく、許可されない遷移も確認することである。

たとえば、次のような操作は業務上禁止される可能性がある。

| 現在の状態 | イベント | 期待結果 |
|---|---|---|
| 承認済み | 編集する | 許可されない |
| 承認済み | 再申請する | 許可されない |
| 取消済み | 承認する | 許可されない |
| 期限切れ | 承認する | 許可されない |
| 却下 | 承認する | 許可されない、または再申請が必要 |

もし、承認済みの申請を履歴なしで編集できてしまう場合、機能としては更新処理が成功していても、業務ルールや監査上は問題になる可能性がある。また、取消済みの申請を承認できてしまう場合、業務上存在してはいけない状態が発生する。

状態遷移テストは、次のような対象に向いている。

- 申請、承認、却下、取消を持つ業務フロー
- 注文、出荷、返品、キャンセル
- 契約の下書き、承認、締結、失効、解約
- チケットの未対応、対応中、解決済み、再オープン
- ユーザーアカウントの有効、無効、ロック、削除
- バッチ処理の未実行、処理中、成功、失敗、再実行待ち
- 外部連携の未送信、送信中、成功、失敗、再送待ち

状態遷移を整理するときは、状態遷移図や状態遷移表を使うと分かりやすい。

状態遷移図では、状態をノードとして表し、イベントによる遷移を矢印で表す。視覚的に流れを把握しやすいため、Product側、開発者、QA、業務担当者の認識合わせにも使いやすい。

一方、状態遷移表では、現在の状態、イベント、次の状態、期待結果を表として整理する。テストケースへ展開しやすく、許可されない遷移も明示しやすい。

状態遷移テストでは、次のような問いが重要になる。

- 取り得る状態はすべて定義されているか
- 各状態から実行できるイベントは明確か
- 各イベントの結果、次にどの状態へ移るかが明確か
- 許可されない遷移は明確か
- 状態遷移時に、履歴、通知、監査証跡、関連データは更新されるか
- 期限切れ、取消、ロック、外部連携失敗などの例外状態は扱われているか
- 同時操作や二重送信が起きた場合、状態は矛盾しないか
- リリース後に状態不整合が起きた場合、検知や調査ができるか

状態遷移テストは、業務システムで特に重要である。なぜなら、業務上の問題は、単一画面の入力値だけではなく、「ある状態で本来できない操作ができる」「ある状態から次の状態に進めない」「履歴が残らない」「状態とデータが矛盾する」といった形で表面化しやすいからである。

そのため、状態を持つ機能では、正常な遷移だけでなく、不正な遷移、例外状態、履歴、権限、通知、データ整合性まで含めて確認する必要がある。

### 6.9 Use Case Testing / Scenario Testing(ユースケーステスト / シナリオテスト)

Use Case Testing(ユースケーステスト)は、ユーザーや外部システムなどのActor(アクター)が、システムとやり取りして目的を達成する一連の流れをもとにテストケースを設計するブラックボックステスト技法である。ISTQB Glossaryでは、Scenario Testing(シナリオテスト)やUser Scenario Testing(ユーザーシナリオテスト)はUse Case Testingの同義語として扱われている。

本資料では、厳密な用語差よりも、ユーザーや業務の一連の流れとして確認する考え方を重視し、Use Case Testing / Scenario Testingとしてまとめて扱う。

同値分割、境界値分析、デシジョンテーブル、状態遷移テストは、入力値、条件の組み合わせ、状態とイベントを構造的に整理するうえで有効である。一方で、実際のユーザーは、個別の条件だけを単独で使うわけではない。ログインし、画面を開き、入力し、申請し、承認を待ち、通知を受け取り、履歴やステータスを確認する、というように、複数の機能をまたいで目的を達成する。

Use Case Testing / Scenario Testingでは、このような一連の流れを、ユーザーや業務上の目的が達成されるかという観点から確認する。

たとえば、申請フローであれば、次のようなシナリオが考えられる。

| シナリオ | 確認する流れ | 主な確認観点 |
|---|---|---|
| 通常金額の申請 | ユーザーが申請を作成し、通常承認される | 入力、保存、承認、ステータス更新、履歴 |
| 高額申請 | 50,000円以上の申請を作成し、追加承認が必要になる | 境界条件、承認ルート、通知、履歴 |
| 申請の却下と再申請 | 承認者が却下し、申請者が内容を修正して再申請する | 状態遷移、権限、履歴、通知 |
| 承認後の変更禁止 | 承認済み申請を編集しようとする | 不正操作、権限、監査証跡 |
| 外部連携失敗 | 申請後の外部連携に失敗する | 異常系、再試行、失敗記録、ユーザー通知 |

Use Case Testing / Scenario Testingでは、正常に完了する基本フローだけでなく、代替フローやエラー処理も重要になる。たとえば、申請が承認される流れだけでなく、却下、取消、再申請、外部連携失敗、権限不足などの流れも、業務上重要であればシナリオとして扱う必要がある。

このように、シナリオを使うと、単一の画面や処理だけではなく、ユーザーが目的を達成するまでの流れを確認対象として整理できる。正常に完了する流れ、途中で分岐する流れ、失敗時に復旧する流れを分けて考えることで、個別機能の確認だけでは見つけにくい問題を確認しやすくなる。

たとえば、申請作成だけを確認すれば、入力フォームや保存処理の問題は見つけやすい。承認処理だけを確認すれば、承認ボタンやステータス更新の問題は見つけやすい。しかし、申請作成、承認、通知、履歴、集計が連動する場合、それぞれの機能が単体では正しく動いていても、一連の流れとしては問題が起きることがある。

たとえば、次のような問題である。

- 申請は作成できるが、承認者に通知されない
- 承認はできるが、履歴が残らない
- 却下後に再申請できるはずなのに、画面上で操作できない
- 追加承認が必要な申請なのに、通常承認フローに進んでしまう
- 承認済みのデータが集計画面に反映されない
- 画面上のステータスとデータベース上のステータスが一致しない
- 操作自体は成功するが、ユーザーに次の行動が伝わらない

Use Case Testing / Scenario Testingは、このような複数機能をまたぐ品質リスクを確認するために有効である。

特に、次のような対象に向いている。

- ユーザーが目的を達成する主要業務フロー
- 申請、承認、通知、履歴、集計のように複数機能が連動する処理
- Product側や業務担当者が受け入れ可否を判断するためのフロー
- リリース前に壊れていてはいけない重要導線
- E2E(End-to-End:エンドツーエンド) Testや受け入れ確認の候補になる流れ
- System Testing(システムテスト)、Acceptance Testing(受け入れテスト)、Integration Testing(結合テスト)で確認したい代表的な利用シナリオ

ただし、Use Case Testing / Scenario Testingにも注意点がある。

すべての条件、境界値、権限パターン、状態遷移をシナリオテストやE2E Testで確認しようとすると、テストケースが大きくなりすぎる。実行時間が長くなり、失敗したときの原因特定も難しくなる。また、画面変更やデータ準備の影響を受けやすく、保守負荷も高くなりやすい。

そのため、細かい入力値や境界値はUnit Test(単体テスト)やAPI Testで確認し、主要な業務フローはUse Case Testing / Scenario Testingで確認する、という分担が重要になる。

たとえば、「50,000円以上なら追加承認が必要」という境界値そのものは、Unit TestやAPI Testで49,999円、50,000円、50,001円を確認しやすい。一方で、「50,000円以上の申請を作成すると、追加承認フローが作られ、承認者に通知され、履歴が残る」という一連の流れは、Scenario TestingやE2E Testで確認する価値がある。

Use Case Testing / Scenario Testingでは、次のような問いを持つとよい。

- このシナリオは、どのユーザーのどの目的を表しているか
- 業務上、最も重要な流れはどれか
- 正常に完了する流れだけでなく、却下、取消、失敗、再試行などの流れも必要か
- どの条件はシナリオ全体で確認し、どの条件はより小さい確認単位で確認するか
- シナリオの成功条件は何か
- シナリオ中に、状態、権限、通知、履歴、データ整合性は期待どおりに変化するか
- このシナリオはリリース判断や受け入れ確認に使えるか
- このシナリオを自動化する価値があるか、それとも手動確認に留めるべきか

Use Case Testing / Scenario Testingは、個別のテスト技法を置き換えるものではない。また、ユースケースやシナリオは、要求や仕様のすべてを完全に表すものではない。必要に応じて、同値分割、境界値分析、デシジョンテーブル、状態遷移テストで整理した観点を組み合わせ、ユーザーや業務の一連の流れに接続することが重要である。

### 6.10 Exploratory Testing(探索的テスト)と異常系・権限・例外観点

Exploratory Testing(探索的テスト)は、事前に固定されたテストケースだけに従うのではなく、テスト対象を学習しながら、確認観点を考え、実行し、結果を観察して、次の確認に反映していくテストアプローチである。

探索的テストは、無計画に自由に触ることではない。軽量な文書で進められることは多いが、確認する範囲、目的、観点、Timebox(時間枠)、記録方法を決めたうえで行う活動である。テスターは、実行中に得た情報をもとに仮説を立て、次に確認すべき観点を調整しながら、未知のリスクや仕様上の違和感を探っていく。

固定されたテストケースは、あらかじめ分かっている条件を安定して確認するうえで有効である。一方で、実際のプロダクトでは、事前にすべてのリスクをテストケースとして書き出すことは難しい。仕様書には明示されていない使い方、ユーザーが迷いやすい操作、複数機能の組み合わせ、エラーメッセージの分かりにくさ、業務上の違和感などは、実際に触りながら気づくことが多い。

探索的テストは、次のような問題を見つけるのに向いている。

- 仕様に明示されていない曖昧な挙動
- ユーザーが迷いやすい画面や導線
- エラーメッセージが行動可能な情報になっていない箇所
- 想定外の操作順序
- 画面表示とAPIやデータの不整合
- 権限の境界が曖昧な箇所
- 状態遷移の抜けや矛盾
- 外部連携失敗時の不自然な挙動
- 二重送信、戻るボタン、リロード、複数タブ操作などで起きる問題
- テストケースには書かれていないが、実務上起きそうな例外条件

たとえば、申請機能に対して探索的テストを行う場合、次のような観点を持つことができる。

| 観点 | 探索する内容 |
|---|---|
| 異常入力 | 必須項目の未入力、長すぎる文字列、不正な日付、0円やマイナス金額 |
| 権限 | 他人の申請を閲覧・編集できないか、URLを直接指定して操作できないか |
| 状態 | 承認済み、取消済み、期限切れの申請に対して不正操作できないか |
| 操作順序 | 入力途中で戻る、リロードする、複数タブで同じ申請を開く |
| 二重操作 | 申請ボタンや承認ボタンを連打した場合に重複処理されないか |
| 外部連携 | 通知や外部APIが失敗した場合に、ユーザーや運用担当者が状況を把握できるか |
| UX(User Experience:ユーザー体験) | エラー時に、ユーザーが次に何をすればよいか分かるか |
| データ整合性 | 画面、履歴、通知、集計で状態や金額が矛盾しないか |

このように、探索的テストでは、機能をただ順番に操作するのではなく、「どこにリスクがありそうか」という仮説を持って確認する。

探索的テストを行うときは、Test Charter(テストチャーター)を使うと整理しやすい。Test Charterは、探索的テストで何を確認するか、どの範囲を見るか、どのようなリスクを探るかを簡潔に示すメモである。

Test Charterに単一の固定フォーマットがあるわけではない。ただし、対象、目的、観点、範囲外、Timebox(時間枠)、制約、記録方法などを整理しておくと、探索的テストの意図と結果を共有しやすくなる。

基本構成としては、たとえば次のような項目を持たせることができる。

| 項目 | 内容 |
|---|---|
| 対象 | どの機能、画面、API、業務フローを探索するか |
| 目的 | 何を明らかにしたいか、どのリスクを探るか |
| 観点 | どのような条件、操作、データ、リスクを試すか |
| 範囲外 | 今回は確認対象にしない範囲は何か |
| Timebox(時間枠) | どのくらいの時間で探索するか |
| 制約 | 使える環境、データ、外部連携、権限などに制限はあるか |
| 記録 | 不具合、疑問点、再現手順、未確認範囲をどう残すか |

次に、申請フローを題材にした具体例を示す。

| 項目 | 具体例 |
|---|---|
| Charter ID | ET-REQ-001 |
| 対象 | 申請作成から承認までのフロー |
| セッション目的 | 高額申請の承認ルート、権限、状態遷移、通知まわりの不整合を探索する |
| 実施者 | QA担当者 1名 |
| 環境 | ステージング環境、PCブラウザ |
| Timebox(時間枠) | 60分 |
| 範囲外 | 管理者設定画面、集計ダッシュボードは今回の確認対象外とする |
| 観点 | 境界値、権限違反、二重送信、承認後の変更、通知失敗 |
| 制約 | 本番相当の外部通知は使わず、テスト用通知環境で確認する |
| 実施メモ | 10:00 通常金額の申請を作成し、通常承認フローを確認。<br>10:15 50,000円ちょうどの申請を作成し、追加承認フローを確認。<br>10:30 承認ボタンを連打したところ、履歴が二重に記録された。<br>10:45 承認済み申請の編集画面URLを直接指定すると、編集画面に入れてしまった。 |
| 発見した問題 | 1. 承認ボタンの二重操作で履歴が重複作成される。<br>2. 承認済み申請に対して、URL直接指定で編集画面へ遷移できる。 |
| 未解決事項 / 追加確認 | 通知失敗時に、申請者、承認者、運用担当者のそれぞれにどのような表示や記録が残るかは追加確認が必要。 |

この例のように、探索的テストでは、完全な事前手順を作らなくても、目的、観点、制約、Timebox、記録方法を明確にしておくことで、確認内容を後から振り返りやすくなる。

また、探索的テストでは、セッション後の共有も重要である。見つけた不具合だけでなく、確認した範囲、確認できなかった範囲、新しく見つかった疑問点、次に探索すべきリスクを共有することで、探索結果をチームの品質情報として扱いやすくなり、次のテスト設計にも接続しやすくなる。

探索的テストは、経験豊富なQAだけが行うものではない。もちろん、ドメイン知識、過去の不具合経験、ユーザー理解があるほど、鋭い観点を持ちやすい。しかし、初学者でも、異常系、権限、状態遷移、二重操作、外部連携失敗、UX上の違和感といった観点リストを持つことで、探索的に確認しやすくなる。

一方で、探索的テストには注意点もある。

探索的テストは、テスターの経験、観察力、ドメイン理解によって確認の深さが変わりやすい。そのため、何を確認したのか、何を見つけたのか、何が未確認なのかを記録しなければ、チームに品質情報として共有しにくい。また、探索的テストだけに依存すると、毎回確認内容が変わり、重要な回帰確認が抜ける可能性もある。

探索的テストは、同値分割、境界値分析、デシジョンテーブル、状態遷移テスト、Use Case Testing / Scenario Testingなどを置き換えるものではない。むしろ、これらの技法で設計した確認を補完し、固定されたテストケースでは見つけにくい問題を発見し、必要に応じて追加のテストケースや回帰テストへつなげる役割を持つ。

たとえば、探索的テストで「承認ボタンを二重クリックすると履歴が二重に作られる」という問題を発見した場合、その場限りの発見で終わらせるのではなく、再現手順を記録し、修正後の確認観点に加え、必要であれば自動テストや回帰テストに組み込むことができる。

このように、探索的テストは、固定テストケースでは見つけにくい品質リスクを発見し、次のテスト設計や自動化に還元するための活動でもある。

### 6.11 テスト設計技法の適用例

ここまで、Risk-Based Testing(リスクベースドテスト)、Equivalence Partitioning(同値分割)、Boundary Value Analysis(境界値分析)、Decision Table Testing(デシジョンテーブルテスト)、State Transition Testing(状態遷移テスト)、Use Case Testing / Scenario Testing(ユースケーステスト / シナリオテスト)、Exploratory Testing(探索的テスト)を見てきた。

これらは、技法名を覚えて個別に使うものではなく、確認したい品質リスクに応じて組み合わせて使うものである。

たとえば、入力値の妥当性を確認したい場合は同値分割や境界値分析が使いやすい。複数条件によって結果が変わる業務ルールではデシジョンテーブルが有効である。状態を持つ業務フローでは状態遷移テストが重要になる。ユーザーの一連の業務フローを確認したい場合はUse Case Testing / Scenario Testingが向いている。固定されたテストケースだけでは見つけにくい違和感や未知のリスクを探る場合は探索的テストが役立つ。

また、どの技法をどの深さで適用するかは、Risk-Based Testingの考え方と関係する。金銭、権限、個人情報、承認、外部連携、監査証跡など、影響が大きい領域では、複数の技法を組み合わせて厚く確認する必要がある。一方で、影響が小さい領域では、代表的な条件に絞る、既存の自動テストで継続確認する、リリース後の監視で補うといった判断もあり得る。

次の表は、実装・仕様例ごとに、主な品質リスクと適用しやすいテスト設計技法を整理したものである。これは固定的な対応表ではない。実際には、仕様の複雑さ、変更範囲、利用頻度、過去の不具合、リリース期限、テスト環境の制約によって、確認の深さや組み合わせは変わる。

| 実装・仕様例 | 主な品質リスク | 適用しやすい考え方・技法 | 確認例 |
|---|---|---|---|
| 申請金額の入力フォーム | 無効な金額が保存される、上限・下限の扱いを誤る | Equivalence Partitioning / Boundary Value Analysis | 0円、1円、通常範囲、上限、上限超過を確認する |
| 50,000円以上なら追加承認が必要 | 閾値判定を誤り、追加承認が不要になる、または不要な追加承認が発生する | Boundary Value Analysis / Equivalence Partitioning | 49,999円、50,000円、50,001円を確認する |
| ユーザー種別と申請状態によって操作可否が変わる | 権限のないユーザーが操作できる、必要なユーザーが操作できない | Decision Table Testing | 申請者、承認者、管理者、権限なしユーザーごとの操作可否を整理する |
| 下書き、申請中、承認済み、却下、取消済みを持つ申請フロー | 本来できない状態遷移が可能になる、必要な遷移ができない | State Transition Testing | 下書きから申請中、申請中から承認済み、承認済みから編集不可などを確認する |
| 申請から承認、通知、履歴記録までの一連の流れ | 個別機能は動くが、業務フロー全体では不整合が起きる | Use Case Testing / Scenario Testing | 高額申請を作成し、追加承認、通知、履歴、ステータス更新まで確認する |
| 承認ボタンや申請ボタンの二重クリック | 履歴や通知が重複する、状態が不整合になる | Exploratory Testing / State Transition Testing | ボタン連打、戻る、リロード、複数タブ操作を確認する |
| 外部通知サービスとの連携 | 通知失敗時にユーザーや運用担当者が状況を把握できない | Decision Table Testing / Use Case Testing / Scenario Testing / Exploratory Testing | 通知成功、通知失敗、再試行、失敗記録、ユーザー表示を確認する |
| 承認済み申請の編集禁止 | 監査上変更してはいけないデータが変更される | State Transition Testing / Decision Table Testing / Exploratory Testing | 承認済み状態で編集画面URLを直接指定しても編集できないことを確認する |
| APIで他人の申請IDを指定する | 他人のデータを閲覧・更新できる | Decision Table Testing / Exploratory Testing | 申請者本人、承認者、無関係ユーザー、管理者でアクセス可否を確認する |
| 検索・絞り込み条件 | 条件の組み合わせにより検索結果が欠落する、過剰に表示される | Equivalence Partitioning / Decision Table Testing | ステータス、期間、ユーザー種別、金額範囲の組み合わせを確認する |
| ダッシュボードや集計表示 | 集計定義の誤り、ステータス反映漏れ、画面とDBの不整合 | Equivalence Partitioning / Use Case Testing / Scenario Testing / Exploratory Testing | 承認済み申請が集計に反映されるか、取消済みが除外されるかを確認する |
| バッチ処理の成功・失敗・再実行 | 処理中断後に再実行できない、重複処理される、失敗が検知されない | State Transition Testing / Decision Table Testing / Exploratory Testing | 未実行、処理中、成功、失敗、再実行待ちの状態を確認する |
| エラーメッセージ表示 | ユーザーが次に何をすればよいか分からない | Exploratory Testing / Use Case Testing / Scenario Testing | 入力エラー、権限エラー、外部連携失敗時のメッセージを確認する |
| 監査ログ・履歴 | 誰が、いつ、何をしたか追跡できない | Use Case Testing / Scenario Testing / State Transition Testing / Exploratory Testing | 申請、承認、却下、取消、編集失敗の履歴が残るか確認する |

この表から分かるように、1つの実装・仕様例に対して、1つの技法だけを対応させるとは限らない。

たとえば、「50,000円以上なら追加承認が必要」という仕様では、金額の扱いそのものには同値分割や境界値分析が使いやすい。しかし、追加承認が必要になった後に、誰が承認できるのか、どの状態へ遷移するのか、通知や履歴がどう残るのかまで確認する場合は、デシジョンテーブル、状態遷移テスト、Use Case Testing / Scenario Testingも必要になる。

また、「承認済み申請は編集できない」という仕様では、状態遷移テストだけでなく、権限条件や直接URL指定のような探索的な観点も重要になる。画面上で編集ボタンが非表示になっていても、APIを直接呼び出したときに更新できてしまえば、品質上の問題になるからである。

このように、テスト設計では、技法を単独で覚えるのではなく、品質リスクに応じて使い分けることが重要である。

整理すると、次のように考えられる。

| 確認したいこと | 使いやすい考え方・技法 |
|---|---|
| 入力値の範囲やカテゴリを整理したい | Equivalence Partitioning |
| 上限、下限、閾値、その前後を確認したい | Boundary Value Analysis |
| 複数条件と期待結果を整理したい | Decision Table Testing |
| 状態とイベントの関係を確認したい | State Transition Testing |
| ユーザーや業務の一連の流れを確認したい | Use Case Testing / Scenario Testing |
| 仕様に書かれていない違和感や未知リスクを探りたい | Exploratory Testing |
| どこを厚く確認するかを決めたい | Risk-Based Testing |

なお、ここまでの表は、主に要求、仕様、受け入れ条件、業務ルール、ユーザー操作からテスト観点を設計するための例であり、ブラックボックステスト技法と経験ベースの確認を中心に整理している。

実務では、これに加えて、コード内部の制御フロー、条件分岐、例外処理、到達していない処理、カバレッジなどを確認するホワイトボックステストの観点が加わることもある。たとえば、Unit Testで分岐条件を確認する、例外処理のパスを確認する、Statement Coverage(ステートメントカバレッジ)やBranch Coverage(ブランチカバレッジ)を参考に未確認のコード領域を見つける、といった確認である。

ただし、ホワイトボックステストへの関与度は、チームの役割分担によって変わる。開発者やSET(Software Engineer in Test:テスト自動化・テスト基盤寄りのエンジニア)が主に担う場合もあれば、QAがコード、API、自動テスト、CI/CD上の品質ゲートまで関与する場合もある。本資料では、6章では要求・仕様・業務リスクから確認観点を設計する考え方を中心に扱い、ホワイトボックス寄りの観点は7章のテスト自動化や品質ゲートの文脈で必要な範囲を扱う。

QAにとって重要なのは、「どの技法を使ったか」ではなく、「どの品質リスクを、どの根拠で、どの確認方法に割り当てたか」を説明できることである。

そのため、テスト設計では次のような問いを持つとよい。

- この仕様で、ユーザーや業務に大きな影響を与えるリスクは何か
- 入力値、境界値、条件組み合わせ、状態遷移のうち、どこに不具合が出やすいか
- どの観点は小さい確認単位で確認できるか
- どの観点は業務フロー全体で確認すべきか
- 固定されたテストケースで確認するべきものは何か
- 探索的に確認した方がよい未知リスクは何か
- 確認しない、または後続の監視・運用で扱う残リスクは何か
- その残リスクは関係者に共有されているか

このように考えることで、テスト設計は、単なるテストケース作成ではなく、品質リスクを確認可能な形に整理する活動になる。

### 6.12 Key Takeaways

6章では、5章で整理した要求、受け入れ条件、具体例、期待される振る舞いをもとに、どの観点で、どの条件を、どの確認単位で見るかを整理した。

テスト設計は、テストケースを大量に作る作業ではない。重要なのは、品質判断に必要な情報を得るために、要求、仕様、業務ルール、ユーザー影響、過去の不具合、運用リスクをもとに、確認すべき品質リスクを明確にすることである。

また、同値分割、境界値分析、デシジョンテーブル、状態遷移テスト、Use Case Testing / Scenario Testing、Exploratory Testingは、それぞれ独立して暗記するものではなく、確認したいリスクに応じて組み合わせて使うものである。Risk-Based Testingは、その組み合わせや確認の深さを判断するための前提になる。

- テスト設計は、テストケース表を埋めることではなく、品質リスクを確認可能な形に整理する活動である。

- 5章で整理したAcceptance Criteria(受け入れ条件)、具体例、業務ルール、期待される振る舞いは、テスト観点、テスト条件、テストケースを考えるための重要な材料になる。

- Test Basis(テストベース)は、テスト観点やテストケースを考えるための根拠になる。要求、仕様、受け入れ条件だけでなく、状態遷移、権限ルール、過去の不具合、問い合わせ、運用上の制約も重要な入力情報になる。

- すべてを同じ深さで確認することは現実的ではない。Risk-Based Testing(リスクベースドテスト)により、影響度、発生可能性、検出しにくさ、回復しにくさ、利用頻度、変更範囲などを考慮し、重要なリスクを優先的に確認する必要がある。

- Equivalence Partitioning(同値分割)は、同じように扱える入力値や条件をグループ化し、代表値を選んで効率的に確認するために有効である。

- Boundary Value Analysis(境界値分析)は、上限、下限、閾値、その直前、その直後など、扱いが変わる境界周辺を重点的に確認するために有効である。

- Decision Table Testing(デシジョンテーブルテスト)は、複数条件と期待結果の組み合わせを整理し、条件漏れ、未定義の結果、仕様の矛盾を見つけるために有効である。

- State Transition Testing(状態遷移テスト)は、状態とイベントの関係を整理し、許可される遷移だけでなく、許可されない遷移、例外状態、履歴、権限、データ整合性を確認するために有効である。

- Use Case Testing / Scenario Testing(ユースケーステスト / シナリオテスト)は、ユーザーや業務の一連の流れとして、複数機能をまたぐ品質リスクを確認するために有効である。ただし、すべての詳細条件をE2E Testで確認しようとすると、実行時間や保守負荷が大きくなりやすい。

- Exploratory Testing(探索的テスト)は、固定されたテストケースだけでは見つけにくい仕様の曖昧さ、UX上の違和感、想定外の操作、権限境界、状態遷移の抜け、例外条件を探るために有効である。

- 探索的テストは無計画に自由に触ることではない。目的、観点、Timebox(時間枠)、記録方法を持ち、必要に応じてTest Charter(テストチャーター)を使って整理することで、チームに共有可能な品質情報にできる。

- 1つの実装・仕様例に対して、1つの技法だけを対応させるとは限らない。たとえば、追加承認の仕様では、境界値、権限、状態遷移、通知、履歴、業務フローを組み合わせて確認する必要がある。

- 6章では、主に要求、仕様、受け入れ条件、業務ルール、ユーザー操作からテスト観点を設計する考え方を扱った。コード内部構造やカバレッジに基づくホワイトボックステスト寄りの観点は、7章のテスト自動化や品質ゲートの文脈で必要な範囲を扱う。

- QAにとって重要なのは、「どの技法を使ったか」ではなく、「どの品質リスクを、どの根拠で、どの確認方法に割り当てたか」を説明できることである。
